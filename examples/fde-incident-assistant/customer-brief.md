# 客户问题简报：结算服务错误率突增

## 1. 用户和业务问题

值班人员在发布结算服务新版本后收到错误率告警。当前需要更快地把指标、变更和日志证据放到同一张结果卡中，判断是否需要停止放量并请求回滚审批。

## 2. 本次范围

- 输入：已脱敏的事故编号、服务名、指标摘要、变更记录和日志摘要。
- 输出：影响摘要、证据列表、待验证假设、建议动作、置信度和审批要求。
- 只做读取、整理和建议，不连接生产系统，不执行回滚。

## 3. 明确不做

- 不宣称自动找到根因。
- 不接收 Token、密码、客户原始日志或个人信息。
- 不绕过现有变更审批、事件指挥和回滚流程。
- 不用实验项目冒充生产交付经验。

## 4. 成功指标

| 指标 | 最小验收条件 |
|---|---|
| 证据可追溯 | 每个关键判断至少引用一个证据编号 |
| 不确定性 | 证据缺失或超时时明确降级，不编造结论 |
| 变更安全 | 所有高风险动作都标为需要审批，样例执行状态始终为 false |
| 可回归 | 四个固定评测案例全部通过 |
| 可运行 | Python 标准库环境可以在一分钟内完成演示 |

## 5. 安全与验收边界

演示数据全部是虚构数据。验收时检查输出结构和安全不变量，不以“程序能运行”代替业务效果验证。若将来接入真实监控或发布系统，必须重新做权限、数据分类、威胁建模、审计、故障域和回滚评审。
