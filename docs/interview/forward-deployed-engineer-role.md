# FDE（Forward Deployed Engineer）岗位技术栈与实战路线

> 学习目标：从零理解 FDE 到底做什么，知道通用 FDE、AI FDE 与 AIOps 的边界；能按目标岗位选择技术，而不是盲学所有工具；最终完成一个有需求简报、可运行代码、评测、故障降级、安全审批和交付文档的作品集项目。
>
> 信息快照：2026 年 8 月 21 日。招聘页面会变化，投递前必须重新阅读目标公司的岗位原文。
>
> 适用人群：想从运维、SRE、DevOps、后端、数据或 AI 应用开发转向客户现场工程交付的人。

## 先说结论

FDE 不是某个软件，也不是“会调用大模型 API 的售前”。它是一类贴近客户真实业务、把模糊问题做成可运行生产系统、再把共性需求反馈给产品团队的工程岗位。

你不需要把本仓库的每个数据库、消息队列和云平台全部学完。比较稳妥的学习组合是：

1. **通用基本盘**：需求发现、Python、Git、测试、REST API、SQL、系统设计、安全、可观测性和交付沟通。
2. **第二语言或全栈能力**：按目标岗位选择 Java、Go 或 TypeScript/JavaScript；需要做客户操作界面时再补 React 等前端框架。
3. **部署与集成**：Docker、CI/CD，再选择一朵云或 Kubernetes 深入；不要把“会列命令”当成能上线。
4. **AI FDE 增量能力**：LLM、Tool Calling、RAG、Agent、MCP、离线/在线评测、成本与延迟、安全护栏。
5. **行业能力**：客户的数据、流程、术语、合规和成功指标。它往往比再背一个框架更决定交付能否成功。

**FDE 可以做 AIOps，但 FDE 不等于 AIOps。** AIOps 是一个应用领域；当客户问题是告警治理、事故响应、根因辅助或自动化运维时，FDE 会用到 AIOps。FDE 也可能交付金融分析、客服、制造、科研或企业知识应用。

## 官方岗位知识地图

```text
客户目标与现场约束
  -> 需求发现与成功指标
  -> 数据、系统、权限和风险盘点
  -> 最小可行原型与高风险假设验证
  -> API / 数据 / 模型 / UI 集成
  -> 评测、安全和架构评审
  -> 灰度上线、观测、培训与采用
  -> 事件响应、迭代和效果复盘
  -> 把共性能力沉淀回平台、组件和交付手册
```

这里的 `UI` 是 User Interface，即用户界面；`API` 是 Application Programming Interface，即系统之间约定好的调用接口；`MCP` 是 Model Context Protocol，即模型上下文协议；`LLM` 是 Large Language Model，即大语言模型。

## 场景开场：客户说“给我做一个智能故障助手”

小白很容易立刻问：“用 LangChain 还是 Dify？”FDE 应先问：

- 谁在什么时刻使用它，当前流程最痛的步骤是什么？
- 目标是缩短取证时间、降低误报，还是允许自动处置？
- 哪些指标、日志、变更和工单能合法读取？数据能否离开客户环境？
- “回答正确”如何评测？错误建议的最大影响是什么？
- 哪些动作必须人工批准？失败后怎样回退到原流程？
- 客户现有身份、权限、审计、网络和发布流程是什么？

如果这些问题没说清，模型回答再流畅也可能无法上线。

## 一句话人话版

**FDE 就像既会做需求侦探、又能写代码和上线值班的工程师：他进入客户真实流程，把目标做成系统，并对系统是否真正被使用、是否安全可靠负责。**

## 为什么要学

只会单项工具的人，遇到客户现场常卡在“工具能运行，但业务没闭环”：需求没有量化、数据权限没打通、失败路径没设计、用户不会用、上线后没人维护。学习 FDE 主线的价值，是把已有的开发、运维、数据和 AI 能力组织成一次可验收的端到端交付。对有运维或 AIOps 背景的人，它还提供了一条把事故证据、可靠性和自动化经验转成客户价值的路径。

## FDE 是什么

FDE 是一种岗位和交付方式，不是统一认证或固定产品。它通常位于客户、产品和工程团队之间：既参与需求发现与范围取舍，也亲手实现、集成、上线和排障；交付完成后，还要把多个客户反复出现的问题沉淀为连接器、模板、评测集、Runbook 或核心产品能力。

## 小白最容易问的十个问题

### 1. FDE 是售前吗

通常不是纯售前。FDE 会参与方案和演示，但核心差别是要写生产代码、接真实系统、处理上线问题并验证业务结果。不同公司边界不同，必须看岗位原文。

### 2. FDE 是外包驻场吗

不能仅凭“贴近客户”判断。FDE 可能短期嵌入客户团队，也可能远程、多客户并行或长期共建。判断一份岗位时要问：代码归谁维护、是否进入核心产品、交付结束后谁值班、出差比例和成长路径是什么。

### 3. 不懂前端能不能做

可以从偏后端、平台或数据型 FDE 切入，但很多客户需要能看见、能操作的界面。最低应理解 HTML、CSS、JavaScript/TypeScript、浏览器请求、表单状态、鉴权和错误展示；目标岗位明确写 full-stack 或 React 时必须补实战。

### 4. 只会 Python 够不够

Python 是很好的第一语言，但生产交付还需要测试、类型与数据校验、异常处理、并发、性能、打包、日志和安全。很多岗位还希望候选人会 JavaScript/TypeScript、Java、Go 或同类语言中的一种。

### 5. 必须会 Kubernetes 吗

不一定。小型交付可能运行在托管平台、虚拟机或客户已有 PaaS 上。你必须会一种可靠部署方式；只有目标环境使用 Kubernetes 时，它才从加分项变成必修。

### 6. 必须会所有云吗

不需要。先理解身份、网络、计算、存储、数据库、日志、密钥和成本这些云的共同概念，再按岗位选择 AWS、Azure 或 Google Cloud 中的一家深入。

### 7. AI FDE 一定要训练模型吗

通常不要求从零训练基础模型，但要理解模型能力边界、Prompt、结构化输出、工具调用、RAG、Agent、评测、延迟、成本和安全。涉及微调或训练平台的岗位才需要更深的 PyTorch、数据和 GPU 能力。

### 8. FDE 包含 AIOps 吗

可以包含。AIOps 是客户场景之一，不是岗位定义。运维背景的人可以把监控、变更、事故和自动化经验变成差异化优势。

### 9. 沟通好是不是比技术重要

两者不能互相替代。沟通帮助找对问题，工程能力帮助做成可靠系统；只有演示没有生产证据，或只有代码不知道业务目标，都不完整。

### 10. 学完这篇能直接获得 FDE 岗位吗

不能。真实岗位通常还考察软件工程基础、系统设计、项目经验、行业理解、英文或当地语言、现场协作和出差条件。学习项目必须诚实标注为实验，不能改写成虚构客户经历。

## FDE 解决什么问题

很多企业并不是缺一个模型或数据库，而是卡在下面的“最后一公里”：

- 业务目标是口头描述，没人把它改写成可测量结果。
- 数据散落在旧系统、表格、API 和人工流程中。
- 演示能跑，遇到权限、延迟、容量和失败恢复就无法生产化。
- 安全、法务、运维和业务对边界理解不同。
- 客户的特殊需求没有沉淀，产品团队反复做一次性定制。
- 系统上线了，但用户不采用，无法证明业务价值。

FDE 的价值是把业务、数据、软件、AI、基础设施和组织协作连成一个可验收闭环。

## FDE 与相近岗位的区别

| 岗位 | 主要关注点 | 常见交付物 | 与 FDE 的重叠和差别 |
|---|---|---|---|
| 产品软件工程师 | 面向多数客户建设通用产品 | 产品代码、测试、发布 | FDE 同样写生产代码，但更贴近具体客户流程与现场约束 |
| 解决方案架构师 | 需求、总体方案、技术选型 | 架构图、方案、PoC | FDE 往往继续把方案写成代码并参与上线和采用 |
| 实施顾问 | 配置、迁移、培训、流程落地 | 配置、数据迁移、培训材料 | FDE 通常承担更深的软件工程和产品反馈责任 |
| SRE / DevOps | 可靠性、平台、交付效率 | SLO、平台、流水线、Runbook | FDE 可使用这些能力，但成功指标还包含客户业务结果和采用 |
| 数据工程师 | 数据采集、建模、质量和计算 | 数据管道、模型、作业 | 数据型 FDE 可能高度重叠，同时还要完成客户应用和交付闭环 |
| AIOps 工程师 | 运维数据、检测、关联、自动化 | 告警治理、RCA 辅助、自动化 | AIOps 是 FDE 可服务的一个业务领域 |

表中是常见边界，不是行业统一职级定义。同一个名称在不同公司可能差异很大。

## 三类常见 FDE

### 通用产品 FDE

围绕公司的平台或 API，为客户完成数据接入、工作流、界面、权限、部署与采用。软件工程和客户沟通是基本盘。

### AI FDE

在通用 FDE 之上，增加模型选型、Prompt、工具调用、RAG、Agent、评测、安全护栏、推理成本和延迟治理。模型只是系统的一层。

### 数据、平台或可靠性 FDE

更偏数据平台、流式处理、云基础设施、可靠性或开发者平台。Kubernetes、Kafka、可观测性和 SRE 可能更重要，前端深度可能较低。

投递前先判断目标岗位属于哪一类，再安排学习优先级。

### 为什么不能把产品清单当能力

客户使用 PostgreSQL 还是 MySQL 会变化，但你必须始终理解事务、索引、权限、备份和迁移；部署在 Kubernetes 还是虚拟机也会变化，但配置、健康检查、容量、发布和回滚始终存在。

因此学习顺序应是：

```text
通用机制
  -> 选择一个代表产品做深
  -> 在项目中形成证据
  -> 学会把机制迁移到客户现有产品
```

## 核心概念一：需求发现与技术范围界定

- **是什么**：需求发现是理解用户、流程、痛点、数据和约束；技术范围界定是明确本期做什么、不做什么、依赖谁以及怎样验收。
- **为什么需要**：客户说的方案可能不是根本问题。直接开工容易做出没人用或无法上线的功能。
- **怎么工作**：访谈用户和负责人，观察当前流程，用基线数据验证痛点，把目标改写为可测量指标，再记录假设与非目标。
- **怎么用或观察**：输出一页问题简报、当前流程图、成功指标、风险清单和待确认问题。
- **坏了怎么查**：若团队反复改需求，检查决策人、用户、成功指标和非目标是否缺失；若演示满意但上线被拒，检查安全、数据、运维是否太晚参与。

### 五类必须问的问题

| 类别 | 小白可以直接问 | 产出 |
|---|---|---|
| 用户 | 谁每天使用？谁批准？谁值班？ | 角色与责任人 |
| 流程 | 现在从触发到完成经过哪些步骤？ | 当前流程图 |
| 数据 | 数据在哪里、谁拥有、质量如何、能否离境？ | 数据清单与权限边界 |
| 结果 | 什么数字变好才算成功？基线是多少？ | 成功指标与评测集 |
| 风险 | 错误结果最坏会怎样？如何停止和恢复？ | 护栏、审批与回滚 |

## 核心概念二：从 PoC 到生产

`PoC` 是 Proof of Concept，即概念验证，用来验证一个高风险假设能否成立；它不是缩小版生产系统。

- **是什么**：把能演示的原型补成可认证、可观测、可扩容、可升级和可恢复的生产服务。
- **为什么需要**：原型常用手工数据、个人 Token 和单机进程，真实环境会遇到并发、权限、脏数据和依赖故障。
- **怎么工作**：建立环境、配置、凭据、数据、版本和发布边界；加入测试、监控、容量、安全、备份与回滚。
- **怎么用或观察**：用上线检查表验证，不以“页面打开了”作为完成标准。
- **坏了怎么查**：先比较实验与生产的输入、身份、网络、数据量和依赖，再定位是代码、配置还是环境差异。

### “成功”至少有五层

```text
代码能运行
  -> 测试与评测通过
  -> 目标环境部署成功
  -> 真实用户路径与故障路径通过
  -> 用户采用且业务指标改善
```

任何一层都不能自动证明下一层。

## 核心概念三：评测驱动开发

- **是什么**：先定义代表真实任务的案例和评分规则，再用它比较版本，而不是随机聊天后凭感觉判断。
- **为什么需要**：AI 输出有概率性；传统系统也可能在某类数据、权限或故障路径上退化。
- **怎么工作**：建立固定数据集，分别检查正确性、证据、格式、安全、延迟、成本和人工升级，再把线上失败脱敏后加入回归集。
- **怎么用或观察**：每次变更记录评测集版本、通过率、关键失败案例、成本与延迟分位数。
- **坏了怎么查**：先区分数据集漂移、评分器问题、模型变化、Prompt/工具变化和依赖故障，不要只调 Prompt 掩盖问题。

### 评测的三层

| 层次 | 检查什么 | 示例 |
|---|---|---|
| 单元测试 | 确定性代码和安全不变量 | 高风险动作永远要求审批 |
| 离线评测 | 固定案例上的质量、证据、格式、延迟和成本 | 100 个脱敏工单的引用正确率 |
| 在线评估 | 真实流量中的采用、升级、失败与业务结果 | 人工接管率、节省时间、错误建议率 |

离线好成绩不等于线上成功；线上业务指标也不能替代安全回归。

## 核心概念四：信任边界与人工审批

- **是什么**：规定用户、模型、工具、数据和生产系统各自能做什么，哪些动作必须由授权人员批准。
- **为什么需要**：模型可能误解、工具可能超时、数据可能被提示注入污染；错误的自动化会扩大影响。
- **怎么工作**：最小权限、读写分离、参数校验、策略门禁、幂等键、审批、审计、速率限制、熔断和回滚共同组成护栏。
- **怎么用或观察**：记录谁在何时基于什么证据批准了哪个动作，动作执行前后都验证目标状态。
- **坏了怎么查**：若出现越权或误操作，先撤销凭据和停止执行通道，保存审计证据，检查授权、租户、工具 Schema 和审批绑定。

## 核心概念五：一次性交付变成可复用产品

- **是什么**：把多个客户都会遇到的连接器、评测、部署模板和排障手册沉淀成产品能力。
- **为什么需要**：只写一次性脚本会让维护成本随客户数量线性增长。
- **怎么工作**：区分客户配置与通用逻辑，记录重复需求，设计稳定扩展点，把验证过的模式反馈给产品团队。
- **怎么用或观察**：看新客户交付周期、定制代码比例、重复缺陷和升级兼容性是否改善。
- **坏了怎么查**：若“通用平台”参数越来越多，检查领域边界是否错误；若每个客户都 fork 代码，检查扩展接口、版本和迁移机制。

## 一条完整的 FDE 系统与交付链路

```text
客户用户 / 业务系统
  -> Web UI、CLI 或现有工作流
  -> API Gateway / 身份认证 / 租户边界
  -> FDE 交付的应用服务
       -> 业务规则与状态机
       -> 客户 API / 数据库 / 文件 / 消息
       -> 可选：LLM / RAG / Agent / MCP 工具
       -> 策略门禁 / 人工审批 / 审计
  -> 指标、日志、追踪、评测与成本数据
  -> 灰度、事件响应、复盘和产品反馈
```

请求链与交付链要同时设计。请求链回答“一次操作怎样走”；交付链回答“需求怎样变成安全上线和持续改进”。

## 编程与软件工程：最低做到什么

### Python

至少能独立完成：

- 数据结构、函数、类、异常、上下文管理和类型标注。
- HTTP 客户端/服务端、JSON、文件和 SQL。
- 超时、有限重试、并发边界、日志与配置。
- `pytest` 或 `unittest`、依赖锁定、代码格式和静态检查。
- 把脚本变成有入口、有退出码、有测试和说明的可维护程序。

入口：[Python 深讲](../tech-stack/foundation/python.md)。

### 第二语言怎么选

| 目标 | 建议选择 | 原因 |
|---|---|---|
| 客户 Web 应用和 AI 产品 | TypeScript / JavaScript | 前后端同语言、浏览器生态和当前 AI SDK 丰富 |
| 企业后端与传统系统集成 | Java | 类型、生态、JVM、中间件和企业系统常见 |
| 平台、云原生和高并发工具 | Go | 部署简单，云原生与基础设施生态常见 |

选择一门做深比三门只会语法更有价值。本仓库已有 [Java](../tech-stack/foundation/java.md) 和 [Go](../tech-stack/foundation/golang.md)；若目标岗位点名 TypeScript/React，应完成一个带表单、API、鉴权、错误态和测试的独立前端项目。

### 代码审查清单

- 输入是否校验，错误是否分为可重试与不可重试。
- 是否为网络、数据库和模型调用设置超时。
- 重试是否有次数上限、退避和幂等保护。
- 日志是否有 `trace_id`、租户、操作和结果，是否泄露秘密。
- 配置与密钥是否离开源码。
- 单元测试是否覆盖正常、空数据、权限、超时和危险动作。
- 能否从制品追到 Git Commit，能否回滚。

## 前端与用户体验：FDE 不能只交付一个命令行

前端最低知识包括：

- 浏览器怎样通过 DNS、TLS、HTTP、Cookie/Token 调 API。
- 表单输入、加载中、空结果、部分失败、重试和超时怎样展示。
- 权限不足与系统故障不能都显示“未知错误”。
- 高风险动作要二次确认并展示影响、依据和审批状态。
- 可访问性不是装饰：键盘操作、焦点、标签和颜色对比会影响真实采用。

一个漂亮演示如果没有失败状态、权限状态和审计入口，仍不是生产交付。

## API 与系统集成

### 接口合同要讲清

| 字段或机制 | 目的 | 正常做法 | 常见坑 |
|---|---|---|---|
| `request_id` / `trace_id` | 关联调用证据 | 入口生成并向下游传递 | 每层各生成一个，无法串联 |
| `tenant_id` | 隔离客户或组织 | 从可信身份解析并在服务端校验 | 直接相信请求正文里的租户 |
| `timeout` | 控制等待预算 | 客户端、网关、服务、下游分层设置 | 无限等待或所有层同一超时 |
| `Idempotency-Key` | 防止重试重复产生副作用 | 同一业务动作复用同一个键 | 每次重试生成新键 |
| 版本 | 支持兼容演进 | 契约测试、弃用窗口和迁移说明 | 修改字段含义但不升版本 |
| Problem Details | 返回机器可读错误 | 稳定错误类型、状态和追踪号 | 让客户端解析自然语言错误 |

深入入口：[RESTful API](../tech-stack/foundation/restful-api.md) 和 [FastAPI](../tech-stack/data-ai/fastapi.md)。

## 数据能力：不是只会写 SELECT

FDE 进入客户现场后，数据问题往往比模型问题更早出现：

1. **语义**：同名字段在两个系统含义是否相同。
2. **身份**：客户、用户、设备和订单怎样稳定关联。
3. **质量**：缺失、重复、迟到、错误时间和脏编码怎样处理。
4. **状态**：哪个系统是事实来源，写入失败如何补偿。
5. **安全**：哪些字段敏感，能否进入模型和测试环境。
6. **迁移**：全量、增量、校验、双写和回退如何设计。

至少学会 SQL、事务、索引、Schema 变更、备份恢复和数据脱敏。需要事件驱动时再补 Kafka 或消息队列；需要文档模型时再选 MongoDB，不要为作品集强塞所有产品。

## AI FDE 增量技术栈

### 模型调用不是全部

```text
用户任务
  -> 输入与权限校验
  -> Prompt / Context
  -> 模型选择与结构化输出
  -> 可选的检索和工具循环
  -> 策略门禁与人工审批
  -> 结果、引用和不确定性
  -> 评测、反馈、成本和延迟
```

### 必须讲清的概念

| 概念 | 人话解释 | 生产检查 |
|---|---|---|
| Prompt | 给模型的任务、上下文和约束 | 是否版本化、测试注入和边界案例 |
| Structured Output | 让输出符合固定字段结构 | Schema 校验失败怎样重试或拒答 |
| Tool Calling | 模型提出调用工具，由程序执行 | 工具权限、参数校验、超时和副作用 |
| RAG | 先检索可信资料，再让模型基于资料回答 | 召回、引用、权限过滤和新鲜度 |
| Agent | 模型在状态和工具之间多步决策 | 最大步数、预算、循环、恢复和审批 |
| MCP | 用统一协议暴露资源、Prompt 和工具 | 服务身份、权限、输入与审计 |
| Eval | 用代表性案例持续测质量与安全 | 数据集版本、评分标准和回归门禁 |
| Guardrail | 限制输入、输出和动作风险 | 不能只靠一句系统 Prompt |

深入入口：[LLM / OpenAI API](../tech-stack/data-ai/llm-openai.md)、[RAG](../tech-stack/data-ai/rag.md)、[LangChain](../tech-stack/data-ai/langchain.md)、[LangGraph](../tech-stack/data-ai/langgraph.md) 和 [向量数据库](../tech-stack/data-ai/vector-database.md)。

## AIOps 场景怎样成为 FDE 作品集

可以选择“事件证据助手”，但要把它写成受控决策支持系统：

```text
告警 / 工单
  -> 关联服务、租户和时间窗口
  -> 只读查询指标、日志、追踪和变更
  -> 生成带引用的候选假设
  -> 匹配 Runbook 与风险等级
  -> 人工审批或只读建议
  -> 执行后验证 SLI 与业务路径
  -> 结果进入复盘和评测集
```

它至少应观察：

- 取证成功率、各数据源超时率。
- 建议被接受、修改或拒绝的比例。
- 无证据回答率、错误引用率和人工升级率。
- 建议延迟、模型/工具成本。
- 动作审批率、执行失败率、回滚率和恢复验证结果。

不要以“模型猜中一次根因”证明系统可靠。

## 安装与启动：运行仓库里的最小 FDE 样例

样例位于 `examples/fde-incident-assistant`，只使用虚构数据和 Python 标准库，不需要 API Key，也不会连接或修改真实系统。

### 前置条件

- 已安装 Python 3.11 或更高版本。
- 已克隆本仓库。
- Windows PowerShell 或 PowerShell 7。

### 启动命令

```powershell
Set-Location D:\zero-to-aiops\examples\fde-incident-assistant # 进入样例目录
python --version                                                # 确认 Python 可用
python .\app.py --scenario checkout-error-spike                # 运行有证据的事故场景
```

### 输出字段字典

| 字段 | 作用 | 期望值 | 常见误解 |
|---|---|---|---|
| `trace_id` | 关联一次处理过程 | 每次运行有唯一值 | 它不是事故编号 |
| `incident_id` | 标识业务事故 | 固定演示编号 | 不能把真实工单号公开提交 |
| `outcome` | 表示处理状态 | `approval_required` 等 | 不是“根因已确认” |
| `confidence` | 表示当前假设把握 | 0 到 1 | 不是统计学准确率，也不能单独决定动作 |
| `hypothesis` | 待验证解释 | 明确写“待验证” | 不应包装成已确认根因 |
| `evidence` | 支撑判断的可追溯记录 | 含 `evidence_id` | 日志片段多不等于证据充分 |
| `proposed_action` | 建议的下一步 | 有停止与验证条件 | 不代表已经执行 |
| `requires_approval` | 是否必须人工批准 | 高风险动作是 `true` | 前端确认框不能替代服务端授权 |
| `action_executed` | 是否真的执行动作 | 样例永远是 `false` | 不能为了演示改成真实执行 |

## 基础实验：完成一次有证据、无自动变更的诊断

### 实验目标

确认应用能把指标、变更和日志放入同一结果，同时区分“相关性假设”和“已确认根因”。

### 精确步骤

1. 阅读 `customer-brief.md`，确认范围和非目标。
2. 执行正常场景：

```powershell
Set-Location D:\zero-to-aiops\examples\fde-incident-assistant
python .\app.py --scenario checkout-error-spike
```

3. 检查输出：

```powershell
$result = python .\app.py --scenario checkout-error-spike | ConvertFrom-Json
$result.outcome
$result.evidence.evidence_id
$result.requires_approval
$result.action_executed
```

### 预期结果

- `outcome` 为 `approval_required`。
- 至少看到 `metric:error-rate` 与 `change:deployment` 两个证据编号。
- 文本说明新版本或依赖链路只是待验证假设。
- `requires_approval` 为 `True`。
- `action_executed` 为 `False`。

### 验证方法

```powershell
python .\evals.py
python -m unittest -v
```

评测最后输出 `PASS: 4/4 evaluation cases`，四个单元测试都显示 `ok`。

### 清理

样例不创建服务、数据库或云资源，无需清理。关闭终端或离开目录即可。

### 如果没有成功，先检查这些

1. `python --version` 是否至少为 3.11。
2. 当前目录是否真的包含 `app.py`、`evals.py` 和 `test_app.py`。
3. 是否把场景写成了支持的名称；可运行 `python .\app.py --help` 查看。
4. Windows 旧终端中文乱码时，先执行 `$env:PYTHONUTF8='1'` 再运行。
5. 评测失败时先看第一个 `FAIL`，不要修改期望值掩盖安全退化。

## 故障注入实验：证据服务超时和危险动作请求

### 实验目标

证明依赖故障时系统会降级，危险请求会被挡住，而不是“为了给答案”编造证据或自动改生产。

### 前置条件

先完成基础实验，理解正常输出。

### 精确步骤

```powershell
python .\app.py --scenario evidence-timeout
python .\app.py --scenario unsafe-auto-remediation
python .\evals.py
```

### 预期结果

证据超时场景：

- `outcome` 为 `degraded`。
- `confidence` 为 `0.0`。
- `evidence` 为空。
- 建议转人工取证，不执行变更。

危险动作场景：

- `outcome` 为 `approval_required`。
- 输出明确拒绝自动执行生产回滚。
- `action_executed` 仍为 `false`。

### 验证方法

四个评测全部通过，说明正常、证据不足、依赖超时和危险动作四条路径都满足当前合同。它只证明这四条固定规则，不证明真实模型质量或生产可靠性。

### 清理

故障是进程内的虚构场景，不会启动后台进程或修改环境，无需清理。

### 如果没有成功

1. 检查是否误改了 `SCENARIOS` 的场景名。
2. 检查所有返回分支是否保持 `action_executed=False`。
3. 检查超时异常是否被吞掉后继续生成结论。
4. 不要把超时改成长时间 `sleep`；单元测试应快速、确定地模拟故障。
5. 若将来接真实工具，先用只读沙箱和假数据做同样测试，再做授权环境验证。

## 常见交付故障与排查

| 现象 | 先收集什么证据 | 可能假设 | 安全处理 |
|---|---|---|---|
| 演示好、上线差 | 真实输入分布、权限、延迟、依赖失败 | 实验数据不代表生产 | 扩充评测，灰度，不直接全量 |
| 用户不用 | 用户路径、人工替代步骤、采用漏斗 | 解决了错误问题或操作成本高 | 回到访谈和流程观察 |
| AI 回答有引用但引用不支持结论 | 检索结果、引用跨度、评分样例 | 召回或归因评测缺失 | 拆开检索与回答评测 |
| 同一请求执行两次 | 请求号、重试日志、动作审计 | 缺少幂等或超时后误重试 | 停止执行，按幂等键核对状态 |
| A 客户看到 B 客户数据 | 身份、租户过滤、缓存键、向量过滤 | 服务端信任了客户端租户或缓存串租户 | 立即隔离、撤权、取证并按事件流程响应 |
| 模型成本突然升高 | Token、步骤、工具调用、重试和版本 | 循环、上下文膨胀或流量变化 | 限制预算和步骤，回退上个版本 |
| 工具超时导致整个请求挂死 | 分层耗时、超时和重试次数 | 没有总预算或重试风暴 | 熔断、降级、有限退避并保留人工路径 |
| 发布后质量下降 | Git、Prompt、模型、工具、数据集版本 | 多项同时变化 | 冻结扩散，按版本矩阵回滚和复评 |

## 生产架构必须回答的八件事

### 1. 内部请求和数据路径

能从用户操作讲到身份、API、业务服务、客户数据、模型/工具、审计和响应，知道每一跳的超时、权限和证据在哪里。

### 2. 状态与一致性

区分会话状态、业务事实、任务状态、审批状态和模型生成内容。模型回答不是事实来源；高风险动作要用业务系统当前状态和幂等键再次确认。

### 3. 高可用

无状态服务可多副本，但数据库、队列、向量索引、模型供应商、客户 API 和身份系统仍可能是共享故障点。要设计降级和人工路径，而不只是加副本。

### 4. 容量与性能

至少测每秒请求、并发、P50/P95/P99 延迟、输入/输出 Token、工具调用次数、数据库连接、队列深度和单位任务成本。`P95` 表示 95% 请求不超过的延迟。

### 5. 安全边界

身份认证回答“你是谁”，授权回答“你能做什么”。租户、资源和动作必须在服务端校验；秘密进入受控密钥系统，日志和评测集要脱敏。

### 6. 升级与回滚

代码、Prompt、模型、工具 Schema、数据索引和策略都要版本化。灰度一次只改变有限变量，定义质量、延迟、成本和安全停止条件。

### 7. 可观测性

既看传统 RED 指标——Rate 请求率、Errors 错误、Duration 时延——也看 AI 特有的评测、拒答、人工升级、工具错误、Token 和成本。Trace 中不要记录秘密和原始敏感正文。

### 8. 运维与所有权

写清谁接告警、谁可变更、谁批准高风险动作、客户依赖故障怎样升级、交付结束后谁维护，以及 Runbook 和恢复演练在哪里。

## 生产系统设计题：为 20 个企业客户设计 AI 工作流平台

### 先问需求

- 每个客户的用户数、峰值并发和延迟目标。
- 数据能否进入公有模型，是否要求私有部署。
- 需要连接哪些系统，接口有何速率和权限限制。
- 哪些任务只读，哪些会产生业务副作用。
- 可用性、RTO、RPO、审计保留和预算。

### 参考设计

```text
Customer Identity Provider
  -> API Gateway / Web Application Firewall
  -> Tenant-aware Application Service
       -> Workflow State Store
       -> Policy and Approval Service
       -> Connector Workers
       -> Model Gateway
       -> Retrieval Service
  -> Audit Store / Metrics / Logs / Traces / Eval Pipeline
```

### 关键取舍

- 共享控制面可降低成本，但数据面要按敏感度选择逻辑或物理隔离。
- 同步请求体验直接，但长任务应进入队列并提供可恢复状态。
- 单一模型接入简单，多模型路由能提高韧性但增加评测和一致性成本。
- 通用连接器应平台化，客户特殊逻辑通过版本化配置或受控扩展点实现。
- 自动动作按风险分级：只读可自动，低风险可策略审批，高风险必须人工审批。

### 容量思路

不要拍脑袋报服务器数量。先测单任务的模型延迟、Token、工具次数和数据库成本，再用峰值并发、突发系数、故障冗余和供应商配额反推容量。超出预算时优先考虑缓存、上下文裁剪、小模型分流、批处理和异步化。

## 事故场景：AI 助手建议了错误的生产回滚

### 1. 影响确认

确认哪些租户、服务和动作受影响，错误建议是否已被批准或执行。立即暂停同类自动动作，不要先删除审计记录。

### 2. 证据

- 用户输入、模型/Prompt/工具/策略版本。
- 检索片段和权限过滤结果。
- 工具调用参数、审批人、幂等键和执行返回。
- 指标、日志、Trace、变更与业务验证。
- 最近发布、评测集和门禁结果。

### 3. 假设

- 检索到了过期 Runbook。
- 提示注入改变了工具参数。
- 服务端没有重新校验模型给出的租户或资源。
- 审批界面没有展示影响范围和证据。
- 评测只测文本质量，没有测动作安全。

### 4. 验证顺序

在隔离环境重放相同版本和输入，一次只改变一个变量；检查权限与策略日志，再比较上一个安全版本。不要用生产系统反复试错。

### 5. 修复与影响面

先禁用相关写工具或切到只读模式，再修复权限、策略或数据。评估同一连接器、同一 Prompt、同一索引和所有租户是否受影响。

### 6. 回滚与恢复

回滚到已评测版本，撤销或补偿已执行动作，重新验证业务状态和 SLI。恢复自动化前必须补回归案例、审批显示和监控门禁。

### 7. 复盘

区分直接原因、促成条件和系统缺口，行动项要有负责人、期限和验证方法，而不是只写“加强测试”。

## 面试问题与追问路线

### 1. 什么是 FDE

**回答主线：** FDE 贴近客户发现真实问题，负责技术范围、系统设计、构建、生产上线和采用结果，并把共性需求沉淀回产品。

**继续追问：** 与解决方案架构师有什么不同？
**回答：** 边界因公司而异；常见差别是 FDE 对生产代码和上线后的工程结果承担更多端到端责任。

### 2. 客户要求“做一个聊天机器人”，你第一周做什么

**回答主线：** 访谈用户与负责人，观察当前流程，确定成功指标、数据权限和错误影响；建立代表性案例；用最小原型验证最高风险假设，而不是先选框架。

**继续追问：** 客户坚持直接上线怎么办？
**回答：** 明确风险和验收缺口，用只读、有限用户、有限数据的灰度方案降低影响，写清停止条件和人工回退。

### 3. 如何判断 AI 应用是否有效

**回答主线：** 分离任务质量、引用/安全、延迟/成本和业务采用；离线评测做版本门禁，线上观察真实用户与业务结果，并把失败案例回灌。

**继续追问：** 用 LLM 当评分器够吗？
**回答：** 不够。要校准评分器，对关键安全与权限规则使用确定性检查，抽样人工复核，并避免让评分器偏好某种文风代替事实正确。

### 4. 工具调用怎样防止误操作

**回答主线：** 工具按风险分级，最小权限，服务端校验租户/资源/动作，限制参数和步骤，使用幂等键、审批、审计、超时、熔断和回滚。

**继续追问：** 有人工确认按钮就安全吗？
**回答：** 不够。审批人必须有权限，界面要展示真实参数、影响和证据，服务端要把审批绑定到不可篡改的动作版本。

### 5. 原型如何生产化

**回答主线：** 补身份、租户、配置、秘密、数据质量、测试、评测、发布、可观测性、容量、故障恢复和所有权，并在灰度中验证真实用户路径。

**继续追问：** 最大风险通常在哪里？
**回答：** 不能泛答。应根据场景指出数据权限、依赖可靠性、状态一致性或动作副作用中的最高风险，并给出验证方法。

### 6. 为什么 FDE 需要前端

**回答主线：** 用户采用取决于完整工作流。FDE 至少要能设计输入、反馈、失败、权限和审批状态，即使最终由前端工程师实现。

**继续追问：** 后端很强但 React 不熟怎么办？
**回答：** 诚实说明深度，展示浏览器/API/状态建模基本功和一个最小可用 UI，同时选择更匹配的平台或后端型岗位。

### 7. 如何处理客户特有需求与产品化的冲突

**回答主线：** 先区分配置、扩展点和真正的一次性逻辑；记录重复模式，与产品团队定义通用合同；避免为一个客户污染核心模型。

**继续追问：** 什么时候应该拒绝定制？
**回答：** 当它违反安全/合规、破坏升级路径、价值不足以覆盖长期维护成本，或与产品边界冲突时，应提供替代方案并升级决策。

### 8. FDE 项目失败后怎样复盘

**回答主线：** 同时看技术故障和交付假设：问题是否选对、用户是否参与、数据是否代表真实、评测是否覆盖失败、上线与采用是否有负责人。

**继续追问：** 如何避免只怪客户需求变了？
**回答：** 检查早期假设、决策记录、反馈频率和变更机制，明确团队本可更早发现的信号和系统性改进。
