## 先说结论

这不是一份只维护 Kubernetes 的岗位，而是一份覆盖面很宽的综合运维岗位。根据 [智联招聘岗位原文](https://m.zhaopin.com/jobs/CC834928100J40826414816.html)，职责同时包含：

- 网络设备、服务器与网络架构升级。
- 网络安全策略。
- Linux 运维、系统优化和脚本自动化。
- Nginx、Tomcat、Apache、Redis、ActiveMQ、MySQL、MongoDB。
- 应用部署、CI/CD、Kubernetes 和灰度发布。
- 服务故障、网络故障和工程事故应急方案。
- 系统集成、部署测试、技术文档和备份归档。
- 桌面运维与非工作时间突发事件处理。

这意味着面试官更可能寻找一名“能独立把问题接住的人”，而不是只背某个产品命令的人。回答时要持续展示五件事：

1. 能从现象建立分层排查路径。
2. 能用指标、日志、抓包、配置和变更记录证明判断。
3. 知道高风险操作前如何备份、评估影响和准备回滚。
4. 能把临时修复沉淀成监控、脚本、Runbook 和复盘。
5. 对没有做过的规模或产品诚实说明边界，再讲迁移思路和实验验证。

## 通用排障回答框架

面试官给出任何故障时，先用下面这套结构，避免变成命令背诵：

1. **确认影响**：单用户、单服务、单节点、单机房还是全公司。
2. **确认时间**：何时开始，是否与发布、配置、网络或证书变更重合。
3. **建立基线**：正常值、异常值、同类节点和历史趋势。
4. **分层取证**：客户端、DNS、网络、负载均衡、主机、进程、应用、数据依赖。
5. **先止损**：切流、回滚、隔离、限流或降级，保留必要现场。
6. **验证假设**：一次只改变一个关键变量，避免“重启后好了”却不知道根因。
7. **恢复验收**：技术指标、业务交易、用户路径和持续观察窗口都通过。
8. **复盘改进**：直接原因、促成条件、监控缺口、操作项、负责人和期限。

一句能体现成熟度的话：

> 我会把恢复服务和查清根因分成两个并行目标。紧急时先按预案止损，但在清理现场前保存日志、指标、配置差异和时间线。

## 网络与服务器主线

### 必须讲清的网络链路

```text
用户终端
  -> 接入交换机与 VLAN
  -> 网关或三层交换
  -> 防火墙、ACL 或 NAT
  -> DNS 与负载均衡
  -> 服务器网卡与监听端口
  -> 应用进程
```

- **VLAN**：虚拟局域网，用逻辑方式隔离广播域。
- **Access 口**：通常只承载一个 VLAN，常连接终端。
- **Trunk 口**：可承载多个带标签 VLAN，常连接交换机、服务器虚拟化平台或无线控制器。
- **ACL**：访问控制列表，按源、目的、协议和端口允许或拒绝流量。
- **NAT**：网络地址转换，常用于内外网地址映射。
- **DNS**：把域名解析为地址；解析正确不等于目标端口一定可访问。

### 问题一：服务器能 ping 通，但 443 访问失败

答题顺序：

1. 确认是单客户端还是所有客户端失败。
2. 用 `nslookup` 或 `dig` 核对域名、CNAME、地址和 TTL。
3. 用 `Test-NetConnection host -Port 443`、`nc -vz` 或 `curl -vk` 判断 TCP/TLS/HTTP 卡在哪层。
4. 检查路由、ACL、防火墙、NAT 和负载均衡健康检查。
5. 在服务器检查 `ss -lntp`，确认监听地址、端口和进程。
6. 用 `tcpdump` 判断 SYN 是否到达、SYN-ACK 是否返回、是否重传或被 RST。
7. 检查证书、SNI、Nginx 日志和上游应用。

追问“ping 通为什么还不够”：

> ping 通只能说明 ICMP 在当前路径上可达。业务访问还依赖 DNS、TCP 端口、TLS、代理配置和应用进程，防火墙也可能允许 ICMP 但拒绝 443。

### 问题二：网络时断时续怎么查

先看四类证据：

- 接口错误、丢包、CRC、协商速率和双工模式。
- 延迟、抖动、重传和路径变化。
- 交换机环路、广播风暴、MAC 地址漂移和生成树事件。
- 防火墙会话表、NAT 端口、链路聚合和设备资源。

不要只连续 ping。应结合多目标对照、`mtr`、交换机端口计数、抓包和设备日志，判断故障发生在终端、接入、汇聚、出口还是服务端。

### 问题三：如何规划网络架构升级

回答必须覆盖：

1. 盘点现网拓扑、地址、VLAN、路由、带宽、设备、单点和业务依赖。
2. 明确目标：容量、安全、可靠性、可维护性还是新业务接入。
3. 设计分区：办公、服务器、管理、备份、访客、生产/工业设备分区。
4. 设计冗余：双上联、链路聚合、网关或防火墙高可用，避免伪冗余。
5. 制定迁移批次、观察指标、回滚路径和应急通信。
6. 先做实验或小范围试点，再分批切换。
7. 验证业务路径、路由收敛、安全策略、监控和配置备份。
8. 更新拓扑、地址表、策略表、变更记录和 Runbook。

### 服务器与 IDC 快问快答

**RAID 1、5、6、10 怎么选？**

- RAID 1：镜像，简单可靠，容量利用率低。
- RAID 5：允许一盘故障，写入有校验开销，大盘重建窗口风险较高。
- RAID 6：允许两盘故障，可靠性更高，写入开销更大。
- RAID 10：镜像加条带，性能和恢复通常较好，但成本高。
- RAID 不是备份，误删除、勒索、控制器故障和站点灾难仍需独立备份。

**硬件故障先看什么？**

看 BMC/IPMI/iDRAC/iLO 告警、RAID 状态、SMART、温度、风扇、电源、内存 ECC、系统日志和厂商诊断。先确认是否有冗余、业务是否可迁移，再决定下线和更换。

**机房巡检看什么？**

供电、UPS、温湿度、消防、门禁、链路、设备告警、容量、备份任务、资产标签和变更记录。巡检不是“看灯正常”，要有阈值、记录、异常负责人和闭环。

## Linux 与脚本主线

### 一分钟性能排查地图

| 现象 | 第一批证据 | 常见方向 |
|---|---|---|
| 系统变慢 | `uptime`、`top`、`vmstat 1` | CPU、运行队列、上下文切换、I/O 等待 |
| 内存紧张 | `free -h`、`vmstat 1`、`dmesg -T` | 缓存、进程 RSS、Swap、OOM |
| 磁盘慢 | `iostat -xz 1`、`pidstat -d 1` | 延迟、队列、利用率、具体进程 |
| 磁盘满 | `df -hT`、`du -x`、`lsof +L1` | 大文件、已删未释放、日志、快照 |
| inode 满 | `df -i`、目录文件数统计 | 海量小文件、缓存、临时文件 |
| 网络慢 | `ss -s`、`ip -s link`、`sar -n DEV 1` | 丢包、重传、连接积压、带宽 |
| 服务异常 | `systemctl status`、`journalctl -u` | 启动失败、权限、配置、依赖 |

### 问题一：Load Average 高但 CPU 不高

不要直接回答“CPU 不够”。Linux 的不可中断睡眠任务也会进入负载统计，常见方向包括磁盘、网络存储、块设备和内核等待。

回答步骤：

1. 用 `uptime`、`top` 看负载趋势和 CPU 的 `us`、`sy`、`wa`。
2. 用 `vmstat 1` 看运行队列、阻塞任务和上下文切换。
3. 用 `ps` 查 `D` 状态任务及等待点。
4. 用 `iostat -xz 1`、`pidstat -d 1` 判断设备延迟和进程 I/O。
5. 如果涉及 NFS、SAN 或云盘，再检查网络、挂载、路径和存储端。
6. 先评估切流或隔离，再处理故障设备或进程。

### 问题二：内存快满了是否需要立刻清缓存

不一定。Linux 会用空闲内存做页缓存，重点看 `available`、Swap 活动、内存压力、OOM 和应用延迟，而不是只看 `used`。

先确认：

- 是否持续发生 Swap in/out。
- 是否出现 OOM Killer。
- 哪个进程的 RSS、堆或映射持续增长。
- 是应用泄漏、缓存策略、并发增长还是资源限制不合理。
- 容器是否达到 cgroup 限制，而宿主机仍有内存。

随意执行清缓存会破坏文件缓存并引起 I/O 抖动，只能作为明确评估后的临时措施，不能替代根因修复。

### 问题三：磁盘显示满，但找不到大文件

优先想到“文件已删除，但仍被进程打开”。`df` 统计文件系统占用，`du` 遍历可见目录，两者可能不一致。

用 `lsof +L1` 查找链接数为 0 但仍被打开的文件。确认进程和业务影响后，通过应用支持的日志重开、平滑重载或受控重启释放空间，不要直接操作进程文件描述符。

### 脚本题怎么拿分

面试官让写巡检或备份脚本时，除了主逻辑，还要主动补充：

- `set -euo pipefail` 或明确的错误处理。
- 参数校验、超时、退出码和结构化日志。
- 只读默认模式和高风险动作的二次确认。
- 临时文件、锁和并发控制。
- 凭据不硬编码。
- 失败告警、重试上限和幂等性。
- 测试环境、回滚和审计记录。

可以这样解释幂等：

> 同一个自动化任务重复执行，不会因为第一次已经执行过就产生额外破坏。例如创建用户前先检查存在性，修改配置前先比较目标状态，并为原文件保留可回滚版本。

## 应用入口与 JVM 主线

### 请求链路

```text
客户端
  -> DNS
  -> 防火墙或负载均衡
  -> Nginx / Apache HTTP Server
  -> Tomcat 应用
  -> Redis / ActiveMQ / MySQL / MongoDB
```

### Nginx、Apache、Tomcat 的边界

- **Nginx**：常用于反向代理、静态资源、TLS 终止、负载均衡、限流和入口治理。
- **Apache HTTP Server**：通用 Web 服务器，也可提供静态资源、模块化认证和反向代理。
- **Tomcat**：Java Servlet 容器，真正运行 Java Web 应用，不等同于前面的 Web 代理。

一个常见架构是 Nginx/Apache 对外接流量，Tomcat 运行应用。生产上是否都需要，要看现有系统和功能，不能为了“完整”重复堆代理层。

### Nginx 502 与 504

**502 Bad Gateway**：代理没有从上游拿到有效响应。常见于上游未监听、连接被拒绝、进程崩溃、协议不匹配、响应头异常或连接被重置。

**504 Gateway Timeout**：代理等待上游超时。常见于应用慢、数据库慢、连接池耗尽、下游超时或代理超时设置不匹配。

排查顺序：

1. 确认影响域名、路径、实例和开始时间。
2. 看 Nginx access/error log 的状态码、上游地址、连接时间和响应时间。
3. 从 Nginx 节点直接访问上游，排除前端路径。
4. 检查上游监听、进程、线程池、连接池、GC 和依赖。
5. 对比最近发布、配置、证书和流量变化。
6. 必要时摘除异常实例、限流、扩容或回滚。
7. 恢复后验证错误率、P95/P99、业务交易和持续稳定时间。

### Tomcat 响应慢

按下面四层取证：

1. **JVM**：堆、GC 停顿、线程、类加载、直接内存。
2. **容器**：Connector 最大线程、当前忙线程、accept 队列和连接超时。
3. **应用**：线程栈、锁、慢方法、错误日志。
4. **依赖**：数据库连接池、Redis、消息队列、外部 HTTP 服务。

不能只把 `maxThreads` 调大。线程增加会提高内存和下游并发压力，如果瓶颈在数据库，可能让故障更严重。

### JVM 高 CPU 怎么答

1. 确认 Java 进程和异常开始时间。
2. 找进程内高 CPU 线程。
3. 将线程 ID 转为线程栈可匹配的格式。
4. 连续获取多份线程栈，区分持续热点和瞬时采样。
5. 结合 GC、应用日志、发布与流量判断是业务循环、锁竞争、序列化、GC 还是依赖重试。
6. 紧急时先摘流或回滚，保留 dump 和指标后再重启。

## 中间件与数据服务

### 四类产品对照

| 产品 | 核心用途 | 高可用重点 | 常见故障 |
|---|---|---|---|
| Redis | 低延迟缓存、计数、会话等 | 主从、Sentinel/Cluster、持久化 | 热 Key、大 Key、内存淘汰、延迟、复制中断 |
| ActiveMQ | Java/JMS 生态的消息代理 | 持久化、主备/共享存储或复制、消费者冗余 | 消息积压、消费失败、死信、磁盘或内存限制 |
| MySQL | 关系数据与事务 | 复制、故障切换、备份与恢复 | 慢 SQL、锁等待、连接耗尽、复制延迟 |
| MongoDB | 文档数据 | Replica Set、选主、写关注、备份 | 索引缺失、工作集超内存、复制延迟、主节点切换 |

### Redis 必答题

**RDB 和 AOF 有什么区别？**

- RDB 是某个时间点的快照，恢复快，但两次快照之间的数据可能丢失。
- AOF 记录写操作，数据窗口通常更小，但文件和恢复成本更高。
- 两者都不是跨故障域备份，仍需验证恢复、保留和异地副本。

**Redis 延迟突然升高怎么查？**

看命令延迟、慢日志、CPU、内存、淘汰、持久化、复制、网络、热 Key、大 Key、客户端连接和版本变更。不要只看 Redis 服务进程是否存活。

**缓存穿透、击穿、雪崩怎么说？**

- 穿透：大量请求查询不存在的数据，可用空值缓存、布隆过滤器和入口防护。
- 击穿：热点 Key 过期时大量请求打到后端，可用互斥重建、逻辑过期或热点预热。
- 雪崩：大量 Key 同时失效或缓存整体不可用，可分散过期、限流降级并保护数据库。

### ActiveMQ 必答题

**Queue 和 Topic 的区别是什么？**

- Queue 是队列，一个消息通常由一个消费者处理，适合任务分发。
- Topic 是主题，消息可广播给多个订阅者；是否能离线后继续收到，要看持久订阅配置。

**如何避免消息“看起来发送成功但实际丢了”？**

要同时考虑生产者确认、消息持久化、Broker 存储与高可用、消费者确认、重试、死信队列、幂等和端到端业务对账。消息系统只能提供某一段交付语义，不能自动保证业务只执行一次。

**消息积压怎么查？**

1. 确认是单队列还是全 Broker，生产速率与消费速率差多少。
2. 检查消费者存活、异常、处理耗时、线程和下游依赖。
3. 检查 Broker 的内存、存储、游标、连接、流控和日志。
4. 评估消息时效、顺序和重复处理风险。
5. 修复消费者或扩容前先验证幂等和下游承载能力。
6. 恢复后观察积压下降斜率，并补消费延迟告警。

如果你主要用过 RabbitMQ，可以说机制有可迁移部分，但要明确 ActiveMQ 常与 JMS 生态结合，术语、协议、持久化和高可用实现并不完全相同。

### MySQL 必答题

**数据库突然慢怎么查？**

从业务错误率和延迟开始，检查连接数、运行线程、慢 SQL、锁等待、事务、Buffer Pool、磁盘延迟、复制状态和最近变更。用 `EXPLAIN` 分析执行计划，但不能只看到“有索引”就结束，还要看选择性、扫描行数、回表、排序和临时表。

**备份怎么保证可恢复？**

明确全量、增量或 Binlog 组合，记录备份点、校验、加密、保留和恢复步骤。定期恢复到隔离环境，验证表结构、行数/校验、关键查询和时间点恢复。主从复制不是备份，误删除可能同步到从库。

**主从延迟怎么处理？**

先看网络、I/O、SQL 线程、长事务、大事务、锁和从库资源。业务侧要明确哪些读能接受陈旧数据；故障切换前检查数据差距，避免把延迟从库直接提升为主库造成数据丢失。

### MongoDB 必答题

**Replica Set 是什么？**

副本集由主节点、从节点和可选投票成员组成。写通常进入主节点，通过 Oplog 复制；主节点故障后满足多数派条件的成员重新选主。

**`writeConcern: majority` 解决什么？**

它要求写入被多数有投票能力的数据成员确认后再返回，提高故障切换后的持久性保证，但会增加延迟。它不是备份，也不能防止应用误删除。

**查询慢怎么查？**

查看慢操作、执行计划、扫描文档数与返回数、索引、工作集、磁盘、锁/并发、分片路由和最近数据增长。索引过多会增加写放大和内存压力，不能“慢就加索引”。

## Docker、CI/CD 与 Kubernetes

### 发布链路必须讲成一条线

```text
代码提交
  -> 测试与安全检查
  -> 构建不可变制品
  -> 构建并扫描镜像
  -> 推送镜像仓库
  -> 测试环境验证
  -> 审批
  -> 小流量灰度
  -> 指标与业务验证
  -> 全量或回滚
```

核心原则：

- 同一个已验证制品逐级晋级，不在每个环境重新构建。
- 镜像标签要能追溯 Commit，生产最好使用不可变标签或 Digest。
- 配置和密钥不写进镜像。
- 数据库变更优先采用向前、向后兼容的分步迁移。
- 自动发布必须有质量门槛、权限、审计、停止条件和回滚。

### Docker 容器启动后立刻退出

排查顺序：

1. 看容器状态、退出码和 OOM 标记。
2. 看标准输出与应用日志。
3. 核对入口命令、参数、工作目录和文件权限。
4. 核对配置、密钥、挂载、DNS、网络和依赖。
5. 核对 CPU/内存限制与宿主机资源。
6. 用相同镜像在隔离环境复现，不直接在生产镜像里临时改文件。

要点：容器需要一个前台主进程。主进程结束，容器就结束；这不等于 Docker 自身故障。

### Kubernetes 一分钟请求链路

```text
kubectl / CI
  -> API Server 认证、鉴权、准入
  -> etcd 保存期望状态
  -> Controller 创建或调整对象
  -> Scheduler 选择节点
  -> kubelet 通过容器运行时启动 Pod
  -> CNI 配置网络
  -> CSI 挂载存储
  -> Service / Ingress 提供访问
```

### Pod Pending

先看 `kubectl describe pod` 的 Events，再按以下方向：

- CPU/内存不足或 requests 过大。
- 节点选择器、亲和性、污点和容忍不匹配。
- PVC 未绑定或存储拓扑不满足。
- 配额、限制范围或调度策略阻止。
- 节点 NotReady 或调度器异常。

### Pod Running 但不 Ready

Running 只表示容器进程已启动；Ready 表示它满足接流量条件。

检查：

- Readiness Probe 的路径、端口、协议、初始延迟和超时。
- 应用是否真正监听。
- 配置、密钥、证书和依赖是否就绪。
- Service selector 与 EndpointSlice 是否包含该 Pod。
- NetworkPolicy、CNI、DNS 和服务间调用。

不要为了让状态变绿直接删除探针。探针失败可能是在保护流量。

### CrashLoopBackOff

看上一次容器日志、退出码、OOM、入口命令、配置、权限、挂载和依赖。`CrashLoopBackOff` 是反复失败后的退避状态，不是根因名称。

### Service 访问不通

按下面顺序缩小范围：

1. Pod IP 是否可直接访问。
2. Readiness 是否通过。
3. Service selector 是否匹配，EndpointSlice 是否有后端。
4. Service 端口、targetPort 和应用监听是否一致。
5. kube-proxy/eBPF 数据路径、CNI 和 NetworkPolicy。
6. CoreDNS、Ingress、负载均衡和外部防火墙。

### Kubernetes 发布失败怎样回滚

先确定失败是新版本、配置、依赖、容量还是平台问题。若新 ReplicaSet 错误率升高或探针失败，停止继续放量并回滚到已验证版本。回滚前确认数据库变更是否兼容；如果 schema 已不可逆修改，只回滚应用可能产生更大故障。

恢复后验证：

- Deployment 状态和期望副本。
- Pod 就绪与重启。
- 入口成功率、延迟和业务交易。
- 数据一致性与队列积压。
- 持续观察窗口内没有再次恶化。

## 灰度发布

### 一个合格的灰度方案

1. **对象**：哪些用户、租户、区域或流量进入新版本。
2. **批次**：例如 5%、20%、50%、100%，每批有观察时间。
3. **指标**：成功率、P95/P99、业务成功、资源、日志错误和队列。
4. **门槛**：相对基线恶化多少必须停止，不能只看“没有报警”。
5. **回滚**：应用、配置、流量和数据库如何恢复。
6. **审计**：版本、批准人、时间、指标和结论可追溯。

### 面试示例

> 我会先确认新旧版本可以并行、数据库变更向后兼容，再把 5% 流量给新版本。每批同时比较新旧版本的请求成功率、P95/P99、关键业务成功率、资源和错误日志。如果达到停止阈值，先把流量切回旧版本，再保留新实例用于取证；如果涉及数据写入，还要检查数据兼容和补偿，而不是只执行镜像回滚。

### 蓝绿、金丝雀和滚动发布

- **蓝绿**：两套完整环境切换，回退直观，但资源成本高，数据库兼容仍是难点。
- **金丝雀**：让少量流量先进入新版本，能控制风险，但需要精细流量和对照观测。
- **滚动发布**：逐步替换实例，资源效率高，但新旧版本会并存，需保证兼容和容量。

## 安全、备份与应急

### 网络安全策略不是只配防火墙

回答至少覆盖：

- 网络和安全域分区，默认拒绝、按需放行。
- 账号实名、最小权限、多因素认证和离职回收。
- 管理面不直接暴露互联网，使用堡垒机/VPN/受控入口。
- 系统补丁、漏洞扫描、基线和资产盘点。
- TLS、证书生命周期、密钥与 Secret 管理。
- 日志集中、时间同步、审计和异常登录告警。
- 终端防护、备份隔离、恢复演练和应急响应。
- 规则变更有申请、测试、批准、验证和回滚。

### 3-2-1 备份

- 至少 3 份数据。
- 使用 2 种不同介质或存储形态。
- 至少 1 份位于不同故障域，最好具备离线或不可变能力。

面试时一定补一句：

> 备份任务显示成功，只能说明任务执行到某一步。只有经过校验和恢复演练，并验证关键业务数据可用，才能证明恢复能力。

### RPO 与 RTO

- **RPO**：最多能接受丢失多长时间的数据。
- **RTO**：故障后要求多长时间恢复服务。

这两个目标由业务影响决定，不应由运维单方面随意填写。更低的 RPO/RTO 通常需要更高成本、更复杂架构和更频繁演练。

### 应急方案六部分

1. 触发条件和故障分级。
2. 值班、指挥、技术、业务和外部厂商的职责。
3. 止损、切换、降级、隔离和回滚步骤。
4. 数据、配置、日志和现场保护。
5. 业务验收、观察窗口和退出应急条件。
6. 时间线、根因、改进项、负责人和截止日期。

## 监控与 AIOps

### 四层监控

| 层次 | 示例 |
|---|---|
| 资源 | CPU、内存、磁盘延迟、接口丢包、温度、电源 |
| 平台 | Kubernetes 控制面、节点、Pod、存储、网络 |
| 应用 | 请求率、错误率、延迟、线程、连接池、队列积压 |
| 业务 | 登录、下单、任务完成、模型推理成功、关键数据时效 |

### Zabbix 与 Prometheus

- Zabbix 适合主机、网络设备、SNMP、传统基础设施和统一资产式监控。
- Prometheus 适合指标标签模型、云原生服务发现和短周期时序指标。
- 企业可以组合使用，关键不是工具数量，而是告警职责、去重、路由、值班和恢复闭环。

### AIOps 加分回答

不要泛泛说“用 AI 自动修复”。可以说：

> 我会先把主机、网络、应用、数据库、发布版本和告警时间线关联起来，用规则和统计方法做事件聚合与异常提示。自动化先从只读诊断和建议开始；涉及重启、切流、扩容或数据操作时保留审批、权限、审计和回滚。

## 桌面运维怎么回答

即使目标是平台方向，也不要轻视职责中的桌面运维。回答应体现服务意识和安全边界：

1. 确认影响用户、业务紧急程度和是否为群体故障。
2. 远程或现场收集系统、网络、账号、软件和外设证据。
3. 先恢复用户工作，再做根因和永久修复。
4. 管理员权限最小化，敏感数据和个人信息不随意查看或复制。
5. 工单记录现象、处理、变更、资产和用户确认。
6. 重复问题沉淀知识库、软件分发、基线或自动化。

群体性“无法上网”要先查 DHCP、DNS、网关、交换机和出口，不要逐台重装电脑。

## 十二个现场故障演练

每题先自己口述 2 分钟，再看要点。

### 1. 全公司突然无法访问互联网

- 确认办公网、服务器区、无线和不同 VLAN 的影响范围。
- 检查网关、DNS、出口链路、防火墙、NAT、运营商和最近变更。
- 用内网、网关、公网 IP、域名四级探测区分 DNS 与链路。
- 如有冗余按预案切换，保留设备日志和会话证据。
- 恢复后验证关键 SaaS、VPN、外部发布和持续稳定性。

### 2. 只有一个 VLAN 不能访问服务器区

- 看网关、三层接口、VLAN 是否存在、Trunk 是否放行。
- 看路由、ACL、防火墙区间策略与回程路径。
- 对比正常 VLAN 配置，检查最近策略变更。
- 抓包确认请求在哪一跳消失，避免盲目放开全部规则。

### 3. Nginx 发布后大量 502

- 对比新旧版本、上游地址、监听端口和健康检查。
- 看 Nginx error log、上游连接和应用启动日志。
- 先摘除异常实例或回滚，不靠延长超时掩盖连接失败。
- 验证入口错误率、业务交易和所有实例状态。

### 4. Tomcat CPU 100%

- 确认流量、发布、定时任务和 GC 是否变化。
- 获取高 CPU 线程与多份线程栈。
- 检查死循环、序列化、锁竞争、重试风暴和 GC。
- 摘流或回滚时先保留线程栈、GC 和应用日志。

### 5. Linux 根分区 100%

- 区分空间与 inode。
- 查日志、临时文件、容器层、Core Dump 和已删未释放文件。
- 先停止继续增长，按应用机制清理或轮转。
- 不直接删除未知文件；恢复后补容量和增长速率告警。

### 6. MySQL 连接数耗尽

- 看当前连接、活跃线程、长事务、锁、慢 SQL 和应用连接池。
- 区分流量增长、连接泄漏、数据库变慢和下游重试。
- 限流、摘除异常实例或终止明确的问题会话前评估事务影响。
- 不把 `max_connections` 调大当作最终修复。

### 7. Redis 内存持续上涨

- 看 Key 数、内存组成、淘汰、命中率、客户端和持久化。
- 识别大 Key、热 Key、无过期 Key 和业务数据结构变化。
- 删除或迁移前确认业务语义和主从/集群影响。
- 补 Key 规范、容量预算、TTL 和增长告警。

### 8. ActiveMQ 消息积压

- 比较生产/消费速率、最老消息年龄和消费者状态。
- 查消费异常、处理时长、下游数据库和 Broker 资源。
- 扩消费者前确认顺序、幂等和下游容量。
- 恢复后验证积压下降、失败消息和业务对账。

### 9. MongoDB 主节点切换后应用报错

- 确认副本集状态、选主、复制延迟和多数派。
- 检查客户端连接串是否包含副本集成员与正确参数。
- 看应用驱动是否支持拓扑发现、重试和超时。
- 验证写入、读取一致性和故障窗口数据。

### 10. Kubernetes Pod 一直不 Ready

- 看 Pod Events、探针失败、容器日志和监听端口。
- 看配置、密钥、依赖、Service Endpoint 和网络策略。
- 判断是应用没有就绪，还是探针设计错误。
- 修复后验证真实用户路径，不只看 Pod 变绿。

### 11. 灰度 10% 后错误率升高

- 立即停止放量，对比新旧版本同一时间窗。
- 根据预设阈值把流量切回旧版本。
- 检查应用、配置、依赖、数据兼容和特定用户特征。
- 保留新版本实例和遥测用于取证，修复后重新从小流量开始。

### 12. 备份任务每天成功，恢复时失败

- 先保护现有备份和生产数据，不反复覆盖。
- 确认备份链是否完整、密钥、版本、校验和依赖是否可用。
- 评估可恢复到哪个时间点以及数据损失。
- 在隔离环境恢复并做业务校验。
- 复盘为什么只监控任务状态却没有恢复演练。

## 工业 AI 场景架构题

### 题目

为多个工厂或客户现场的机器视觉/智能设备设计一套应用交付与运维方案。现场网络可能不稳定，中心端要统一管理版本、模型、配置、监控和故障，关键生产不能因为中心网络短时中断就立即停止。

### 先问清约束

1. 现场数量、服务器与设备规模。
2. 是否有实时控制，允许的延迟和停机时间。
3. 中心与现场的网络、带宽、专线/VPN 和离线时长。
4. 应用、模型和配置更新频率。
5. 数据是否允许出厂，是否涉及隐私或合规。
6. RPO、RTO、维护窗口和现场支持能力。
7. 是否已有虚拟化、Kubernetes、CI/CD 和监控平台。

### 参考架构

```text
研发与中心端
  Git / CI
    -> 制品与镜像仓库
    -> 签名、扫描、版本与审批
    -> 分批发布控制

安全连接
  专线或 VPN
    -> 身份认证与最小权限
    -> 断点续传与带宽控制

工厂或客户边缘端
  本地运行应用、模型与必要数据
    -> 本地健康检查与缓冲
    -> 版本 A/B 或可回退目录
    -> 本地监控、日志与告警
    -> 网络恢复后汇总到中心
```

### 设计时必须讲的取舍

- 现场关键功能应具备一定自治能力，不能把所有请求都依赖中心。
- 应用、模型、配置和数据结构分别版本化，并记录兼容矩阵。
- 大文件和模型分发要支持校验、断点续传、限速与失败回退。
- 每次先选低风险站点试点，再按批次推广。
- 监控既有中心视角，也保留现场本地告警和离线缓冲。
- 远程操作使用受控通道、最小权限、审批和审计。
- 数据回传要明确分类、脱敏、保留和带宽成本。
- 工业控制网络与办公/互联网区域隔离，跨区访问按需开放。

### 面试收尾

> 我不会在需求不清时直接决定所有现场都上 Kubernetes。资源规模小、应用简单的边缘站点可能更适合受控的容器编排或系统服务；规模较大、服务多且需要统一调度时再评估 K3s/Kubernetes。关键是可观测、可升级、可回退、断网可运行和安全可审计。

## 可能的现场操作题

### Linux

- 找出监听 8080 的进程。
- 找出近 10 分钟错误日志。
- 判断磁盘空间、inode 或已删未释放文件。
- 查看某服务最近一次启动失败原因。
- 写一个带超时、日志和退出码的健康检查脚本。

### 网络

- 解释一个 TCP 连接从 SYN 到建立。
- 判断 DNS、端口、TLS 还是 HTTP 故障。
- 读一段 `tcpdump` 或 `mtr` 结果。
- 设计两个网段之间的最小放行策略。

### Nginx

- 写反向代理和上游健康相关的基本配置。
- 解释 Host、X-Forwarded-For、超时和日志字段。
- 根据 access/error log 判断 502 或 504。

### Kubernetes

- 根据 Events 判断 Pending。
- 根据日志和探针判断 CrashLoopBackOff/NotReady。
- 解释 Deployment、Service、Ingress、ConfigMap、Secret、PVC。
- 演示发布状态、回滚和验证。

### SQL 与中间件

- 使用 `EXPLAIN` 分析慢查询。
- 解释 Redis TTL、持久化和内存淘汰。
- 判断消息积压是生产太快还是消费太慢。
- 说明 MongoDB 副本集故障后的客户端行为。

## 高频面试题速答

### 1. 你如何判断故障是网络还是应用？

先确认影响范围，再从 DNS、路由、TCP、TLS、HTTP 到应用依赖逐层探测。客户端和服务端同时取证，必要时抓包。端口可达不代表应用健康，应用报超时也不一定是网络问题。

### 2. 为什么不能一出故障就重启？

重启可能临时恢复，但会丢失线程、连接、内存和现场证据，也可能扩大影响。紧急时可以按预案受控重启，但应先确认影响、保存关键证据、准备回滚并验证恢复。

### 3. 你如何做容量规划？

从业务量和增长预测映射到请求、并发、数据、网络和资源；使用历史峰值和压测建立单实例基线；保留故障冗余和发布余量；设置预测告警并定期校准。

### 4. 你如何保证变更安全？

明确范围、依赖、风险、验证、审批、窗口、观察指标和回滚；先测试和小范围试点；一次只改变可控变量；变更后做技术与业务验收并记录。

### 5. 监控告警太多怎么办？

先按用户影响和可行动性清理，无明确动作的告警降级为看板或事件；做去重、聚合、抑制、维护窗口和分级路由；用 SLO 和业务信号补足纯资源阈值。

### 6. 如何处理不会的技术问题？

先说明经验边界，再从相近系统的共同机制回答，列出需要确认的版本、架构和证据，最后给出隔离环境验证方案。不要猜产品参数，也不要假装做过。

### 7. 为什么想来这家公司？

只使用你真实认同的部分：

> 我关注到岗位同时覆盖基础设施、应用交付、Kubernetes 和工业智能场景。这种岗位需要把传统运维稳定性与自动化平台能力结合起来，符合我的发展方向。我也希望进一步了解当前团队的基础设施规模、客户现场支持边界和最优先的稳定性目标。

### 8. 能接受非工作时间处理突发事件吗？

可以表达责任意识，同时了解制度：

> 对影响业务的突发事件，我能按值班和应急机制响应。我也重视明确的故障分级、轮值、升级路径、补休或值班安排，以及通过复盘减少重复夜间故障。想了解团队目前的值班频率和应急机制。

## 岗位判断与风险边界

### 值得关注的机会

- 能同时积累网络、Linux、应用交付和 Kubernetes 的完整链路经验。
- 公司业务涉及机器视觉、自动化和工业场景，适合向 AIOps/边缘运维延伸。
- 岗位强调独立集成、部署、测试和方案，可能有较完整的交付责任。

### 面试必须确认的风险

- 职责横跨网络、服务器、安全、中间件、数据库、K8s 和桌面，需确认是否“一人包全部”。
- 招聘信息要求 5 至 10 年经验，要确认薪酬与实际责任、值班和出差是否匹配。
- “工作时间之外突发事件”要确认轮值频率、响应要求、补休和值班机制。
- 工业客户场景可能涉及驻场、出差、弱网和非标准环境，要确认支持边界。
- 要确认网络架构升级和安全策略是否有预算、审批、同事和厂商支持。

这些问题不是为了在面试中对抗招聘方，而是判断双方是否匹配。

```text
业务影响

  -> 假设与验证
  -> 止损与恢复
  -> 风险与回滚
  -> 复盘与长期改进
```
