## 先认准这份岗位，别把准备方向走偏

老师先帮你划一道线：这个岗位是“让 AI 应用平台持续稳定工作”，不是“从零训练一个大模型”，也不是“把所有技术栈重新背一遍”。招聘明确聚焦**存量服务稳定性**，多次说明不参与新服务部署上线工作。你仍需理解配置变更、版本兼容和恢复流程，但不必把大部分准备时间投入新建集群、复杂发布流水线或模型训练。

与[河北鹰眼智能运维工程师路线](./hebei-eagle-eye-operations-engineer-role.md)相比，我们保留岗位拆解、学习优先级、真实故事卡、故障题、架构题和模拟面试方法；把主线从“网络、服务器和应用交付”移到“模型调用、智能体任务、知识库、实时通信和云原生治理”。旧岗位的两天日期、工业场景和技术权重不能照搬。

这也不是把 AIOps 和 AI 平台运维当成同一个词。AI 是人工智能；AIOps（Artificial Intelligence for IT Operations）是用数据和智能方法辅助运维判断；AI 平台运维是维护承载 AI 应用的系统。Kubernetes 是管理容器应用的平台，K8s 是它的常见简称。你可以用 AIOps 分析 AI 平台的日志和告警，但岗位的基本功仍是看懂链路、控制风险、验证恢复，而不是给每个问题都接一个模型。

如果你已有 Linux、虚拟化、Java 应用升级、数据库或现场排障经验，这些不是作废的旧能力。它们能迁移成资源分析、配置核对、变更回退、数据恢复和跨团队协作。真正需要补的是：为什么聊天页面返回 200 仍可能失败，为什么重试会重复执行工具，为什么 Pod 正常而任务失败，以及知识库更新为什么不仅是上传文件。

先不要说“我精通 AI 运维”。今天先画出一条请求链，把一个失败任务追到最后一次有证据的状态。这一步做好，后面的名词才有落点。

## 老师带你看一条真实类型的业务链

先补最小前置：服务是持续处理请求的程序；请求是用户或程序发给它的一次操作，响应是返回的信息。API 是 Application Programming Interface，即应用程序接口；RESTful API 是按资源和 HTTP 方法组织的一类接口设计，不是某个特定产品。HTTP 是浏览器和 Web 服务常用的通信协议，200 是响应状态码之一。资源不够、通信失败和业务结果不完整，是不同层次的问题。

假设用户问：“请查这批订单的问题，生成分析，并建立一个待人工确认的工单。”前半段是问答，后半段可能改变系统状态。我们先不管用了多少产品，把输入、状态、证据和副作用分开。

```text
用户浏览器
  -> 网关与身份校验
  -> 后端接口 / 任务受理
  -> Agent Runtime（智能体运行环境）与任务编排
       -> RAG（检索增强生成）读取获授权的知识
       -> 模型路由 -> LLM（大语言模型）调用
       -> 工具调用 -> 查询或受控写操作
       -> 任务状态 / 检查点 / 结果存储
  -> 流式事件或任务查询 -> 用户得到最终结果

各层产生的指标、日志、追踪 -> 可观测系统 -> 告警与人工处理
```

上面的箭头主要表示请求或数据流；最后一行是观测数据流。模型、工具和检索可能循环出现，不保证所有任务都按这条直线走。LLM 负责依据输入生成输出，不是负责把工作流状态可靠地落盘；网关可校验访问与限流，不代表后端已经完成任务。

第一次看图，只回答四个问题：请求在哪里排队，任务由谁持久保存，输出通过什么连接发送，哪一步会产生不能随意重复的动作。查询通常不改变业务记录；创建工单、发送消息、修改配置等属于副作用，重放之前必须核对结果。

还要区分三种编号：`request_id` 关联一次接口请求，`task_id` 标识业务任务，`trace_id` 串起一次被追踪的调用。一次任务重试会产生多次请求；一个长任务可能跨多段追踪。三者不必相等，把它们混成一个字段会让调查丢掉重试和恢复的关系。

## 第一条技术主线：模型调用不是普通的短接口

### Token、上下文、Prompt 和路由先讲成人话

Token 是模型处理文本等输入的计量单位，不等于一个汉字、单词或字节。Context 是这一次调用可以使用的上下文；它可能包含系统说明、用户消息、历史对话、检索材料、工具描述和工具结果。Prompt 是给模型的指令与材料，不只是用户输入框里的一句话。

为什么要管理它们？内容越多，可能增加等待、成本和窗口压力；删得过度，又可能丢掉关键约束。先确认模型的窗口与输出限制，再按实际请求构成分配预算：必要指令、保留历史、检索材料、工具结果与输出空间。估算和供应商实际用量要分开，不能用字符串长度假装精确 Token 统计。

排查上下文过长时，按同任务的输入构成找增长来源：历史是否重复拼接，工具是否返回了整张表，检索是否取了过多片段，是否把错误堆栈全塞入 Prompt。修复可以是限制检索、结构化工具输出或有边界的摘要，不是静默删除用户重要要求。摘要也是一次生成，可能丢信息，须做回归。

模型路由决定把请求送给哪个模型或供应商。切换模型不是改一个名字就结束：参数、工具格式、流式事件、能力、窗口、延迟、费用和数据授权都可能不同。用固定回归题和故障样本验证；涉及敏感输入时，不能因为故障就擅自转发到未授权服务。

### 超时和重试为什么会把小故障放大

先分清连接超时、等待响应超时、流中无进展和整个任务截止时间。每次调用的超时不自动等于整个任务的上限：串行步骤和每层重试会把总时间拉长。用户已经取消时继续后台重试，还可能继续产生费用或副作用。

429 只是 HTTP 状态，先读错误类型、服务端等待提示和当前配额；临时速率限制可有界等待，余额、授权或硬额度问题需要负责人处理。退避是逐渐加长等待，抖动是让许多请求不要同一时刻再次冲击服务端。要同时限制总尝试次数、总耗时、并发、队列和每租户预算。供应商 SDK 若已重试，应用层不能再不加核算地包一层。[OpenAI 官方指南](https://developers.openai.com/api/docs/guides/rate-limits)给出了这类边界；实际供应商以自身错误说明为准。

熔断是在持续异常时暂缓调用，防止下游被重复打击；它不是凭空修好下游。恢复尝试必须受控，降级结果要告诉用户，不把简化答案伪装成正常答案。不能对已经开始输出、可能调用工具或写入结果的请求简单整体重试。

**30 秒回答**：“我先识别失败阶段和错误类别，再看请求、Token、并发与预算。临时错误按提示做有界退避，永久配置或额度错误停止重试。若已产生输出或副作用，先核对任务和工具结果，再决定是否恢复。”

**继续追问**：“扩容十个 Pod 能解决吗？”参考思路是：应用资源瓶颈可能改善，外部配额却不会因此增加；更多调用者反而可能扩大 429。用队列等待、外部限流、应用资源和成功率对照，决定改善的是哪一层。

## 第二条技术主线：流式响应与长任务要分开验收

### SSE 和 WebSocket 各解决什么

SSE 是 Server-Sent Events，服务端沿 HTTP 连接持续发送事件，适合单向进度或文本输出。WebSocket 建立双向持续通信通道，适合双方都要实时发消息的场景。它们都需要身份授权、超时、连接数量和错误处理，不是换个协议就保证稳定。

SSE 常见字段 `event` 表示事件类型，`data` 是内容，`id` 是事件标识，空行分隔事件。标准 EventSource 可以自动重连，但许多模型调用使用 POST 加流式读取，不是原生 EventSource；不要把浏览器自动行为泛化到所有客户端。具体格式见 [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。

你可以把流理解成一边做一边汇报进展，不过汇报通道不是任务账本。HTTP 200 说明开始了成功响应，不保证后续所有事件送完；收到几个片段也不代表最终结果已经保存。我们的业务协议可以约定 `completed` 事件作为验收条件，但它不是所有 SSE 服务必有的标准事件名。

首输出慢时，把时间拆成受理、排队、检索、模型开始和首片段抵达。TTFT 是 Time To First Token，即等待首个 Token 的时间；先声明从模型请求发出还是更早的用户请求受理开始计时，不能把不同起点的指标直接比较。客户端只看得到首个内容块时，就单独记录“首内容块时间”，一个块可能装多个 Token，不冒充精确 TTFT。业务首事件还可能只是心跳，既不是首内容块，也不是首 Token。持续输出慢，再看事件间隔、代理缓冲、后端生成速度和客户端读取速度。重连是否能补发，必须由服务端保留事件与去重策略支持，不能只凭 `id` 断言可恢复。

### “页面不动”有三种不同意思

第一种，连接还活着，但没有业务进展；心跳只能证明某段连接可用。第二种，任务还在执行，输出连接已经断了；是否继续后台运行是业务契约。第三种，任务已经失败或结束，客户端没收到最终状态。先查任务记录、最新进展时间、上游状态与事件序号，再讨论恢复。

不能把这里的业务设计套到所有协议。尤其 MCP 的断流与取消规则有版本差异：本页核对的 [2026-07-28 Streamable HTTP 规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)明确了关闭响应流的取消语义，且不支持用 `Last-Event-ID` 恢复；旧版本和普通业务 SSE 不应混为一谈。面试先问现场版本、客户端及契约，别背一个永久正确的“断流绝不取消”。

**三分钟回答骨架**：先区分传输和业务任务，再画浏览器、网关、接口、运行器与状态存储。说明受理、首片段、最终事件和结果落库分别由哪条证据证明。列出超时、缓冲、无进展和取消四类问题，给两个假设和一条反证，最后讲修复后如何验证完整结果、不重复工具动作以及不再泄漏连接。

## 第三条技术主线：Agent 能工作，也必须能安全停下来

### Agent、Runtime、Harness、Memory 的关系

Agent 是智能体：它根据目标和上下文选择下一步动作，例如查知识、调用工具、观察结果再继续。Multi-Agent 是多个智能体协作；节点增多也会增加等待、错误传播、权限和状态管理的复杂度，不保证天然更聪明或更稳定。

Runtime 是承载实际执行的运行环境与服务。Harness 常用来指围绕模型组织工具、状态、上下文、限制、反馈与执行循环的配套机制，不是一个所有产品都采用同一实现的标准组件。岗位里看到这个词，先问“用的是哪个框架、版本和执行模型”，再查对应配置与监控。

Memory 在这里是保存会话或跨任务信息的机制，不是单纯服务器内存。短期会话状态、长期业务记忆、工作流检查点和模型窗口内的文本有不同生命周期。必须确认作用域：用户、租户、会话、任务或全局。故障时看键或记录是否串租户、是否过期、恢复后是否丢状态、保留与删除是否符合要求，不能为了排障把真实聊天全文公开。

LangChain 帮助组合模型、工具和相关应用能力；LangGraph 提供面向状态与工作流的编排能力。知道名字不算服务运维经验。要能说清当前状态存在哪里、失败在哪个边界、谁批准副作用、什么条件结束、框架版本如何与已有状态兼容。

### 检查点不等于业务动作只执行一次

Checkpoint 是检查点，保存可恢复的运行状态。它的意义是减少从头再来的成本，而不是自动替外部系统证明所有动作的结果。任务恢复可能重放部分流程；LangGraph Functional API 会复用已持久化的 task 结果，但未完成的 task 仍可能重跑。外部写入要设计幂等或先查已有结果。[官方恢复与幂等说明](https://docs.langchain.com/oss/python/langgraph/functional-api)明确了这种边界。

想象工具已经创建工单，响应途中丢失，检查点尚未记下结果。如果只看“没有收到成功”，再创建一次，就可能有两个工单。幂等键把同一个逻辑动作稳定地标识出来，工具服务应在自己的数据边界内原子去重，并校验同一个键的请求内容是否一致。只在调用者内存放一个集合，不能保证跨进程、重启和并发时安全。

恢复顺序是：核对任务身份与版本，查检查点及工具回执，明确哪些步骤完成、失败或未知；有可验证回执则接续未完成步骤；不能确定副作用结果时进入人工核对或待恢复状态。安全暂停是正确处置，不等于“脚本必须硬把任务跑成成功”。

同理，任务取消要有持久状态、执行器配合和下游处理。撤掉网页连接不一定撤掉数据库里的任务，取消接口成功也未必能回撤已发生的外部动作；具体语义看业务和协议。明确在途动作、补偿、审批和审计，比笼统承诺 exactly-once（全链路恰好一次）更可靠。

### MCP、A2A、Function Calling 别混成“工具接口”

Function Calling 是模型产生结构化调用意图，由应用检查参数、权限和实际执行；模型说“调用成功”不是工具真的成功。MCP 是 Model Context Protocol，为应用接入工具和上下文提供协议机制；A2A 是 Agent2Agent，关注智能体之间协作的消息、任务和成果。一个工作流可能同时用它们，但职责不同。

排查 Function Calling：查工具名、参数格式、业务校验、执行权限、回执与错误返回。排查 MCP：查协议协商、传输、服务可达、工具声明及每次请求的鉴权授权，不能把发现到工具当成获得执行权限。排查 A2A：查关联上下文、任务编号、状态与交付成果；有响应不等于有完成成果。依据 [A2A 生命周期](https://a2a-protocol.org/latest/topics/life-of-a-task/)，终态任务的后续工作应形成新任务，不能把已完成任务任意改回运行态。

“Skill”也不能仅按名字判断安全，它可能包含工具配置、说明、依赖或执行代码。来源可信、最小权限、输入验证、超时与资源限制、写动作审批和审计都要检查。检索材料、工具返回和远端智能体的文本是数据，不能变成越权执行的授权。

## 第四条技术主线：RAG 与数据服务怎样一起坏

RAG 是 Retrieval-Augmented Generation，先检索相关材料，再把材料交给模型生成答案。向量是文本等内容的数值表示，用来做相似性检索；相似不等于事实正确，也不保证具备读取权限。不要把任何一个“相关分数”当成所有模型通用的准确率。

知识库更新至少经过读取、解析、分块、生成向量、写索引、权限元数据、版本切换和回归。原文文件只是源头。上传成功可能只证明受理，后面还会遇到解析失败、任务积压、索引错误、权限丢失或旧缓存。

建立十个固定问题：常见问题、刚更新内容、容易混淆的问题、应拒答的问题、不同权限的问题。每题记录期望来源、实际命中片段、引用、版本和是否允许读取。先判检索有没有找到正确材料；找到却答错，再看 Prompt、上下文、工具结果和模型。回归不是主观比较两个“看起来都挺像”的答案。

更新需要可辨识的版本。尽量在隔离索引或待生效版本中构建，核对权限及回归后受控切换，保留回退路径。不完整的旧新索引混用、嵌入模型和向量维度不匹配，会让答案难以解释。知识库回退、任务检查点和数据库回退是不同动作，不能用一个“回滚镜像”替代全部状态恢复。

MySQL / PostgreSQL 可以承担业务记录或任务状态；Redis 常用于缓存、配额计数或队列等，真实用法需查现场设计。缓存不是可靠状态存储的默认替身，Redis 用作关键状态时还要核对持久化、复制、故障切换及数据损失边界。数据库副本与缓存副本也不是历史备份。

慢请求时，要查连接池等待、慢查询、锁、事务长度、索引与存储延迟，不能把所有时间归到模型。连接池越大也可能越挤压数据库。恢复验证要覆盖任务编号、租户权限、检查点、工具回执和索引版本的关系：某张表能查询，不代表跨系统状态一致。

**面试追问**：“更新后只有一个租户答错怎么办？”先确认受影响租户、问题样本与时间，再比对权限过滤、源文档版本、索引、检索参数与缓存。让同权限和不同权限的样本做对照，不能直接关闭权限过滤来证明“检索好了”。

## 第五条技术主线：K8s 正常，为什么 AI 平台仍失败

Pod 是承载容器的基本工作单元；Deployment 管理声明的副本与更新；Service 提供稳定访问入口；Ingress 配置外部 HTTP 路由；ConfigMap 保存非敏感配置；Secret 承载敏感配置对象，编码不是加密承诺。理解对象后，再查谁给任务服务提供网络、配置、权限和资源。

Pod 的 Running 阶段表示已绑定节点、容器已创建，至少一个容器正在运行或启动/重启，不代表全部容器健康，更不证明工具鉴权、模型配额、检索准确或任务完成。阶段与容器细节可核对 [Pod 生命周期](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)。Readiness 是是否接流量的探针；Liveness 是是否应重启的存活判断。依赖外部模型一次失败就触发重启，可能放大故障、丢掉在途任务，并不能恢复外部配额。

资源 `requests` 参与调度和资源分配，`limits` 约束使用。CPU 限制可能造成节流，内存压力可能产生 OOM，即内存不足处理。先看容器资源与任务并发，不只看节点总 CPU。具体机制见 [Kubernetes 官方资源说明](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)。

一套日常只读顺序是：确认当前集群与命名空间，核对目标资源，查看事件和容器前次退出原因，关联日志与同窗口指标，再比对配置/镜像/权限版本。初学者先读 [Kubernetes 的排障章节](../tech-stack/cloud-native/kubernetes.md)，不要求今天重新建一套集群。

下面是隔离练习集群的观察示例，名称均需替换成自己的已核对对象；没有 `kubectl` 和授权练习集群时，不执行，改用纸面记录分析。禁止直接把示例粘进生产终端：

```bash
kubectl config current-context # 核对正在连接哪套集群，不能只靠终端颜色判断
kubectl -n ai-lab get pods,deployments,services # ai-lab 是事先确认的练习命名空间
kubectl -n ai-lab describe pod task-worker-0 # 示例 Pod，关注 Events 与容器状态
kubectl -n ai-lab logs task-worker-0 --previous --tail=100 # 有重启时看前一容器日志
```

`--previous` 没有前次容器时会报错，这不证明日志服务坏了；多容器 Pod 还需明确容器名。查日志要受权限与脱敏约束，不导出 Secret 或用户 Prompt 全文。日志、事件有保留期，观察记录应说明查询时间和缺失范围。

扩容前判断工作负载：无状态接口可按瓶颈放大，有状态任务执行器要确认租约、并发去重、检查点与优雅停止。缩容时停止接新任务、处理在途任务和恢复接管，不能只看副本数字降了。RBAC 是基于角色的访问控制，应把查看权限与写操作权限分开，批量动作有范围、审批、回退和业务验收。

## 第六条技术主线：观测口径比漂亮图表更重要

指标是聚合数字，日志记录事件，追踪描述调用路径。三者围绕同一任务与时间窗口结合，才能解释“变慢发生在哪段”。你应能画出排队、检索、模型、工具和状态写入的分段耗时，而不是只有一个接口平均时间。

| 必备观测 | 先定义口径 | 异常时先联看什么 |
|---|---|---|
| 任务受理、终态及成功率 | 明确任务类型、统计窗口、重复请求、等待任务与取消的处理 | 任务状态、错误分类、在途数量和缺失记录 |
| 排队、首输出、完成耗时 | 从哪个时间点算，首事件还是首 Token，分位数如何统计 | 并发、队列、检索/模型耗时和输出速度 |
| 模型错误、尝试与消耗 | 按供应商/模型/错误类别区分，逻辑任务与每次调用分开 | 配额、预算、重试层数、路由和授权 |
| 工具错误及未知结果 | 区分未执行、已执行、响应丢失、回执待核对 | 幂等键、工具结果、审计与检查点 |
| RAG 与状态服务 | 检索命中、引用、版本、权限、数据库/缓存状态 | 更新批次、慢查询、锁、连接与存储 |
| 容器与节点资源 | 区分节点、容器、限制和实际使用 | 节流、OOM、重启、探针与在途任务 |

长任务用“本窗口完成数 / 本窗口受理数”会因跨窗口产生误导，甚至大于 100%。可以按受理批次追踪最终结果，或把窗口终态比例、在途年龄、逾期数量分开展示；口径一致后再设目标。重试成功也要计入成本和原始失败，别只留下最终绿色。

OpenTelemetry 的 [GenAI 语义约定](https://github.com/open-telemetry/semantic-conventions-genai/tree/main/docs/gen-ai)仍在演进，字段和指标名应与现场 SDK、采集器及约定版本对齐。上表是业务观测设计，不是宣称每个工具都自动提供的固定指标清单。

任务编号适合日志和追踪关联，不宜直接作为 Prometheus 标签无限增长。高基数会产生大量时间序列。模型、租户分组也要控制范围；可公开的学习材料只用合成编号，不放真实租户、凭证、个人对话或业务文档。追踪采样和日志丢失会造成证据空缺，找不到记录不等于事件没发生。

AI 运维指标可以进入 AIOps 链：指标发现任务失败率变化，日志与追踪提供错误分类，规则或模型辅助归并事件，人工核对证据，受控 Runbook 执行修复。模型只给假设时，不能直接赋予集群管理员权限让它自行试错。

### 基础实验：一个完整结果怎样才算成功

第一步，先在纸上写预测：正常流包含输出与终态，任务只有验证终态才算完成，逻辑动作和调用次数不是同一个数量。第二步运行脚本，找到正常基线，逐项解释实际返回的状态、事件和结果。第三步运行测试，检查退出码与断言，而不是只截最后一行。

默认输出是 JSON（带名称和值的结构化文本）。精确验收：`evidence_scope=offline_event_sequence_simulation` 标识离线模拟；`normal.rate.outcome`、`normal.stream.outcome` 和 `normal.agent.recovery.outcome` 均为 `completed`。`classroom_checks_passed=true` 表示课堂判据通过，不是模型或平台健康证明。

把运行环境、命令、实际输出、预期和差异分别保存。正常实验通过，只证明这套合成输入下的判定逻辑符合断言，不证明模型质量、网络可靠性或生产吞吐量。

### 故障实验：限流、断流、响应丢失分别怎么处理

同一次运行还会给出三类可回收的故障分支。先预测，再对照：限流应在预算内停止或恢复，不能无限循环；已收到部分流但没有完成事件，应判未完成而不是成功；工具已经执行但回执丢失，恢复必须核对已有结果，不能再产生一个业务动作。

默认故障组要核对三个位置：`faults.rate_limit` 的 `statuses=[429,429,200]`、`attempts=3`、等待列表 `[1,2]`；`faults.stream_interrupted.failure` 的 `http_status=200`，但 `completion_marker_seen=false`、`outcome=incomplete`；`faults.long_task_interrupted` 的 `writes_before_recovery=1`、`side_effect_writes=1`、`recovery.decision=reuse_receipt`，说明恢复前后业务副作用数量均为 1，不是再写一次。

再从仓库根目录复制两条变参命令，先写预测再执行：

```powershell
python -B examples/ai-platform-operations-lab/lab.py --rate-failures 8 --max-attempts 3
if ($LASTEXITCODE -ne 0) { throw '课堂检查失败，先保存输出' }
python -B examples/ai-platform-operations-lab/lab.py --agent-failure unknown-state
if ($LASTEXITCODE -ne 0) { throw '未知状态保护检查失败' }
```

第一条模拟连续限流，包含首请求最多尝试 3 次；预期 `faults.rate_limit.outcome=stopped_attempt_budget`、`attempts=3`。第二条让工具状态无法核对；预期 `faults.long_task_interrupted.recovery.outcome=paused_unknown`，副作用数量仍为 1。它们可以在课堂检查通过时退出码为 0，因为我们验证的正是安全停止，**不是宣称这两个业务任务成功**。Linux/macOS 用相同参数替换为 `python3` 命令，具体失败停止写法见实验 README。

拿正常组当基线，记录故障现象、至少两个可能解释、哪条证据支持当前判断、修复/恢复的条件和复测结果。尤其把“结果未知，暂停核对”单独写出来，不能为了统计成功率强行归成失败重试或成功。

更多参数变化和停止反例以实验 README 为准。`--budget-seconds` 只限制累计虚拟等待，不是把排队、网络、推理都算入的真实端到端截止时间。默认数据全部在一次进程内，退出即收回，无生产资源要删除；使用 `-B` 也不会产生缓存。自己保存的学习证据保留即可。没有真实网络、持久数据库与并发执行器，所以它没有验证重启后恢复、跨节点幂等、SSE 网络行为、真实协议兼容或性能。

先检查版本与当前目录，再检查仓库是否完整解压、脚本文件是否存在、参数是否符合 README。测试失败保留具体断言和输出，不先修改预期“让它通过”。如果结果与概念理解冲突，回到本页重试、终态和检查点章节解释差异；真实服务的表现还需要自己的授权环境再验证。

## 六道故障题：先口述证据，再考虑动作

这些是练习场景，不是招聘方实际事故。每题先说影响范围与最近变更，至少列两个假设；再说什么证据能排除其中一个，最后给止损、恢复验收与回退。不要把题干中的现象直接写成根因。

### 1. 模型 429 增多，应用 CPU 很低

假设一是外部请求或 Token 配额，假设二是某批任务形成重试风暴，假设三是额度或配置问题。查同窗口的错误类别、服务端提示、每任务尝试数、模型/租户分布和队列，而不只看 CPU。若单次长 Prompt 激增，单看请求数不足以反证 Token 限制。

先限制新增高消耗并发、抑制重复重试并告知用户排队/降级；涉及额度交负责人确认。修复后同时看最终成功、等待、尝试数和成本。不要擅自无限加钱、切未授权供应商或把全部任务直接重放。

### 2. 200 返回了，但用户只看到半句话

假设上游生成中断、代理缓冲/超时、客户端读取停止。查任务终态、流最后事件、最后有效进展时间，以及各跳日志和配置。若后台任务已经完整保存，但客户端缺最终事件，不能先说模型生成失败；若根本没有终态，也不能仅凭 200 说浏览器坏了。

止损是明确提示未完成、保存当前任务并避免整体自动重试。有恢复协议则依约接续，没有则先核对副作用再创建新的受控尝试。恢复验收包含完整结果、终态和连接释放，不只看第一段文字出现。

### 3. Worker 重启后出现重复工单

假设工具回执未入检查点、两个执行器同时接管、幂等键不稳定或下游去重不原子。核对任务状态、执行器租约、工具审计、幂等键与请求内容。时间相近的两个请求不是“模型想了两次”的充分证据。

暂停该类写工具任务，保留回执与重复对象，按业务流程确认需补偿的动作。修复后注入“写成功但响应丢失”以及并发接管情形，验证不会多产生业务效果。恢复流程版本不兼容时，不能把旧检查点直接丢掉重跑。

### 4. 知识库更新后新答案不对，旧答案仍正常

假设导入未完成、检索路由仍指旧版本、缓存、分块或权限元数据异常。先用固定问题查源版本与实际检索片段，再判断模型生成。若正确文档根本未命中，修改 Prompt 不一定解决问题。

停止继续切换或回到已验收版本，保留新旧索引与回归结果；不能混入未经验证的片段后宣布恢复。复测含新内容、旧内容、无答案和越权问题，验收不仅是“答案听起来更顺”。

### 5. 扩 Pod 后成功率更低、数据库连接更多

假设外部配额没增加、连接池总量增长、工作任务重复接管或共享缓存瓶颈。观察每副本并发、总连接、队列与外部错误；把扩容时间纳入时间线。若容器节流下降但外部 429 上升，表明改善一层却压坏另一层。

受控回退副本/并发之前先照顾在途任务，核对总连接预算与实例配额；恢复后看全链路成功和数据状态，不单看副本 Ready。缩容是写动作，必须走现有授权和变更流程。

### 6. MCP 工具能发现，却调用失败；A2A 任务长期等待

两件事分别诊断。MCP 查实际协议、传输、每次请求身份和工具权限、参数及错误体；发现工具不代表可执行。A2A 查任务是否在等待补充输入或授权、执行器是否有进展以及成果是否生成；等待状态可能是合法交互，不全是卡死。

禁止以关闭鉴权、扩大管理员权限或绕过人工确认来“恢复”。先修复缺失配置或交互，把未知结果留给授权负责人。验收同时含合法调用通过与越权调用被拒，不能只有正例。

## 生产设计题：接手一套已有 AI 平台，你怎么稳住它

### 练习条件，不是公司的真实规模

假设平台已有 200 个活跃连接、每秒受理 8 个任务，任务平均处理 30 秒，有查询工具和少量受审批写工具；模型由外部供应商提供。要求工作时间内交互首输出可观察，长任务可查询与受控恢复，不能发生越权或重复业务写入。具体服务目标需要和业务确认，不能拍脑袋写“全部请求 100% 成功”。

先问任务类型与比例、峰值和突发、外部配额、同一租户上限、任务数据量、最长执行时间、状态保留、现有恢复机制、允许丢失多少状态以及现有值班分工。Little 定律的简化估算是稳态平均在途量约等于到达率乘平均在系统内时间；这里按 8 × 30 算约 240 个，不是精确的 Worker 数，也不是峰值上限。排队、重试和长尾要另做测量。

### 把已有资源与状态归属画清

浏览器到网关提供受控入口；接口服务验证身份、校验请求并生成可追溯任务；执行器按租户并发和全局预算拉取任务；模型路由核对授权与能力；知识库按权限及版本检索；工具服务管理自己的幂等记录和写权限；状态后端持久保存任务与检查点；观测系统记录结果、错误、成本和恢复。

先盘点而非立刻重建。接口多副本只解决一类单点，任务状态、队列、检索、数据库、工具和外部模型仍有各自故障域。数据库可用性和历史恢复分开设计；回执、检查点和知识库版本须有可核对关系。执行器租约、重复领取、防止旧持有者继续写入的机制要结合现场实现确认。

### 至少讲清三个取舍

**同步等待还是异步任务**：短查询保持直接响应较简单；长任务用任务编号与持久状态能降低对单连接寿命的依赖，但增加状态查询、取消、过期和恢复复杂度。流式进度可以叠加在异步任务上，并不是与异步互斥。

**扩容还是限并发**：应用资源不够可以考虑扩容；外部配额或数据服务是瓶颈时优先控制入口和租户预算。增加吞吐不能靠无限排队，队列也有容量、过期与公平性；到限时明确拒绝或延期，不制造不可观测的等待。

**自动恢复还是人工核对**：纯读取、结果可核对且无副作用的步骤可有界重试；写动作、未知回执和授权变更需要幂等、核对或审批。自动化节省人工，但不能以重复工单、越权或泄露为代价。

**记录完整输入还是脱敏观测**：输入有助于复现，也可能包含个人或业务秘密。默认保存合成样本、版本、错误类别、长度与关联标识，真实内容按权限与保留策略访问。学习项目不能复制公司文档或聊天记录。

### 存量变更怎么升级与回退

建立模型配置、Prompt、知识库、工具声明、框架、镜像和检查点结构的版本清单。先在隔离环境或授权小范围验证，再通过现有团队执行受控变更；本岗位不承担新服务上线，并不意味着可以跳过变更流程。

升级任务执行器时，要验证旧检查点可读、旧在途任务如何完成或迁移、工具格式是否兼容、模型切换后的输出是否满足需求。回退不仅是旧镜像，还可能需要配置、索引和状态的兼容方案。不能靠数据库倒回一个时间点就默认为所有外部动作也被回撤。

交付设计图之外，再交观察窗口、停止条件、审批人、回滚/补偿步骤和恢复验收。验收包含成功任务、失败任务、取消、权限拒绝、未知结果处理和备份恢复；没有真实平台时说明这是纸面设计，待哪些实验支撑。

### 30 秒版本

“您好，我有［真实年限］年［真实运维方向］经验，主要承担［实际负责的系统和职责］。我擅长按链路取证、控制变更风险和验证恢复。最近针对这个岗位补强模型调用、流式服务和智能体长任务，完成了［明确是个人实验或生产项目］。我希望把已有稳定性经验用于 AI 平台的持续运行保障。”

### 90 秒版本

前 30 秒讲经历和主线；接着 30 秒讲一个真实故障：影响、证据、你做的动作、实际验证结果；最后 30 秒讲 AI 差距和补强。若没有 AI 生产经验，就说“没有独立维护过生产 AI 平台，以下是个人实验和我的验证计划”，不要把路线里的场景改成工作经历。

### 三张卡应该分别证明什么

| 故事卡 | 只填写自己的真实事实 | 面试官可能继续问 |
|---|---|---|
| 稳定性与事故 | 时间线、业务影响、两种假设、证据、止损、验收与复盘 | 为什么排除网络？为什么不是直接重启？ |
| 变更、配置或恢复 | 版本/对象、权限、审批、备份、兼容、回退和业务验证 | 镜像回退能否恢复数据？谁负责最终验收？ |

STAR 是 Situation、Task、Action、Result，即背景、任务、动作、结果，用来组织表达，不是把未知事实补齐的模板。结果没有测量就不写节省百分比；未查清根因就说已恢复但根因待验证，并说明后续证据。

## 面试递进：从定义走到反例

每组先合上答案讲 30 秒，再扩成三分钟。准备时录音，检查是否只是报产品名称。

### 组一：为什么传统运维经验还不够

参考回答：主机、网络、数据库和容器基础仍适用，但 AI 应用多了模型预算、生成的不确定性、长任务状态、工具副作用和流式交付。资源健康不能代替任务成功与授权正确。需要增加任务级观测、上下文治理和安全恢复。

追问“模型输出错是运维问题吗”：先分类，可能是数据、检索、Prompt、模型能力，也可能是版本或链路问题。运维负责可观测、版本与复现协同，不应宣称单独解决所有算法质量问题。

### 组二：怎么判断长任务真的卡住

参考回答：定义合法等待和最长无进展时间，再查任务状态、执行器归属、最近心跳、最近业务进展、下游状态及检查点。心跳只说明活性，工具结果未知与等待用户输入要独立处理。先确认可恢复边界，再取消或接管。

追问“重启 Worker 就行吗”：重启可能丢掉内存状态、引起重放、重复副作用；只有确认持久状态、租约及幂等、在途动作和回退条件后才能决策。

### 组三：怎样控制成本而不牺牲任务正确性

参考回答：按租户与模型记录预算、尝试数和实际消耗，查历史拼接、检索片段和工具输出，先减少无效重复。模型切换、摘要与缓存分别做回归，缓存键包含权限和版本等必要语义，不把他人结果复用给当前用户。

追问“压缩所有历史为什么危险”：可能丢失约束、审批或关键事实；摘要本身会引入错误，应保留必要结构化状态与来源，并用固定测试确认。

### 组四：怎样让 AI 故障告警有用

参考回答：围绕用户和任务定义完成率、首输出、在途年龄、错误分类与预算；指标发现范围，日志和追踪解释阶段。没有真实任务标识或终态时，应先补数据，不把接口 200 比例叫 Agent 成功率。

追问“用模型自动修复可以吗”：先只读归并与假设建议，再用可验证规则、审批、最小权限、限定资源和回退控制执行。模型没有证据或权限时必须停止，不能通过试错扩大影响。

### 组五：这个岗位为何还问数据库和 K8s

参考回答：任务和知识服务依赖持久状态、连接、锁、缓存、网络与资源。模型请求变慢可能在连接池或队列，执行器重启也涉及检查点。按链路比较分段证据，比“AI 问题全找模型”可靠。

追问“多副本等于高可用吗”：不等于。共享状态、工具、检索、外部供应商和同故障域仍可能单点；还要看数据损失、接管、幂等、权限与恢复演练。

### 五项必做任务与判据

**任务一：接口与任务分离。** 给出“HTTP 200、三个输出片段、没有终态、后台状态未知”，让你说明成功判据和下一步。合格答案不判成功、不立刻整体重试，先核对任务与副作用；缺终态还可能是传输或观测缺口，不能直接断言模型失败。答错回第二条主线。

**任务二：共享配额。** 两个租户共用模型配额，一方出现流量突发。画全局、租户与每任务预算，说明排队、公平性和停止条件。合格答案区分请求与 Token、外部配额与本地资源，预防重试同步放大；明确数字待测。答错回模型主线和设计题。

**任务三：写成功、回执丢失。** 给出同一逻辑动作的新旧执行器接管，要求两个假设、回执证据和恢复。合格答案使用稳定动作身份、参数核对及下游原子去重；无可验证结果时暂停核对，不能声称内存集合保证跨节点恰好一次。答错回 Agent 主线与离线故障实验。

**任务四：知识库权限。** 新版本对管理员正确，对普通用户错误。合格答案先核对权限与实际命中，不通过关掉过滤解决；回归包括正确回答、应拒答和旧新版本。答错回 RAG 主线，重新做十题回归集。

**任务五：十分钟接手演练。** 不看文章画出任务链，讲一个真实案例，再说明一次存量配置变更的审批、回退、在途任务和验收。合格答案职责范围准确、能接受两次“为什么”、不虚构乐搭内部实现或自己的生产经验。答不出回岗位对照、故事卡和生产设计。

### 附加编码题：你自己写一个只读统计器

不要只运行别人写好的程序。用 Python 标准库写一个 `analyze.py`，从标准输入读取本实验输出的 JSON，校验 `evidence_scope` 和必需字段，只统计以下三个课堂结果：`faults.rate_limit.outcome`、`faults.stream_interrupted.failure.outcome`、`faults.long_task_interrupted.recovery.outcome`。不要把 `normal` 和流恢复分支再计一次，更不能把这个课堂口径叫生产任务成功率。

默认输入应统计出两项 `completed`、一项 `incomplete`；`unknown-state` 输入应变成一项 `completed`、一项 `incomplete`、一项 `paused_unknown`。每类输出数量与只读处理建议，例如断流去核对终态，未知写结果转人工核对，不生成修改集群或重放工具的命令。

自行约定并实现明确的退出码：输入合法且无未完成/暂停项为 0，需要关注为 1，输入格式非法为 2。用损坏 JSON、缺字段和这两组正常输入测试；坏数据必须报错，不默认补成成功。字段未知时保存异常类型并停止统计。脚本只读，不需要公司数据或模型账号。

合格证据是你写的代码、至少四个测试和实际输出；能解释为什么“脚本运行完”不等于“平台健康”，以及如何迁移到有明确分母和时间窗口的生产统计。答不出来，回 [Python](../tech-stack/foundation/python.md) 的文件/JSON/异常处理与本页观测口径。这个题目检验要求 10 的脚本、统计与告警能力，不强制采用某个自动化平台。

### 模拟面试如何复评，而不是给自己打一个好看总分

按岗位相关性、机制、证据、恢复与安全、表达各记“缺失 / 部分做到 / 独立做到”，为每个不足写下一次实验或重练题。缺前置、猜根因、无副作用核对、泄露凭证、越权操作、把模拟当生产，都属于必须返工的红线；其他项再好也不能抵消。
