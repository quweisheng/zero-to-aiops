# AIOps 学习路线

这条路线按“转岗作品集”设计，不按教材目录设计。每一阶段都要产出可以放到 GitHub 的证据。

## 从完全零基础开始：先跟老师走完一圈

如果你还不认识命令行、文件路径和端口，先别用下面的周数衡量自己。周数是一份可调整的课程安排，验收通过再向后走。我们先做一件小事：在自己的电脑上打开一份网页，解释页面为什么能出现，再保存一次观察记录。文件是保存内容的对象，目录是组织文件的位置，程序是执行指令的进程，端口是帮助操作系统把网络请求交给某个程序的编号。把这四个对象认清，后面大量术语就有落点了。

第一站读 [Markdown](../tech-stack/foundation/markdown.md)，学会保存学习笔记。第二站读 [Shell 与 PowerShell](../tech-stack/foundation/shell-powershell.md)，只练进入目录、查看文件和读取报错；Windows 终端和 Linux 终端的命令不要混用。第三站读 [网络](../tech-stack/foundation/networking.md)，用一次浏览器请求理解域名、地址、端口和响应。第四站读 [Git](../tech-stack/foundation/git.md)，把一份笔记保存为可追踪的版本。

你现在可以回答：“我改了哪个文件，在哪个目录运行，哪个程序负责处理，结果保存在哪里？”这句话比背十个产品名更有用。若文件找不到，先检查当前目录；若程序找不到，检查安装与命令搜索路径；若访问失败，先确认服务是否运行，再检查端口和响应。这是后续排障的共同起点。

```text
Notebook（学习笔记：记录自己的观察）
  -> Local experiment（本地实验：让一个操作有结果）
  -> Evidence（证据：输入、输出和运行环境）
  -> Explanation（解释：为什么出现这个结果）
  -> Independent practice（独立练习：换条件后再做一遍）
```

箭头表示学习顺序。今天的验收是自己写一页笔记，包含目标、环境、操作、实际输出、失败记录和下一步。没有故障经验的同学从隔离实验开始，明确写“个人实验”；有生产经验的同学只写自己真实参与、可脱敏说明的部分。

## 每门技术怎样读三遍

第一遍跟着做。只读“老师带学、核心概念、基础实验”，记录不理解的名词。碰到英文图时，把中文注释遮住，尝试用自己的话解释英文对象；解释不出就回正文，不急着记缩写。

第二遍带着问题重做。修改一个条件，例如把服务端口写错，先预测报错，再查证据。能预测“在哪里出错、如何验证”说明理解开始从模仿变为推理。别同时修改三个参数，否则难以确认哪一个导致变化。

第三遍做架构和面试练习。给实验增加容量、安全、备份和升级约束，回答“数据由谁保存”“一个节点挂了怎么办”“怎样知道恢复了”。用三分钟讲清数据路径，再让同学追问一个反例。每次追问暴露的缺口都回到下一周计划。

## 老师带你把技术串成一项作品

选一个“网页访问变慢”的问题。先做最小网页和接口，记录每次请求的时间与结果；用指标看错误比例，用日志找一次失败的细节，用链路看延迟分配。接着定义什么时候需要通知值班者，写出检查和回滚步骤，最后尝试用简单规则总结异常。机器学习放在有基线、有标签和可比较结果之后。

这里 Metrics 是“随时间变化的数值指标”，Logs 是“发生过哪些事件的日志”，Traces 是“同一次请求跨组件的追踪记录”。Collector 是“收集并转发遥测数据的程序”，Runbook 是“条件、检查、动作、验证和回滚写清楚的操作手册”。CI/CD 是“持续集成与持续交付或部署”，把改动先检查，再按流程交付。后面阶段中的这些英文都指向具体工作，不是另一套考试名词。

一个阶段没有完成时，先诊断是知识、工具还是时间问题。知识问题回到最小概念；工具问题记录安装和错误；时间问题缩小当天实验目标。不要靠增加每天阅读页数补偿没有理解，也不用等全部 114 门技术读完才做第一个项目。

## 0. 起点盘点

先写清楚自己的已有能力：

- Linux：排障、性能、网络、系统服务。
- 脚本：Shell、Python、自动化任务。
- 监控：是否用过 Zabbix、Prometheus、Grafana、ELK、SkyWalking、APM。
- 云原生：Docker、Kubernetes、CI/CD、发布。
- 故障经验：至少 3 个真实故障故事。

## 1. 第 1-2 周：SRE 思维

目标：把“会运维”转成“会定义可靠性目标并减少重复劳动”。

- 学 SLI、SLO、错误预算。
- 学 toil，找出自己工作里最值得自动化的 3 类重复劳动。
- 学事件复盘，写无责复盘模板。
- 产出：3 篇故障案例卡，1 篇 toil 清单。

验收标准：

- 能解释一个服务的核心 SLI。
- 能说清楚一个告警为什么有业务意义。
- 能把一个手工处理动作拆成输入、判断、动作、回滚。

## 2. 第 3-5 周：可观测性基础

目标：让指标、日志、链路和告警形成闭环。

- Prometheus：采集、PromQL、Alertmanager。
- Grafana：仪表盘、变量、告警视图。
- OpenTelemetry：Collector、trace、metric、log 的关系。
- 日志：结构化日志、日志模板、错误聚合。
- 产出：可观测性实验室。

验收标准：

- 一个 demo 服务有 metrics、logs、traces。
- 一个仪表盘能看出延迟、错误率、吞吐量和资源使用。
- 一个告警能触发，并且能写出处理 runbook。

## 3. 第 6-8 周：Python 数据分析与异常检测

目标：能用运维数据做第一个可解释模型。

- Python：pandas、numpy、matplotlib。
- 特征：滑动窗口、均值、方差、P95、错误率、日志模板计数。
- 基线：固定阈值、动态阈值、同比/环比。
- 模型：IsolationForest 或简单时序异常检测。
- 产出：指标异常检测器。

验收标准：

- 能读取样例指标数据并输出异常时间段。
- 能解释误报和漏报。
- 能把检测结果转成告警建议，而不是只画图。

## 4. 第 9-12 周：AIOps 项目化

目标：完成能写进简历的项目。

- 告警降噪：相同服务、相同依赖、相同时间窗口聚合。
- 根因线索：变更记录、拓扑依赖、错误日志、资源指标关联。
- Runbook：推荐动作、人工确认、执行记录、回滚。
- 产出：告警降噪器或 Runbook 助手。

验收标准：

- 项目 README 能让别人 10 分钟内跑起来。
- 有架构图、输入输出样例、效果对比和局限性。
- 面试时能讲清“为什么这样设计，风险怎么控制”。

## 5. 第 13-24 周：求职强化

目标：把学习成果转成岗位匹配度。

- 每周投递 5-10 个岗位，并记录关键词。
- 每周做 2 次面试题复盘。
- 每两周改一次简历项目表达。
- 补齐 Kubernetes、CI/CD、云平台、数据库、中间件等岗位共性要求。

验收标准：

- 简历有 2 个 AIOps 相关项目。
- 能讲 8 个运维工程故事。
- GitHub 最近 3 个月有持续提交记录。
