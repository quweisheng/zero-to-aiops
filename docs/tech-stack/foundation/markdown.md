## 场景开场

“这次故障我明明处理过，但让我复盘时，只剩下一堆聊天记录和几张截图。”

运维经验如果不写下来，很容易散掉。更麻烦的是：你以为自己写了笔记，别人打开却发现：

- 标题层级乱。
- 命令和输出混在一起。
- 表格渲染坏了。
- 相对链接点不开。
- 代码块把后面的正文吞掉。
- README 只有口号，没有运行方式。
- runbook 没写风险和回滚。

Markdown 的价值不是“排版好看”，而是用普通文本把工程知识写成结构化、可版本管理、可审查、可发布的网站内容。

对 AIOps 知识库来说，Markdown 是基础设施。Prometheus 配置怎么写、Docker Compose 实验怎么跑、事故怎么复盘、面试故事怎么讲，都要先能用 Markdown 说清楚。

## 一句话人话版

Markdown 是工程知识库的纯文本写作格式：用简单符号表达标题、段落、列表、链接、图片、代码块、表格和任务列表，既适合人读，也适合 Git 管理和网站渲染。

## Markdown 是什么

Markdown 是轻量标记语言。它用纯文本符号表达文档结构，再由解析器转换成 HTML。

```text
Markdown text（文档源文本）
  -> parser（解析器）
  -> HTML（网页标记）
  -> GitHub / VitePress / browser（代码平台、文档框架或浏览器）
```

例子：

````markdown
# Prometheus

Prometheus 用于采集和查询指标。

- 指标采集
- PromQL
- 告警规则

```bash
prometheus --config.file=prometheus.yml
```
````

渲染后会变成：

- 一级标题。
- 段落。
- 列表。
- 代码块。

它的关键优势不是功能多，而是：

- 纯文本，适合 Git diff。
- 语法少，学习成本低。
- 平台支持广，GitHub 和 VitePress 都能渲染。
- 可以和代码、配置、命令放在同一个仓库。

## Markdown 和 Word 的区别

| 对比 | Markdown | Word |
|---|---|---|
| 文件形式 | 纯文本 | 二进制或复杂文档格式 |
| Git diff | 清楚看到每行变化 | 不适合逐行 review |
| 代码块 | 天然支持 | 容易格式乱 |
| 自动构建网站 | 很适合 | 通常需要转换 |
| 协作 review | 适合 PR | 不适合代码仓库流程 |
| 排版能力 | 简洁有限 | 排版能力强 |

Markdown 适合工程知识库，不是因为它比 Word “高级”，而是因为它更适合版本控制、自动化构建和技术内容维护。

## 解析模型

Markdown 解析大致分两类：

```text
block parsing（块级解析）
  -> headings（标题）
  -> paragraphs（段落）
  -> lists（列表）
  -> block quotes（引用块）
  -> code blocks（代码块）
  -> tables（表格）

inline parsing（行内解析）
  -> emphasis（强调）
  -> links（链接）
  -> images（图片）
  -> code spans（行内代码）
  -> escapes（转义）
```

也就是说，Markdown 先识别“这一块是什么”，再识别块里面的行内元素。

例子：

````markdown
## 排障步骤

执行 `docker compose ps` 查看服务状态。
````

块级结构：

- `## 排障步骤` 是 heading。
- 空行后是 paragraph。

行内结构：

- `` `docker compose ps` `` 是 inline code。

理解这个模型后，很多渲染问题就好查了：表格坏了通常是块级结构没写对，链接坏了通常是行内语法或路径问题，代码块吞正文通常是 fenced code block 没闭合。

## 空行和段落

Markdown 中，段落通常由空行分隔。

正确：

````markdown
第一段：描述故障现象。

第二段：描述排查结论。
````
不清晰：

````markdown
第一段：描述故障现象。
第二段：描述排查结论。
````
在很多渲染器里，这会被当成同一个段落，中间只是软换行。

AIOps 文档建议：

- 每段只讲一个意思。
- 段落之间留空行。
- 命令、输出、结论分开写。

## 标题

标题用于组织层级。

语法：

````markdown
# 一级标题
## 二级标题
### 三级标题
#### 四级标题
````
规则：

| 规则 | 原因 |
|---|---|
| 一个文档通常只有一个 `#` | 表示文档主题 |
| 不要跳级 | 从 `##` 直接到 `####` 会破坏结构 |
| 标题后加空格 | `## 标题` 比 `##标题` 更兼容 |
| 标题要具体 | `## 排障` 比 `## 其他` 更可读 |

坏例子：

````markdown
# Docker
### 镜像
## 容器
````

好例子：

````markdown
# Docker

## 核心概念

### 镜像

### 容器
````

VitePress 会根据标题生成页面锚点和右侧目录。标题层级乱，目录也会乱。

## 段落和换行

Markdown 中普通换行不一定表示新段落。

````markdown
第一行
第二行
````
很多渲染器会显示成同一个段落中的软换行。

如果要新段落，用空行：

````markdown
第一段。

第二段。
````
如果确实要硬换行，可以使用两个空格加换行，或 HTML `<br>`。但工程文档里建议少用硬换行，优先用列表或新段落组织。

## 强调和加粗

语法：

````markdown
这是 *强调*。
这是 **加粗**。
这是 ***加粗并强调***。
````
AIOps 文档中，加粗适合用于：

- 关键结论。
- 风险提示。
- 字段名第一次解释。

不要整段加粗。整段都强调，等于没有重点。

## 行内代码

行内代码用于命令、路径、字段名、文件名、配置键。

````markdown
执行 `docker compose ps` 查看服务状态。
配置文件是 `prometheus.yml`。
字段 `scrape_interval` 表示抓取间隔。
````

适合加行内代码的内容：

| 类型 | 示例 |
|---|---|
| 命令 | `git status` |
| 文件 | `README.md` |
| 路径 | `docs/tech-stack/` |
| 配置字段 | `scrape_interval` |
| 环境变量 | `PATH` |
| 指标名 | `http_requests_total` |

如果行内代码本身包含反引号，可以用更多反引号包住。

````markdown
``Use `code` inside.``
````

## 代码块

代码块用于命令、配置、代码、输出。

基础写法：

`````markdown
```bash
docker compose ps
```
`````

渲染出来是：

```bash
docker compose ps
```

代码块建议写语言：

| 内容 | 语言标记 |
|---|---|
| Shell 命令 | `bash` |
| PowerShell | `powershell` |
| YAML | `yaml` |
| JSON | `json` |
| Python | `python` |
| 普通文本输出 | `text` |
| Markdown 示例 | `markdown` |

为什么要标语言：

- 代码高亮更清晰。
- 读者知道这段是什么。
- 文档站构建器能选择合适高亮规则。

如果你在 Markdown 文档中讲“如何写代码块”，要用四个或更多反引号包住外层，避免内层三个反引号提前结束。

`````markdown
````markdown
```bash
git status
```
````
`````

## 命令和输出要分开

坏例子：

````markdown
执行 docker ps 看到 CONTAINER ID IMAGE STATUS...
````

好例子：

`````markdown
运行命令：

```bash
docker ps
```

预期输出包含：

```text
CONTAINER ID   IMAGE     STATUS
```
`````

为什么要分开：

- 读者知道哪些要复制执行。
- 输出不会被误当命令。
- 后续排障能对照预期。

## 列表

无序列表：

````markdown
- Prometheus
- Grafana
- Docker Compose
````

有序列表：

````markdown
1. 启动 Prometheus。
2. 打开 `/targets`。
3. 确认 target 是 UP。
````

建议：

- 步骤用有序列表。
- 并列概念用无序列表。
- 每一项尽量语法结构一致。

嵌套列表要缩进：

````markdown
1. 检查 Prometheus。
   - 打开 `/targets`。
   - 查看 Last Error。
2. 检查 Grafana。
   - 打开 data source。
   - 点击 Save & test。
````

嵌套太深会影响可读性。超过两层时，考虑拆成小标题。

## 引用

引用使用 `>`。

````markdown
> 注意：`docker compose down -v` 会删除命名卷，Grafana 数据可能丢失。
````

适合：

- 注意事项。
- 外部原话的短引用。
- 风险提示。

不要把普通正文都写成引用。引用应该是特殊信息。

## 链接

行内链接：

````markdown
[Prometheus 官方文档](https://prometheus.io/docs/)
````

相对链接：

````markdown
[Docker 深讲](../cloud-native/docker.md)
````

链接由两部分组成：

```text
[显示文本](目标地址)
```
建议：

| 做法 | 原因 |
|---|---|
| 链接文本写清楚 | 不要写一堆“点击这里” |
| 相对链接指向具体文件 | VitePress 构建更稳 |
| 文件名大小写一致 | Linux 和 GitHub Pages 区分大小写 |
| 定期构建检查 | 防止死链 |

坏例子：

````markdown
[点击这里](../docker.md)
````

好例子：

````markdown
[Docker 深讲](../cloud-native/docker.md)
````

## 图片

图片语法：

````markdown
![Prometheus targets 页面](./images/prometheus-targets.png)
````

结构：

```text
![替代文本](图片路径)
```
替代文本不是随便写，它应该描述图片内容。这样图片加载失败时，读者仍然知道它是什么。

建议：

- 图片放在当前专题附近的 `images/` 目录。
- 文件名用小写和连字符。
- 不提交敏感截图。
- 截图前遮掉 token、IP、客户信息。

## 表格

GFM 支持表格。

````markdown
| 技术 | 作用 | AIOps 场景 |
|---|---|---|
| Prometheus | 指标采集 | 异常检测输入 |
| Grafana | 可视化 | 值班 dashboard |
````

表格的必要结构与可选内容：

- 表头行。
- 分隔行。
- 数据行可以没有；但用于解释字段时应填入有意义的示例。

对齐写法：

````markdown
| 字段 | 含义 | 示例 |
|:---|:---:|---:|
| left | center | right |
````

排障：

| 现象 | 原因 |
|---|---|
| 表格不渲染 | 分隔行缺失 |
| 某列错位 | 某行少了 `|` |
| 竖线显示异常 | 单元格里有未转义的 `|` |

如果单元格里要写 `|`，可以用反斜杠转义：

````markdown
`a \| b`
````

## 任务列表

GFM 支持 task list。

````markdown
- [x] 创建 GitHub 仓库
- [x] 启动 VitePress
- [ ] 补齐 Prometheus 实验
- [ ] 发布 GitHub Pages
````

适合：

- Issue 验收标准。
- 学习计划。
- PR checklist。
- 事故行动项。

任务列表的价值不是“打勾好看”，而是让完成标准明确。

## 删除线

GFM 支持删除线：

````markdown
~~旧方案：手动登录服务器修改配置~~
新方案：通过 GitHub Actions 发布配置。
````

适合在复盘或方案演进中保留上下文。不要滥用删除线制造阅读负担。

## 自动链接

GitHub 会自动识别部分 URL。

````markdown
https://github.com/quweisheng/zero-to-aiops
````

但在正式文档中，更建议写成有意义的链接文本：

````markdown
[zero-to-aiops 仓库](https://github.com/quweisheng/zero-to-aiops)
````

因为裸链接不说明读者点进去会看到什么。

## 转义

如果你想显示 Markdown 符号本身，可以用反斜杠转义。

````markdown
\*这不是强调\*
\# 这不是标题
````

渲染后会显示星号和井号。

常见需要转义的字符：

```text
\ ` * _ { } [ ] ( ) # + - . ! |
```

表格里尤其要注意 `|`。

## HTML

Markdown 允许嵌入部分 HTML。

````markdown
<br>
<details>
<summary>展开排障细节</summary>

这里是详细内容。

</details>
````

但知识库里建议少用 HTML：

- 不同平台支持不一致。
- 可读性降低。
- VitePress 和 GitHub 渲染可能有差异。

只有在 Markdown 表达不了时，再少量使用。

## Frontmatter

很多静态站点生成器支持 Frontmatter。VitePress 使用 YAML Frontmatter 设置页面元数据。

例子：

````markdown
---
title: Prometheus 精讲
description: 从零学习 Prometheus 数据模型、PromQL 和告警规则
---

# Prometheus 精讲
````

Frontmatter 必须放在文件最开头。常见用途：

- 页面标题。
- 描述。
- layout。
- sidebar 控制。
- outline 控制。

普通 GitHub README 不需要 Frontmatter。VitePress 页面可以用。

## GitHub 写作特性

GitHub 还支持一些平台能力：

| 特性 | 示例 | 用途 |
|---|---|---|
| Issue 引用 | `#12` | 引用 issue 或 PR |
| 用户 mention | `@username` | 提醒用户 |
| commit SHA | `abc1234` | 引用提交 |
| task list | `- [ ] task` | 跟踪任务 |
| alerts | `> [!NOTE]` | 显示提示块 |

GitHub alerts 示例：

````markdown
> [!WARNING]
> 不要把 token 提交到仓库。
````

注意：GitHub alerts 在 GitHub 上效果好，但不是所有 Markdown 渲染器都支持。VitePress 支持自己的容器语法，具体在 VitePress 篇讲。

| 项 | 内容 |

## 好 Markdown 的判断标准

一篇好的工程 Markdown 文档，至少满足：

- 标题层级清楚。
- 每段只讲一个意思。
- 命令和输出分开。
- 代码块标语言。
- 表格字段解释完整。
- 链接文本具体。
- 图片有替代文本。
- 实验能复现。
- 排障写现象、原因、检查、处理。
- 最后有学习证据。

不好的文档常见问题：

- 只有概念，没有命令。
- 只有命令，没有解释。
- 只有截图，没有步骤。
- 只有结论，没有证据。
- 只有链接，没有自己的理解。

## 常见故障排查

### 标题没有出现在目录里

检查：

- 是否写成了代码块。
- 是否跳级太严重。
- VitePress 是否配置了 outline。
- 标题是否在 HTML 或特殊容器里。

|---|---|

`````

```

`````

### 链接在 GitHub 能点，VitePress 构建失败

可能原因：

- VitePress 检查 dead links 更严格。
- 内部页面或章节锚点不存在；外链连通性通常不是构建器内部死链检查的同一范围。
- 相对路径在站点路由中不成立。

处理：

- 示例本地地址写成代码：`localhost:9090`。
- 内部链接指向具体 `.md` 文件。
- 运行 `npm run docs:build` 验证。

检查：

- 文件是否提交。
- 路径是否正确。
- 大小写是否一致。
- 是否被 `.gitignore` 忽略。
- VitePress public 目录规则是否正确。

原因：GitHub 和 VitePress 渲染器不同。

处理：

- 尽量使用 CommonMark 和 GFM 基础能力。
- 少用平台专属扩展。
- 对 VitePress 页面使用 VitePress 支持的语法。
- 构建后检查页面。

## Markdown 与 VitePress 的关系

VitePress 会读取 Markdown 文件，转换成网站页面。

```text
docs/**/*.md（文档目录及其子目录的源文件）
  -> VitePress（文档构建框架）
  -> Vue + markdown-it（界面框架与文本解析器）
  -> static site（静态站点）
```

所以写知识库时要同时考虑：

- GitHub 上能读。
- VitePress 构建能过。
- 页面目录清晰。
- 内部链接稳定。
- 代码块高亮语言被支持。

有些 GitHub 支持的语法，VitePress 不一定同样支持。反过来，VitePress 的容器、Frontmatter、Vue 组件，GitHub README 也不一定支持。

## 小白可能会问

### 为什么不用 Word 记学习笔记？

Word 适合复杂排版和办公文档。Markdown 更适合工程知识库，因为它是纯文本，Git diff 清楚，能和代码、配置、CI、文档站放在同一个仓库里。

### README、runbook、故障复盘分别怎么写？

README 是导航，回答“这个项目是什么，怎么用”。Runbook 是操作手册，回答“出问题时怎么处理”。故障复盘是事后总结，回答“发生了什么，为什么发生，怎么避免再发生”。

### 代码块为什么要标语言？

标语言能让文档站高亮正确，也让读者知道这段是 bash、PowerShell、YAML、JSON 还是输出文本。命令用 `bash` 或 `powershell`，输出用 `text`。

### Markdown 写得好，对 AIOps 求职有什么帮助？

它能让你的经验变成作品集：文档结构清楚、实验可复现、排障有记录、配置有解释。面试官看到的是工程表达能力，不只是“我学过”。

### 为什么我的表格总坏？

通常是缺少分隔行、列数不一致、单元格里有未转义的 `|`。先写最小表格，再逐步加内容。

## 面试怎么讲

Markdown 是我沉淀工程知识的基础格式。它用纯文本表达标题、段落、列表、代码块、表格、链接和图片，适合 Git 版本控制和 Pull Request review，也能被 GitHub 和 VitePress 渲染成页面。在 AIOps 学习里，我会用 Markdown 写 README、技术深讲、runbook、事故复盘和实验记录，并且把命令、输出、配置字段、排障现象和学习证据写清楚。这样运维经验不会停留在聊天记录里，而是沉淀成可复用、可展示、可自动构建的知识库。

## 老师带你把“写出来”推进到“交付得可靠”

先跟我看一个真实工作方式：值班同学收到“支付接口错误率升高”的告警，打开你的 Markdown 手册，照着查日志，再把证据交给负责人。此时文档是否可靠，不取决于加粗漂不漂亮，而取决于他能否分清**这是待执行命令、这是示例输出、这是已经验证的事实、这是未经验证的猜测**。如果四者混在一起，一份语法完全正确的文档也可能误导操作。

因此，写操作段落时依次回答：在哪里执行？需要什么权限？查什么对象？预期看到什么？看不到时走哪条分支？会不会修改状态？如何退出或回退？例如 `kubectl delete` 不是“排查命令”，它会删除对象；即使把它放进漂亮的代码块，也不会自动变安全。初学者先学习区分只读检查与变更操作，这是 Markdown 承载运维知识时最重要的边界。

### 解析器为什么会把后面的标题吞进代码块

解析器（parser，把文本识别成结构的程序）通常先认出段落、列表、代码块等块级结构，再处理段落里的链接、强调等行内结构。你可以把它想成老师先划分作文段落，再看句子里的重点。AST（Abstract Syntax Tree，抽象语法树）是一些实现用于保存这种层次的结构，并非所有工具都会向用户暴露同一种 AST。

围栏代码块由连续反引号或波浪号划定。闭合围栏必须使用相同字符，数量至少达到开始围栏的数量。如果开始用了四个反引号、结束只有三个，结束标记并没有真正结束代码块；之后的标题可能按代码显示。定位时先找“页面从哪一行开始变样”，再向上找最近的围栏，不要先怀疑网站缓存。嵌套展示 Markdown 示例时，外层比内层多一个反引号，就是利用这条规则。[CommonMark 围栏代码块规则](https://spec.commonmark.org/0.31.2/#fenced-code-blocks)

Markdown 是输入语言，渲染器是解释这门语言的软件，主题是最后的外观。表格能不能识别属于语法或扩展，表格是否横向滚动属于样式；链接目标是否存在属于内容或构建校验。把这三层分开，才能判断该修改文章、解析设置还是页面 CSS（层叠样式表）。不要看见一个显示故障就同时改三层。

### 可回收故障实验：亲眼看见围栏失配

前提是已能在本地编辑 Markdown，并有编辑器预览；不用连接生产系统。使用一个新建的临时笔记 `markdown-fence-lab.md`，不要改正式 runbook。

1. 输入 `# 围栏实验`，空一行，输入三个反引号加 `text` 作为开始围栏。
2. 下一行输入 `这是代码中的文字`，再用三个反引号关闭。空一行，输入 `## 验证标题`。预览应显示一个代码块和一个真正的二级标题。
3. 把开始围栏改成四个反引号，关闭围栏仍保留三个。这就是本实验唯一的故障注入。预期“验证标题”变成代码文字；不同编辑器高亮略有差异，但它不应被认成独立标题。
4. 把结束围栏也改成四个反引号。确认标题恢复、代码复制按钮不再包含后续正文；这才算验证修复，而非只看源码觉得对了。
5. 清理：关闭预览，删除自己刚创建的临时笔记。如果要保留证据，将故障前后截图和原因写入实验记录，不把错误围栏留在正式文章。

如果现象不符，先检查编辑器是否正在预览当前文件，再确认反引号不是中文输入法产生的其他符号，最后确认开始围栏前没有使其进入另一种块结构的缩进。本实验验证的是解析规则，不声称网站构建工具一定会把这种语法问题当成错误；很多解析器会合法地把余下全文解释为代码，所以“构建成功”仍需补充页面阅读检查。

### 生产知识库：谁是源文件，谁是发布结果

仓库里的文章是维护入口，生成的 HTML（网页结构文件）是发布结果，搜索索引是派生数据。修改 HTML 而不修改源文件，下次构建可能丢失；修改文章却不重新生成索引，页面可能已更新但搜索仍指向旧内容。每次发布至少记录提交号、依赖锁文件、构建命令、产物和部署状态，才能回答“用户看到的是哪一版”。

本文讨论了 VitePress，但当前仓库实际使用 React、Vite 和 `marked` 解析 Markdown；`npm run docs:build` 是 `npm run build` 的别名。不要因为文章提到一种工具就给仓库安装第二套站点。开始操作前先看 `package.json` 中 `scripts`（可运行脚本）和真正的内容生成程序。对外部项目，同名命令可能执行完全不同的动作。

发布的状态链应当是“编辑完成 → 本地检查通过 → 提交 → 推送 → 远程构建 → 部署成功 → 页面与搜索验证”。中间任何一步成功，都不能替代后续步骤。静态站点的高可用依赖托管和内容分发服务，不靠给 Markdown 文件加副本；故障回退是重新部署已验证的旧产物或旧提交，同时检查索引与页面版本一致。不要把回退源文件等同于用户立刻看到了旧页面。

安全上，允许可信维护者写 HTML 与允许陌生用户提交 HTML 是两种威胁模型。Markdown 渲染不天然等于 HTML 安全净化；处理不可信内容时，需要独立的安全过滤、协议白名单和页面安全策略。链接中的凭据、截图中的内部地址、日志中的个人信息也不会因转成 Markdown 而消失。提交前先脱敏，泄露后不能只删除最新一行就当历史消失。

在 AIOps 的 RAG（检索增强生成，用检索到的资料辅助模型回答）知识库里，标题层次还能帮助分块；但要同时保存来源路径、章节、适用版本、更新时间和权限范围。否则模型可能把旧版重启步骤推荐给新集群。知识检索命中只是“找到了文本”，不能替代操作授权和人工审批。

### 面试递进回答：从格式到工程约束

**30 秒回答：**Markdown 是适合版本控制的轻量标记文本。我会把它用于 README、实验、故障手册和复盘，并明确语法方言与渲染环境。交付时检查源码、链接、构建、页面以及搜索索引，而不只检查有没有语法错误。

**3 分钟展开：**从作者提交到读者访问，依次经过解析、生成、部署和缓存。说明 CommonMark 与 GFM 的边界，演示围栏或相对链接的故障，再讲提交号如何关联线上产物，最后解释不可信 HTML、脱敏和回滚策略。答案应包括一个你能展示证据的案例，而不是虚构“我在生产处理过”。

追问“构建通过，为什么页面仍错误？”答题先区分允许但不符合预期的语法、主题渲染差异、部署未切换、缓存和索引未更新，用本地生成页面、远程提交号和线上正文逐项验证。追问“怎样治理一万篇 runbook？”应回答模板约束、明确负责人、适用版本、链接检查、过期提醒、权限与审查、生产验证记录，以及按告警或服务组织检索；文件数量不是知识可用性的指标。

## 文档工程课堂：把语法、内容与验证分开

### 为什么同一份源码在不同平台长得不一样

Markdown 不是一个保证全部扩展一致的单一浏览器语言。CommonMark 定义一组核心语法，GFM 在相应基础上增加常用能力，文档框架还可能加入提示块、组件、目录与元数据。老师希望你先记录目标渲染器及其版本，再选择扩展；GitHub 上渲染正常，不自动证明本地网站支持同一种写法。

AST 是一些解析实现使用的结构表示，便于把标题、段落、链接和代码分别处理。建立搜索索引时应知道自己取的是源文本、解析后的纯文本还是渲染 HTML；把围栏代码中的示例标题也当作正文标题，会产生重复导航或错误摘要。统计正文长度同样要排除代码与输出，避免一篇只有命令的大文件看起来像充分讲解。

### 文档中的代码示例也有输入与输出契约

一个可复现示例至少说明执行目录、解释器、所需依赖、输入文件、完整命令和退出方式。`$`、`PS>` 这类提示符可以帮助识别环境，但若被读者当成命令一起复制就会出错；更适合在正文说明环境，在代码块里放可执行部分。示例输出独立标为 text，并说明是预期还是实际观测，不把虚构输出包装成实测日志。

长代码不等于讲解充分。每个参数应解释它改变什么行为、何时适用、成功怎么看、失败先查什么。危险命令必须先说明目标范围、授权和恢复边界；只在最后加一句“谨慎操作”不足以帮助小白。对于不可逆动作，前置检查和停止条件比自动清理命令更重要。

### 链接需要区分源码位置、网站路由和片段标识

相对链接在源码平台上通常以文件所在位置为依据，网站构建器则可能将它转换成页面路由。部署前缀、是否保留扩展名、目录首页规则会影响最终地址。标题生成的片段 ID 还可能因标点、空格、大小写或重复标题发生变化；改一个标题有时会使别处的章节链接失效。

因此重构文档时要同时查入链，而不是只移动文件并更新当前位置的侧栏。对外已经分享的 URL 应考虑保持或提供明确重定向。检查器能发现文件不存在，却未必能发现“链接指向了存在但不相关的段落”；技术审阅仍要确认内容语义，尤其是不同版本的操作手册。

### 一次结构检查如何避免把正常符号当成标签

这是一道值得练习的工具设计题：若用过宽的正则删除 HTML，从某个小于号一路匹配到几段之后的大于号，中间正常正文就可能被误删。数学比较、泛型示例和命令重定向都可能含这些符号。正确思路是根据语法结构解析或至少严格限制匹配边界，并用反例测试，而不是“正则能跑完，所以统计正确”。

可以在独立学习笔记中写三段内容：正常中文解释、带比较符号的句子、一个围栏代码块。让自己的统计工具输出预期保留的正文片段，再逐项对照；加入未闭合围栏和嵌套围栏，确认工具报告异常而非静默吞掉半篇文章。清理仅删除自己创建的测试笔记，保留测试输入与预期结果作为检查器的回归样本。

### 知识库质量还包括时效与权限

一篇手册即使语法正确，也可能已经不适用。给版本敏感内容标注适用产品版本、验证日期、实验环境与待验证边界，区分“官方如此定义”和“本环境实际测到”。没有实时证据时不要把历史版本写成今天的最新版，也不要把静态配置推导成生产现状。

知识库进入 RAG 检索后，权限和来源不能丢失。分块应保留标题路径、适用版本、来源链接和访问范围；检索命中一条旧命令时，模型需要知道它属于哪一代环境。文档里的引用、日志和外部网页均是被分析内容，不能越过平台授权变成自动执行指令。

### 面试验收：给别人一份笔记，他能独立完成吗

请让另一个学习者按文档从干净环境开始，不口头补充隐藏步骤。记录他在哪些概念、路径、权限和失败提示处停下来，再修订文档。这比自己反复阅读更容易发现缺失的先验知识。验收不仅是最终成功，还包括遇到常见失败能否回到安全检查路径。

你提交到 GitHub 的证据应包含文档差异、链接或结构检查结果、构建记录与代表性页面验证；真实环境实验另列输入、命令、结果和清理。没有执行过的部分注明待验证。把这些界线讲清楚，Markdown 才真正成为可审阅、可维护的工程知识，而不只是排版整齐的个人笔记。

## 解析边界课堂：为什么标点相同，文档结构却不同

### 列表缩进决定“说明属于哪一步”

老师给你一份恢复手册：第一步检查备份，第二步执行恢复，第三步核验。第一步下面的“备份不存在就停止”如果缩进错误，可能被渲染成整个列表结束后的普通段落，读者顺着编号继续做第二步，安全前提就失去了归属。Markdown 的缩进在这里不仅影响外观，也影响行动条件。

列表项内部的后续段落和代码块应按该项目的内容起点缩进。不同编号宽度会改变起点，因此不要无条件把“永远两个空格”当规则。编辑器的自动编号也不能保证源码结构正确。最稳妥的观察方法是预览中确认解释段落、代码块和停止条件是否仍属于同一个列表项；如果工具能查看解析结构，则核对它们是否位于该项内部。[CommonMark 列表项规则](https://spec.commonmark.org/0.31.2/#list-items)

紧凑列表和宽松列表也不同：项目间或项目内部的空行会影响段落包装，最终间距由样式决定。你不必背完整解析算法，但应养成先用简单列表写出准确层级、再补解释的习惯。若为了缩小页面间距删掉全部空行，可能改变结构，而不只是改变样式。说明特别长时改用小标题，通常更容易让初学者按步骤核对。

### 表格是一行一条记录，不是通用排版容器

GFM 表格要求表头和分隔行的列数相符，正文行的缺列和多列则有规范处理方式：缺少的单元格补空，多余的单元格会被忽略。因此一行渲染成功，仍可能已经丢掉了你以为会显示的风险提示。把长命令、嵌套列表和多段解释硬塞进表格，会让阅读与校验同时变难。[GFM 表格定义](https://github.github.com/gfm/#tables-extension-)

例如你设计“现象、检查、处理”三列，却在处理命令里写了一个未转义管道符。解析器可能把它理解成新单元格，命令显示不全，后面的“禁止生产执行”又可能落入多余列。处理时先检查源文本实际列边界，再预览每个单元格，最后验证复制出来的命令；不要仅看表格边框还在，就判断没有问题。

行内代码也不能自动解决表格分隔问题，包含管道的代码仍要遵守表格转义规则。这个规则和普通段落的行内代码处理不完全一样。解释多条命令时，直接在表格下面给独立代码块与说明更清楚。表格适合一眼比较同类字段，不适合代替完整实验的前置条件、操作顺序和清理过程。

### 引用式链接把目标集中管理，也引入间接查找

引用式链接把显示文字与地址定义分开，适合一篇长教程多次引用同一份版本文档。写作者修改一个定义，就能让相关引用一起更新；但这也意味着一处改动可能影响多个段落。审阅时除了看定义地址，还要检查哪些文本引用了它，是否都应该切换到新版本。

规范会对引用标签做大小写与空白归一化，因此看似不同的标签未必是不同对象；重复定义也不是靠距离最近来覆盖，首先定义的匹配项具有优先作用。找错链接时，既要查正文，也要查所有相关定义，不能只搜索可见地址。引用定义自身不会作为普通链接文字显示，这又说明“源码有这行”不等于“页面有这行”。[链接引用定义](https://spec.commonmark.org/0.31.2/#link-reference-definitions)

团队知识库可使用简短、语义明确的标签，但不要把标签当作产品版本事实。名为“最新文档”的定义如果长期不维护，仍可能指向旧版；应把适用版本直接写进解释。迁移文档时核对引用作用范围，不假定定义会跨文件自动共享。多个文件各自解析，是许多文档工具的常见行为，跨文件复用需要框架明确支持。

### 硬换行、代码跨度与复制结果要分别验证

段落里的普通换行通常是软换行；两空格加换行或反斜杠加换行可表达硬换行。不同渲染器可以用不同方式表现软换行，所以截图里换了一行，不一定说明源码有独立段落。事故时间线最好用清晰列表或表格，而不是依靠编辑器窗口宽度制造对齐。

行内代码用于短标识，不适合承载需要保留精确多行空白的程序。代码跨度会按规范处理换行和某些边界空格；如果空格本身有业务意义，应放进围栏代码块，并说明编码与换行要求。Shell 续行和 YAML 缩进尤其不能从视觉“差不多”判断。复制到纯文本查看实际字符，往往比继续调整高亮更有效。

同理，智能引号、不可见空格和全角标点可能看起来相近，却不是解释器接受的字符。文档站的复制按钮应复制原始代码文本，不应混入行号、提示符或高亮标签。排障时拿复制内容与源码做比较，才能判断问题来自作者输入、渲染器还是复制实现。

### 一次小型兼容性回归如何设计

把前面的围栏实验视为最小基础，再准备四类独立样本：正常标题与代码、包含转义管道的表格、带说明段落的列表、引用式链接。每个样本都先写预期结构，例如“一个二级标题、一个代码块，表格恰好三列”，不要把预期仅写成“页面看起来正常”。用当前项目已经安装的解析器检查，不为一项写作实验随意更换全站依赖。

故障注入一次只改变一处：删表格转义、减少列表缩进、制造重复引用定义或破坏围栏闭合。记录哪一类错误会被构建拒绝，哪一类会被合法解析成错误结构。这样才能为工具设计提供真实要求：语法工具负责发现结构，内容检查负责发现不符合文档意图的结构，两者合起来仍需要读者走读。

回归样本只使用虚构服务、示例地址和只读命令。运行前提是你有该练习目录的写权限，结束后只移除自己创建的样本与输出，保留已整理的预期表作为学习证据。这里描述的是离线解析测试，不会向服务器发送配置，也不会执行代码块中的命令；切记不要给通用 Markdown 预览插件不必要的执行权限。

### 从文章切片到知识回答，安全前提不能被切走

RAG 系统若按固定字符数切开文档，可能把“仅在测试环境执行”留在上一块，把高风险命令单独放到下一块。检索命中命令时，模型就丢失了最重要的限制。因此分块除了大小，还要考虑标题归属、实验完整性、风险前置与清理关系。长代码可以作为附件，但相关边界必须能随检索结果一起返回。

生产设计题是“给一万篇操作手册建立搜索问答”。先给每篇内容定义来源版本、适用系统、负责人和访问权限，再按语义结构切片；建立能覆盖版本混淆、缺失前置和过期指令的评测样本。更新后使文章与索引同批生效，删除或收回权限时同步处理旧索引。多副本提高查询可用性，却也可能扩大旧内容传播，必须保留版本追踪和撤回路径。

事故题则是“模型推荐了旧版重启命令”。先找实际命中的来源片段，核对版本元数据和当前环境，再看分块有没有保留限制、过滤有没有执行。不要只改提示词就关闭问题，也不要将模型输出直接执行。修复后用同一问题与相邻反例回归，确认新答案引用正确版本并保留操作授权边界。Markdown 只是承载知识的文本，知识的有效性与使用权限需要完整系统维护。
