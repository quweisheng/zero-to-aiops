## 官方知识地图

```text
需求与约束
  -> 功能需求 / 非功能需求
  -> 当前状态与数据基线
  -> 候选方案与可行性验证
  -> 总体架构 / 详细设计
  -> 容量 / 高可用 / 安全 / 可观测性
  -> 实施计划 / 验收 / 回滚 / 运维移交
  -> ADR 与持续复盘
```

`ADR` 是 Architecture Decision Record，即架构决策记录；它说明当时为什么选择某方案，而不只是记录最终结果。`HLD` 是 High-Level Design，总体设计；`LLD` 是 Low-Level Design，详细设计。

## 老师带你从一句需求走到一份能验收的方案

我们先把“稳定的平台”写在黑板上。你问稳定是什么意思，业务说“别让用户下不了单”。这时先画用户真正经历的一次操作：打开页面、提交订单、确认库存、确认支付、查询结果。页面能打开不代表订单成功，订单写入成功也不代表支付结果已经正确保存。架构的第一步是找出用户承诺对应哪条完整路径。

接着画三张不同的图。业务图回答“谁要完成什么”；组件图回答“哪个程序负责哪件事”；部署图回答“程序在哪些机器、网络和故障域里运行”。它们可以使用 C4 的上下文、容器、组件视角，但这里的 Container 是架构模型中可运行或存储数据的单元，并不专指 Docker 容器。别让画图术语制造新的误解。

把箭头也讲清楚。网页到订单服务的箭头可能表示同步请求：网页在等待响应；订单服务到消息队列的箭头表示提交事件：消费者之后处理。若都画成相同箭头却不写语义，评审者无法判断超时是否影响下单、重试会不会重复扣减、故障时哪些状态已经改变。

### 第一课：把“快”变成能计算的数字

假设课堂要求“每天处理一百万个请求”。一天有 86,400 秒，平均速率约为 11.6 次每秒。学生常在这里直接配一台服务器。老师要追问：促销的十分钟是否占了一天一半请求？如果是，峰值约 833 次每秒，和平均值相差很大。这里的 QPS/RPS 分别常用来表示每秒查询或请求数，方案应写明究竟统计哪种请求。

再问延迟。平均延迟很容易被大量快速请求压低，P95 表示按耗时排序后约 95% 请求不超过的值。它不是“95% 的服务器”，也不是把每台机器的 P95 相加或平均就能得出的总体 P95。先定义请求类型和观察窗口，再测分布。读操作和写操作的成本不同，不能把健康检查吞吐当订单处理能力。

容量估算需要输入量、单次成本、并发等待和故障冗余。稳态下可以用“在途请求数约等于每秒请求数乘平均处理时长”建立初步关系：每秒 600 次、平均 0.2 秒，则平均约 120 个请求同时在系统里。这个关系需要稳定流量和口径一致；高峰排队、重试风暴或无界队列出现时，平均数会掩盖失稳。

服务器不能永远按压测极限运行。假设一副本在指定接口组合下测得每秒 260 次，课堂暂取 65% 作为可用承载预算，则每副本约 169 次。600 次峰值需要至少 4 个健康副本；若要求坏一个仍扛住，至少部署 5 个。65% 是本题假设，生产要靠延迟曲线、抖动和故障演练选择，不能照抄。

### 基础实验：自己算一次故障后的容量

前置条件是本机安装 Node.js，能打开终端并进入本仓库根目录。运行 `node --version` 应看到版本号；若提示找不到命令，先解决安装和命令搜索路径。实验用内置数字，不访问云平台，也不修改机器配置。

```powershell
node examples/teacher-led-reliability-lab/lab.mjs architecture
node examples/teacher-led-reliability-lab/lab.mjs architecture --fault
```

先预测再执行。正常案例部署 5 副本，损失 1 副本后剩余安全吞吐为 `4 × 260 × 0.65 = 676`，应看到 `ONE_REPLICA_FAILURE_CAPACITY_OK`，意思是“本模型通过损失一副本后的容量校验”。故障案例只部署 3 副本，剩余吞吐为 338，出现 `CAPACITY_SHORTFALL`，表示存在容量缺口。脚本返回 0 说明课堂判断按预期执行，不说明故障方案健康。

用纸笔复算 `safeRps`（安全吞吐）、`survivors`（故障后的副本数）、`requiredWithOneFailure`（容忍一副本失败所需总数）。如果结果不符，先检查参数、当前目录和脚本版本。这项实验不创建文件或服务，无须删除资源；自行保存的输出由你保留为证据。它验证算术，不证明真实生产的线性扩容能力。

### 第二课：五副本为什么仍可能一起失败

你把五个副本放在同一台宿主机，宿主机断电就全部消失。分到五台机器，如果共享同一块存储、同一交换机或同一个身份服务，仍存在共同故障点。故障域是“一次事故会共同影响的一组资源”，需要顺着请求和状态依赖去找，不能只数副本。

状态更关键。无状态服务通常可以接替请求，但数据库里只有一个主副本时，应用再多也没有解决数据可用性。数据库复制又有同步、异步和确认策略，分别影响写入延迟、可用性与潜在数据损失。方案必须说清客户收到成功响应时，数据已经保存在哪些地方；如果没有确认，重试应怎样避免重复业务效果。

把一次订单写入分成“请求收到、校验通过、数据库提交、返回响应”。若提交后网络断开，客户端不知道成功与否。靠重试解决连通性时，必须同时设计幂等键或查询确认。幂等的意思是在规定条件下重复执行不会增加业务效果；它通常依赖持久状态和唯一约束，不是给请求随便加一个字段就成立。

跨可用区增加冗余，也增加网络延迟、流量成本和协调复杂度。你需要问业务容忍的是单机、单机架、单可用区还是整个站点故障。题目只要求恢复半小时以内，和要求区域故障无感切换，方案成本可能完全不同。不要在未明确恢复目标时默认最复杂的多活架构。

### 第三课：数据库扩容后，为什么应用更慢了

假设应用每个副本最大开 100 个数据库连接，原来 3 副本最多 300 个，扩到 10 副本理论上可争抢 1,000 个。如果数据库安全预算只有 400 个，应用扩容反而制造连接等待、锁竞争和超时。容量设计要沿链路计算，包含定时任务、迁移工具和运维连接的预留。

缓存可以减少读压力，但引入失效、旧数据和回源问题。消息队列可以吸收短暂突发，但如果消费长期小于生产，积压会持续增长。负载均衡可以分配流量，但不能把有问题的业务数据自动变正确。每引入一个组件，说明它改善哪个瓶颈、增加哪种状态和谁负责维护。

我们再做三个取舍练习。第一，读多写少且允许短暂旧值时，可以考虑缓存；库存扣减不能仅依赖客户端看到的缓存值。第二，用户可以稍后看到结果时，任务异步化可能合适；用户必须立即知道支付是否完成时，仍需明确确认路径。第三，统一平台减少重复维护，但也扩大管理面故障的影响；独立实例提高隔离，却增加升级和治理成本。

### 故障实验：用反证修订一份高可用方案

这次不需要服务器。新建一份自己的笔记，写下课堂方案：“应用 5 副本，同一机房，共用一套数据库；每天备份一次；故障后 30 分钟恢复，最多丢 5 分钟数据。”先列四个假设：机房可用、备份可读、复制延迟满足目标、恢复操作有权限。

依次注入纸面故障：机房不可用、备份加密密钥缺失、最近可用备份是 23 小时前、恢复人员无法访问存储。每次只改变一项，写出它如何影响 RTO 或 RPO。只做每天一次备份且没有其他可恢复日志或复制，不能证明最多丢 5 分钟；有备份但无密钥，也不能证明半小时可恢复。

修复方案应具体到新增证据：配置日志归档并验证恢复点，准备密钥恢复流程，在隔离目标重建服务，计时完成业务读写验收。再次逐项核对，保留初稿和修订稿。清理只涉及自己创建的草稿，建议作为学习证据保留。这是生产模拟，不宣称已经做过真实机房灾备演练。

### 第四课：把安全和可观测性写成操作能力

安全先从人和程序分别拿什么身份开始。用户进入网页、服务调用服务、程序访问数据库、运维人员修改配置，是四种不同的权限关系。最小权限意味着每种身份只具有完成其职责的必要能力，并能审计谁在什么时间做过什么；不是所有服务共用一个管理员账号再依靠约定。

日志里的账号、请求标识和时间帮助关联事件，也可能带入隐私。方案需要规定采集字段、脱敏方式、保留时间和查询权限。密钥的创建、分发、轮换和撤销要形成流程；把密码放进配置管理仓库，会让版本历史长期保留敏感信息。

可观测性要覆盖三条链：用户功能是否成功、内部资源是否接近限制、观测系统自己是否在正常采集。若采集程序停止，仪表盘可能显示旧值，不能据此宣布用户恢复。让每个验收项都有数据源、查询、时间窗口和负责人，避免上线现场临时找指标。

### 第五课：升级回滚需要同时看代码与数据

应用代码从版本一切到版本二，再切回版本一，看起来很容易。如果版本二把数据库字段改了、写入了旧版本无法识别的数据，回滚二进制并不等于回滚业务。先分析接口、配置、数据模式和事件格式的兼容矩阵。

一种常见思路是先做兼容扩展：增加新字段但保留旧读写路径，验证新版本后再迁移数据，最终在确认旧版本退出后清理旧结构。每一步都有停止条件。这里不是承诺所有变更都能原地回退；无法回退的变更要在方案中明确前向修复和备份恢复路径。

上线前保存基线，先小范围放量，再验证业务指标、错误、延迟和资源。观察多久要覆盖代表性流量；凌晨五分钟的少量成功请求不能证明高峰也可用。回滚触发条件提前写清，比事故中临时争论更容易形成一致行动。

### 课堂面试：30 秒、3 分钟与连续追问

30 秒回答：“我会先把业务目标变成可测量的用户路径、容量和恢复目标，再设计组件责任、状态归属及故障域。对最高风险假设做实验，记录方案取舍，并把安全、可观测性、升级、回滚和业务验收纳入交付。”

3 分钟回答依次讲四块：需求中最重要的用户动作是什么；一次请求经过哪些组件、状态在哪里提交；峰值和故障后容量怎么计算、依赖有什么上限；上线失败怎样停止、恢复和证明业务正常。把课堂数字与真实测量分开表达。面对“为什么不用多活”，先问允许丢失多少数据、能等多久、谁来承担跨站一致性成本。

追问一：“压测 260 次每秒，五副本是不是就是 1,300？”参考思路是共享瓶颈和扩展效率；用不同副本数的实验测吞吐与延迟，确认数据库、锁和网络是否先成为上限。追问二：“有三副本为什么还要备份？”复制会传播误删和坏数据，备份提供其他时间点的恢复能力。追问三：“组件都健康，业务仍失败怎么办？”回到用户路径和端到端数据正确性，逐步缩小失败阶段。

生产设计题：“两个可用区、600 次峰值每秒、最多丢 5 分钟、半小时恢复，设计告警处理平台。”你的答案应包含持久事件账本、幂等处理、跨区失败策略、容量假设、备份恢复演练和权限审计。事故复盘题：“扩容后数据库超时增多”，先比较连接预算、等待和请求变化，再验证单一假设；不要把时间先后直接写成已证明因果。

### GitHub 学习证据：让方案可以被质疑和改进

提交需求追踪表、三张图、容量计算、正常和故障实验结果、一条带取舍的 ADR、升级兼容矩阵，以及修订前后的灾备方案。标明哪些是假设、哪些是测试、哪些尚未验证。请同学只根据这些文件复述方案；若他无法说明为何选某组件，就回去补理由，而不是再画一张更复杂的图。

## 方案工作坊：设计一个能处理告警的可靠平台

### 需求先写成验收题，而不是组件购物单

同学，客户说“希望告警接入 AI 自动修复”。先别列模型、数据库和 Kubernetes。我们先确定：从哪些系统收事件，是否有重复，峰值多少，通知多久必须送到，哪些动作只能人工批准，允许丢多少记录，故障后多久恢复，以及现有人员能维护什么。

把每个需求写成可验证条件。例如“同一来源重复提交同一事件，不重复创建处理任务”；“无权租户无法查询其他租户原始日志”；“模型不可用时仍能通知并进入人工流程”。这些条件会直接影响账本、幂等、权限和降级设计，而不只是最后验收时补几行文字。

需求也可能冲突。希望所有数据永久保留，又要求低成本和严格最小化收集，就需要分级、保留与归档策略。希望所有动作立即自动执行，又要求每次人工批准，则需要区分风险等级和执行阶段。架构评审的重要工作之一，就是把这种冲突提前讲清楚。

### 画出内部状态路径，而不是只画网络连线

事件到达入口后，先验证身份与格式，再写入持久事件账本；调度器建立处理任务，分析组件形成候选解释，策略判断是否需要批准，执行器进行受控操作，验证器检查业务结果，最后记录反馈。每一步都说明输入、输出、失败重试和状态归属。

事件账本像收件登记册，但它的关键不是“有一张表”，而是成功确认与持久写入的边界。入口如果先返回成功后才保存，进程中途退出可能丢事件；如果保存成功但响应丢失，来源重试就可能产生重复。定义稳定事件标识、唯一约束与结果查询，可以帮助处理这两个方向的不确定性。

任务和事件也不要混成一个对象。一个事件可能需要多次分析或不同动作，一个任务有独立版本和执行状态。这样才能在模型升级后重新分析历史事件，而不把旧事件当新故障再次触发实际修复。

### 缓存、队列和数据库分别承担什么承诺

数据库保存需要长期确认的业务事实，队列组织待处理工作，缓存减少重复读取。它们可以在具体产品中合并部分职责，但方案必须说明真实保证，不能因为都能存键值就随意互换。

如果事件只在易失内存队列里，进程重启可能丢任务；如果队列消息已确认消费，但数据库结果尚未提交，中途故障可能丢处理效果；如果数据库已提交而消费确认丢失，则可能重复处理。常见可靠设计需要把这些状态边界组合起来，使用幂等、事务或可恢复任务协议，而不是依赖“正常情况下消息只来一次”。

缓存里的分析结果可能过期，不能作为授权或当前目标状态的唯一证据。执行前仍要读到适用的新状态，并核对对象版本。对只读解释允许短暂旧数据，与对写入操作要求强前置校验，是两种不同风险策略。

### 一致性不是所有系统都必须选同一种

一致性讨论的是不同读写者在什么时刻能观察到哪些状态。通知列表稍晚几秒更新，可能可接受；资金或库存的关键约束则通常不能随意允许重复效果。先找必须一起成立的不变量，再选择事务边界和协调方式。

例如“一个任务同一时刻只能被一个执行器有效领取”是一个不变量。仅在页面上把状态改成运行中，不能阻止两个进程同时读取旧状态并执行。需要服务器端原子条件更新、租约或适合系统的协调机制，并解释持有者失联后如何接管、旧持有者恢复后如何被阻止继续操作。

跨区域设计还要面对通信延迟与分区。网络断开时，两边继续独立写入可能产生冲突；禁止一边写入会影响可用性。答案不应停留在背 CAP 三个字母，而要说明具体业务在何种分区下允许什么操作、拒绝什么操作、恢复后怎样对账。

### 把超时预算沿调用链分配

用户允许等三秒，不意味着每个依赖都可以各等三秒。同步调用链上的等待与重试会累积。给入口、鉴权、存储和分析分配合理预算，并把不适合在这个窗口完成的工作转为异步任务，向用户提供状态查询。

重试也要有次数、退避和总时长预算。三层组件各重试三次，可能把一次用户操作放大成很多下游请求。不是每种错误都适合重试：输入不合法、权限拒绝通常需要修改请求，暂时网络失败才可能适合有限重试，而且写操作必须考虑重复效果。

故障隔离可以通过并发上限、队列上限、超时和分级降级降低扩散。所谓 Circuit breaker（熔断）是当失败条件满足时暂时停止某些调用、随后受控探测恢复，不是把所有错误隐藏起来。设计时说明触发依据、恢复探测和对用户的替代结果。

### 容量测试要覆盖故障与过渡态

稳定运行一小时成功，不代表节点失败后的重分配、发布期间的新旧共存、模型加载和历史事件回放同样安全。测试矩阵应包含正常峰值、短时突发、一个关键节点不可用、下游变慢和恢复后的积压排空。

测量不只记录最大吞吐，还要记录延迟分布、错误率、资源使用、队列增长和恢复时间。若队列持续变长，短时间内看起来吞吐不错也可能不可持续。把输入速率、处理能力和待处理数量一起看，才能判断是否达到稳定状态。

不要把实验机器的数字直接承诺给客户。记录硬件、数据规模、接口组合、版本和限制，说明哪些结果可外推、哪些需要补测。对最关键的不确定性做小型概念验证，比先部署完整复杂平台再发现基本假设错误更经济。

### 从设计文档走到交付证据

每个重要需求连接一个设计决策、一项测试和一条运维动作。例如“模型失效仍能响应”对应确定性规则兜底、停用模型的故障演练、人工接管 Runbook；“允许五分钟数据损失”对应恢复点设计、隔离恢复验证和备份失败告警。

评审时主动展示被放弃的方案及理由，包括成本、团队能力、升级复杂度和故障面。不是组件越多越专业，而是每个组件都有明确责任、每个风险都有可验证处理方式。暂时未解决的事项放进风险清单，不能藏在图中一个叫“高可用”的方框里。

最后请另一位同学扮演值班人员，只根据你的材料回答“哪个组件坏了会影响什么，先看哪里，谁有权修复，如何回退”。若他无法回答，说明方案还停留在设计者脑中。补齐这些信息，才更接近可以交付、可以维护、可以接受面试追问的技术方案。

## 核心原理

### 功能需求、非功能需求与约束

- **是什么**：功能需求说明系统做什么；非功能需求说明性能、可靠性、安全等质量；约束说明不能改变的边界。
- **为什么需要**：同一个功能在不同可用性和合规要求下，成本可能相差数倍。
- **怎么工作**：把口头描述改写成可测量条件，例如“月可用性 99.9%、P95 小于 300 ms”。
- **怎么看或怎么用**：建立需求追踪表，每项需求必须有负责人、验收方法和优先级。
- **坏了怎么查**：评审争论技术细节时，回到原始业务目标和约束，检查是否存在未确认假设。

### SLI、SLO、RTO 与 RPO

- **是什么**：SLI 是服务水平指标；SLO 是目标；RTO 是故障后允许多久恢复；RPO 是最多允许丢失多久的数据。
- **为什么需要**：没有数字的“高可用”和“不能丢数据”无法设计也无法验收。
- **怎么工作**：先选用户可感知指标，再定义统计窗口、目标和错误预算，最后反推冗余与灾备。
- **怎么看或怎么用**：方案中写明数据源、计算公式、告警阈值和演练频率。
- **坏了怎么查**：若指标长期达标但用户仍投诉，说明 SLI 可能没有代表真实体验。

### 容量模型与故障域

- **是什么**：容量模型估算峰值资源；故障域表示一次故障会同时影响的范围。
- **为什么需要**：平均负载不能代表峰值，三副本若都在同一节点也不是真正高可用。
- **怎么工作**：使用峰值 QPS、单实例吞吐、增长率和冗余系数计算容量，再把副本分散到节点、机架或可用区。
- **怎么看或怎么用**：用压测验证单实例基线，用 topology spread、反亲和和存储副本验证分散。
- **坏了怎么查**：容量不足先确认假设与真实数据是否偏离；故障扩大则检查副本是否共享网络、电源、存储或控制面。

### 候选方案、PoC 与 ADR

- **是什么**：候选方案用于比较，PoC 是 Proof of Concept 概念验证，ADR 保存决策与取舍。
- **为什么需要**：避免凭产品熟悉度拍板，也避免 PoC 只展示“能安装”。
- **怎么工作**：用同一组硬性条件和评分维度比较方案，对最高风险假设设计 PoC。
- **怎么看或怎么用**：ADR 记录背景、选项、决定、后果和重新评估条件。
- **坏了怎么查**：实施后条件变化时回看 ADR，不把旧决定当永久真理。

### 上线、回滚与运维移交

- **是什么**：上线计划描述变更步骤，回滚定义停止条件与恢复动作，移交保证系统可持续运维。
- **为什么需要**：安装成功不是交付完成，未知告警和无法恢复的备份都会变成生产风险。
- **怎么工作**：先建立基线，再灰度实施，按技术与业务指标验证，越过阈值立即停止或回滚。
- **怎么看或怎么用**：必须有 Runbook、仪表盘、告警、权限、备份恢复演练和负责人。
- **坏了怎么查**：上线异常先冻结继续扩散，保存证据，按预先定义条件回滚，而不是现场争论。

## 在 AIOps 中的作用

AIOps 架构必须同时设计数据源、标签、时间、拓扑、模型/规则、告警、自动化和审计。自动修复要定义触发条件、权限、幂等、超时、人工审批、熔断与回滚；否则“智能化”会把误判放大成变更事故。

## 入门实验：为多集群平台写一页方案并自动检查

### 实验目标

完成一页最小可行性报告，确保关键章节不是空标题，并能说明一个核心取舍。

### 实验步骤

1. 使用上面的模板填写 `solution-lab/feasibility.md`。
2. 场景限定为：两套 Kubernetes 集群、50 个服务、需统一镜像和监控，核心服务 RTO 30 分钟、RPO 5 分钟。
3. 至少比较“单管理平台多集群”和“每集群独立管理”两种方案。
4. 执行检查：

```powershell
$required = '业务目标与范围','当前状态与约束','非功能目标','候选方案与取舍','目标架构与容量','安全、可观测性与运维','实施、验收与回滚','风险、成本与结论'

$missing = $required | Where-Object { $text -notmatch [regex]::Escape($_) }

```

### 验证结果

终端输出 `PASS: 必需章节齐全`；文档中每个目标都有数字和验收方法，每个主要风险都有负责人或缓解动作。

### 如果没有成功

1. 检查文件路径和 UTF-8 编码。
2. 若章节存在但名称不同，统一标题或调整检查列表。
3. 章节齐全但内容空泛时，补数据来源、负责人、验收命令和失败处理。
4. 无法比较方案时，说明需求和约束还没有问清，不要先画最终架构图。

## 方案深化课堂：从数字目标到决策门槛

### 一、先确定哪些请求应该进入分母

老师给你两张报表，一张说成功率百分之九十九点九，另一张说用户频繁失败。两者可能都没有算错，但统计对象不同。第一张也许把大量健康检查与静态资源算进成功请求，第二张只关心提交订单。设计 SLI 时先明确用户动作、哪些结果算成功、哪些请求算有效，以及统计窗口。用户取消、权限拒绝与服务故障应按预先约定分类，不在事故后临时调整口径让指标好看。

多副本的整体错误率应由各副本错误数之和除以请求数之和，而不是简单平均各自比例。一个副本只处理十次请求，另一个处理十万次，它们不能拥有相同权重。延迟百分位的聚合更要保留分布信息，不能直接平均各自的百分位。这些算术细节会影响告警、容量与验收，因此指标来源也是架构合同的一部分。

错误预算把可靠性目标变成可消耗的失败额度。假设课堂按一万次有效操作、百分之九十九点九成功目标计算，允许失败十次；五次失败仍在预算内，一百次已经超出。它不是鼓励制造错误，而是让团队讨论风险与交付速度时有共同尺度。[Google SRE 的 SLO 实施章节](https://sre.google/workbook/implementing-slos/)提供了目标、测量和错误预算的思路。事故的严重程度仍结合用户影响，不能因为月度预算还有余额就忽略数据错误。

取一次窗口内实际错误率除以允许错误率，可以理解预算消耗速度。短窗口消耗过快有助于及时发现故障，长窗口帮助避免只对瞬时波动过度反应。选阈值时要考虑流量规模：一分钟只有两次请求，失败一次得到百分之五十，不代表已经有大量用户受影响；也不能因此永远忽略低频关键操作。用合成探针与业务事件补充，是一种需明确成本的选择。

### 二、候选方案评分前先设不可妥协条件

如果候选甲便宜，但数据必须跨出禁止区域，不能给它“合规零分、其他满分”然后靠加权总分获胜。硬约束先淘汰不合格方案，剩下的再按成本、运维难度、扩展性与迁移代价比较。每个分值最好有证据来源与不确定范围；没有测试的性能优势标为假设，不把厂商峰值直接当现场承载。

总拥有成本不仅是采购价，还包括支持订阅、许可证计量、备份容量、跨站传输、监控保存、值班和升级演练。商业产品要核对版本和物料清单，开源产品也有集成与维护成本。退出成本同样重要：数据能否导出，格式是否兼容，许可证到期后哪些能力受影响，替代系统需要多久。预算表如果只列第一年的机器价格，会把后续风险藏起来。

做一个敏感性推演：假设两方案初始成本相近，甲每新增一租户要部署独立组件，乙共享管理面。分别计算十、五十、一百租户时的容量与维护工作；再加入单租户异常会影响谁的隔离要求。甲可能在小规模简单可靠，乙可能在大规模更经济，但需要更严格的配额和权限。结论应写明在哪些规模或约束变化时重新评审，不能只写“选择先进方案”。

### 三、恢复计划也有依赖图和关键路径

把恢复拆成找回身份与密钥、取得备份、恢复存储、启动数据服务、启动应用、校验数据和切换入口。某些动作可并行，某些必须等待前一步。RTO 是用户恢复的总时间，不是把每个团队最短操作时间挑出来相加。没有访问密钥，后面的解密和恢复都不能开始；控制面不可用时才临时申请机器，也可能增加不可预测等待。

[AWS 可靠性框架的恢复策略说明](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_planning_for_recovery_disaster_recovery.html)区分备份恢复、保留核心基础设施、缩小规模待机和多站点服务等取舍。这里借用的是设计方法，不照搬该云的时间承诺。需要快速恢复时，提前准备资源可以减少灾后动作，却增加持续成本；多站点同时写入还增加冲突处理和隔离责任。

纸面故障实验把三个步骤设为：恢复身份五分钟、恢复数据库十五分钟、启动应用三分钟，业务校验再四分钟。先画依赖关系，正常总计二十七分钟。故障轮让密钥取回额外等待十分钟，预期突破三十分钟目标；恢复轮改成经授权的预备取回流程并重新验证时间。清理只删除虚构故障标记。若学生用数据库恢复十五分钟宣布达标，说明漏算关键路径。本轮没有实测这些时间，数字只用于训练方法。

### 四、上线完成要包含降级模式与交接能力

一个告警平台不能因为模型超时就停止通知。设计降级时应说明保留哪些核心能力、停止哪些自动动作、怎样告诉使用者当前模式，以及恢复后是否重放积压。模型分析可以晚到，已经执行过的修复不能不加判断再次执行。任务版本、幂等记录、批准状态和当前目标状态必须在恢复后重新核对。

控制面故障与数据面故障也要分开。管理网页打不开，已有服务可能继续运行；但创建新资源、调整规则和凭据轮换可能受阻。方案应列出现有工作负载、新建工作负载、扩容和恢复各自依赖哪些控制服务。把所有控制能力与业务实例放进同一故障域，会让平时不明显的依赖在灾后同时失效。

运维移交用反向演示验收：让未参与建设的同事只凭材料定位一个模拟故障、判断权限、找到回退步骤并说明数据影响。若必须靠设计者口头解释，记录缺口并补文档。文档章节检查只证明标题存在，无法证明内容正确；前文自动检查不应被叫成架构验收工具。最终证据包括反例、失败记录与修订理由，能解释“为什么不能这样做”通常比只有成功截图更能证明理解。

最后独立复述一个被放弃的方案：它满足了哪些目标，违反了哪个约束，缺少哪项证据，以及将来什么变化会让它值得重新考虑。能清楚回答这四问，说明决策来自条件与证据，而不是把个人熟悉的工具包装成唯一答案。
