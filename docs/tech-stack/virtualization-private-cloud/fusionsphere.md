## 场景开场

凌晨，业务说“虚拟机重启了三次，系统一直没恢复”。平台上同时出现：

```text
VRM：虚拟机反复重启告警
CNA：一台主机短时断连
存储：某条路径抖动
网络：没有明显丢包告警
业务：数据库连接仍失败
```

如果只看到虚拟机现在是 Running 就宣布恢复，会漏掉两个事实：虚拟机可能仍在不稳定重启；客户机起来也不代表数据库、IP、挂载和应用顺序已经正确。

FusionSphere 排障的关键不是会点“重启”，而是把控制面任务、CNA 执行、网络、存储、客户机和业务验证放在同一条时间线上。

## 一句话人话版

FusionCompute 是华为服务器虚拟化平台：VRM 统一管理资源和任务，CNA 在计算节点上真正运行虚拟机，并把服务器、网络和存储组织成可管理的资源池。

## 小白先问

### FusionSphere 和 FusionCompute 是一个东西吗

不能简单画等号。FusionSphere 在不同年代和材料中可能指产品族或不同云形态；FusionCompute 是服务器虚拟化主线。现场先看产品全名、登录页面、版本和 BOM。

### FusionSphere 底层是不是 OpenStack

FusionSphere OpenStack 是华为基于 OpenStack 增强的企业形态；FusionCompute 的核心运维主线是 VRM/CNA。不能把所有写着 FusionSphere 的环境都判断成 OpenStack。

### VRM 挂了，虚拟机都会关机吗

已运行虚拟机通常由 CNA 数据面继续承载，但集中管理、任务、部分调度和故障处置能力会受影响。具体行为以目标版本和故障范围为准。

### 开了 HA 就不用备份了吗

不行。HA 主要处理宿主机故障后的虚拟机恢复；误删、数据损坏、勒索、历史恢复和异地灾难需要备份/复制/容灾。

## 核心架构：VRM 与 CNA

### VRM 五件套

是什么：VRM 是 Virtual Resource Management，虚拟资源管理控制面。

为什么需要：多台计算节点、网络、存储和虚拟机需要统一清单、权限、任务、策略和告警。

怎么工作：管理员或 API 向 VRM 提交意图，VRM 校验资源与权限，选择目标并向 CNA/相关资源执行，最后汇总任务、事件和状态。

怎么观察：Web 客户端查看集群、主机、虚拟机、任务、事件、告警、容量与性能；受控环境可使用版本匹配的 API/SNMP。

坏了怎么查：区分浮动地址、单节点地址、主备关系、管理网络、DNS/时间、证书、数据库空间、服务状态和最近变更；禁止同时重启主备。

### CNA 五件套

是什么：CNA 是 Computing Node Agent，部署在计算节点上的虚拟化执行面。

为什么需要：真正的 CPU/内存调度、虚拟网络、虚拟磁盘和虚拟机生命周期必须在宿主机执行。

怎么工作：接收管理任务，调用本地虚拟化、网络和存储能力创建或运行虚拟机，并上报状态。

怎么观察：从 VRM 看主机状态、资源、事件和性能；在授权 SOP 下检查主机硬件、链路和版本匹配信息。

坏了怎么查：先看单主机还是多主机、管理心跳还是数据面、硬件/BMC、网络、存储路径、资源耗尽和最近维护。

### 控制面与数据面

```text
管理面：管理员 -> VRM -> 任务/策略/告警
数据面：业务 -> VM -> CNA -> 网络/存储/物理硬件
```

VRM 页面可用不证明业务数据面健康；VRM 页面暂时不可用也不等于所有运行中 VM 已停止。事故声明要分别验证。

## 资源对象模型

```text
数据中心/站点
  -> 资源池或集群
     -> CNA 主机
     -> 虚拟机
           -> vCPU（虚拟处理器）/ 内存 / vNIC（虚拟网卡）/ 虚拟磁盘
     -> 虚拟网络/端口组
     -> 数据存储
```

| 对象 | 关键状态 | 容量问题 | 事故关联键 |
|---|---|---|---|
| 集群 | 可用主机、HA/调度策略 | 故障冗余和可售容量 | cluster ID |
| CNA | 在线、维护、告警 | CPU/内存/网卡/路径 | host ID/序列号 |
| VM | 运行、电源、任务 | vCPU/内存/磁盘 | VM ID/业务映射 |
| 数据存储 | 在线、可访问、容量 | 使用率、时延、路径 | datastore ID/LUN |
| 网络 | 端口组、VLAN、uplink | 带宽、队列、错误 | network/port/VM ID |
| 任务 | 排队、执行、成功、失败 | 并发和超时 | task/request ID |

名称可重复或被修改，自动化和 AIOps 关联优先使用稳定 ID，并保留名称用于人读。

## 一台虚拟机的创建链

```text
管理员/自动化提交参数
  -> VRM 认证与授权
  -> 校验模板、资源池、主机容量、网络和数据存储
  -> 选择集群/CNA/数据存储
  -> 准备虚拟磁盘和网络端口
  -> CNA 创建虚拟硬件
  -> 从镜像/磁盘/网络启动
  -> 安装或调用客户机工具（若方案需要）
  -> VRM 汇总任务、事件、状态
  -> 业务探针验证应用
```

页面显示“任务已提交”只是控制面受理，不代表所有后端步骤完成。

### 创建失败怎样定位停点

1. 保存任务 ID、对象 ID、时间、操作者和错误码。
2. 看卡在资源选择、磁盘、网络、创建还是启动。
3. 检查配额/容量与故障冗余，不只看总量。
4. 查目标 CNA、数据存储、网络和镜像同时间告警。
5. 找最近变更：维护、固件、交换、存储、补丁、策略。
6. 只在确定失败阶段后执行最小修复；不反复点创建制造残留。

## 计算虚拟化与资源争用

vCPU 不是独占物理核，虚拟内存也不等于永久独占物理内存：

```text
应用线程
  -> 客户机 OS 调度到 vCPU
  -> CNA/Hypervisor 调度到物理 CPU
```

客户机 CPU 40% 仍可能慢，因为 vCPU 在宿主机等待。容量要同时看：分配、实际使用、峰值、争用、故障后余量和增长。

### 容量四本数

| 数字 | 含义 | 误区 |
|---|---|---|
| 物理总量 | 安装的 CPU/内存/存储 | 忽略系统与故障预留 |
| 已分配 | 给 VM/资源的逻辑量 | 不等于同时真实消耗 |
| 实际使用 | 当前/区间真实负载 | 瞬时低不代表可过度出售 |
| 可承诺余量 | 满足 HA、维护和增长后可用 | 不能用“总量-已用”直接代替 |

生产设计至少按一台主机故障或计划维护后仍满足关键负载计算，而不是集群平时刚好不满。

## 网络完整路径

```text
应用 socket（套接字，程序收发网络数据的接口）
  -> 客户机协议栈
  -> vNIC（虚拟网卡）
  -> 虚拟交换/端口组
  -> CNA（计算节点代理所在主机）物理 uplink（上联链路）/绑定
  -> TOR（机架顶部交换机）/汇聚交换机
  -> VLAN（虚拟局域网）/路由/安全设备
  -> 目标服务
```

管理、业务、存储、迁移等平面应按现场设计隔离。VLAN、MTU、绑定、网关和端口不能跨版本硬背。

### VM 有 IP 但不通

1. 客户机：IP、掩码、网关、路由、DNS、防火墙、监听端口。
2. 虚拟层：vNIC 是否连接、端口组/VLAN 是否正确、策略是否放行。
3. CNA：uplink、绑定成员、错误/丢包、MTU。
4. 物理网：交换端口、trunk、VLAN、路由、ACL/防火墙。
5. 对端：服务监听、返回路由、负载均衡和应用日志。

不要把“能 ping”当业务正常，也不要关闭全网安全策略试错。

## 存储完整路径

```text
应用读写
  -> 客户机文件系统/卷管理
  -> 虚拟磁盘
  -> CNA 存储协议与多路径
  -> SAN/NAS/分布式存储网络
  -> 阵列/存储池/磁盘
```

FusionCompute 添加数据存储前需要识别适配器和设备。设备扫描不到时，应检查分区呈现、SAN zoning、iSCSI/NFS 网络、认证、多路径、驱动/固件和兼容矩阵，而不是一直刷新。

### I/O 慢的证据顺序

1. 业务操作和时间窗。
2. 客户机延迟、队列、错误和文件系统。
3. 虚拟磁盘与目标数据存储。
4. CNA 路径、HBA/NIC、队列和错误。
5. 交换网络/存储端口。
6. 阵列/分布式存储容量、缓存、热点、重建和磁盘故障。
7. 同时段迁移、快照合并、备份和扩容。

## 快照、HA、备份和容灾

| 能力 | 解决什么 | 不解决什么 |
|---|---|---|
| 快照 | 短期回退某个虚拟磁盘状态 | 长期独立备份、存储故障 |
| VM HA | 宿主机失败后在其他资源上恢复 VM | 应用零中断、数据逻辑损坏 |
| VRM 主备 | 管理控制面冗余 | 业务跨站容灾 |
| 备份 | 独立恢复点和历史恢复 | 自动接管全部业务 |
| 存储复制/双活 | 数据跨故障域保护 | 应用顺序、DNS、依赖编排 |
| UltraVR/DR 编排 | 保护组、切换、回切和演练 | 未配置的业务依赖和人为验证 |

RPO（允许丢多少数据）和 RTO（允许停多久）是经验证的业务目标，不是看产品页后自动成立。用最近一次恢复/切换演练报告证明。

## VRM 主备与心跳故障

集群部署通常通过浮动管理地址访问。VRM 主备心跳中断会降低可靠性，甚至带来数据不一致风险。

证据顺序：

1. 当前谁是主、谁是备、浮动地址在哪里。
2. 两节点各自状态和管理网络双向连通。
3. NTP/时间偏差、证书有效期和名称解析。
4. 数据库空间、磁盘和关键服务状态。
5. 最近网络、证书、密码、恢复或补丁变更。
6. 原厂告警 ID、版本文档和工单。

红线：未确认角色和一致性前，不同时重启、不强制双主、不删除同步状态、不随意倒换。

## 升级与回滚

升级不是把 VRM/CNA 包换成更大版本：

```text
当前完整版本与拓扑
  -> 目标版本与升级路径
  -> 硬件/固件/驱动/存储/网络/备份配套表
  -> 健康预检查和容量余量
  -> 配置/数据库/关键业务备份
  -> 维护窗、顺序、停止条件
  -> 分阶段升级
  -> 平台和业务双重验收
  -> 观察期
```

“回滚”能否原地完成取决于版本。数据库和配置已迁移后，可能只能恢复备份或按原厂方案回退。变更前必须把回退入口、最大允许时间和数据影响写清。

应升级原厂的情况：闭源控制面内部错误、主备不一致、补丁签名/BOM、跨版本回退、License 重签、数据存储一致性、容灾反向同步和厂商专用工具操作。

## 安全边界

1. 管理网与业务网隔离，管理入口经过堡垒机/受控终端。
2. 按角色最小权限，日常只读、变更、审计和紧急账号分开。
3. 密码、证书、API 凭据进入安全保管，不写脚本和仓库。
4. 时间同步是证书、审计和主备判断基础。
5. 高危操作双人复核，记录任务 ID、审批单、影响和回滚。
6. SNMP/API 使用专用只读账号、限速和来源限制。
7. 导出的支持包、清单和截图脱敏后才可离开受控环境。

## 可观测性与 AIOps

### 必采信号

| 信号 | 示例 | 用途 |
|---|---|---|
| 指标 | 主机/VM CPU、内存、存储时延、网络错误、容量 | 趋势与范围 |
| 告警 | VRM 心跳、CNA 状态、VM 重启、存储路径 | 触发事件 |
| 任务/事件 | 创建、迁移、重配置、维护、HA | 解释状态变化 |
| 日志 | 控制面、CNA、网络、存储、认证 | 定位阶段和错误 |
| 审计 | 操作人、对象、时间、结果 | 关联人为变更 |
| 拓扑 | 业务-VM-CNA-网络-存储 | 爆炸半径与根因 |

推荐关联键：告警 ID、任务 ID、VM ID、host ID、datastore ID、网络 ID、变更单和统一时间窗。

### AIOps 只读诊断流程

```text
告警进入
  -> 补齐对象与拓扑
  -> 关联同时间任务/变更
  -> 检查同故障域其他对象
  -> 计算容量和趋势
  -> 输出假设与下一条只读证据
  -> 人工审批修复
  -> 业务探针验证和复盘
```

自动化不直接重启主备、迁移全场 VM 或清理存储状态。

## 面试怎么讲

### 30 秒版本

FusionCompute 是华为服务器虚拟化平台，VRM 是统一管理控制面，CNA 是运行虚拟机的计算执行面。一次 VM 创建还依赖网络、数据存储和镜像。生产运维要区分管理面与数据面、HA 与备份/容灾，并用任务 ID、对象 ID、告警、拓扑和变更记录排障。版本、补丁、License 和升级必须以现场证据及目标版本原厂文档为准。

### 3 分钟版本

先澄清 FusionSphere 是产品族称呼，主线是 FusionCompute；画出管理员 -> VRM -> CNA -> 虚拟机/网络/存储。再讲 VRM 主备、资源对象、VM 创建链、计算争用、网络和存储路径。生产上用故障域和 N+1 设计集群，用独立备份/DR 保护数据，用最小权限、证书、NTP 和审计保护管理面。排障按任务、告警、对象、依赖和业务探针收证据；闭源控制面、主备一致性、补丁、License 和跨版本回退及时升级原厂。

### 连续追问

1. **VRM 和 CNA 区别？** VRM 管意图和状态，CNA 执行虚拟机数据面。
2. **VRM 挂了为何 VM 还能跑？** 管理控制面与已运行数据面分离，但集中管理和部分调度受影响。
3. **HA 等于零中断吗？** 不等于，VM 重启和应用恢复有时间，还要处理依赖与数据。
4. **快照能否代替备份？** 不能，通常依赖原数据存储且长期快照影响容量/性能。
5. **创建 VM 失败怎么查？** 拿任务 ID 沿 VRM、资源、CNA、网络、存储、镜像定位停点。
6. **升级怎么回滚？** 先按目标版本文档定义能否原地回退，否则靠配置/数据库备份和完整恢复方案。

## 老师带你看懂管理页面背后的机器

先看一台普通服务器：CPU 执行指令，内存保存正在使用的数据，磁盘保存长期数据，网卡连接其他机器。虚拟化让多台客户机共享这些物理能力，每台客户机看见自己的虚拟硬件。它并没有凭空增加物理计算能力，而是让分配、隔离和迁移更方便。

VRM 像机房调度室，记录资源、权限和任务；CNA 像每台服务器上的执行人员，真正落实虚拟机的运行与设备连接。调度室电话断了，已经工作的机器可能继续运行，但新任务、状态汇总和部分故障处理会受到影响。这个类比用于理解分工，真实主备和恢复行为仍按目标版本确认。

客户机 OS 是虚拟机里的操作系统，宿主是承载虚拟机的物理计算节点。Guest Tools（客户机工具）帮助平台与客户机协作，可能涉及状态上报和特定生命周期动作；它不是业务健康的最终裁判。工具正常，也可能数据库密码错误、文件系统没挂载或应用没有监听。

### 内存为什么不能随便超分

分配给虚拟机的内存、客户机实际使用、宿主实际占用和故障后可承诺余量是不同数字。某些内存回收机制可以改善平均利用率，但应用突然进入峰值时，内存压力仍会真实存在。换页把部分内存内容转到磁盘，会显著改变响应时延。

CPU 同样存在两级调度：客户机调度线程到 vCPU，虚拟化层调度 vCPU 到物理执行资源。应用线程在等待 I/O 或调度时，CPU 使用率未必很高。看见低 CPU 不能排除性能问题，要把客户机等待、宿主争用、存储队列和业务时延放在同一时间窗。

老师给你一道容量题：4 台宿主各有 100 单位可用容量，业务峰值 280。坏一台剩 300，看似满足；但如果同时有 30 单位维护与迁移开销，就已经不足。N+1 要以明确的工作负载和故障场景计算，不能只凭节点数量命名。

## 网络与存储课堂：两条线要一路追到物理层

vNIC 是虚拟网卡，端口组把一组接入规则组织起来，uplink 是从虚拟交换环境连接物理网络的上联。TOR 是 Top of Rack，通常指机架顶部接入交换机。VLAN 是二层逻辑隔离，路由负责跨网络转发。虚拟机 IP 正确，不代表上联交换口允许这个 VLAN。

排障做四次逐步扩大的验证：客户机本机服务、同宿主测试对端、跨宿主测试对端、跨网段业务入口。同宿主成功而跨宿主失败，会把注意力引向上联和物理承载；跨网段才失败，则继续检查网关、路由、安全设备和返回路径。测试必须使用允许的无敏感数据目标。

SAN 是存储区域网络，NAS 是通过文件协议提供共享访问的存储。LUN 是逻辑单元，是块存储给主机识别的一个逻辑设备。Zoning（分区）控制 SAN 里哪些端口能互相通信，主机映射决定哪个主机能看哪块卷；两者都正确，客户机才可能最终拿到对应磁盘。

Multipath（多路径）提供到同一逻辑设备的多条通路，避免一根线断掉就无法访问数据。两条路径如果经过同一个单点交换机，冗余的故障覆盖仍有限。核验要把虚拟磁盘、数据存储、LUN、适配器、交换端口和阵列控制器串起来，而不是只看“路径数量等于 2”。

## HA 与迁移课堂：重新开机不等于业务无感

HA 接管通常需要发现故障、确认处置条件、选择可用资源、启动虚拟机，再等待客户机和应用恢复。每个阶段都会消耗时间。核心数据库还要做恢复与一致性检查；用户看到的停机时长应从业务失败到业务恢复计量。

热迁移一般要求源与目标有兼容的处理器、网络、存储和迁移条件。它并非对任何失败宿主都有效：源机已经失去执行能力时，需要另一类故障恢复流程。迁移过程中也会消耗网络与内存复制能力，不应在存储已拥塞时同时迁移所有虚拟机。

快照记录某个时间点的磁盘关系，后续写入和合并会产生额外空间与 I/O。长时间不合并可能扩大恢复和维护成本。备份需要历史恢复点和独立保护，容灾还要恢复入口、网络、应用依赖和数据权威。你应该分别记录这四种能力的范围和验证证据。

## 事故课堂：一台 CNA 断连之后，先确认谁还能写

如果管理面说 CNA 离线，第一步不是在其他宿主强行启动相同数据库虚拟机。管理心跳丢失可能是管理网断了，原机业务与存储仍在运行。两份实例同时写同一数据，会带来更严重的一致性风险。

先通过授权渠道确认电源、管理和业务路径、存储访问、主机角色与平台 HA 事件。若需要隔离旧节点，让厂商支持的故障恢复流程确保只有一侧拥有写入权。恢复后核对 VM 身份、IP、挂载、数据库恢复日志和业务事务，不把电源亮起当作事故结束。

面试的三分钟展开可以按“职责、路径、故障、取舍”组织：先解释 VRM/CNA，再画 VM 到网络和存储，接着讲管理断连与数据面存活的差异，最后说明容量预留、隔离、备份与原厂版本边界。连续追问“为什么不能马上切”时，回答数据单写者和故障证据；追问“怎么证明恢复”时，回答平台状态、业务探针和数据校验三层验收。

## 资源调度课堂：为什么大虚拟机未必比小虚拟机更快

应用能用多少 CPU，先受应用并行程度限制。只有少量活跃线程的程序，分配大量 vCPU 可能没有明显收益，却增加调度承诺与迁移负担。先从客户机线程、等待与业务吞吐判断瓶颈，再看宿主争用；不能把业务响应慢直接转成“再加八核”。同样，提高上限与提高保证资源是不同动作，应按该版本资源策略核对。

NUMA 是非一致性内存访问：多处理器机器上的内存分属不同邻近节点，访问本地与远端内存代价可能不同。大页减少部分地址转换开销，但需要相应内存组织与应用条件。华为 [DCS 方案](https://e.huawei.com/cn/solutions/storage/virtualization/datacenter-virtualization)列出了 NUMA、大页与 CPU 服务质量优化；它证明产品有相应优化方向，不证明任何现场参数都该打开。

把一台宿主看成两个各有三十二核和一百二十八 GiB 的资源区域。一个要求四十核、二百 GiB 的虚拟机，不可能全部放入任一区域。若应用对内存访问敏感，需要理解虚拟拓扑与物理放置的对应；强制只使用一个区域又可能让创建失败。这里是帮助理解的容量模型，不是 FusionCompute 默认调度算法，实际设置要按版本与负载测试。

基础步骤比较十六核六十四 GiB 与四十核二百 GiB 两种请求，画可能放置。故障步骤把一个区域的大部分内存分配给其他业务，预测总内存仍有剩余但局部约束不满足。恢复方案是调整放置、合理规格或资源池，而不是删除未知虚拟机。核验记录宿主可用、虚拟机承诺与业务时延，清理只还原纸面分配。

通用原理可继续阅读 [Linux NUMA 内存策略](https://www.kernel.org/doc/html/latest/admin-guide/mm/numa_memory_policy.html)，但这些内核说明不能替代华为平台支持操作。闭源管理环境里直接修改宿主底层参数，可能绕过平台管理和破坏支持状态；课堂学习原理，生产使用受支持接口，是必须保持的边界。

## 迁移机制课堂：需要搬的不只是虚拟磁盘

热迁移通常要把执行所需内存与设备状态移到目标，并在合适时刻切换运行位置。预复制类机制会在源仍运行时先传内存，再补传期间被修改的页面，最后短暂协调切换。脏页是迁移过程中又被写过的内存页，不是坏内存。该解释是通用虚拟化原理，具体 FusionCompute 模式、收敛策略和停顿条件依据现场版本，不从通用 QEMU 直接推定私有实现。[QEMU 迁移开发说明](https://www.qemu.org/docs/master/devel/migration/main.html)可用于理解这一机制。

假如有效迁移带宽每秒一 GiB，而应用持续修改页面每秒一点二 GiB，预复制可能很难自然收敛。实际还受重复修改、压缩、限速与实现影响，不能把这个差值当作精确时长公式。解决方向是先验证迁移条件和脏页负载，必要时在业务允许窗口降低写入或使用支持的其他迁移方式，不反复点击重试。

迁移网络与业务网络共享物理上联时，大量并行迁移会抢带宽。即使逻辑上分了 VLAN，物理链路容量仍共享。计划维护应限制并发并观察客户机延迟、链路利用率和迁移进度。源主机已经失去运行能力时，不能再期待热迁移保存其所有内存；此时进入故障恢复与数据一致性流程。

迁移目标还必须能看到正确数据存储与业务网络。源目标端口组名字一样但 VLAN 不同，会出现迁完虚拟机仍运行却失联；存储名称相同但对应不同设备，风险更高。迁移预检应比较对象标识、设备可见性、网络映射与兼容矩阵，不只比较人类可读名称。

生产模拟选择一台无敏感数据的教学虚拟机，在纸上列源、目标、网络与数据存储。基础步骤满足全部条件，预测迁移后业务地址不变且路径可达；故障步骤仅改变目标上联的业务 VLAN，预测迁移任务可能完成但业务失败。恢复步骤还原网络映射并复验应用。清理撤销模拟差异，不执行真实迁移；要获得真实迁移证据，必须另有授权实验集群。

## 数据存储课堂：添加、发现、格式化不能混成一个操作

“主机发现设备”意味着主机能识别底层资源，“添加数据存储”意味着平台将它纳入可使用对象，“格式化”则可能改变盘上数据结构。三者风险完全不同。遇到已有签名或未知数据卷，不能为了让按钮变绿选择格式化。先确认 LUN 身份、用途、已有文件系统和所有访问者，必要时交给存储与平台负责人联合确认。

华为[添加数据存储文档](https://info.support.huawei.com/hedex/api/pages/EDOC1100413637/FZN1022J/01/resources/zh-cn_topic_0000001497798293.html)要求按主机和存储接入情况准备资源。由此建立新主机验收表：每台应见哪些数据存储、实际见到哪些、路径是否冗余、容量与对象标识是否匹配。新增 CNA 在线不能代替这张表；若只在原主机正常，一迁移就可能暴露漏呈现。

快照删除通常意味着平台处理快照关系并可能合并数据，不是简单删除一份无关小文件。合并会消耗空间、吞吐与时间，不能在数据存储快满时未经评估批量操作。先确认快照依赖、剩余空间、备份任务和合并进度，选择小范围维护窗口。手工删除底层快照文件会破坏平台关系，应明确禁止。

一个常见证据陷阱是客户机删了很多文件，但数据存储占用没有立刻下降。客户机文件系统、虚拟磁盘分配方式、块回收能力、快照引用与存储后端都影响回收。先画被删除数据还被哪层引用，再查支持的回收路径，不把“没有马上降容量”当作磁盘损坏。回收也不是安全擦除，不能据此证明敏感数据无法恢复。

## 资产导出课堂：一份配置包为什么不等于全量台账

配置备份主要服务平台恢复，资产台账服务查询与关系分析，业务清单服务影响评估。三者内容可能重叠，但不能互相替代。你需要确认备份是否覆盖租户全部虚拟机、历史任务、网络关联和容量字段；缺少明确说明就不声称它是全量资产导出。

只读导出先写范围：哪个管理入口、哪个站点、当前角色、过滤条件、分页方式和采集时间。然后记录页面总数、导出行数、唯一对象数与重复数。看到控制台一百台而导出八十台，应先查权限、筛选、分页和采集中变化，不能用补空行让数量对齐。数量相等也不证明身份集合相同，还要比较对象 ID。

基础离线步骤建立三条虚拟机记录，各带 VM ID、CNA ID 和数据存储 ID，手工确认可反查关系。故障步骤重复一条并删另一条，行数仍为三，预测“只看总行数”会误通过。恢复步骤按 ID 去查缺失而不是直接去重后宣布成功；预期完整集合重新对齐。清理恢复合成表，不导出真实租户数据。

采集过程中虚拟机可能迁移。先查到旧宿主，后查到新宿主的网络状态，不一定说明数据库损坏，可能是不同时间切片。尽可能使用受支持的一致快照或标明各表时间与任务，不能把跨二十分钟的导出拼成某一秒的精确拓扑。AIOps 模型应把关系的新鲜度与来源作为证据，不只保存最后一个名字。

## 主备与权限课堂：能登录备用节点，不证明可安全提升它

管理主备关系关乎角色和数据同步，而不仅是两个地址能否打开。登录页面响应说明入口可达，仍需确认角色、复制状态、浮动地址归属和对端观察。一个节点管理网断开但仍在运行，另一边不能仅凭 ping 失败就强制接管。涉及隔离和数据权威的动作必须走该版本告警处理与原厂流程。

紧急账号是正常身份系统不可用时的受控恢复入口，不是每天共享使用的快捷方式。设计保管人、启用审批、最小操作范围、使用时限和事后轮换。审计要能回答实际使用者，不能把所有动作都归到一个公共用户名就结束。恢复日常身份服务后，复验普通角色权限与紧急入口回收。

证书轮换与时间同步也需要正反验证。新证书加载后用新连接验证信任链、名称和有效期；旧长连接可能继续工作，不能代表新登录成功。时间漂移既能影响证书判断，也能污染事故先后顺序。采集器记录时间偏差与数据延迟，不能把所有记录强行拼成一个没有误差的时间点。

## 两级实验验收：从合成报告到现场证据

基础报告使用仓库固定健康样例，仅证明指定规则未发现异常。报告里的版本是样例证据，不是当前环境探测结果；没有主机账号和网络连接，就不可能据此宣布某现场 VRM/CNA 版本已确认。先在报告标题写“合成”，再解释每个容量数字的单位和分母，让读者不会把演练截图当作生产截图。

故障层使用固定退化样例，不修改健康样例本身。观察备用管理节点离线、组件未完全就绪与容量越线，再分别写“冗余下降”“资源风险”“业务影响待验证”。恢复步骤重新运行健康样例并检查退出码零；对故障样例，退出码二才是预期检测成功，不要把它当作工具崩溃重试十次。

输出报告前确认目标文件不存在，复跑时改用新的独立文件名或先人工归档本轮旧报告，防止覆盖别人的证据。清理仅删除自己记录下来的输出文件，保留原始 fixtures 与脚本。完整回收还包括不再需要的测试账号和临时访问授权；本地合成实验没有创建这些平台资源，不写虚构清理结果。

生产设计题的最终答案应落到一张验收表：平台控制面、虚拟机运行、网络可达、存储可用、业务事务、数据恢复与剩余冗余分别有证据。某一项未知就标记未知，不能用其他绿色状态覆盖。当前本篇没有运行 FusionCompute 或操作虚拟机，新增迁移、资源放置与台账课均是可复算模型，真实验证还需授权环境。

### 运维交接练习：谁来确认应用已经恢复

准备一张四阶段时序卡：宿主失联、虚拟机重新启动、数据库完成恢复、业务交易成功。基础步骤分别记录平台、客户机、数据库和应用证据，恢复耗时从用户受损开始计算。故障步骤把第三阶段改为日志重放失败，预期即使虚拟机运行也不能结束事故。恢复步骤由数据库负责人处理一致性问题后重新验证交易，清理只还原合成卡，不重启真实数据库。

恢复后还要检查是否存在未回收临时措施，例如关闭的调度规则、临时放开的网络、暂停的备份和被静默的告警。每项都有原配置、批准人、到期与回收证据，不能把事故缓解措施自动变成长期架构。与原厂交接时附上这些变更，可避免后续分析把人为临时状态误认为产品默认状态。

最后让另一位同学仅凭版本账、对象关系和时序卡复述事故。如果对方必须询问“哪台主机、哪个卷、现在谁还在写”，说明证据仍不够完整。补齐这些关系比再贴一张总览截图更有价值；真实名称与地址可以脱敏，但替代编号必须保持一致，否则关联链会断开。
