## 官方知识地图

```text
硬件与 DCOS（数据中心操作系统）
  -> 服务器、BMC（带外控制器）、PXE（网络引导）/装机、固件、兼容性、硬件监控

计算
  -> CVM（云主机）、镜像、规格、宿主、调度、配额、生命周期

网络
  -> VPC（逻辑私有网络）、子网、路由、ENI（弹性网卡）、安全组、ACL（访问控制列表）
  -> EIP（弹性公网地址）/NAT（地址转换）/专线（按 BOM）、CLB（负载均衡）

存储
  -> CBS（云硬盘）创建、挂载、快照、性能、容量和后端故障域

治理
  -> region/AZ（地域/可用区）、tenant（租户）、CAM（访问管理）
  -> API（程序接口）、task（任务）、audit（审计）、Terraform（声明式资源管理工具）
```

## 场景开场

控制台显示 CVM 创建失败，错误文字只有“内部错误”。真正链路至少经过身份、配额、镜像、计算调度、网络端口和云盘。若只重试，可能创建重复卷、残留端口和更多任务。

## 一句话人话版

TCE IaaS 把机房的服务器、网络和存储包装成可按租户通过 API 申请的 CVM、VPC、CLB 和云盘资源。

## 小白问题

- CVM 是不是一台物理服务器？不是，它通常是运行在资源池上的云虚拟机。
- VPC 是 VLAN 吗？不是，VPC 是租户逻辑网络，底层可能结合多种虚拟与物理网络技术。
- 安全组和防火墙一样吗？安全组常绑定实例/网卡进行状态化访问控制，边界防火墙职责更广；现场实现按产品确认。
- 云盘快照是不是备份？快照是恢复手段之一，不自动等于跨故障域、长期、可验证备份。

## IaaS 对象模型

```text
Region（地域）
  -> VPC（逻辑私有网络，通常是地域级）
     -> Subnet（子网，关联某个 AZ 可用区）
        -> ENI（弹性网卡）/ private IP（私有地址）
           -> CVM（云主机）
              -> CBS volumes（云硬盘，检查可用区约束）
     -> CLB frontend/backend（负载均衡前端入口/后端目标）
```

这是逻辑资源关系图，不是物理布线图。VPC 通常可覆盖同地域多个可用区，子网才关联具体可用区；现场 TCE 产品范围以对应版本文档为准。控制对象靠 ID 关联，不用名称猜关系。CMDB（配置管理数据库，即资源与业务关系账本）还应映射业务、负责人、环境、数据等级和变更单。

## DCOS 与硬件生命周期

公开兼容性指南出现 Data Center Operating System（DCOS）自动装机和硬件监控能力。可以把这一层理解为“把裸金属服务器纳入云底座的工厂线”：

```text
BMC/带外
  -> 硬件发现与兼容性
  -> PXE/DHCP/DNS/镜像
  -> RAID/HBA/NIC/固件
  -> OS/云底座安装
  -> 健康检查
  -> 加入资源池
```

### 自动装机失败怎么查

1. BMC、电源、管理网和账号权限。
2. PXE、DHCP、TFTP/HTTP、DNS 和路由。
3. 服务器/CPU/NIC/HBA/RAID 与目标 TCE 兼容矩阵。
4. 固件、驱动、磁盘布局和安全启动。
5. 任务 ID、失败阶段和目标版本文档。

不要为“让它装上”关闭所有安全、刷未知固件或跳过兼容检查。固件/RAID 变更需要维护窗和原厂边界。

## CVM 五件套

是什么：Cloud Virtual Machine，按规格、镜像、网络和磁盘创建的云主机。

为什么需要：把物理资源池按租户按需交付，支持 API、配额、镜像和生命周期。

怎么工作：控制面校验请求并调度宿主，连接虚拟网络与云盘，再启动客户机。

怎么观察：实例状态、task/request ID、镜像、规格、VPC、ENI、CBS、宿主故障域、客户机控制台和监控。

坏了怎么查：先定位创建/启动/网络/磁盘/客户机哪一阶段，再检查依赖，不重复创建。

### 状态不能只看 Running

```text
控制面实例状态：Running
客户机 OS：可能启动失败
网络：可能无路由/策略阻断
云盘：可能文件系统未挂载
应用：可能未监听或依赖失败
```

最终验收用业务探针。

## 镜像与初始化

镜像不仅是一个磁盘文件，还包含 OS、驱动、cloud-init/初始化代理、分区、安全基线和兼容性。

镜像治理：

- 来源、校验和、负责人、版本和漏洞扫描。
- Guest OS 与 TCE/CVM 驱动兼容。
- 不含固定密码、SSH 私钥、Token、机器身份和真实数据。
- 首次启动脚本幂等、有超时、日志和失败标记。
- 旧镜像下线前确认仍有重建/回滚需求。

“实例已创建但无法登录”要查启动日志、网卡/驱动、初始化、SSH/RDP、密码/密钥和安全组，不能先重装。

## 计算调度、配额和容量

调度要同时满足 AZ、规格、资源、亲和/反亲和、硬件特性和平台策略。报容量不足不一定是全平台 CPU 不够，可能是目标 AZ、特定型号、连续大页、GPU/RDMA 或故障冗余不足。

### 容量公式心智模型

```text
可承诺容量
= 物理可用
- 控制面与系统预留
- N+1/故障预留
- 维护预留
- 已承诺资源
- 增长与突发安全余量
```

超分比必须结合工作负载峰值和 SLO，不按一个固定行业数字照抄。

## VPC、子网和路由

### VPC 五件套

是什么：租户隔离的逻辑私有网络。

为什么：让业务自定义地址、子网、路由和安全边界，不直接暴露物理网络细节。

怎么工作：控制面创建逻辑对象，数据面通过虚拟交换/路由、隧道或其他网络能力转发。

怎么用：规划不重叠 CIDR、AZ 子网、路由、DNS、出口和互联。

坏了怎么查：从 ENI/IP、子网、路由、安全组、ACL、NAT/专线、物理底座逐层检查。

### CIDR 规划

地址规划要考虑：当前规模、增长、容器 Pod/Service 网段、数据库、管理、跨 VPC/专线和并购互联。网段重叠会让路由与混合云复杂化，不能事后只靠 NAT 全解决。

## 安全组与 ACL

安全规则最小化：源/目标、协议、端口和方向明确。不要用 `0.0.0.0/0` 临时放通后忘记回收。

排障：

```text
应用是否监听
  -> 客户机防火墙
  -> 安全组
  -> 子网 ACL
  -> 路由/NAT/专线
  -> 对端返回路径
```

状态化/无状态、规则优先级和默认行为按现场版本确认。

## CLB 完整路径

```text
客户端 DNS
  -> CLB VIP/监听器
  -> 证书与协议（若终止 TLS）
  -> 转发规则
  -> 健康检查
  -> 后端 CVM/TKE 节点与端口
  -> 应用
```

### 后端不健康

检查健康路径、Host、协议、端口、预期状态码、超时、阈值、安全策略和应用日志。把健康检查关闭只能隐藏问题，还会把流量发给坏实例。

### 会话与连接容量

关注新建连接、并发、带宽、后端连接、超时、长连接、四层/七层和客户端 IP 传递。容量设计以目标版本规格与压测为准。

## CBS 云硬盘完整路径

```text
应用
  -> 文件系统/卷管理
  -> 客户机块设备
  -> CVM 虚拟 I/O
  -> CBS 接入/网络
  -> 后端存储节点/磁盘
```

### 生命周期

创建 -> 可用 -> 挂载 -> 客户机识别 -> 分区/文件系统 -> 挂载点 -> 使用 -> 卸载 -> 解挂载 -> 删除。

控制面“已挂载”不证明客户机已 mount；强制解挂载可能损坏数据。先停止写入、卸载文件系统并核对设备身份。

### 性能

IOPS、吞吐、时延和队列要一起看。小随机 I/O、顺序大块、读写比例和同步写对性能影响不同。还要检查实例规格、文件系统、客户机队列、网络和后端重建。

### 快照与备份

快照前确认应用一致性，数据库可能需要冻结/flush 或使用专用备份。恢复必须定期演练；有快照记录不等于可恢复。

## CVM 创建故障证据链

1. request ID/task ID/resource ID。
2. 身份、租户、配额和策略。
3. Region/AZ、规格和可用容量。
4. 镜像状态与兼容。
5. VPC/subnet/ENI/安全组。
6. CBS 创建/挂载。
7. 宿主与硬件告警。
8. 客户机启动与初始化。
9. 同时间审计和变更。

每完成一层都记录正常/异常证据，避免同时改多处。

## API 与异步任务

云 API 常返回请求已接受，后台任务继续执行。客户端要保存 request ID，轮询状态有退避、超时和终止状态。

写操作需要客户端 token/幂等策略、服务端去重和结果查询。客户端超时后先查任务，不生成新意图重复创建。

API 凭据：最小权限、短期优先、密钥轮换、来源限制、审计和安全注入。签名失败先查时间、endpoint、region、凭据和规范化请求，不打印 SecretKey。

## Terraform 生产边界

```text
代码评审
  -> init/provider lock（初始化并锁定服务商插件版本）
  -> validate（校验配置语法与内部一致性）
  -> plan（生成预期变更计划）
  -> 审批
  -> apply（执行批准后的变更计划）
  -> TCE task/request（平台侧任务与请求记录）
  -> 资源验证
  -> state 安全保存
```

高风险变更查看 replace/destroy；关键数据库、云盘、网络资源使用保护策略并人工复核。drift 先判断是紧急操作、控制台变更还是 Provider 读写差异，不直接 apply 覆盖。

## 高可用设计

- 控制面按产品支持部署冗余。
- 工作负载跨宿主和故障域，反亲和不等于跨 AZ。
- CLB 后端跨故障域并有应用健康检查。
- 数据盘/数据库保护按 RPO/RTO 设计。
- 单 AZ 故障后剩余容量足够。
- DNS、专线、出口和管理面也有冗余。

平台 HA 不代替应用无状态/会话、数据库复制和依赖恢复。

## 安全与审计

每个 API/控制台动作关联操作者、角色、源、request ID、资源 ID、时间和结果。机器账号和人员账号分开。高危网络、云盘删除、镜像共享和规格变更进入审批。

日志脱敏，不记录凭据、完整 userdata、云初始化秘密和业务数据。镜像与 Terraform state 按敏感资产保护。

## 故障实验：安全组或健康路径错误

仅在授权测试租户：

1. 创建测试 VPC/subnet/security group/CVM，部署无数据 HTTP 服务。
2. 通过 CLB 使用 `/healthz` 检查。
3. 故意把测试安全组后端端口改错或健康路径改为 `/wrong`。
4. 记录 CLB 后端不健康、CVM 仍运行和应用本地正常。
5. 用审批过的原配置回滚。
6. 验证 CLB、端到端请求和审计记录。
7. 删除测试资源前核对资源 ID，保留脱敏证据。

不能在生产注入，也不能用全放通作为修复。

## 高频排障

| 现象 | 先看 | 处理主线 |
|---|---|---|
| CVM Creating/Error | task、配额、AZ、镜像、VPC、CBS | 找停点和共同故障域 |
| 登录失败 | console、OS、初始化、网络、安全组 | 区分客户机与平台 |
| 业务超时 | DNS、CLB、路由、规则、应用、依赖 | 端到端逐跳 |
| CLB 不健康 | listener/规则/探针/后端日志 | 修探针或应用 |
| CBS 挂载卡住 | 卷状态、attachment、客户机、后端 | 不强制破坏状态 |
| I/O 延迟 | 文件系统、队列、实例、CBS、后端 | 同时间趋势和任务 |
| Terraform 漂移 | state、审计、控制台/紧急变更 | 先确认权威状态 |

## 生产设计题

设计一个三层业务：CLB -> 多 AZ CVM/TKE -> TDSQL，静态对象入 COS，数据盘用 CBS。说明 CIDR、路由、安全组、负载健康、故障域、容量、备份、审计、Terraform state、升级与业务探针。单 AZ 失败后必须计算剩余连接和容量。

## 事故题

“CVM 创建失败率升高，现有 CVM 正常。”这更像控制面/容量/新建依赖，而非全数据面故障。比较新建任务的 AZ/规格/镜像/VPC/CBS，查看最近配额和变更，保护现有业务，不贸然重启数据面。

## 面试回答

### 30 秒

TCE IaaS 把硬件通过 DCOS 和云控制面变成 CVM、VPC、CLB、CBS 等租户资源。创建 CVM 会经过认证授权、配额、AZ 调度、镜像、网络和云盘。排障时我拿 request/task/resource ID 定位停点，再查共同故障域和审计，不把控制台“内部错误”当根因。

### 连续追问

1. **Running 为何业务不通？** 客户机、网络、CLB、应用和依赖仍需验证。
2. **容量不足只看 CPU？** 不，可能是单 AZ、规格、内存、GPU/RDMA、存储或故障余量。
3. **安全组故障怎么查？** 监听、客户机防火墙、安全组、ACL、路由和返回路径。
4. **CBS 快照是备份吗？** 不自动等于独立、跨域、应用一致且已验证恢复。
5. **Terraform apply 成功就结束？** 还要跟 TCE task、资源状态、业务和 state。

## 老师带你做一张真正能用的 IaaS 申请单

先把产品缩写放下。业务同事说“给我两台服务器”，你不要马上开始创建。老师会带你追问：运行什么服务，每秒多少请求，附件放哪里，哪些人能访问，停几分钟能接受，数据最多能丢多久？这些答案决定云资源之间的关系。

以“告警工单服务”为例：浏览器访问统一域名，CLB 把流量发给两台 CVM，应用把工单保存到数据库，把截图保存到对象存储。两台 CVM 应尽量落在不同故障域，应用会话不能只放在其中一台的内存里。否则负载均衡把下一次请求发到另一台时，用户就像重新登录了一次。

先画访问关系，再写资源清单。前端需要访问入口的 HTTPS 端口，CLB 需要访问应用端口，应用需要访问数据库和对象存储，运维机需要通过受控管理入口访问服务器。每条箭头同时填写来源、目标、协议、端口、负责人和验证方法，这就是安全组设计的起点。

```text
浏览器 -> DNS（把域名查成地址）-> CLB（分发请求）
                                  -> CVM A（应用实例）
                                  -> CVM B（应用实例）
应用实例 -> 数据库（工单记录）
应用实例 -> 对象存储（截图文件）
审计与监控 -> 关联资源 ID、变更和业务探针
```

请注意，CLB 选择的是可用后端，它不会替应用复制内存会话、补偿失败事务或检查截图内容。资源层和业务层都要各自交作业。测试时至少包含登录、查询、提交一条可回收工单和读取测试附件，不能只访问首页返回 200。

### 把硬件缩写翻译成你能观察的东西

BMC 是服务器的带外管理控制器，主操作系统坏了也可能用它看电源和硬件状态。PXE 是从网络引导装机的方式；DHCP 分配网络启动参数；DNS 解析名字；TFTP/HTTP 运送启动或镜像文件。装机任务停住，先找停在“拿不到地址”“拿不到启动文件”还是“系统装完不能纳管”，它们属于不同环节。

RAID 是多个磁盘的组合与冗余方式；HBA 是连接存储的主机适配器；NIC 是网卡；Firmware 是设备固件。兼容性矩阵不是一张可忽略的采购清单，驱动、固件和设备型号组合会决定网络或磁盘在特定负载下是否稳定。你不需要第一天背所有型号，但应学会记录“实际型号、当前版本、目标版本要求、来源文档”四列。

GPU 是图形/并行计算处理器，RDMA 是让网络数据直接访问内存的传输机制。普通 CVM 能创建不证明 GPU/RDMA 规格也有容量。专用硬件、驱动、网络和调度约束必须一起匹配，不适合套一个“CPU 剩多少”的公式。

### 配额、余量和性能是三本不同的账

配额是允许一个租户最多申请多少，余量是目标资源池还能承诺多少，性能是运行后能否在目标时延内完成请求。租户配额不足时，全机房再空也可能创建失败；配额很多时，指定可用区也可能已经没有合适规格。

假设你有 3 台宿主，每台稳定承载 100 单位业务负载，平时总峰值是 210。平均利用率 70% 看起来不高，但坏一台只剩 200，就无法承载 210。N+1 的意思是按失去一个故障单元后仍满足业务来规划，不能把“有三台”直接写成“有容灾”。

CPU 超分像给多名学生安排非同时使用的自习座位，提高利用率的前提是他们不会同时到齐。数据库、批处理和模型推理的峰值行为不同，超分策略也不同。需要观察宿主争抢、客户机等待、内存换页、存储时延及业务 P95/P99（95%/99% 请求不超过的时延），再讨论提高比例。

### 云盘为什么有三个“容量变大了”

第一层是云平台认为卷容量已扩大；第二层是客户机重新识别到更大的块设备；第三层是分区、逻辑卷和文件系统把新增空间用起来。平台完成第一层后，`df` 仍显示原容量并不必然是云盘扩容失败。

Linux 客户机只读观察可使用 `lsblk -f` 看设备、文件系统和挂载点，`df -hT` 看已挂载文件系统容量，`findmnt` 看实际挂载关系。正常要能把云盘 ID、稳定设备标识和业务目录关联起来。不要拿 `/dev/sdb` 这种可能变化的名称作为唯一身份，也不要为了试试而执行格式化。

挂载、扩容、快照和恢复的具体写操作取决于客户机系统、文件系统和 TCE 版本。先按本文把层次分清，再跟对应文档操作。需要数据库一致性时，让数据库备份流程参与，文件系统快照本身不懂一笔业务事务是否完成。

## 本地课堂实验：一条错误健康路径怎样制造“服务器都正常，入口却失败”

这个实验只运行在自己的电脑，不需要 TCE 账号。它模拟 HTTP 健康检查语义，不模拟 CLB 内部实现。前置条件是安装 Python 3，终端执行 `python --version` 能显示版本。

在一个新建的空学习目录创建 `healthz` 文本文件，内容是 `ok`，然后打开第一个终端执行：

```powershell
python -m http.server 18080 --bind 127.0.0.1 # 只对本机开放当前目录
```

窗口持续运行是正常的，不要等待它自动结束。在第二个终端执行：

```powershell
curl.exe -s -o NUL -w '%{http_code}' http://127.0.0.1:18080/healthz
curl.exe -s -o NUL -w '%{http_code}' http://127.0.0.1:18080/wrong
curl.exe -s -o NUL -w '%{http_code}' http://127.0.0.1:18080/healthz
```

预期依次是 `200`、`404`、`200`。`-s` 减少输出，`-o NUL` 不打印响应正文，`-w` 显示 HTTP 状态码；请求没有改变服务器状态。故障注入只是第二次把检查路径写错，恢复就是重新使用存在的路径。

现在你能解释了：同一台机器、同一个进程、同一个端口都正常，健康检查仍可能因为路径错误而失败。真实 CLB 还要检查 Host 请求头、协议、端口、预期状态码、超时和连续失败阈值，所以不要把这三次请求误写成“已经验证 TCE CLB”。

如果三个结果全是 `000` 或连接失败，先看第一窗口是否仍在运行、端口有没有被占用、本机地址是否写成 `127.0.0.1`。如果第一个也是 404，检查 `healthz` 是否存在于启动服务器时所在的目录，Windows 是否把文件名保存成了 `healthz.txt`。清理时在第一窗口按 Ctrl+C 停止服务，再请求一次应连接失败；只回收自己创建的测试文件。

## 三分钟汇报练习：业务创建失败，你怎样带着大家查

先说影响：“现有工单查询正常，新建 CVM 在某个可用区失败。”再说已知事实：“失败集中在同一镜像和卷类型，任务停在系统盘准备阶段，其他镜像对照创建成功。”然后提出可证伪的假设：“可能是镜像可用性、镜像到存储路径或该后端容量问题。”每条假设都指定下一份证据，而不是让计算、网络、存储团队各自猜。

把请求受理、任务结束、资源状态、客户机启动、业务验收列成时间线。接口成功只能证明这一阶段成功，Terraform 返回也要结合 Provider 的等待语义和实际业务验证。恢复时先停止新的失败申请，限制重试产生的残留；修复依赖后在测试租户验证一台，再放开受影响范围。

面试官追问“如果必须紧急恢复呢”，你应说明用已验证镜像或其他可用资源池替代是否符合网络、数据位置和授权条件，哪些资源不能跨区直接移动，谁批准临时方案，以及如何回到正常设计。会指出方案的约束，比说“直接迁过去”更接近实际平台工程。

最终的 GitHub 证据应该让别人看得见推理过程：一张资源图、一份假设与证据表、健康检查的三次结果、故障前后容量计算和清理记录。实际客户内网地址、密钥、账号与业务数据用合成值替换；示例值不是现场资产。

## 进阶带练：把“一次创建”拆成能补偿的状态机

### 请求超时不等于创建失败

老师先给你一条消息：“页面转了三十秒，报请求超时。”它只说明调用方在等待期限内没有取得确定结果。请求可能没到平台，可能已受理但任务还在排队，也可能已经创建成功，只是响应在返回途中丢失。三个情况的下一步不同，所以先保存 request ID（本次请求编号）、task ID（后台任务编号）和可能已产生的资源 ID，再查状态。不要看到超时就换一个客户端去重复创建。

幂等是“同一个业务意图多次提交，不额外制造副作用”，不是“每个请求都必然只执行一次”。如果对应 TCE 现场 API 支持客户端幂等标识，重试应复用同一个意图标识，不能每次生成新值；若不支持，则先查询任务和资源清单，并在自动化层记录意图与资源关系。具体参数名、有效期和支持操作以现场版本 API 为准，这里不把某个公有云接口字段照搬成所有 TCE 的能力。

再想一步：计算创建失败后，已经分配的网卡、IP 或系统盘怎么办？一个后台任务可能跨越多个系统，每步分别成功，并非一个数据库事务包住全部动作。补偿流程必须知道哪些资源属于本任务、是否被其他对象引用、是否带业务数据。网络创建失败时不能直接删除同名所有卷，重试创建也不应接管其他人的同名实例。名称便于人看，资源 ID 和关联 ID 才用于精确操作。

### 本地推理实验：识别未结束的请求和孤立资源

前提是 PowerShell，无需管理员、云账号或网络。下面全部是内存中的合成对象，不调用 TCE。先执行基线：

```powershell
$createLabTasks = @(
  [pscustomobject]@{Intent='order-01'; Task='task-a'; State='Succeeded'; VM='vm-a'},
  [pscustomobject]@{Intent='order-02'; Task='task-b'; State='Running'; VM=''}
)
$createLabDisks = @(
  [pscustomobject]@{Disk='disk-a'; Intent='order-01'; VM='vm-a'},
  [pscustomobject]@{Disk='disk-b'; Intent='order-02'; VM=''}
)
$createLabTasks | Format-Table
$createLabDisks | Where-Object { -not $_.VM } | Format-Table
```

预期出现一项未挂载的 `disk-b`。请先作答：它能删吗？不能据此决定，因为同一个意图的 `task-b` 仍在运行，系统盘可能正在准备。未挂载只是当前关系，不是垃圾分类结论。你需要等待任务终态，并确认平台是否还会接着引用它。

注入一个“调用方超时后另起新意图”的错误，再查询：

```powershell
$createLabTasks += [pscustomobject]@{Intent='order-02-retry'; Task='task-c'; State='Succeeded'; VM='vm-c'}
$createLabTasks[1].State = 'Succeeded'
$createLabTasks[1].VM = 'vm-b'
$createLabDisks[1].VM = 'vm-b'
$createLabTasks | Format-Table
```

预期出现 `vm-b` 与 `vm-c` 两个完成结果，虽然业务最初只想创建一台。这不是 TCE 自动去重能力的测试，而是展示调用方丢失意图关系会发生什么。恢复合成数据时，执行 `$createLabTasks = $createLabTasks | Where-Object Task -ne 'task-c'`，再次查询应只保留两条原始任务；真实云上不能照这个筛选直接删资源，要由负责人确认哪台已经接入流量、持有数据和计费责任。

清理执行 `Remove-Variable createLabTasks,createLabDisks`，只清理本实验内存变量。若输出没有出现预期行，先确认按顺序执行、变量名没有拼错，以及你没有在新终端丢失前一步状态。记录“期望一台、实际两台、缺失的是意图关联”的解释，比仅截图表格更有学习价值。

## 网络专题课堂：请求进得来，不代表响应回得去

**路由是什么？** 它决定目的地址属于哪个下一跳；像分拣规则，先问地址该往哪里送。**安全组是什么？** 它决定某方向某类通信可不可以发生。**NAT 是什么？** 地址转换改变报文中源或目标地址，便于私网出站或入口映射。这三件事各自不同：路由正确可以被安全规则拒绝，全放通也无法修复不存在的路由。

我们沿一条请求来查：客户端解析域名后连接 CLB；CLB 按监听器与转发规则选后端；后端应用完成处理，再沿有效返回路径送回。具体 CLB 模式是否保留客户端源地址、探测从何处发起，必须查现场配置和产品文档，不能凭“CLB 一定如何”编规则。只给业务来源放行，却遗漏合法健康探测来源，会让本来可用的应用被判为不健康；反过来只允许探针也不等于业务来源可访问。

NAT 还带来容量。很多短连接通过同一个出口访问相同目标时，源端口和连接跟踪表都是有限资源；总带宽未满，不代表还能无限新建连接。证据包括连接建立失败率、并发连接、端口使用、会话超时和目的分布。修复需要连接复用、合理超时、分散出口或扩容，而不是随手缩短所有会话时限。更改出口地址还可能影响下游白名单，必须通知依赖方并准备回退。

看到“ping 通但网页失败”，请按协议层分开解释。ICMP 回应只能证明某类网络交互成功，不证明 TCP 监听、TLS 证书、HTTP 路径或应用权限。看到“内网地址访问成功，域名失败”，再分 DNS 返回值、CLB 路径和 Host 头。带着成功与失败的同时间对照，会比把所有安全规则截图发群更快定位。

## 存储与镜像专题：云主机启动依赖一张什么样的盘

镜像不只是“压缩后的操作系统”。它还承载启动方式、驱动、分区布局、初始化代理和兼容性条件。新镜像在某规格启动失败，要检查 BIOS/UEFI 启动模式、磁盘与网卡驱动、架构和控制台启动日志；不能因为同样写着 Linux 就认定能在所有资源池运行。制作模板时移除克隆后不应重复的身份与临时凭据，并按操作系统支持流程处理机器标识，不盲删系统文件。

cloud-init 是常见云初始化机制，可在首次启动配置账号、网络或启动脚本；是否使用、传入方式与执行阶段以现场镜像为准。实例 Running 而初始化还没完成时，SSH 或应用尚未就绪可能只是另一阶段。初始化脚本要有日志、可重入设计和失败退出，不能把长时间安装依赖塞进没有超时的启动循环。脚本含秘密时，控制台、元数据服务、镜像和日志的读取权限也成为安全边界。

临时盘和持久盘必须按生命周期分类。停机、重建、迁移或释放实例对本地盘和云盘的影响可能不同，重要数据不能靠“上次重启还在”证明可靠。把卷删除策略、快照保留、加密密钥和恢复演练写入申请单。加密盘备份只保存密文而丢失密钥授权，也不能恢复业务。盘恢复出来后，数据库恢复、文件系统检查与应用一致性仍是独立验收项。

## 设计题完整作答：怎样承诺单可用区故障仍能服务

先把故障目标写成可验收句子：某一可用区不可用时，已有工单可查询，新工单在约定恢复时间内继续创建，最多丢失多少已确认数据另行明确。接着检查现场 BOM 和 License 确有多可用区及所需数据产品；只有一个实际故障域时，不把两个逻辑标签叫成双区容灾。

应用跨区部署，CLB 与 DNS 故障切换经过验证；数据库复制方式、仲裁和隔离机制另行设计，避免两个分区同时自认主节点。附件和数据库记录要能对应恢复点，不能出现记录恢复到今天、附件只恢复到昨天而毫无标识。若数据库不支持业务要求的跨区同步承诺，应明确降低 RPO 目标、增加机制或修改方案，而不是让平台 HA 掩盖这一缺口。

容量按失去一整个区后的资源来算，除了 CPU、内存，还包括目标区 IP、存储吞吐、数据库连接、CLB 后端上限和出口容量。恢复过程会产生镜像拉取、卷恢复和集中登录等突发负载，也要纳入压测。演练先在测试租户使用受控流量和合成数据，从冻结新变更、故障判断、切换到恢复验证逐步执行；回切必须确认数据方向与主从角色，避免把已经更新的副本覆盖成旧状态。

面试追问“平台提供高可用还要你做什么”，可以这样答：平台负责它声明的资源故障恢复边界，我负责验证业务状态、依赖、剩余容量和恢复时间的组合结果。证据不是组件数量，而是明确的故障条件、观测结果、数据核验与受控回切记录。

## 地址规划带练：网段包含、重叠与可用地址是三道题

CIDR 用网络前缀描述一段地址。一个网段是不是位于某 VPC 内，两个网段有没有交集，以及能分给实例多少地址，是不同问题。即使地址位于同一大范围内，两个子网相互重叠也会产生路由歧义；把地址换个名称并不能消除交集。跨专线还要比较对端、容器和灾备网络，不能只检查当前一张申请单。

下面使用 Python 标准库做纯离线检查，不连接云平台，不创建文件。语法来自 [ipaddress 官方参考](https://docs.python.org/3/library/ipaddress.html)。在 Python 终端依次执行，变量仅保存在当前进程内：

```python
from ipaddress import ip_network

vpc = ip_network("10.44.0.0/16")
subnet_a = ip_network("10.44.1.0/24")
subnet_b = ip_network("10.44.2.0/24")
assert subnet_a.subnet_of(vpc) and subnet_b.subnet_of(vpc)
assert not subnet_a.overlaps(subnet_b)
print("NETWORK_PLAN=OK")
```

基础预期输出 `NETWORK_PLAN=OK`。`subnet_of` 判断完整包含，`overlaps` 判断是否有任何交集，`assert` 要求条件成立；不是只看网段字符串不同。故障步骤继续执行下段，把第二个子网改成第一个的一部分：

```python
subnet_b = ip_network("10.44.1.128/25")
print("OVERLAP=", subnet_a.overlaps(subnet_b))
subnet_b = ip_network("10.44.2.0/24")
assert not subnet_a.overlaps(subnet_b)
del vpc, subnet_a, subnet_b
```

预期先输出 `OVERLAP= True`，随后恢复检查通过，最后清理三份内存对象。若网段有主机位导致异常，先检查网络地址是否正确，不随手关闭严格校验把错误输入掩盖。若版本没有对应方法，确认 Python 版本并阅读同版本文档；本课不安装任何依赖。

这个实验不计算 TCE 可分配地址数。平台可能保留部分地址，网卡、入口、容器和故障恢复也会消耗地址，应按现场规则单独扣除。一个前缀的数学地址总量不等于租户可用量，控制台剩余量也不等于预留故障容量之后的可承诺量。

## 声明式交付课堂：计划不是授权，状态文件不是无害缓存

Terraform 的配置表达期望，状态文件记录它管理的资源与对象关系，计划展示将要执行的变化。三者职责不同。计划成功只表示工具生成了方案，不表示方案安全、已有审批或业务一定正常；`apply` 成功还要根据 Provider 等待语义核对云任务与实际资源。批准人应看到创建、原地更新、替换和删除的确切目标。

保存的计划可能包含敏感数据，状态也可能保留密码、密钥或其他属性，即使终端展示时做了隐藏。HashiCorp 的[敏感状态说明](https://developer.hashicorp.com/terraform/language/state/sensitive-data)强调保管边界，因此不要把 plan、state 或完整机器可读输出当作普通学习日志提交。公开证据只保留人工核对的脱敏变更摘要，远端存储、加密、访问控制和审计另行配置。

从计划到执行之间，其他管理员可能做了紧急修复，配额和资源状态也可能改变。旧计划不是无限期有效的操作许可，应明确批准时间窗、配置提交、Provider 版本和目标租户。执行前出现新变更就重新评估，不因为昨天审批过类似资源就覆盖今天的紧急配置。按[官方 plan 命令说明](https://developer.hashicorp.com/terraform/cli/commands/plan)理解计划用途，再结合现场变更流程。

状态漂移也不只有一种处理。控制台临时扩大安全范围可能需要撤销；事故中切换到正确云盘可能应先更新声明；Provider 读取差异可能需要验证兼容性。先用审计判断变化来源和当前业务权威，再决定让配置追上现实还是让现实回到配置。直接执行自动修复会把合理的紧急措施冲掉。

纸面练习准备“配置允许两个后端、状态记两个、现场已有第三个应急后端”三份记录。基础步骤比较差异，故障步骤把第三个识别为应急容量却仍计划删除，学生应暂停执行并查工单。恢复步骤由负责人决定纳入或排空回收，再生成新计划。清理删除虚构计划，不连接 Terraform 后端，更不运行真实 `apply`。

## 资源退场课堂：删除实例不等于整条业务关系消失

应用下线先停止新请求与任务，再确认长连接和队列处理，随后检查数据库、附件与备份保留，最后回收不再需要的云资源。CVM、云盘、弹性网卡、地址、CLB 后端、快照和权限未必同生命周期；具体随交付产品和删除策略变化。把所有同名资源一起删除不是可靠清理。

资源编号与所有权标签共同帮助确认范围，但标签本身可被修改，不能作为唯一授权。清理单写创建意图、实际编号、引用者、数据级别、保留期限和批准人。某个卷当前未挂载，可能用于灾备或等待重建；某个入口没有后端，可能是灰度切换暂时排空。闲置状态不自动等于可删除。

两级纸面模拟先列一台应用实例、一块数据盘、一份快照和一个共享安全组，标明独占与共享。故障步骤让自动清理把共享安全组也选中，预测其他实例会受到影响。恢复步骤从候选集合移除共享对象，并检查数据盘保留要求；验证每个删除候选均无未授权依赖。清理只恢复列表，不删除平台资源。

下线后的安全验收还包括撤销机器凭据、去掉白名单、关闭采集目标与更新 CMDB。凭据留存会使已经不存在的服务仍能访问云 API；监控目标未回收会不断产生噪声。反过来，审计与事故证据不能因业务删除而随意销毁，应按规定保留。资源、身份和证据分别有退出流程。

## 性能与故障恢复课堂：控制面吞吐也是有限资源

批量创建几百台 CVM，会同时使用调度、镜像分发、云盘创建、网卡分配和状态查询能力。即使物理容量充足，控制面任务队列也可能增长。先看请求到受理、受理到调度、资源准备到启动各阶段耗时，区分容量不足与供应速度不足。把调用超时调得无限长，只会隐藏等待，不会增加交付能力。

恢复尖峰需要有界并发、退避和队列。调用者在失败时立即全部重试，会让控制面承受更多重复查询和申请；退避应有总等待上限与终态判断。排队期间对用户明确状态和请求编号，不显示一模一样的“内部错误”迫使用户重复点击。运维自动化记录完成率和排队时间分布，而非只看每秒请求数。

假设平台安全供应速度每分钟二十台，而故障恢复需要一百台，即使其他环节无开销也至少有五分钟的供应窗口。业务 RTO 若只有两分钟，不能靠“平台支持自动创建”兑现，需要提前准备已就绪容量或调整方案。真实速度还取决于镜像、卷与网络，因此这只是教学下界，不是 TCE 性能承诺。

本轮新增实验只执行数学和内存对象层逻辑，不启动 HTTP 服务、不创建云主机、不探测生产网络。前面的本地健康检查实验若由读者自行执行，应使用独立空目录、确认端口未被占用，并在完成后停止自己启动的进程；不能结束其他占用同端口的程序。学习记录分清计划、静态检查、离线执行与真实平台验收，避免把不同证据层混为一谈。

## 网络和资源变更的停止条件实战题

题目是给一个正在使用专线的租户扩大地址空间。第一反应不应是找到修改网段按钮，而是盘点当前路由、对端宣告、地址重叠、安全规则、DNS 与依赖白名单。即使平台允许添加地址，合作方仍可能没有到新网段的返回路由。一个成功创建的子网，只证明控制面接收了声明，不证明端到端业务可达。

基础纸面步骤选择不与当前网络重叠的新前缀，在两端路由表中写明下一跳，定义一条可回收测试请求。故障步骤遗漏对端返回路由，预测源端能发出但无法完成往返。恢复步骤补充经批准的准确路由并检查是否影响更具体前缀，不用默认路由或全放通掩盖问题。清理只还原模拟路由，不修改实际专线。

停止条件可以是发现未知重叠、关键流量走了非预期下一跳、现有连接失败增加或对端无法确认变更。此时停止后续批次并保持旧路径。回退不仅是删除新网段：已使用新地址的实例、DNS 缓存和外部白名单都要按顺序恢复，否则平台回退成功，业务仍会访问不存在的地址。

另一个设计追问是资源规格变更。增加 vCPU 或内存是否需要停机、是否改变计费和宿主放置、客户机能否识别、应用是否按新资源调整，均要按现场支持范围核对。不能只根据控制台可选择某规格便承诺在线无感扩容。对于依赖本地盘、特殊驱动或固定授权的业务，先检查迁移和硬件变化的额外约束。

容量与安全审批在这里相交：为紧急扩容临时突破配额，会增加同资源池其他租户的争用风险。申请单应写影响域、持续时间和归还条件，不能只记录新增实例数。AIOps 可以计算候选池余量并生成对照方案，但业务优先级、授权范围和跨租户资源取舍需要负责人决定。

本轮已经实际执行本文离线地址模型，正常输出规划通过，重叠输出为真，恢复断言通过，最后只清理内存对象；没有新建文件或发送网络请求。这份证据验证网段集合判断，不验证 TCE 保留地址、路由编程、专线和负载均衡，现场仍需另行验收。
