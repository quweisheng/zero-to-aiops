## “相关的所有技术栈”到底指什么

TCE 是全栈私有化云平台，不是一个进程，也不是固定安装所有腾讯云服务。本路线把“所有”定义为：

### 平台必修域

1. 服务器、CPU、内存、网卡、HBA/RAID、交换与带外管理。
2. DCOS/云底座与服务器生命周期。
3. CVM 计算、镜像、规格、配额和调度。
4. VPC、子网、路由、安全组、ACL、CLB 和互联。
5. CBS/CFS/COS 等块、文件、对象存储。
6. 地域、可用区、租户、项目、账号、角色和 CAM。
7. 控制台、云 API、SDK、CLI、Terraform 和审计。
8. 监控、日志、告警、事件、拓扑、容量和变更。
9. 安全、备份、容灾、交付、补丁、升级与原厂支持。

### 按现场 BOM/License 选修域

- TKE、镜像仓库、微服务与云原生套件。
- TDSQL、Redis、CKafka、Pulsar 等数据与中间件。
- HCC、TurboFS、RDMA 和智算能力。
- INTA、NIPS 及其他安全产品。
- 大数据、AI 和行业 PaaS。

腾讯公有云产品目录不能直接当作 TCE 现场清单。每学一个产品都要问：BOM 有吗、License 有吗、部署了吗、版本是什么、谁维护、是否验证过。

## 官方知识地图

```text
产品边界
  -> TCE / TCS / TStack / CDC/CDZ / 公有云

基础设施
  -> 服务器、网络、存储、DCOS、硬件兼容

IaaS（基础设施即服务：申请计算、网络与存储）
  -> CVM、镜像、VPC、CLB、CBS/CFS/COS

PaaS（平台即服务：在基础资源之上交付数据库、容器等能力）
  -> TKE、TDSQL、Redis、CKafka、Pulsar、微服务、大数据、AI

治理面
  -> 地域/AZ、租户、CAM、配额、计量、API、Terraform、审计

运维面
  -> 监控、日志、告警、拓扑、容量、巡检、备份、DR（灾难恢复）、升级、安全
```

## 场景开场

业务申请一台 CVM，控制台长时间显示“创建中”。十分钟后，数据库、容器和消息平台也出现零星告警。

可能的停点不是一个：

```text
身份/配额
  -> 可用区计算容量
  -> 镜像
  -> VPC 端口和安全策略
  -> CBS 卷
  -> 宿主机/硬件
  -> 客户机启动
  -> 应用安装与健康检查
```

如果同一可用区的 TKE 节点和数据库同时异常，还要怀疑共享网络、存储、宿主机或变更，而不是每个产品各重启一次。

## 一句话人话版

Tencent TCE 是把计算、网络、存储、容器、数据库、中间件、安全和云管理能力私有化部署到客户环境中的企业级全栈云平台。

## TCE、TCS、TStack 与分布式云形态

| 形态 | 官方定位概括 | 学习重点 | 不能推断 |
|---|---|---|---|
| Tencent TCE | 基于腾讯云成熟体系的私有化全栈云 | 本路线主体 | 不能说“就是 OpenStack” |
| Tencent TCS | Kubernetes 与中间件组成的云原生 PaaS | 容器、微服务、中间件 | 不等于完整 TCE IaaS |
| Tencent TStack | 官方明确描述采用 OpenStack/Kubernetes 等开源架构 | OpenStack + K8s + 产品化 | 不是 TCE 别名 |
| CDC/CDZ 等 | 公有云能力延伸到客户附近/专属环境 | 网络、控制面位置、责任边界 | 不等于完全私有化 TCE |

TCE 官方还出现企业版、大数据版、AI 版、敏捷版等应用形态。它们是方案/产品形态，不代替现场完整版本与组件台账。

## TCE 的三类平面

### 管理面

用户、控制台、API、租户、权限、配额、工单、计量、审计、运维门户。

### 控制面

接收资源意图，保存状态，调度计算/网络/存储/服务实例，执行生命周期任务。

### 数据面

业务真实流量和数据：CVM、容器、负载均衡、虚拟网络、云盘、文件/对象、数据库和消息。

```text
管理面可登录 ≠ 控制面所有任务成功 ≠ 数据面业务健康
```

事故通报要分别给证据。

## 地域、可用区与故障域

```text
Region 地域
  -> Availability Zone 可用区
     -> 集群/资源池
        -> 机柜/供电/交换/存储故障域
           -> 宿主机/服务节点
```

多 AZ 只是基础条件。业务是否跨 AZ 还取决于实例放置、数据库复制、存储、网络、负载均衡、DNS、应用状态和演练。

### 高可用层级

| 层级 | 典型目标 | 验收证据 |
|---|---|---|
| 进程/副本 | 单服务实例故障自动恢复 | 副本、切换事件、探针 |
| 节点 | 单服务器故障 | 实例/Pod/服务恢复记录 |
| 集群 | 局部控制面或资源池故障 | 仲裁、容量与故障演练 |
| AZ | 机房级故障 | 跨 AZ 数据和流量切换 |
| 地域 | 城市/地域灾难 | DR 演练、RPO/RTO |
| 应用 | 端到端业务可用 | 真实业务探针与数据核对 |

## 租户、账号、项目、角色与资源

多租户云必须回答：谁、以哪个角色、在什么范围、对哪个资源、执行什么动作。

```text
身份
  -> 租户/组织/项目范围
  -> 角色与策略
  -> API/控制台动作
  -> 资源 ID
  -> 审计记录
```

具体对象名称按目标版本确认。最小权限原则：日常只读、业务资源操作、平台管理、安全审计和紧急账号分离；机器账号不与个人共用；密钥有轮换、吊销和使用审计。

## 一次 CVM 创建的总链路

```text
用户/自动化
  -> TCE 入口和身份认证
  -> 权限、租户、配额校验
  -> 创建任务/request ID
  -> 选择地域、AZ、规格和宿主资源
  -> 获取镜像
  -> 创建 VPC 端口/安全策略
  -> 创建或挂载 CBS
  -> 启动 CVM
  -> 注入初始化配置（若启用）
  -> 上报状态与审计
  -> 业务探针验证
```

页面的任务状态是线索，不是根因。保存 request ID、task ID、resource ID、错误码和发生时间，才能跨计算、网络、存储查同一次操作。

## 一次业务访问的总链路

```text
用户
  -> DNS（域名解析）
  -> 边界/WAF（应用防火墙，若有）
  -> CLB（负载均衡）监听器和转发规则
  -> VPC（私有网络）路由/安全组/ACL（访问控制列表）
  -> CVM（云服务器）或 TKE Service/Ingress（容器平台服务入口与路由）
  -> 应用
  -> TDSQL/Redis/MQ/COS（数据库、缓存、消息队列、对象存储）等依赖
```

“CVM 能 ping”只证明一小部分网络。业务成功还需要域名、证书、负载均衡健康检查、端口、应用协议、依赖和返回路径。

## TCE 与 OpenStack/Kubernetes 的关系

### 可以复用什么

- OpenStack：IaaS 的租户、计算、网络、镜像、卷和请求链心智模型。
- Kubernetes：容器声明式 API、控制循环、Pod/Service/Storage 等通用原理。
- KVM/Ceph/MySQL/Kafka/Redis：各领域基础机制。

### 不能直接复用什么

- 内部服务名、数据库、消息总线、端口和修复命令。
- 版本矩阵、控制台、License、升级路径和厂商 SLA。
- 产品实现细节和现场已安装组件。

TCE 官方定位是自研私有化全栈，不应写成“OpenStack 套壳”。TStack 才是官方明确描述使用 OpenStack/Kubernetes 的另一形态。

## 硬件与兼容性

兼容性指南按计算、存储、网络、数据库、中间件、安全、平台和服务器管理等分组查询推荐硬件/软件。

变更前至少核对：

- 服务器型号、CPU 代际、NUMA、内存。
- NIC/HBA/RAID 型号、固件、驱动和链路速度。
- 交换机、光模块、存储设备和协议。
- Guest OS、内核、云驱动。
- GPU/RDMA/TurboFS/HCC 的专属配套。
- TCE 目标版本和 Hotfix。

“硬件能启动”不等于“在目标 TCE 版本受支持”。兼容矩阵例外需原厂书面确认。

```text

```

### 证据等级

| 等级 | 证据 | 能说明什么 |
|---|---|---|
| A | 腾讯官方公开页、兼容性、官方代码仓库 | 公开产品能力和资料存在 |
| B | 经授权的目标版本产品/升级文档 | 该版本的操作和限制 |
| C | 现场控制台、BOM、License、合同、工单、演练 | 现场实际状态 |

正式报告不能拿 A 级资料替代 C 级现场事实。

## Terraform 与云 API

TCE 官方提供独立 Terraform Provider，并公开私有 endpoint、Region 和凭据配置思路。使用前必须核对 Provider 版本支持的 TCE 版本与具体资源。

```text
Terraform configuration（声明想要的资源）
  -> provider plugin（调用云接口的插件）
  -> TCE private API endpoint（私有接口入口）
  -> identity/tenant authorization（身份与租户授权）
  -> plan（展示预计变更）
  -> apply task/request ID（执行并记录任务/请求编号）
  -> resource state + audit（资源状态与审计）
```

生产规则：

1. 凭据进入安全注入，不写 tfvars/仓库。
2. 先 `plan` 并审批，保存不可含敏感值的计划摘要。
3. state 是敏感资产，远端加密、锁定、备份和最小权限。
4. 不导入未知资源后立刻 apply。
5. Provider 升级单独变更，检查 schema/state migration。
6. API 返回成功后仍验证资源和业务。

## 容量与性能

### 五种容量不能混算

1. 物理安装量。
2. 平台保留与控制面消耗。
3. 已分配逻辑资源。
4. 实际使用和峰值。
5. 扣除故障/维护余量后的可承诺容量。

每个 AZ 按 N+1/业务目标计算，不用整个地域总量掩盖单 AZ 热点。

关键层：CVM vCPU/内存、宿主机、VPC 带宽/连接、CLB 新建连接和并发、CBS IOPS/吞吐/时延、CFS/COS 容量与请求、TKE Pod/节点、数据库连接/复制、MQ lag/磁盘。

## 安全责任边界

平台方负责底座与产品控制面安全，租户/业务团队仍负责账号、网络策略、系统补丁、应用漏洞、数据、密钥和错误配置。具体边界按合同和服务目录确认。

安全主线：

- CAM/最小权限和临时凭据。
- 管理面网络隔离、堡垒机、MFA 和紧急账号。
- 安全组、ACL、WAF/防火墙与零信任边界。
- KMS/Secret 管理，代码与镜像不含明文秘密。
- CloudAudit/平台审计的不可抵赖和留存。
- 漏洞、补丁、镜像、供应链和基线。
- 脱敏日志、数据分级、备份隔离和恢复演练。

## 高可用、备份和容灾

```text
组件多副本
  != 数据备份
  != 跨 AZ 高可用
  != 跨地域灾备
  != 应用端到端恢复
```

设计时逐项定义：故障域、复制模式、仲裁、RPO/RTO、应用一致性、流量切换、DNS、依赖顺序、回切、双写防护和演练。

营销材料中的能力不是现场承诺。用保护关系、复制状态、备份恢复、切换报告和业务核对证明。

## 可观测性与 AIOps

### 统一证据模型

```text
resource_id（资源编号）+ tenant（租户）+ region/AZ（地域/可用区）+ time（时间）
  -> metric（指标）
  -> log（日志）
  -> alarm/event（告警/事件）
  -> task/request_id（任务/请求编号）
  -> audit/change_id（审计/变更编号）
  -> topology neighbors（相邻依赖资源）
  -> business probe（业务验证探针）
```

跨产品 RCA 先确定共同故障域和时间：同 AZ 多服务异常优先看共享基础设施/变更；单租户异常优先看权限、配额、VPC 和业务配置。

### 自动化分级

| 级别 | 动作 | 示例 |
|---|---|---|
| L0 | 只读采集 | 版本、容量、告警、任务、拓扑 |
| L1 | 生成建议 | 假设、下一步检查、影响面 |
| L2 | 人工审批的低风险操作 | 测试实例重试、规则恢复 |
| L3 | 高风险/闭源内部动作 | 升级、主备、数据修复、DR 切换 |

L3 需要原厂/授权 SOP、审批、备份、停止条件和回滚。

## 基础实验：平台证据与容量报告

使用 [private-cloud-evidence-lab](https://github.com/quweisheng/zero-to-aiops/tree/main/examples/private-cloud-evidence-lab)：

```powershell
cd examples\private-cloud-evidence-lab
powershell -ExecutionPolicy Bypass -File .\Invoke-PrivateCloudAudit.ps1 `
  -InputPath .\fixtures\healthy.json `
  -OutputPath .\evidence\healthy-report.md
```

预期：PASS；报告显示 TCE 产品形态、合成版本、管理节点、CVM/对象存储容量和 CVM/TKE/观测组件摘要。

实验只验证台账、阈值和报告逻辑，不证明真实 TCE 组件或版本。

## 故障实验：跨平台容量与组件副本异常

```powershell
powershell -ExecutionPolicy Bypass -File .\Invoke-PrivateCloudAudit.ps1 `
  -InputPath .\fixtures\degraded.json `
  -OutputPath .\evidence\degraded-report.md
```

预期退出码 2；TCE 对象存储越过 90%，CVM 分配接近阈值，TKE 控制面 2/3 且 degraded。

不要直接得出“根因就是容量”。下一步应核对趋势、配额、故障冗余、业务指标、组件日志、同 AZ 告警和最近变更。

## 跨产品故障定位总流程

1. **影响**：哪些租户、业务、地域/AZ 和操作失败。
2. **时间**：首次失败、告警、变更、缓解和恢复统一时区。
3. **入口**：DNS/控制台/API/CLB 是否可达。
4. **任务**：request/task/resource ID 停在哪一阶段。
5. **依赖**：计算、网络、存储、身份、数据库、中间件。
6. **故障域**：同宿主、机柜、交换、存储、AZ 是否成片。
7. **容量**：资源、连接、队列、磁盘和复制是否越线。
8. **变更**：Terraform、控制台、升级、策略、硬件维护。
9. **修复**：最小动作、影响面、审批、停止条件、回滚。
10. **验证**：平台状态 + 业务探针 + 数据核对。

## 高频故障矩阵

| 现象 | 证据 | 假设方向 | 红线 |
|---|---|---|---|
| CVM 创建失败 | request/task、配额、AZ、镜像、VPC、CBS、宿主 | 资源或依赖停点 | 不反复创建 |
| CVM 有 IP 业务不通 | 路由、安全组、ACL、CLB、监听、应用 | 策略/返回路径/应用 | 不全放通 |
| 云盘 I/O 异常 | 卷、挂载、IOPS/时延、路径、后端告警 | 容量、网络、设备、任务 | 不强制解挂载 |
| TKE 节点 NotReady | event、kubelet、runtime、CNI、VPC、证书 | 节点/网络/证书 | 不批量删节点 |
| 数据库延迟 | SQL、连接、锁、复制、磁盘、分片 | 热点/复制/存储 | 不直接重启集群 |
| MQ 积压 | 生产/消费、partition/subscription、lag、磁盘 | 消费者/分布/下游 | 不随意重置 offset |
| 升级失败 | 版本、BOM、预检、备份、失败阶段 | 兼容/健康/包 | 不删升级状态 |
| DR 切换失败 | 复制、仲裁、网络/DNS、依赖、演练 | 数据/流量/顺序 | 防止双写 |

## 生产设计题

题目：为金融核心与互联网业务设计双 AZ TCE。

回答必须包含：业务分级与 RPO/RTO；地域/AZ/故障域；CVM/TKE/数据库/存储跨 AZ 策略；CLB/DNS 流量；控制面和数据面容量；CAM/审计/密钥；备份和异地 DR；BOM/License/维保；升级灰度和回退；业务级演练。

不能只画“两个机房各一套”。要说明数据怎样复制、谁仲裁、网络怎样接管、故障后容量够不够、怎样防双写、如何证明恢复。

## 事故题

题目：一次网络变更后，同 AZ 的 CVM、TKE 和 TDSQL 同时超时。

先冻结变更和限制影响，按共同故障域检查物理/虚拟网络、路由、MTU、ACL、存储网络是否共享；关联审计与变更单。不要三个产品分别重启。回退最小网络变更后，用业务探针和数据一致性验证，再复盘变更模拟、灰度和监控盲区。

## 老师带你把整张地图连成一个业务故事

第一次看私有云产品清单，你可能觉得全是字母。我们换个入口：公司要上线一个“告警分析助手”，值班员上传日志，系统生成候选原因，并把处理结果保存为工单。先不选品牌，先问数据从哪里来、经过哪里、最后保存在哪里。

浏览器先找到业务域名，入口负载均衡把请求送到应用。应用可以运行在 CVM 云主机上，也可以运行在 TKE 管理的容器中。工单等结构化记录进入数据库，临时热点信息可能使用缓存，耗时分析通过消息队列交给后台工作者，日志原文件和模型文件放到适合的存储。

每个组件都不是“装上就自动连接”。应用必须配置数据库连接，网络必须允许必要访问，账号必须有读写权限，上传文件的元数据必须和工单关联。消息消费失败需要重试与去重，模型调用超时需要任务状态和用户反馈。这些业务责任不会由私有云替你定义。

```text
用户 -> 域名与入口 -> 应用（CVM 或 TKE）
应用 -> 数据库（任务、工单与权限记录）
应用 -> 对象/文件存储（日志与模型文件）
应用 -> 消息队列（异步任务）-> 后台分析工作者
各层 -> 指标、日志、审计 -> 值班判断与恢复
```

现在把 TCE 放回图里：它交付和管理基础资源以及实际采购的平台服务。BOM 是 Bill of Materials，在这里是交付组件清单；License 是授权范围；实际部署清单说明现在运行什么。这三份材料重合的部分，才是你本次可以设计和验证的能力。

### 字母第一次出现时，先学职责再学按钮

CVM 是云虚拟机，VPC 是逻辑私有网络，CLB 是负载均衡，CBS 是块存储云盘，CFS 是共享文件存储，COS 是对象存储。TKE 是容器管理相关产品，TDSQL 是数据库产品家族，CAM 是身份访问管理。这一组可以先记成“算、连、分流、存、管”。

HCC 是面向高性能计算的能力，RDMA 是减少网络传输中 CPU 参与的数据访问机制，TurboFS 是相应文件存储产品能力；这些名称出现于某份方案，并不证明普通资源池已经具备完整配套。INTA、NIPS 等安全项也应逐项核对产品含义、版本、部署点和授权。遇到陌生缩写时，从正式组件清单拿到全名，不要根据缩写猜内部架构。

SDK 是便于代码调用接口的软件开发包，CLI 是命令行工具，API 是程序接口。它们都是通向平台的入口，不能绕过权限和资源语义。Terraform 再把资源期望写成可评审配置，但其 state（状态文件）可能保存资源关联及敏感信息，因此必须受控存储。

## 三本账课堂：为什么“采购了、安装了、能用了”要分别验收

第一本是采购与支持账：型号、数量、产品形态、许可和维保期限。第二本是实际运行账：主版本、补丁、构建号、节点角色、组件状态和故障域。第三本是业务服务账：哪个租户的什么应用依赖这些资源，成功率、时延、数据保护和责任人是什么。

假设采购账有对象存储，运行账显示组件正常，但业务上传一直 403。你不能说“平台已装，所以应用问题无需检查”，也不能说“上传失败，所以对象存储全坏”。应核对调用身份、桶策略、签名时间、密钥权限和实际请求；把失败定位到准确的接口与身份范围。

再假设兼容性页面出现 3.10.12。它能支持“有相关资料或兼容条目”这个结论，却不能支持“现场已经升级到 3.10.12”。现场证明需要控制台/组件版本、升级报告和原厂记录；主版本相同仍可能有不同 Hotfix。版本核验是一种证据推理能力，面试与现场交付都会用到。

老师给你的练习是：为一个虚构租户写三行台账，并在每个结论旁边注明来源和时间。拿不到证据的字段写“待核实”，不要用公有云默认值补空。这比把产品列表背熟更接近一个 FDE 或平台工程师的工作。

## 生产课堂：从“有双机房”推到“真的能恢复”

先确定业务允许丢多少数据、停多久。RPO 是允许的数据时间缺口，RTO 是恢复时间目标。例如教学场景要求工单数据不丢超过 5 分钟、服务 30 分钟内恢复，那么数据库复制滞后、备份间隔、入口切换和人工操作总时间都必须进入预算。

同步复制意味着一次写入要等待对端相关确认，通常提高数据保护但增加链路时延与可用性约束；异步复制先在本地完成再传送，会留下复制滞后窗口。具体确认点和一致性由所用产品决定，不能从“有复制”三个字推出零数据丢失。

网络隔断时，要明确哪一侧允许写。仲裁是决定谁拥有服务或数据权威的一套规则；隔离是阻止不应继续写的一侧访问数据。两侧同时恢复接收写入，可能产生无法自动合并的冲突。恢复优先保护数据权威，然后再恢复流量。

故障域容量要独立计算。平时两边各承载一半，任一侧失效后剩余侧是否能容纳全部关键业务？数据库连接、CLB 并发、存储重建和日志回补可能同时上涨，不能只算 vCPU。可以对低优先级批处理降级，但应在预案里写明触发条件和恢复顺序。

验证也要按业务链进行：身份和域名恢复，应用启动，数据库达到可用恢复点，对象可读取，队列消费不重复产生业务效果，最后执行测试事务。只看所有组件绿色，可能漏掉密钥、配置和数据语义不兼容。

## 跨产品排障课堂：用对照组把假设缩小

面对同一可用区的 CVM、TKE 和数据库同时超时，老师会先让你找一个成功对照组：另一个可用区是否正常，同租户不同网络是否正常，同网络不同应用是否正常。每个对照都减少一种解释，而不是立即重启一个产品。

接着建立时间线：网络变更发生、首个连接错误、存储时延上升、节点心跳缺失、用户开始报障。发生时间与采集时间要分开，采集器断线后补发的告警可能晚到。共同依赖与共同时间只建立合理假设，还需要链路、规则命中或接口证据确认。

自动化报告可以给出“相关性较强的候选原因”，并附上证据和下一项只读检查。执行网络回退、主备切换或闭源内部修复前，仍须核对影响范围、原厂操作边界和数据保护条件。把相关性写成已确认根因，会导致后续人员采取错误动作。

给自己做一次三分钟口头汇报：第一分钟讲业务图和产品职责；第二分钟讲创建请求、异步任务与证据；第三分钟讲故障域、恢复目标和实际授权边界。每分钟都配一个你完成的实验结果，清楚标注本地合成验证与真实 TCE 验证的区别。

## 交付精讲课堂：拿到产品清单后，怎样确认能承诺什么

老师请你负责接收一套私有云。交付方给出几十个产品名称，业务方希望下周上线。第一步不是把名字写进架构图，而是建立能力证据链：合同和授权允许什么，版本手册声明什么，现场实际部署什么，测试已经证明什么。四者的交集才是本次可承诺的能力；任何一项缺失，都把结论标为待核实。

以对象存储为例，清单里有 COS，并不能直接承诺某一种跨区复制、保留锁、加密模式或 API 兼容行为。要核对现场版本、产品规格、许可证、控制台/API 实际可见功能和用例验证。与公有云同名是一条学习线索，不是现场功能完全一致的证明。涉及私有文档和补丁差异时，通过授权支持渠道获取，不编造后台命令填空。

交付验收应从功能单项走到组合链路。CVM 能创建、数据库能登录、对象能上传各自通过，还要验证应用凭据、网络、时间、TLS、容量和数据关系连接起来后能完成一笔业务。把单项全绿自动相加成业务全绿，恰好会漏掉最多的跨团队问题。

### 版本矩阵为什么比一个“平台版本号”更重要

平台大版本、组件构建、Hotfix（专项补丁）、客户机驱动和第三方软件可能各有版本号。主版本相同不保证补丁一样，补丁一样也不保证硬件、固件和依赖一样。记录时每项包括来源、采集时间、适用节点或集群范围、兼容文档和维护责任人。发现不一致先判定是否是受支持的滚动窗口，再决定是否属于漂移。

升级不能只讨论目标功能，还要检查源版本支持路径、备份、空间、冗余、未结束任务和已知问题。控制面或数据格式升级可能跨越不可逆点，是否支持降级由原厂文档与演练证明，不是保留旧安装包就自动成立。变更窗口把预检、升级、业务验收、观察和失败处理都算进去，不能把整个窗口耗尽在复制介质上。

## 资源台账精讲：一行云主机信息怎样连接到故障域

一个能用来排障的台账，不只列名称、IP 和 CPU。至少要有租户/项目、地域/可用区、资源 ID、宿主或承载关联、网络与子网、卷与存储后端关联、业务负责人、重要等级、变更时间和证据来源。由于权限边界，租户未必有权看物理宿主，应由平台管理员在受控系统维护关联，而不是把全部基础设施细节暴露给所有租户。

关系比字段数量更重要。一台虚拟机可能挂多个卷，一个存储池承载许多业务，一个物理链路又服务多个资源池。如果只保存各产品独立表格，没有稳定关联 ID，跨产品事故只能靠人猜。同名资源可能位于不同租户、地域或集群，名称不得作为唯一连接键。地址也会变化，不能把 IP 永久等同资产身份。

台账还需要覆盖率。导出了三百行不说明云里只有三百个对象：可能有分页、筛选、权限或离线资源被漏掉。记录控制台/API 总数、实际导出数、分页是否结束、查询范围和失败页；总数对不上先解释差额，不能直接给领导一份“完整资产”。监控数据与台账的时间也需对齐，昨天宿主上的实例今天已经迁走，旧关联会误导根因分析。

### 本地关系校验实验：找出看不见的资源

前提只有 PowerShell，以下是内存合成台账，不读实际 TCE。定义两台虚拟机和三块卷，先查看：

```powershell
$tceLessonVMs = @(
  [pscustomobject]@{Id='vm-a'; Zone='zone-a'; Owner='team-red'},
  [pscustomobject]@{Id='vm-b'; Zone='zone-b'; Owner='team-blue'}
)
$tceLessonVolumes = @(
  [pscustomobject]@{Id='vol-a'; AttachedTo='vm-a'},
  [pscustomobject]@{Id='vol-b'; AttachedTo='vm-b'},
  [pscustomobject]@{Id='vol-c'; AttachedTo='vm-not-in-export'}
)
$tceLessonVolumes | Where-Object { $_.AttachedTo -notin $tceLessonVMs.Id } | Format-Table
```

预期输出 `vol-c`。老师问你：“是不是孤儿盘，可以删除？”还不能。它可能真的没有合法挂接，也可能虚拟机导出漏页、查询权限不足，或两份表采集时刻不同。模型发现的是关系无法在当前样本中闭合，不是数据删除许可。

模拟查明“原来漏了一页”，补入缺失对象：

```powershell
$tceLessonVMs += [pscustomobject]@{Id='vm-not-in-export'; Zone='zone-b'; Owner='team-blue'}
@($tceLessonVolumes | Where-Object { $_.AttachedTo -notin $tceLessonVMs.Id }).Count
```

预期变成 0，说明这份合成表的挂接引用已闭合；它仍不证明物理盘健康、账单准确或业务能读写。把“异常出现→证据补齐→异常消失”写入记录，解释为什么不直接删除。清理执行 `Remove-Variable tceLessonVMs,tceLessonVolumes`。若结果不符，检查是否按顺序执行、字段名和 ID 是否一致、是否在同一终端；实验不会留下真实云资源。

## 业务连续性精讲：不同故障需要不同恢复工具

主机硬件故障、整个可用区失联、管理员误删、勒索软件和应用写错数据不是同一种事故。跨主机副本可以应对部分硬件故障，却可能同时复制错误写入；异地备份可以保留历史，但恢复耗时可能超过在线切换。需要按威胁分别配置高可用、备份、不可变保留、异地恢复和业务补偿，不能用“容灾”两个字代替所有设计。

RPO/RTO 也必须按业务链计算。数据库达到某个恢复点，对象附件和消息消费偏移还在另一个时刻，可能出现工单引用不存在附件、任务重复执行或漏处理。为每种数据定义权威来源、可重建部分、恢复顺序和核对方法。比如搜索索引可由原始记录重建，但原始记录不能靠搜索结果完整恢复；热缓存丢失可以重建，却可能引起数据库瞬时压力。

故障切换首先判断谁有数据权威。网络分区时两侧都活着，必须通过产品支持的仲裁和隔离决定哪一侧可写；入口切流只改变用户去哪里，不会自动阻止旧主写入。回切同样是一次有风险的数据方向变更，需要确认复制追平、差异处理、旧写入者已隔离和验证窗口，不是把 DNS 再改回来那么简单。

恢复计划还包括人。谁有权限取备份和密钥，谁能改网络和入口，谁确认数据正确，谁对业务恢复签字，都需要预先约定。原厂支持的到场或响应时间、离线介质位置、异地网络带宽会直接影响恢复时长。纸面三十分钟但等待账号审批两小时，就是未达标，不能把它排除在事故时间线之外。

## AIOps 精讲：从“告警聚合”走到可信的候选根因

假设同一时刻产生三百条告警。先用资源关系、故障域和时间把事件分组，而不是只按告警标题相似度合并。网络故障可能导致存储超时、数据库等待、应用错误和采集器断连，最晚到达的“应用不可用”并不必然是最初原因。采集时间、事件发生时间和变更时间分别保存，避免补发告警倒置因果顺序。

一个好的候选根因报告应包含支持证据、反证、受影响对象、尚未检查的依赖和下一步只读验证。举例：“同交换故障域的三个产品同时退化，另一域对照正常，变更时间相近”只能提高网络相关假设的可信度；要进一步找具体路由差异、丢包或设备证据。没有证据就标不确定，不让模型把流畅的故事包装成确定结论。

自动动作按影响分级。查询健康、整理日志、关联变更可以自动化；扩容或重启也需明确资源、幂等条件和停止阈值；主备切换、删除数据、缩小保留期和闭源内部修复更要审批。每次动作都记录执行前状态、目标 ID、命令或 API 意图、返回结果和业务复验，不能只留下“AI 已处理”的一句话。

## 面试设计题完整展开：双区告警分析平台

我先界定现场已交付能力与授权，再按业务拆出同步访问、异步分析、工单记录、日志文件和模型制品。同步入口使用可验证的健康检查，应用跨故障域部署；数据库、消息和存储根据各自一致性能力选择复制与恢复。模型分析失败时保留任务状态并允许受控重试，模型结果只作为建议，不自动获得生产变更权限。

容量按失去一个区后承接关键业务来算，把镜像拉取、日志回补、对象恢复、数据库连接和模型任务排队也纳入。允许延后的批量分析有明确降级优先级；关键工单读写不能被 GPU 训练或日志扫描挤占。安全上区分人员、流水线和模型工具身份，秘密通过受控机制注入，审计独立保留并校准时间。

验收从小规模功能到失败演练，逐项证明断一台、断一个依赖、管理面失联时的影响。没有获准故障注入时使用桌面推演并标注范围，不把推演写成实测。最后把版本/BOM/License、三本台账、业务链、容量预算、恢复证据和原厂边界一起交付，这比只画两个 AZ 框更能承受面试追问。
