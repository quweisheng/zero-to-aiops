## 官方知识地图

```text
治理：租户 -> 用户/角色 -> 策略 -> 配额 -> 资源归属 -> 运营报表
观测：业务探针 -> 指标/日志/链路 -> 告警 -> 事件 -> 工单
安全：身份 -> 网络边界 -> 主机/容器 -> 应用/数据 -> 审计
运维：资产版本 -> 容量 -> 备份恢复 -> 变更 -> 升级 -> 原厂支持
```

CAM 是访问管理；BOM 是组件清单；License 是许可；SLO 是希望达到的服务质量目标；Runbook 是按条件执行的操作手册。运维面向系统健康，运营面向资源供给、租户使用、成本和服务质量，两者不是一回事。

## 场景开场：凌晨“几千条告警”怎样开始处理

假设某交换机变更后，CVM 网络超时、TKE 节点离线、数据库连接失败、日志断流同时出现。逐条关闭告警会浪费时间；直接重启每个产品可能扩大影响。

应先确认业务影响，按同一时间、同一 AZ（可用区）、同一网络路径聚合告警，再关联变更记录。几千条症状可能只有一个共同依赖异常。AIOps 的价值是帮助找到这种关系，不是获得不受限制的生产修改权限。

## 一句话人话版

TCE 运维安全就是给私有云建立“谁能操作、谁做过什么、哪里出问题、怎样安全恢复”的完整账本。

## 小白先问

### 有管理员账号就可以操作所有东西吗？

技术权限与业务授权不同。管理员能删资源，不等于有权删；数据库、网络、租户和平台分别有责任边界。必须遵守审批和最小权限。

### 平台告警正常，为什么用户还打不开网页？

平台监控可能只知道机器在线，不知道登录、查询和提交是否成功。必须加入模拟用户完成关键事务的业务探针。

### 有日志就等于有审计吗？

应用日志记录程序行为，审计记录主体、动作、目标、时间和结果。两者应关联，但用途、访问权限和保留周期不同。

### 安全设备越多越安全吗？

没有策略验证、误报治理、容量评估、例外到期和回滚，叠加设备会变成新的故障源。

## 为什么要学、它解决什么问题

平台规模扩大后，最危险的不是不会点击某个按钮，而是不知道该按钮影响哪些租户，也不知道失败后如何恢复。本技术栈解决权限失控、告警噪声、资源争抢、变更不可追溯和灾备“有配置没验证”的问题。

## 核心概念一：主体、角色、策略与资源

**是什么：** 主体是人或程序；角色是一组可被承担的身份；策略描述允许或拒绝哪些动作、哪些资源及什么条件。

**为什么需要：** 值班员只需要查看健康，自动采集器只需要读指标，不应该都使用超级管理员。

**怎样工作：** 认证确认“你是谁”，授权判断“你能否执行这个动作”。策略还可能结合租户、资源范围、网络来源等条件；具体求值规则看现场版本。

**怎样用和观察：** 给只读巡检建立独立身份，保存策略版本；在测试租户验证允许的查询成功、越权操作被拒绝。查看审计中的调用主体和 request ID（请求编号）。

**坏了怎样查：** 区分凭据失效、认证失败、授权拒绝、资源不存在和网络不可达。不要把所有 403 都处理成“给全权限”。

## 核心概念二：审计链与时间线

**是什么：** 审计链将人员/程序、操作、资源、任务和变更单对应起来。

**为什么需要：** 同一时刻可能有自动扩容、补丁发布、人工修改，单看告警无法确定先后。

**怎样工作：** 用统一时间基准，记录事件发生时间与采集时间；通过 request ID、task ID、资源 ID 和工单 ID 连接记录。

**怎样观察：** 以故障前后 15 分钟为初始窗口，向外扩展；同时检查日志是否延迟、时钟是否偏移、采集器是否断连。

**坏了怎样查：** “没有审计记录”可能是没发生，也可能是权限、保留周期、采集异常或查错租户。不能直接下结论。

建议脱敏事件结构：

```json
{
  "occurredAt": "2026-08-31T10:00:00+08:00",
  "observedAt": "2026-08-31T10:00:04+08:00",
  "actor": "demo-readonly-role",
  "action": "DescribeResources",
  "resourceId": "demo-resource-001",
  "requestId": "demo-request-001",
  "changeId": "demo-change-001",
  "outcome": "success",
  "source": "synthetic"
}
```

这不是 TCE API 的真实字段定义，而是学习用的归一化事件模型。保留原字段映射，避免统一格式时丢掉证据。

## 核心概念三：指标、日志、链路和业务探针

**是什么：** 指标看趋势，日志看细节，Trace（调用链）看请求跨服务经过哪里，探针看用户能否完成任务。

**为什么需要：** CPU 正常不能证明数据库锁等待正常；端口可连接不能证明事务提交成功。

**怎样工作：** 从业务成功率/延迟向下关联应用、PaaS、IaaS、硬件和网络。为每层定义负责人、采集周期和数据时效。

**怎样观察：** 同时展示成功率、P95/P99 延迟（绝大多数请求的耗时边界）、流量、错误、饱和度与最近变更。

**坏了怎样查：** 指标突然归零先查采集链路；没有数据不等于零故障。日志增长也可能只是重复错误，不等于业务增长。

## 核心概念四：SLO、错误预算与告警分级

SLO 是业务目标，例如教学假设“关键查询月成功率 99.9%”，不是本文承诺的 TCE SLA（合同服务保证）。错误预算是允许失败的余量，用来判断当前是否还能继续高风险发布。

实现方法是先定义什么算一次有效请求、什么算成功、在哪个窗口统计，再配置告警。P1 可以表示大面积关键业务不可用，P2 表示局部或冗余损失，P3 表示趋势风险；具体级别按单位制度。

使用时观察短窗口快速恶化和长窗口持续消耗，不要只设 CPU 超过某值。异常时检查样本量、分母、维护窗口和探针自身；不能通过删除失败样本“修复”SLO。

## 核心概念五：容量、配额与故障预留

容量是物理/服务可承载量，配额是租户可申请上限，预留是故障或维护时必须剩下的空间。三者不能混为一谈。

例如总内存 100 单位，已用 70，单故障域占 25，看似还剩 30，但失去一个故障域后只剩 75，可用余量很小。再加迁移、缓存和增长，已不适合继续大量开通。

容量看当前、增长速度、峰值、最大故障域和扩容交付周期。磁盘还要看 IOPS（每秒读写次数）、吞吐、延迟、重建空间和备份窗口；只看 TB 容量会漏掉性能瓶颈。

异常时先确认口径：裸容量还是可用容量、分配还是使用、是否含副本、是否有失效资源。不能将“逻辑删除”直接计为已回收物理空间。

## 核心概念六：备份、复制与灾难恢复

复制让数据在多个位置存在，备份提供可回到历史状态的副本，DR（灾难恢复）是让业务在故障后恢复运行的整个流程。

RPO 是最多允许丢多少时间的数据，RTO 是多久恢复。两者必须从业务倒推，不能用“有三副本”代替。

一份合格恢复方案要说明备份范围、加密密钥、保存位置、不可变/离线策略、恢复顺序、业务验证、切回条件。恢复测试在隔离环境进行，不覆盖生产数据。

如果备份任务成功却恢复失败，要检查是否只备份了数据而没备份配置/密钥，是否版本不兼容，是否缺少增量日志，是否从未验证恢复时间。

## 安全产品应该放在哪一层

以下是职责映射，不是现场已安装清单。

| 能力 | 人话解释 | 主要证据 | 常见边界 |
|---|---|---|---|
| CAM/身份联合 | 发钥匙并限制能开哪些门 | 策略、登录和 API 审计 | 不能代替主机内部权限 |
| 安全组/网络 ACL | 控制流量能否经过 | 规则、命中、五元组 | 不代表业务内容安全 |
| NIPS | 检查网络攻击行为 | 命中规则、动作、流量 | 阻断策略要评估误伤 |
| WAF（若部署） | 检查 Web 请求攻击 | URL、规则、请求标识 | 不能修复应用逻辑漏洞 |
| 主机安全 | 检测主机风险和异常行为 | 进程、文件、基线、漏洞 | Agent 自身也要监控 |
| 数据库审计（若部署） | 记录数据库访问行为 | 账号、SQL 摘要、来源 | 注意敏感 SQL 脱敏 |
| KMS/密钥管理（若部署） | 管理加密钥匙 | 密钥版本、授权、审计 | 丢失密钥可能无法恢复数据 |
| 日志/安全运营平台 | 汇总事件并关联分析 | 规则、工单、时间线 | 采集缺口会影响判断 |

NIPS 是网络入侵防御；WAF 是 Web 应用防火墙；KMS 是密钥管理服务。名称相同不保证不同版本支持相同动作。

## 架构与数据流

```text
用户业务 -> 入口/CLB（负载均衡）-> 应用 -> 数据库/缓存/消息/存储
                |        |             |
                +------ 指标/日志/Trace（链路追踪）+
                              |
资产与拓扑 + 审计变更 + 业务探针 -> 事件关联 -> 工单/Runbook（处置手册）
                                                   |
                                  人工审批 -> 最小变更 -> 验证 -> 复盘
```

CLB 是云负载均衡，将流量分发给后端。自动化执行账户与观测账户分离，观测系统被攻破时不应直接获得全平台写权限。

## 部署与启动：先交接，再接管

TCE 运维系统不是下载一个安装包便能独立上线。交接至少包括：

1. 产品形态、版本、补丁、构建号与组件 BOM。
2. 管理/控制/业务/存储网络图及访问边界。
3. 账号、角色、紧急访问流程与凭据保管，不把密码写入文档。
4. 监控、日志、审计的覆盖范围、保留期、容量和备份。
5. HA（高可用）拓扑、故障域、仲裁、备份与恢复演练记录。
6. License、维保有效期、原厂联系人和升级路径。

启动检查顺序是基础电源/网络/时间/DNS，再依赖服务和平台组件，再租户服务，最后真实业务探针。具体先后必须用本版本原厂运行手册，不能按通用文章停启闭源组件。

## 配置和操作字典

| 项目 | 用途/常见设置 | 应验证什么 | AIOps 场景与坑 |
|---|---|---|---|
| 采集周期 | 例如教学用 60 秒 | 数据时效与采集负载 | 周期过长漏尖峰，过短压垮 API |
| 保留期 | 按合规和容量配置 | 到期清理、检索、恢复 | 审计与普通日志不能一刀切 |
| 告警聚合键 | 资源、故障域、症状 | 同故障合并但保留原告警 | 不能把不同租户事故混掉 |
| 静默窗口 | 绑定变更单和到期时间 | 窗口自动结束 | 永久静默会隐藏事故 |
| 只读策略 | 限制动作和资源 | 正反权限测试 | 不给采集器全管理员 |
| 凭据轮换 | 分阶段替换并验证 | 新凭据生效、旧凭据失效 | 双方不同步会导致采集断流 |
| Runbook 停止条件 | 影响扩大、证据不符、超时 | 自动停止并升级 | 不能无限重试写操作 |
| 备份校验 | 恢复到隔离目标 | 记录数、校验和、业务查询 | 下载成功不是恢复成功 |

只读查看动作通常是描述资源、查询指标、检索审计；具体 API 名和参数由版本文档确认。不要将教学字段直接请求生产 API。

## 基础实验：无云环境也能做一次值班巡检

前提：Windows PowerShell 5.1+，已取得本仓库。实验只读取合成 JSON，不连接真实 TCE，不需要账号或 License。

在仓库根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File examples/private-cloud-evidence-lab/Invoke-PrivateCloudAudit.ps1 -InputPath examples/private-cloud-evidence-lab/fixtures/healthy.json -OutputPath examples/private-cloud-evidence-lab/evidence/healthy.md
Get-Content examples/private-cloud-evidence-lab/evidence/healthy.md -Encoding UTF8
```

`InputPath` 是证据快照，`OutputPath` 是生成报告路径。输出必须尚不存在，复跑换新名称，不能覆盖旧证据。工具拒绝缺失/空列表、无时区时间、非法类型和范围及重复对象；总量和期望组件数为零会失败，使用量超过总量仍报告风险。预期得到 `PASS`，并看到版本台账、容量、组件和人工确认清单；PASS 只表示这份输入未触发规则。

验证：检查报告写明 `synthetic-demo`，并能回答“版本证据来自哪里”“是否验证业务”。若文件找不到，确认当前目录与路径；中文乱码检查 UTF-8；命令失败先看异常，不要更改系统全局执行策略。

## 故障注入实验：备用管理节点离线与容量越线

前提同上，故障已注入另一份合成输入，不停止任何真实服务。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File examples/private-cloud-evidence-lab/Invoke-PrivateCloudAudit.ps1 -InputPath examples/private-cloud-evidence-lab/fixtures/degraded.json -OutputPath examples/private-cloud-evidence-lab/evidence/degraded.md
$LASTEXITCODE
Get-Content examples/private-cloud-evidence-lab/evidence/degraded.md -Encoding UTF8
```

预期退出码 `2`，报告 `DEGRADED`，包括备用管理节点离线、容量越线与 `tke-control-plane` 未完全就绪。退出码 2 是检测到异常，不是脚本损坏。

任务：把发现项分为“业务已受损”“冗余受损”“容量风险”“证据不足”；报告本身不含完整业务证据，因此不能把所有 CRITICAL 都直接宣布为全网中断。

验证与清理：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File examples/private-cloud-evidence-lab/verify.ps1
Remove-Item -LiteralPath examples/private-cloud-evidence-lab/evidence/healthy.md,examples/private-cloud-evidence-lab/evidence/degraded.md
```

只删除上面生成的两份报告，可重新运行恢复。若结果与预期不同，检查输入是否选错、是否运行了旧脚本、字段单位是否一致。

## 现场只读扩展：建立四张清单

得到现场授权后，按本版本控制台或只读 API 分别收集资产版本、组件健康、告警变更、业务验证结果。每份记录注明时间、租户、区域和证据来源，脱敏后转为实验输入模型。

不能把合成实验的 `ready/expected` 简化规则照搬为真实平台健康判断；不同组件可能有主备、分片、多数派或异步状态，需按产品语义解释。

## 高可用、容量和性能设计

监控、日志与审计本身也需要高可用。采集器断开后要有有界缓冲、重试退避和丢弃策略；日志平台满盘时不能反向拖垮业务。

采集请求量可先估算为 `资源数 × 每资源调用次数 ÷ 周期秒数`。例如 6000 个资源、每周期两次请求、60 秒周期，平均约 200 次/秒，还没有算重试和集中启动尖峰。要批量、分页、抖动调度、限流并遵守平台配额。

高基数标签是取值非常多的标签，例如用户 ID、原始 URL、request ID。它们适合日志检索，不宜无约束放进每条时序指标，否则存储和查询成本急剧增长。

## 升级与回滚

1. 核对 TCE、组件、操作系统、驱动、固件、监控 Agent 的兼容关系。
2. 查已知问题、支持期限、许可和原厂升级路径。
3. 备份配置、策略、审计规则和必要数据，实际恢复验证。
4. 选测试租户/小故障域灰度，记录升级前基线。
5. 持续观察业务成功率、延迟、告警和采集缺口。
6. 触发停止条件后按已验证方案回退；涉及数据格式/Schema 变更不能假定降包即回滚。

升级和紧急补丁不等于必须同时做架构调整。扩大变化范围会降低归因能力。

## 排障字典

| 现象 | 先收集证据 | 假设与验证 | 处置边界 |
|---|---|---|---|
| 全平台告警暴增 | 时间、AZ、变更、网络探针 | 共同依赖还是多点故障 | 先冻结变化，不批量重启 |
| API 403 | 主体、动作、资源、策略版本 | 权限还是凭据/租户错误 | 最小权限修正，不给全权 |
| 指标突然全零 | 采集心跳、最后时间、API 错误 | 采集失败而非业务变空 | 恢复采集并标注缺口 |
| 日志延迟 | 队列、磁盘、吞吐、丢弃计数 | 入口过载或出口故障 | 有界缓冲、分级限流 |
| 管理主备异常 | 角色、心跳、时间、网络 | 单机还是脑裂风险 | 禁止凭单一告警强制倒换 |
| 备份恢复失败 | 备份链、密钥、版本、校验 | 缺增量或不兼容 | 隔离验证，升级原厂 |
| License 告警 | 许可范围、有效期、平台时间 | 到期/资源超限/时间异常 | 走授权续期流程，不绕过许可 |
| 安全策略误拦截 | 请求标识、命中规则、业务样本 | 确认具体规则和影响 | 有期限的最小例外，不整体关闭 |

## 生产设计题

为两地三中心的政企私有云设计值班体系。不要先报产品名，先确认业务等级、RPO/RTO、审计保留、数据边界、人员值班和原厂响应要求。

答案需要包括：租户隔离和角色分工、管理面专网、观测平台自身 HA、跨故障域备份、统一资源/变更编号、分级事件响应、紧急授权、故障演练、密钥恢复、容量扩展和退场交接。核心取舍是安全、可恢复性、时延、成本与运维复杂度。

## 事故题：安全规则发布后登录失败

先收集失败比例、时间窗口、入口请求标识、规则命中与发布记录；提出“新规则误伤登录请求”假设，再用脱敏测试请求对比规则前后，不抓取用户密码。

若证据支持，按审批回退具体规则或设置短期最小例外，记录受影响入口与租户。验证登录和其他关键事务，观察攻击风险是否上升，保留回退前证据。不能关闭整个安全平台来证明问题。

## 面试怎么讲

### 30 秒回答

我把 TCE 运维分为身份权限、资产版本、可观测、容量、备份恢复、变更和安全闭环。先用业务探针确定影响，再以资源 ID、请求 ID、故障域和变更时间关联告警；修复必须有授权、停止条件、验证和回滚。

### 3 分钟展开

先解释管理面和数据面不同，再画业务到基础设施的依赖图。介绍最小权限采集、统一审计时间线、SLO 与容量预留，然后讲一次安全策略误伤的证据链、灰度回退和复盘。最后说明 TCE 组件与能力以现场版本/BOM 为准，闭源主备、补丁、数据恢复和 License 问题升级原厂。

### 递进追问与答题线索

1. **监控与审计区别？** 健康趋势对比操作追溯；追问保留和权限怎样不同。
2. **几千条告警怎么降噪？** 按时间/资源/故障域/依赖聚合，保留原始证据；追问如何避免误合并。
3. **为什么不能全自动恢复？** 有状态操作存在不确定结果和影响面；追问幂等、审批和停止条件。
4. **怎样证明灾备有效？** 在隔离环境恢复并验证业务与 RPO/RTO；追问密钥、增量链和切回。
5. **采集平台如何扩容？** 先算资源数、周期、基数、吞吐、保留与重试放大；追问采集失效时告警谁。
6. **原厂支持需要什么？** 版本/BOM/补丁、脱敏时间线、资源与任务编号、复现、影响和已做操作。

## 老师带你值一次班：先说清业务，再打开告警列表

你刚接班，屏幕出现“数据库连接失败”“节点失联”“日志采集断开”。老师不会让你立即点确认，而是先写一句影响描述：哪个业务、哪些用户、从什么时候开始、哪些操作失败。只有这些问题清楚了，才知道应该按重大业务中断还是局部冗余受损来组织处置。

告警是规则对某个信号的判断，事件是已经发生的事情，事故是影响服务目标、需要协调恢复的一段过程。三者数量不相等。一个网络事故可以产生几千条告警；告警静默后，事故也可能仍在继续。

第一张纸写时间线，第二张纸写依赖图，第三张纸写假设和验证结果。时间线区分事件发生与采集到达；依赖图连接业务、租户、可用区、网络和存储；假设表明确下一项证据是什么。这三张纸让多人协作时不必反复猜“刚才谁做过什么”。

### 告警合并怎样避免把真正的问题藏起来

按同时间、同故障域和依赖关系聚合，可以减少重复通知，但必须保留原告警与独立业务影响。两个租户同时出现 403，可能是共同身份源故障，也可能分别改错策略；时间相近只是线索。

维护静默应包含范围、变更编号、开始结束时间和自动到期。静默的是通知，不应停止采集。变更窗口里出现意料外的业务失败，仍应升级响应。永久关闭一条吵闹规则会让后续真正故障失去信号。

## 老师带你算错误预算，而不是背一个九

假设教学服务月内有 100 万次有效请求，成功率目标 99.9%，允许失败数量是 1,000 次。如果一小时已经失败 600 次，就消耗了大部分预算。这里的目标是团队设定的 SLO，不是 TCE 合同的 SLA。

首先定义分母：探针请求、用户请求、主动取消是否算有效请求；再定义分子：HTTP 200 但正文报告业务失败能否算成功。统计规则含糊时，仪表盘数字会很好看，用户却一直抱怨。

短窗口告警发现快速恶化，长窗口发现持续消耗。低流量业务还要看样本量，一次失败可能让一分钟成功率跌到 0%，但不一定表示全平台故障。容量、成功率、延迟和错误预算一起看，才能决定先恢复还是继续发布。

## 变更课堂：回滚是一套能执行的动作

“有问题就回滚”不够。请你写出原配置在哪里、谁有执行权限、哪些对象会受影响、数据是否兼容、最多允许试多久、恢复后验证什么。软件包保存了旧版本，却缺少迁移前数据库和密钥，不构成可执行回滚。

变更分阶段设置停止条件：预检不通过不开始，试点业务成功率下降停止扩展，冗余受损停止下一批，有状态数据不一致立即保护写入。停止条件要能从证据判断，不能写成“情况严重时再说”。

事故中的紧急变更也保留最小记录：动作、资源 ID、操作者、时间、理由、结果。记录不应拖延必要恢复，但没有记录会让下一班无法判断哪些临时规则需要回收。

## 安全课堂：认证、授权、审计为何要分别验证

认证像核验证件，授权像决定能进入哪间房，审计像记录谁在何时开了哪扇门。登录成功只通过第一关。巡检程序应该只有读取必要状态的权限；能调用 API 不表示能读取所有租户或所有审计。

做一个授权测试时，除了验证允许的查询成功，还要验证越界查询被拒绝，并在审计中找到对应主体和动作。保留的是脱敏请求编号与结果，不是完整凭据。机器账号轮换先验证新凭据，再撤销旧凭据，防止采集器成片断线。

安全设备误拦截时，先取脱敏请求样本、命中规则与影响范围。若证据支持误伤，回退具体规则或设置有到期时间的最小例外，再验证业务与安全目标。关闭整套安全平台会同时改变太多条件，既扩大风险，也削弱根因判断。

## 原厂协作课堂：怎样提交一份能接着查的工单

工单包含产品全名、完整版本与补丁、组件和故障域、首次失败时间、业务影响、任务/资源编号、可复现条件、成功对照、已执行动作和当前状态。闭源内部问题需要厂商工具与支持流程，但你仍负责把证据整理成可继续分析的结构。

不要把“控制台报内部错误”作为全部描述，也不要预先写一个没有证明的根因。可以写：“失败集中在某可用区同一规格，旧实例正常；已排除用户权限，存储任务仍待核实。”这类边界清楚的描述比“应该是平台 BUG”更能推动定位。

面试三分钟展开时，用一次安全策略误伤为主线：先确认登录影响，再关联规则变更，使用对照请求验证，限定范围回退，最后做正反安全测试和例外回收。追问全自动化时，说明只读诊断、建议生成与有状态写操作的分级，以及超时后查询结果、防重复执行和人工接管条件。

## 权限求值课堂：加一条允许，并不总能修复拒绝

权限系统通常同时考虑主体、动作、资源与条件。腾讯 CAM 官方[策略文档入口](https://cloud.tencent.com/document/product/598)可以帮助理解显式拒绝与允许的关系，但现场 TCE 的可用语法、条件键和联合身份规则仍应查对应发行版。排障不只看某一条允许策略，还要看实际承担角色、会话、资源范围和其他限制。

例如巡检角色允许读取测试租户，脚本却携带另一个角色的凭据；又如策略动作正确，但资源编号属于另一个区域。终端看到同一个拒绝文字，原因却不同。先记录脱敏主体、动作、目标编号、区域、策略版本与请求标识，再做最小范围对照。不能通过不断追加通配允许来“试出”权限，最终会留下无法解释的越权集合。

临时凭据往往包含访问标识、秘密及会话令牌等组成，实际组合依据身份产品。它有有效时间和权限边界，不能只替换其中一个字段，也不能把刷新失败直接当成业务资源故障。轮换时保存的是凭据版本和成功失败结果，不输出秘密；先让少量采集器验证新会话，再逐批切换与撤销旧会话，监控采集缺口。

基础纸面实验准备“观察者读取本租户”“观察者读取他租户”“观察者删除本租户资源”三项预期，分别允许、拒绝、拒绝。故障步骤把资源范围错误写成全平台，预测第二项变成越权。恢复步骤还原范围并再次复验三个动作，清理删除虚构策略文本，不在真实租户试删除。正反两组证据同时成立，才叫权限符合设计。

账号还要有生命周期。员工调岗、承包商退场、服务下线时，角色绑定、机器凭据、堡垒机入口和应用权限都应分别回收；只禁止网页登录可能留下 API 凭据。紧急账号启用要能关联实际人员和事件，使用后轮换并复验。权限审计关注“现在谁还能做什么”，不只是“曾经创建了多少用户”。

## 自动化课堂：审批通过后仍要重新验证目标状态

一份操作计划在审批时针对资源版本甲，执行前资源可能已被他人修复为版本乙。自动化若只按名字寻找对象，可能作用于删除重建后的另一份资源。因此执行前核对不可变编号、当前版本、预期前置条件和批准窗口；不符合就停止并重新评估。审批不是一张允许永久修改所有同名对象的通行证。

脚本锁的作用是限制并发执行，但锁失效后旧执行者可能仍在运行。涉及数据写入时，需要目标系统支持的并发控制、版本条件或隔离机制，不能只靠一份本地锁文件承诺单写者。平台没有相应原子条件时，应明确人工协调和执行范围，不能自创一个字段冒称服务器会强制校验。

两级模拟用一个内存中的资源卡片：编号固定，版本为七，计划只允许在版本七执行。基础步骤读取卡片并核对，预期通过；故障步骤在审批后将版本改成八，预期拒绝执行并标明状态已变化。恢复步骤由审批人确认新状态后重新生成计划，而不是把版本硬改回七。清理删除卡片与计划，没有调用云接口。

执行超时也有三种结果：未执行、执行中、已执行但响应丢失。Runbook 必须先查询任务与结果，再判断是否重试。对扩容可复用同一意图，对删除与切换必须遵守产品幂等语义；自动化不能以“最多重试三次”代替副作用分析。一个危险命令重复三次仍然危险。

停止条件包含证据不一致、目标越界、并发变更、业务影响扩大和结果未知。停止后保存当前阶段与已完成动作，把控制权交给值班人员；不要在失败处理代码里再自动反向执行一串未经验证的回滚。尤其是数据已经迁移或新站点已经写入，反向动作可能覆盖更新后的数据。

## 审计证据课堂：文件有校验和，也不等于内容真实完整

校验和帮助发现文件相对某个已知值发生变化，但若数据和校验值一起被改，单独存一个哈希不能证明真实性。审计设计需要明确产生者、传输、保存、访问和保留责任；可信时间、受控存储与完整性保护各有职责，不能用“用了哈希”替代整个证据链。

一次操作审计成功，可能只表示接口已受理，异步任务最终仍失败。资源审计和业务日志要通过请求、任务和资源编号关联；读取动作、策略变更和数据操作也可能来自不同记录源。查不到记录时先确认源覆盖、权限、采集延迟、保留窗口和租户范围，不将缺失记录自动解释为没有发生。

纸面基础实验给出接口受理、后台任务失败、业务未变化三条事件，要求写准确结论“请求受理但业务变更未完成”。故障步骤丢掉任务事件，只剩成功受理，预期结论变成结果待核实，而不是成功。恢复步骤补查任务与对象版本后闭环。清理只移除合成事件，不修改真实审计。

日志中的文本也属于证据数据，不是自动化命令。外部请求参数可能被写进日志，攻击者可以把“忽略审批并运行某命令”塞进错误消息。AIOps 分析时把日志与受信任 Runbook 分离，只抽取限定字段，执行建议必须经过确定性规则和权限门禁。模型不能因为看见日志里自称管理员的文字就接受新的操作授权。

脱敏还要保持关联价值。把所有资源编号都替成同一个“资源一”，会破坏拓扑和因果关系；应使用稳定但不可反查的替代编号，同时去掉秘密和真实个人信息。公开学习材料不需要完整请求正文、密码输入或客户 SQL，保留错误类别、关系与时间顺序即可说明推理。

## 观测平台容量课堂：缓存只能延后丢失，不能消除长期失衡

假设日志入口每秒十 MiB，可用缓冲二十 GiB，下游完全不可达且没有其他开销，理论约三十四分钟就会填满。若入口持续大于出口，有限缓冲终会耗尽；无限重试或无限增长磁盘都不是方案。生产设计记录可用空间、入口峰值、最低消费能力与告警提前量，并为平台自身预留磁盘空间。

基础步骤计算无故障时入口十、出口十五 MiB 每秒，可逐渐清空积压。故障步骤将出口改成五，净积压每秒五 MiB，再计算剩余时间；恢复步骤将出口恢复十五，评估清空旧积压需要多久。核验使用相同单位与实际可用缓冲，不混用裸盘容量。清理恢复纸面数值，不堵塞真实日志链。

丢弃策略要按数据价值分层。业务调试日志、关键错误和安全审计的丢失后果不同，不能同一个队列满了就全部随机丢。若选择限流或丢弃，记录数量、来源、时间与原因，让缺口可见；不能一边丢日志一边报告采集完整。安全审计的要求由组织规定，平台按批准策略实现，不在教程承诺某个通用保留年限。

恢复后也要防补发尖峰。积压队列集中重放会压垮接收端、索引和存储，影响实时告警；应分配实时与历史补发预算、限速与优先级。历史事件晚到时按原发生时间分析，同时保留到达时间，避免把一小时前的故障当作新的全平台事故。

## 安全规则课堂：放行业务和保持防护是两项同时验收的目标

安全策略灰度前先做合成正常流量与已授权的规则测试样本，记录预期动作。上线后观察正常请求误拒绝和风险请求处置，不只统计拦截数量；拦截量增加可能是攻击增加，也可能是规则过宽。缺少分母和业务上下文时，“拦得多”并不等于策略更好。

误伤处置从命中规则、请求标识和匹配字段入手。例外范围应尽可能落在明确入口、路径、来源或调用身份，并有到期和复验。不能为了一个文件上传接口关闭整个租户防护。例外上线后同样用合法与不合法样本验证，确保扩大范围没有越过批准边界。

还要考虑安全组件的容量和失效模式。检测、代理或外部认证增加了新的处理环节；达到容量时会排队、拒绝还是按策略降级，应在交付中明确并演练。安全与可用性的取舍不能由故障现场随口决定，更不能默默从拒绝变成全放行。现场采用旁路或串联等形态，依据实际 BOM 与架构核对。

## 恢复设计课堂：先恢复钥匙和目录，还是先恢复业务机器

恢复不是按照产品清单从上到下开机，而是按依赖关系组织。身份、DNS、时间、证书、密钥、镜像和备份目录可能被多个业务共享。如果备份解密依赖的密钥服务自己只备份在同一份加密备份里，就形成循环依赖，必须在设计阶段拆开。独立保存的恢复材料仍要安全保管和定期验证。

基础纸面练习列出应用、数据库、镜像仓库、密钥服务与备份索引，给每条恢复依赖画箭头。故障步骤让密钥服务恢复依赖自己的密钥，预期识别出无法启动的循环。恢复方案由安全与平台团队提供受控的独立恢复入口，再验证先后顺序。清理只还原依赖图，不导出真实密钥。

恢复成功还要测业务数据一致性、身份边界和观察链。数据库能启动但应用凭据失效，用户仍无法使用；应用能访问但审计全部断流，也未满足安全交付要求。RTO 从用户受影响到服务满足约定目标计量，准备材料、恢复平台、恢复数据、追平与验收都占时间，不能只记虚拟机开机速度。

最后分清商业授权与技术可行性。某功能在公开方案里出现，不代表客户已采购；License 允许使用也不证明配置正确；支持合同有效也不表示任何跨版本组合都受支持。交接表把 BOM、授权、兼容矩阵与实测证据并排保存，疑点交原厂确认，不绕过许可、不猜内部修复命令。

### 值班交接的最后一项：未完成条件不能丢

交接时分列已恢复业务、剩余冗余风险、仍在重建的对象、临时安全例外与待原厂确认项。每项写下一次检查依据、责任人和停止条件；不能只留下“观察中”三个字。若下一班不知道何时结束观察，临时放行和告警静默就容易变成永久配置。

合成报告的复跑应使用新的输出名，避免覆盖上一轮证据。健康样例的零退出码、退化样例的二退出码与无效输入的失败是不同结果，接入自动化时不得全部归并为“脚本成功”。本轮新增安全策略、依赖恢复和审批状态课仅作纸面推演，没有发放凭据、调用真实云接口、修改安全设备或运行生产恢复。
