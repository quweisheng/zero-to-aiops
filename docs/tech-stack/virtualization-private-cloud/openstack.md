## 官方知识地图

```text
OpenStack IaaS（基础设施即服务）
  -> 身份与目录：Keystone
  -> 计算：Nova 与 Placement
  -> 网络：Neutron
  -> 镜像：Glance
  -> 块存储：Cinder
  -> 对象存储：Swift
  -> 控制台：Horizon
  -> 数据库、消息队列与高可用
```

`IaaS` 是 Infrastructure as a Service，即通过 API 提供计算、网络和存储等基础资源。

## 场景开场

业务申请一台虚拟机，界面最终显示 ERROR。问题可能不在“虚拟机服务”本身：身份认证、规格容量、镜像下载、网络端口、存储卷或计算节点任一环节失败，都会让创建流程中断。

## 一句话人话版

OpenStack 把数据中心的计算、网络和存储包装成带租户隔离的 API，让用户像使用公有云一样申请资源。

## 小白可能会问

- OpenStack、VMware vSphere 和 Kubernetes 分别管什么？
- 为什么创建一台云主机会经过这么多服务？
- Project、User、Domain 和 Role 是什么关系？
- 控制节点正常，为什么实例仍然创建失败？

## 为什么要学

岗位点名 IaaS，并要求 Rancher、Kubernetes 和存储经验。OpenStack 常承载 Kubernetes 节点、负载均衡器和持久卷；其告警、日志、资源拓扑与变更记录也是 AIOps 根因分析的重要上下文。

## OpenStack 是什么

OpenStack 是一组互相配合的开源云服务。它不是单个进程：Keystone 管身份，Nova 管计算生命周期，Neutron 管网络，Glance 管镜像，Cinder 管块存储，Placement 记录资源供给与分配。

## 它解决什么问题

- 通过 API 自助申请和回收基础设施。
- 用 Project 隔离不同团队和环境。
- 统一调度多台计算节点上的资源。
- 把网络、镜像和存储接入同一资源生命周期。
- 为配额、审计、自动化和容量管理提供标准接口。

## 核心原理

### Keystone 身份、项目和目录

- **是什么**：Keystone 负责认证、Token、Project、Role 和服务目录。
- **为什么需要**：多租户云必须知道“谁以什么权限访问哪个项目”。
- **怎么工作**：客户端提交凭据换取 Token，再从服务目录找到 Nova、Neutron 等 API 地址。
- **怎么看或怎么用**：用 `openstack token issue`、`openstack catalog list` 验证身份和目录。
- **坏了怎么查**：先查凭据、Project、Domain、时间同步和 endpoint，再查 Keystone 日志。

### Nova 与 Placement

- **是什么**：Nova 管云主机生命周期，Placement 管 CPU、内存等资源供给和分配记录。
- **为什么需要**：创建实例需要从众多计算节点中找到满足规格的目标。
- **怎么工作**：Nova API 接收请求，调度器查询 Placement，选定计算节点后由 nova-compute 执行。
- **怎么看或怎么用**：看 server event、调度器日志、hypervisor 资源和 allocation candidate。
- **坏了怎么查**：出现 NoValidHost 时检查配额、库存、聚合、trait、资源超售与 Placement 同步。

### Neutron 网络

- **是什么**：Neutron 管 Network、Subnet、Port、Router、Security Group 和 Floating IP。
- **为什么需要**：云主机需要租户隔离、地址分配、路由和访问控制。
- **怎么工作**：API 创建逻辑资源，网络后端和 Agent 在节点上实现交换、路由或隧道。
- **怎么看或怎么用**：从 Port 状态、绑定主机、安全组、路由和底层网络逐层检查。
- **坏了怎么查**：先区分 DHCP、二层、三层、SNAT/DNAT 和安全组问题，不要只执行 ping。

### Glance 与 Cinder

- **是什么**：Glance 保存镜像元数据和镜像内容入口；Cinder 提供可挂载的块存储卷。
- **为什么需要**：镜像是系统模板，卷负责独立于实例生命周期保存数据。
- **怎么工作**：创建实例时下载或访问镜像；挂卷时 Cinder 后端创建卷并返回连接信息。
- **怎么看或怎么用**：检查 image/volume 状态、后端容量、服务状态和连接日志。
- **坏了怎么查**：镜像卡住查存储与格式，卷挂载失败查后端、协议、网络和主机映射。

## 架构和数据流

```text
用户 / 自动化
  -> Keystone 获取 Token 与服务目录
  -> Nova API 接收创建请求
  -> Placement 与 Scheduler 选择计算节点
  -> Glance 提供系统镜像
  -> Neutron 创建并绑定端口
  -> Cinder 按需创建并挂载卷
  -> nova-compute 启动实例
```

控制服务常依赖数据库保存状态、依赖消息队列传递异步任务。API 返回已受理，不代表后端流程已经全部成功。

```yaml
clouds:
  lab:
    auth:
      auth_url: https://keystone.example.internal/v3 # Keystone v3 认证入口
      username: learner # 实验账号，不要使用全局管理员
```

这里有意省略密码。`clouds.yaml` 不是 PowerShell 脚本，不要假定 `${OS_PASSWORD}` 会在 YAML 里自动替换。使用平台提供的应用凭据、受保护的 `secure.yaml` 或进程环境变量注入认证材料；公开仓库只保存无凭据模板。

## 命令 / 配置 / API 字典

| 名称 | 作用 | 常用写法 | 正常结果 | 常见坑 |
|---|---|---|---|---|
| `token issue` | 验证认证链路 | `openstack --os-cloud lab token issue` | 返回 Token 与 Project | 本机时间偏差或 Domain 错误 |
| `server list` | 列云主机 | `openstack server list --long` | 返回状态、网络和规格 | 查错 Project |
| `network list` | 列逻辑网络 | `openstack network list` | 返回网络 ID 和状态 | 只看网络，不看 Port 绑定 |
| `volume list` | 列块存储卷 | `openstack volume list` | 返回卷状态与大小 | `available` 与 `in-use` 含义混淆 |
| `compute service list` | 看计算服务心跳 | `openstack compute service list` | State 为 up | 服务 up 不代表容量满足请求 |

## 在 AIOps 中的作用

OpenStack 能提供 API 延迟、服务心跳、消息堆积、资源容量、实例事件和租户拓扑。AIOps 可将“实例 ERROR”与同时间段的调度失败、Neutron Port 异常或 Cinder 后端容量告警关联起来，并触发只读诊断 Runbook。

## 入门实验：生成只读云资产快照

### 实验目标

验证认证与主要服务 API，并把当前项目资源保存为可复盘证据。实验只读，不创建或删除资源。

### 实验步骤

```powershell
$env:OS_CLOUD = 'lab' # 选择 clouds.yaml 中的 lab 配置
New-Item -ItemType Directory -Force openstack-lab | Out-Null
openstack token issue -f value -c expires | Out-File -Encoding utf8 openstack-lab\auth-expiry.txt # 只保存认证到期时间，不输出令牌
openstack server list --long | Out-File -Encoding utf8 openstack-lab\servers.txt # 保存云主机清单
openstack network list | Out-File -Encoding utf8 openstack-lab\networks.txt # 保存网络清单
openstack volume list | Out-File -Encoding utf8 openstack-lab\volumes.txt # 保存卷清单
```

### 验证结果

认证到期时间查询成功，三个清单文件存在。空项目可以没有资源行，但不应出现 401、403 或 endpoint 连接错误。不要使用 `--debug` 收集公开证据，它可能显示请求头、令牌和环境信息。

### 如果没有成功

1. 401 先查账号、密码、Domain 和 Project。
2. 403 查 Role 与策略，不要换成管理员绕过问题。
3. 连接错误查 DNS、证书、代理和 endpoint interface。
4. 单个服务失败时用 `openstack catalog list` 核对该服务地址。

## 常见故障排查

| 现象 | 先检查 | 处理思路 |
|---|---|---|
| 实例长期 BUILD | request ID、任务状态、消息队列 | 沿 Nova 请求链路定位停点 |
| NoValidHost | 配额、Placement、规格、聚合、容量 | 找出未满足的调度条件 |
| 实例有 IP 但不通 | Port、DHCP、路由、安全组、底层网络 | 按二层到七层排查 |
| 卷卡在 attaching | Cinder 后端、连接协议、计算节点日志 | 修复后端或残留连接状态 |
| API 间歇超时 | HAProxy、API worker、数据库、消息队列 | 关联延迟、连接数和队列积压 |

## 老师带你补齐前置知识：先把一台云主机拆开

先别急着装一整套云。我们一起看业务同事交来的申请：“我要一台 4 核、8 GiB 内存的 Linux 服务器，能访问订单数据库，还要能重启后保留附件。”这句话里至少有四种不同需求：计算规格、操作系统来源、网络连通、数据生命周期。OpenStack 的多个服务，正是围绕这些边界分工。

物理服务器是真实的主板、处理器、内存和磁盘。Hypervisor（虚拟机监控器）把硬件能力分给虚拟机；KVM 是 Linux 的硬件虚拟化能力，QEMU 提供虚拟设备等配套能力。Nova 调用这一层来开关虚拟机，它自己不会模拟一颗 CPU。你在云平台点“关机”，也不等于把宿主机电源拔掉。

vCPU（虚拟处理器）是一份供虚拟机使用的处理器执行资源。4 vCPU 通常不承诺永久独占 4 个物理核心。是否独占、是否允许超售，要看规格额外属性、CPU 绑核和资源池政策。GiB 是按 1024 计算的容量单位，和按 1000 计算的 GB 不完全相同；做容量账时必须统一单位。

镜像像一份系统母版，卷像一块可独立管理的硬盘，快照像某一时刻的状态记录。它们不是互相替代的三个名字。创建自定义镜像前要清除机器身份和秘密；保留卷不等于有异地备份；快照成功也不证明数据库可以正常恢复。

现在请你用自己的话复述：Nova 决定虚拟机生命周期，Glance 管系统模板，Cinder 管卷，而客户机里的文件系统和数据库仍由应用团队管理。如果只能说“这些都是存储”，下一步很容易把“卷已挂载”误判为“业务数据已可读”。

### 身份为什么要分四层

User（用户）回答“谁来操作”；Project（项目）回答“资源归哪个团队或环境”；Role（角色）回答“在这个范围能干什么”；Domain（域）用于组织身份对象，避免大组织里的同名用户、项目混在一起。它们不是四级文件夹，角色赋予是一条带范围的关联关系。

例如同一个人可以在测试项目当成员，在生产项目只读。认证通过得到有范围的 Token（访问令牌）以后，Nova 仍按策略检查这次动作是否允许。401 更接近身份材料未被接受，403 更接近已经认出你但不允许做这件事。看见 403 就换管理员，会绕过本来应该被验证的隔离边界。

Endpoint（服务入口地址）回答“去哪找服务”。一个服务可能有 public（面向用户）、internal（内部）和 admin（管理）入口；具体配置随部署而异。能打开 Horizon，不代表本机能访问服务目录里的 internal 地址。先检查入口类型、DNS 名称解析、TLS 证书和路由，再排查密码。

安全观察可从 `openstack catalog list` 和 `openstack endpoint list` 开始，后者可能需要管理权限。预期是找到服务类型、区域和接口类别，而不是把完整输出发到公网。记录脱敏后的地址类型与是否可达就够了。

## 跟着一次创建请求，把“异步”真正听懂

老师先问你：前台说“申请已收下”，你能立即住进房间吗？不能，后台还要确认空房、做清洁、发门卡。OpenStack 返回请求受理后，也要协调好几个服务；它们不是一起按下一个数据库提交按钮。

```text
用户请求（带身份与规格）
  -> nova-api（计算接口：校验并登记）
  -> scheduler（调度器：找满足条件的宿主）
  -> Placement（资源账本：库存与分配）
  -> conductor（协调器：协调构建和数据库访问）
  -> nova-compute（计算执行者：操作虚拟化层）
  -> Neutron / Glance / Cinder（网络 / 镜像 / 卷）
  -> 虚拟机启动 -> 客户机初始化 -> 应用验收
```

图是帮助理解的职责图，实际调用会交错或并行。数据库记录资源状态，消息队列传递内部任务；RPC 是 Remote Procedure Call，意思是“让另一个服务帮我执行一个动作”。网络丢包、任务重投、服务重启，都可能使不同视图短暂不一致。官方 [Nova 架构](https://docs.openstack.org/nova/latest/admin/architecture.html) 是继续阅读的入口。

`vm_state` 是实例主状态，`task_state` 描述正在进行的动作，`power_state` 是观察到的电源状态。不同 API 权限和版本可能显示不同扩展字段。任务未结束时，不要只盯 `ACTIVE` 或 `ERROR`；先问正在创建、迁移、扩容还是删除，最后一次成功在哪一步。

Request ID（请求标识）是跨日志追查的线索，但各服务间不一定始终共用一个编号。还要保存实例 ID、卷 ID、端口 ID、时间窗和关联请求 ID。日志时间必须统一时区，主机时钟偏差也要考虑，否则你会把后发生的错误看成前置原因。

假设创建请求超时，客户端不知道后台结果。正确操作是先按实例名、资源 ID 或请求事件查询已受理结果，确认是否存在残留资源，再决定重试。重新点十次可能让十份任务同时消耗卷和 IP。自动化要给请求设超时、轮询退避、终止状态和业务侧去重记录。

### Placement 为什么不是“看一眼 top”

调度资源账本记录的是可分配库存和已承诺资源，`top` 看的是此刻 CPU 活跃程度。两者回答不同问题：一台机器当前很闲，也可能已经给其他实例承诺完内存，或不满足专用 CPU、NUMA、GPU 等条件。

Flavor（规格）除了 vCPU、内存和磁盘，还可能有 extra specs（额外约束）。Trait（特征）表示资源提供者具有的能力；Aggregate（聚合）把具有共同属性的宿主组织起来；Availability Zone（可用区，AZ）是给用户选择的故障或调度范围，具体物理含义由运营者设计。不能仅凭 AZ 名称认为它们位于不同机房。

`NoValidHost` 应理解成“所有候选都没通过条件”，不是“CPU 一定满了”。先看配额，再看目标 AZ 和规格，再看 Placement 库存、分配和特征，最后才分析过滤器与宿主故障。资源账本异常时要使用对应版本支持的修复流程；直接删数据库记录可能留下真实虚拟机而账本认为资源空闲。

## 网络课堂：能分清四件事，就能少走很多弯路

Network（网络）是逻辑二层范围，Subnet（子网）是 IP 地址段和分配规则，Port（端口）是设备接入网络的连接点，Router（路由器）负责在不同网络之间转发。这里的 Port 不是 TCP 的 80 端口，两者同名但所属层次不同。

一块虚拟网卡连接 Neutron Port，Port 带有 MAC 地址、固定 IP、安全组等信息。控制面创建了 Port，执行节点还要完成绑定和转发表配置。端口存在但绑定失败，实例就像登记了门牌，却还没有接通道路。使用 `openstack port show PORT_ID` 检查设备、固定 IP、状态和绑定线索，管理员能看到的字段可能更多。

```text
客户机应用
  -> 客户机 IP / 路由 / 防火墙
  -> 虚拟网卡与 Neutron Port（接入点）
  -> 虚拟交换与隧道（跨宿主传输）
  -> 虚拟或物理路由（跨网段）
  -> 地址转换 / 外部网络
  -> 对端服务及返回路径
```

Provider Network（提供者网络）通常映射已有的物理网络；Self-service Network（自助网络）让租户按需组织隔离网络。后者常借助 Overlay（覆盖网络）封装，像在外层信封写宿主地址、内层信封写虚拟机地址。底层物理网络叫 Underlay（承载网络）；外层路不通，内层地址再正确也没用。具体 OVS、OVN 或厂商驱动要按部署识别，不能把一种 Agent 命令用于所有环境。参见 [Neutron 网络概念](https://docs.openstack.org/neutron/latest/admin/intro-os-networking.html)。

MTU（最大传输单元）限制一次传送的数据包大小。隧道还要添加外层头，所以“短 ping 成功、较大 HTTPS 响应卡住”值得检查路径 MTU 和分片，不要直接归咎应用。DHCP 是自动发放地址和网络参数的协议；DNS 把名称查成地址；它们可以分别失败。

Floating IP（浮动 IP）常通过地址转换把外部访问映射到实例固定地址，它通常不是直接写在客户机网卡上的第二个地址。SNAT 改源地址，常用于出站；DNAT 改目标地址，常用于入站映射。你要沿去程和回程一起查：请求到达服务器但回复走错网关，客户端仍然会超时。

安全组是允许哪些流量进入或离开端口的规则集合。检查协议、来源、方向、目标端口和实际绑定对象，而不是只问“防火墙开了吗”。先允许来自实验客户端的必要端口，保留应用探针；把所有入站全放通会失去辨别是哪条规则出错的机会。

### 老师给你一张排障次序卡

从客户机本地访问服务成功，只能证明进程和本地路径正常。接着从同网段实例访问，能验证接入与安全组；再从跨网段访问，能验证路由；最后从外部地址访问，补齐地址转换和边界路径。每次只多跨一层，失败范围就缩小了。

如果没有客户机权限，先使用云平台 Port、实例控制台日志、路由和安全组只读证据。客户机文件系统、数据库内容并不会因为你是云管理员就自动成为可公开采集的数据。把“未获得权限，因此这一层待验证”写在记录里，也比猜一个根因可靠。

## 存储课堂：从“卷挂载成功”走到“业务真的能恢复”

Cinder 把后端存储包装成卷 API，驱动与阵列或软件存储交互。Attachment（连接记录）说明某个实例与卷的关联；设备路径说明操作系统看见了哪块盘；文件系统挂载点说明文件从哪里读取。这三层必须对齐。

多路径 Multipath 是到同一存储设备的冗余通路，不是多份数据。两条链路必须指向同一个稳定设备标识；设备名 `/dev/sdb` 可能在重启后变化。排查“挂错盘”时要核对卷 ID、序列号、文件系统 UUID 和挂载点，不能看到盘大小一样就格式化。

卷扩容包括云盘容量变化和客户机分区、文件系统扩展等不同动作。扩容返回成功后，客户机可能尚未重扫设备，文件系统也可能仍用旧大小。反过来，缩容风险更大，不应把扩容命令反着理解。真实操作先按后端、文件系统和目标版本文档确认支持范围。

IOPS 是每秒 I/O 次数，吞吐是每秒传输字节数，时延是一次请求花费的时间。假设每次 4 KiB、每秒 10,000 次，大约是 39 MiB/s；顺序大块传输可能吞吐很高、IOPS 却不大。不能看到“带宽没有跑满”就断言存储没有瓶颈，同步写确认、队列和后端重建都可能抬高时延。

Crash-consistent（崩溃一致）快照相当于某一刻突然断电后的磁盘状态；Application-consistent（应用一致）还需要应用协调，把内存中的关键状态落稳。数据库恢复可能依赖日志重放，有快照但缺少事务日志，仍可能达不到恢复目标。RPO 是最多允许丢多少时间的数据，RTO 是允许多久恢复服务，先用业务语言确定这两个目标再选备份方式。

## 无云环境的第一课：亲手算一次调度与故障余量

你只需要 Windows PowerShell；这个实验不安装 OpenStack，也不访问任何云账号。它模拟“每台宿主必须同时满足 CPU 和内存”的最小约束，帮助你读懂调度失败。真实调度还要增加 NUMA、设备、网络和策略条件。

把下面内容保存为 `placement-classroom.ps1`，在你新建的学习目录运行 `powershell -File .\placement-classroom.ps1`。

```powershell
$hostsForLab = @(
    [pscustomobject]@{Name='host-a'; FreeCPU=8; FreeGiB=4},
    [pscustomobject]@{Name='host-b'; FreeCPU=2; FreeGiB=32},
    [pscustomobject]@{Name='host-c'; FreeCPU=8; FreeGiB=16}
)
$needCPU = 4
$needGiB = 8
$candidates = @($hostsForLab | Where-Object {
    $_.FreeCPU -ge $needCPU -and $_.FreeGiB -ge $needGiB
})
$candidates | Format-Table # 基线只有 host-c 同时满足两个条件
if ($candidates.Count -ne 1 -or $candidates[0].Name -ne 'host-c') {
    throw '基线与预期不同，请检查数字和逻辑运算符'
}

$afterFailure = @($hostsForLab | Where-Object Name -ne 'host-c')
$remaining = @($afterFailure | Where-Object {
    $_.FreeCPU -ge $needCPU -and $_.FreeGiB -ge $needGiB
})
if ($remaining.Count -eq 0) { 'FAULT: NoValidHost in the simplified model' }

$hostsForLab[0].FreeGiB = 12 # 在模型中增加 host-a 内存余量，模拟容量修复
$recovered = @($hostsForLab | Where-Object {
    $_.Name -ne 'host-c' -and $_.FreeCPU -ge $needCPU -and $_.FreeGiB -ge $needGiB
})
if ($recovered.Count -ne 1) { throw '恢复验证失败' }
'RECOVERED: ' + $recovered[0].Name
```

预期先显示 `host-c`，再出现 `FAULT`，最后为 `RECOVERED: host-a`。请你观察：故障后总计仍有 10 个空闲 CPU 和 36 GiB 内存，但不能拼成一台符合要求的宿主，这就是资源碎片的一种形式。真实系统还会因为不能跨 NUMA 节点放置而出现更细粒度的碎片。

故障注入是从候选集移除 `host-c`，恢复是在模型里增加 `host-a` 的内存；没有停真实宿主，也没有改配额。若输出不符，先检查是否误把 `-and` 写成 `-or`、数字是否被改动、数组是否保留了三行。清理只需关闭当前 PowerShell 窗口，内存变量随会话消失；脚本和输出可以保留作为证据。

### 有测试云后，再做一次真实错误闭环

前置条件是云管理员给你一个独立实验 Project、只用于实验的网络和实例，以及允许创建资源的配额。先保存测试实例、安全组和端口 ID，正常从指定实验客户端访问无状态 HTTP 服务。只删除该实验安全组中那一条“允许实验客户端访问 HTTP 端口”的规则，其余不变。

预期客户端超时，实例仍然 `ACTIVE`，客户机本地访问仍成功，端口仍然绑定。记录删除动作和规则 ID，用原参数恢复同一条必要访问规则，再确认远程 HTTP 恢复。这个实验教的是逐层验证，不是全局关闭网络安全。不同云的规则创建和删除权限不同，所以实际命令应从 `openstack security group rule create --help` 和现场授权范围取得，不能把生产组当练习对象。

完成后删除自己创建的无数据测试资源，按端口、实例、卷、浮动 IP 清单核对残留。不要依据“名称里带 lab”批量删除。基础模型实验和真实平台实验要分别记录，前者通过不等于后者已经做过。

## 生产设计课：控制面健康不等于整朵云健康

现在把业务要求换成“一个宿主坏掉不能拖垮所有订单服务”。我们首先分故障域：宿主、电源、机架交换机、存储池、可用区和机房。两台虚拟机放在同一宿主，不满足宿主故障隔离；放在不同宿主但共用一个无冗余存储控制器，也不能称为端到端高可用。

API 服务可在负载均衡后多副本部署，但数据库、消息队列、网络后端和证书服务也必须单独规划。控制面不可用时，已有实例可能继续运行，却不能完成新建、迁移、挂卷等动作。这个特征既是判断故障范围的线索，也说明“已有业务正常”不能证明云平台完全健康。

Nova Cells（计算单元）用于组织扩展和隔离部分控制依赖，不能把一个 Cell 自动当作独立机房。存储复制、管理数据库备份、镜像备份和云主机数据备份要分别规划；备份恢复演练还应包含服务目录、策略、密钥保护和数据库版本。

Evacuate（故障疏散）与 Live Migration（热迁移）解决不同情形。热迁移依赖源宿主仍可参与；疏散需要防止原宿主重新带着同一实例写盘。Fencing（隔离故障节点）是在无法确信旧节点停止时切断其写入能力，保护数据单写者约束。没有确认隔离就强制启动第二份数据库，可能把可用性问题变成数据损坏。

容量报告至少分配额余量、Placement 承诺、宿主实际峰值和故障后余量四本账。假设三台宿主各能承载 100 单位工作，总业务峰值 210；失去一台只剩 200，就不满足单节点故障后的目标。不能把“平均使用率 70%”解释成一定安全。

升级时先核对发行版支持路径、各服务版本顺序、数据库迁移、消息协议和驱动兼容。新控制面与旧计算节点之间的兼容不是无限期保证，数据库 schema（结构）升级也不总能逆向。回滚计划必须明确在哪一步还能换回旧组件、在哪一步需要从备份恢复、谁宣布中止以及恢复多久。

AIOps 在这里适合把同一时间窗的实例失败率、消息积压、卷后端时延、宿主告警与变更记录连接起来。先让规则回答“失败是否集中在同一个 AZ、镜像或存储池”，再让模型辅助排序假设。自动化第一步执行只读诊断；涉及疏散、重建、强制解挂载时，必须带资源身份、前置条件、审批和恢复验证。

## 大厂面试课堂：从一句话答到三分钟

**30 秒回答：**OpenStack 是通过 API 管理计算、网络和存储的模块化 IaaS。Keystone 处理身份，Nova 协调实例生命周期，Placement 维护资源库存与分配，Neutron 实现网络对象，Glance 和 Cinder 分别提供镜像与卷。创建是跨服务异步流程，排障要从请求和资源 ID 找到停在哪一步。

**3 分钟回答：**先用一台实例的创建讲价值：租户提交规格、镜像和网络，身份和策略检查通过后，由调度器寻找同时满足库存和约束的宿主，计算服务协调镜像、端口和卷，再启动客户机。API 受理、平台状态、客户机启动和业务可用是不同验收阶段。状态保存在各服务数据库中，消息队列协调异步任务，失败时可能产生重试和残留，因此自动化要保存意图、查询结果并避免重复创建。

接着谈三个取舍。第一，超售提高资源利用率，但要按工作负载峰值和故障余量约束；第二，自助覆盖网络提高租户灵活性，但多了隧道、MTU 和网络后端排障成本；第三，控制面多副本改善管理可用性，却不自动保护实例里的数据库。最后说验证方法：用请求事件和资源 ID 连接 API、调度、端口、卷和宿主证据，通过分层探针确认业务恢复，并把故障域、容量和备份恢复写进设计。

老师继续追问你：

1. **“总内存很多为什么不能创建？”** 总量不能证明单个候选满足内存、CPU、NUMA、设备和策略约束；展示前面的调度模型，再说明真实 Placement 账本与宿主现状的区别。
2. **“消息队列断了，所有实例会关机吗？”** 不应这么推断。已有客户机由虚拟化层执行，管理任务和状态同步先受影响；继续检查网络或存储是否也依赖受损组件。
3. **“实例 ACTIVE，应用失败，云平台能免责吗？”** 不能仅凭状态免责。要一起验证虚拟网卡、存储路径、客户机和应用，明确证据责任边界。
4. **“为什么不直接改数据库为正常？”** 修改展示状态不会补回真实端口、卷或虚拟机，还可能破坏分配账本。应恢复依赖并用版本支持的协调工具处理残留。
5. **“两地双活怎样回答才可信？”** 先问业务一致性和 RPO/RTO，再分别设计网络、控制面、存储与数据库仲裁；明确网络分区时谁可写以及如何隔离，不能只画两个机房和一条复制箭头。

事故复盘题是：“只有新创建的实例失败，已有订单请求正常，昨天更新过基础镜像。”先以成功旧镜像和失败新镜像做对照，检查镜像格式、启动模式、驱动和初始化；同时比较 AZ、规格与卷后端排除共同原因。暂停分发新镜像并保留失败实例证据，用已验证旧镜像在测试项目重现成功，之后再小批恢复发布。证据不能支持镜像根因时，继续沿调度与网络链路调查，不因时间相近就提前结案。

## Nova 精讲课堂：资源分配与虚拟机进程为什么会短暂不一致

先区分“资源账本已经记账”和“虚拟机已经运行”。Placement 保存资源提供者的库存、用量和约束，Nova 根据候选执行构建；账本中的 allocation（分配记录）用于防止重复承诺资源，但它本身不是一个 QEMU 进程。构建中途失败时，资源和外部对象可能要通过回滚或后续修复释放，因此短暂不一致必须结合任务状态判断。

看到宿主机很空但调度报 `NoValidHost`，先别只加 CPU。规格可能要求专用 CPU、NUMA 拓扑、巨大页、某种 trait（能力标签）、可用区或反亲和；资源提供者库存、reserved（保留量）、allocation ratio（分配比例）和已分配记录也会影响结果。把“总空闲内存”与“满足这一规格的可用候选”分开，是调度排障最重要的一步。

迁移更能体现账本语义。迁移期间源和目标可能同时占用资源承诺，直到切换成功并完成确认或清理。不要看到两边都有记录就立即删除其中一份，否则可能让另一个新建任务错误地使用仍被迁移占用的容量。先查实例动作、迁移记录、源/目标进程和对应分配关系，再按版本支持的修复工具处理。

Cells v2 把计算控制规模划分为多个单元，单元内有自己的计算服务相关数据库和消息范围，全局仍有 API 层等共同组件。它帮助限制某些故障和扩展范围，但不自动等于租户安全边界，也不等于可用区。一台 API 正常不能证明所有 cell 都能构建实例；失败若集中在某个 cell，取证要限定对应数据库、消息队列与计算服务，而不是重启全云。跨 cell 移动有单独的支持条件，参阅 [Nova 跨单元规格调整](https://docs.openstack.org/nova/latest/admin/configuration/cross-cell-resize.html)，不能把其冷迁移能力误写成任意跨 cell 热迁移。

## 热迁移精讲：不是把一台正在工作的电脑瞬间复制过去

Live Migration（在线迁移）需要把运行状态转移到另一宿主，尽量缩短暂停。典型预复制会先搬内存，源虚拟机继续运行并继续修改部分内存，再复制这些脏页，最后短暂停机切换。若脏页产生速度长期高于有效复制速度，就可能难以收敛。数据库写入和内存密集型任务比空闲虚拟机更难迁移，不能用空机演练承诺所有业务零抖动。

存储路径也不同：共享存储时目标可访问同一份虚拟磁盘，仍需协调访问与切换；块迁移还要搬磁盘数据，带宽、时间与空间需求更大。卷驱动、多路径、CPU 兼容、网络端口迁移、NUMA/大页/直通设备都会影响是否支持。VF、GPU 直通或专用硬件实例不能默认按普通虚拟机迁移，先查实际发行版和驱动支持矩阵，并参阅 [Nova 在线迁移说明](https://docs.openstack.org/nova/latest/admin/live-migration-usage.html)。

一个 64 GiB 内存虚拟机通过有效 4 GiB/s 路径传输，首轮内存复制理想下界约十六秒，后续脏页与切换另算。如果业务每秒新增五 GiB 脏页，这个路径可能追不上。数字用于理解收敛约束，不是实际迁移参数建议。生产要监控复制速率、剩余数据、暂停、业务延迟及源/目标负载，并明确何时取消、何时停止新迁移，避免把整个资源池同时拖入迁移高峰。

Fencing（隔离旧执行者）在故障疏散更关键。宿主与控制面断联，不等于它真的停止运行。若在另一宿主启动同一共享盘的写入者，而旧宿主其实仍在写，就可能形成双写损坏。自动恢复必须依赖可信隔离与支持的存储语义，不能用“ping 不通”作为关机证据。先保护数据再追求恢复速度，这是大厂故障题经常追问的边界。

## Neutron 精讲课堂：端口、绑定和地址分别回答什么

Port（端口对象）包含 MAC、固定 IP、安全组与绑定等信息，是连接虚拟机与网络的重要对象。IP 分配成功只证明地址被记录，不证明虚拟网卡已在目标宿主正确接入。绑定决定端口由哪个宿主及后端方式实现；Nova 与 Neutron 的动作互相衔接，状态短暂不同步要看创建或迁移阶段。

同一套 Neutron API 可以采用不同网络后端，例如传统代理架构或 OVN。OVN 有逻辑网络模型、控制组件和南向数据库等职责，不能把旧版 Linux Bridge/OVS agent 的命令与日志路径无脑套到所有部署。排障第一步记录实际插件、驱动、版本和拓扑，后面才选工具。本文给的是共同推理链，不代替发行版运维手册。

端口安全和安全组限制流量或地址使用，allowed address pairs（允许地址对）等能力常用于受控虚拟 IP 场景。它们不是让所有虚拟机随便伪造地址的开关。负载高可用需要浮动虚拟 IP 时，要同时设计谁拥有地址、如何切换、底层能否识别、反欺骗规则和回切，不能只在客户机加一个地址就宣称高可用完成。

DHCP 为客户机提供地址配置，Metadata Service（元数据服务）向实例提供初始化信息；不同后端的路径实现不同。虚拟机能拿到 IP，不证明能取到初始化数据；初始化数据取不到，可能导致账号或脚本未完成。观察客户机日志、网络路径和后端服务，禁止把真实 user-data、密钥或含凭据的元数据响应保存到公共学习仓库。

## Cinder 精讲课堂：挂载状态不能替代文件系统一致性

Volume（卷）可在实例之外独立存在，Attachment（挂接关系）描述它与实例的连接。卷状态为 `in-use`，不一定证明客户机内已有文件系统挂载；Linux 看见块设备，也不代表数据库打开了正确的数据目录。验收要串起卷 ID、挂接对象、稳定设备标识、文件系统与业务目录，而不是只比较 `/dev/sdb` 这种可能变动的名字。

多挂载是特定卷类型与后端支持的能力，不自动让普通文件系统支持多个主机并发写。即便底层允许两台连接同一块盘，文件系统和应用还要有集群协调、锁和隔离，否则元数据容易损坏。把块设备共享误认为共享文件服务，是初学者很危险的混淆；需要文件语义时评估 Manila 或其他受支持共享文件方案。具体能力边界见 [Cinder 多挂接说明](https://docs.openstack.org/cinder/latest/admin/volume-multiattach.html)。

扩容要经过后端卷、客户机设备、分区/逻辑卷与文件系统等层。快照则涉及崩溃一致性和应用一致性：在任意时刻冻结块状态，数据库可能需要日志恢复；若要求业务事务一致，应由数据库或应用配合准备并验证恢复。卷快照与独立备份的故障范围、密钥和保留机制不同，云平台控制台绿色不替代恢复测试。

## 控制面事故课堂：消息队列恢复后为什么不能立即放开所有任务

消息队列负责服务之间的协调调用，不是长期业务状态的唯一数据库。故障时任务可能超时，恢复后可能积压、重投或继续完成原动作。若客户端此时又无上限重试，就会制造任务风暴和残留对象。先统计受影响的请求与资源，限制新任务进入，逐类确认终态与补偿结果，再逐步恢复创建流量。

数据库、消息队列和身份服务各自的高可用也不是简单“多装几份”。需要确认一致性模型、仲裁、连接池、证书、备份与恢复顺序。Keystone 的令牌验证与密钥分发会影响跨节点认证，系统时间差会放大过期判断问题；不要在多个节点各自随意轮换密钥。版本相关轮换和恢复操作必须按官方流程，先在测试环境验证旧令牌的过渡行为。

面试可以用一场完整事故作答：新建虚拟机全部卡住，但旧业务正常。我先证明故障属于控制路径，按请求编号与实例编号找共同停止阶段；如果消息队列异常，保护现有计算进程并暂停集中重试，修复队列后先验证一个测试创建及其网络、卷与客户机，确认残留和配额恢复，再小批放开。回滚或补偿只针对已确认对象，不能通过全云重启把诊断问题扩大为业务事故。

学习到这里，你应能把 OpenStack 看成多个持续协作的控制系统，而不是一组需要背诵的希腊神名字。下一步用本地模型记录资源约束，再在授权测试云用真实请求与对象关联验证同样的推理；没有测试云的部分就标注桌面推演，不写成生产实测。

### 老师再追问：只读采集账号为什么也要设计生命周期

前面的资产实验能导出表格，但表格存在并不能证明采集完整。先预测：同一个账号切换项目后，为什么服务器数量可能突然变成零？可能确实没有实例，也可能选择了错误项目、区域或服务接口，还可能角色不允许查看其他项目。不能先把零解释成所有实例都被删除。一次可信采集需要同时留下查询范围、成功状态、采集时间、分页完成情况和总数；再按实例标识关联端口、卷与计算主机。显示名称可以重复，资源标识才适合做关联键。

这里引入 Application Credential，即应用凭据：用户为自动化程序委派一组项目内权限，让程序不必保存用户登录密码。它不是“创建出来就天然只读”的账号。默认角色范围、可选择角色及服务策略要一起核对；只允许选择自己拥有的角色，也不意味着那些角色安全。比如用户本来能删实例，沿用其完整角色集合的采集程序也可能拥有删除权。先列出采集确实需要的查询，再让管理员按现场策略授予最小权限。[Keystone 应用凭据指南](https://docs.openstack.org/keystone/latest/user/application_credentials.html)解释了角色委派、过期和轮换机制，具体服务是否执行更细的访问规则仍要看部署配置。

如何验证而不破坏资源？在测试项目使用批准的权限检查或无副作用接口确认允许的查询能成功，同时让管理员核对写接口策略；不要在生产用“试删一台机器”验证拒绝。凭据标识可进入受控台账，秘密值只进入密钥管理系统，不进入源码、截图或资产报表。给凭据设定负责人和有效期，先部署新凭据并确认采集连续，再撤销旧凭据，避免午夜过期后整片图表消失。自动化还要把认证失败与业务资源异常分开告警。

做一个纸面复验：准备两个项目，各有名为 `web` 的不同实例。第一轮按项目与标识记录两条；故障轮故意只按名称合并，预期资产数错误地缩成一条；恢复轮改回项目与标识，验证数量和卷关联恢复。清理时丢弃这两条虚构记录，不更改真实云资源。前面的命令若改变了 `OS_CLOUD` 环境变量，结束时应恢复原值；实验前没有该变量才移除它。报告中注明“未覆盖其他项目”比写“全云巡检正常”更有价值，因为后者扩大了证据本身能支持的范围。
