# Runbook

> 目标：不是写一篇“故障处理说明”，而是能把告警、检查、判断、动作、风险、审批、验证、升级、记录和自动化边界写成故障现场可执行的流程，并能逐步把低风险步骤变成脚本或自动化 runbook。

## 场景开场

同一条告警来了：

```text
OrderApiHighErrorRate
```

老同事会这样处理：

```text
先看 Grafana 的错误率和 p95。
再看 30 分钟内有没有发布。
如果发布后开始升高，先评估回滚。
如果日志是 database timeout，看连接池和慢查询。
如果下游 payment-api 也在 5xx，拉 payment team。
回滚后观察 15 分钟。
```

新人只看到一行红字：

```text
order-api 5xx is above 5%
```

Runbook 的价值，就是把老同事脑子里的处理路径写成别人也能执行、能验证、能升级、能自动化的步骤。

## 一句话人话版

Runbook 是故障处理说明书：把触发条件、影响、检查步骤、判断逻辑、安全动作、风险、审批、验证恢复和升级条件写清楚，让处理过程可重复。

## 官方知识地图

Runbook 可以按这张地图理解：

```text
Runbook（运行操作手册）
  -> Metadata（元数据）
     -> service（服务）
     -> owner（责任人）
     -> alertname（告警名称）
     -> severity（严重级别）
     -> last_updated（最后更新时间）
  -> Trigger（触发条件）
     -> alert rule（告警规则）
     -> user report（用户报告）
     -> maintenance task（维护任务）
  -> Context（上下文）
     -> user impact（用户影响）
     -> dashboards（仪表盘）
     -> logs（日志）
     -> dependencies（依赖）
  -> Preconditions（前置条件）
     -> permissions（权限）
     -> environment（环境）
     -> approvals（审批）
     -> tools（工具）
  -> Diagnosis（诊断）
     -> checks（检查）
     -> commands（命令）
     -> expected output（预期输出）
     -> decision tree（判断分支树）
  -> Actions（动作）
     -> safe actions（经评估的低风险动作）
     -> risky actions（高风险动作）
     -> approval（批准）
     -> rollback（回滚）
  -> Verification（验证）
     -> SLI back to normal（服务指标恢复正常）
     -> alerts stop（告警停止）
     -> user reports stop（用户不再报告故障）
  -> Escalation（升级处理）
     -> owner（责任人）
     -> SME（领域专家）
     -> SEV upgrade（提高事件级别）
  -> Automation（自动化）
     -> inputs（输入）
     -> steps（步骤）
     -> actions（动作）
     -> outputs（输出）
     -> audit（审计）
```

初学路线：

```text
write markdown runbook（用Markdown编写手册）
  -> attach to alert annotation（关联到告警注解）
  -> test in a drill（演练验证）
  -> add commands and expected outputs（补命令与预期结果）
  -> add decision tree（增加判断分支）
  -> automate read-only checks（自动化只读检查）
  -> automate low-risk actions（自动化低风险动作）
  -> require approval for high-risk actions（高风险动作进入审批流程）
```

## 老师带你写一份别人真的能执行的手册

半夜值班的新同学看到“服务异常，请重启”。他不知道是哪套环境、哪个实例、是否允许操作，也不知道重启后应检查什么。Runbook 是“运行操作手册”，核心价值是把不确定的现场判断变成明确的条件、证据与动作。我们先写给第一次接触系统的人读，再考虑自动化。

第一句话写用户影响：“订单查询失败，已有订单写入是否受影响尚未确认。”第二句话写对象：“生产 A 租户的查询服务，只读检查范围为指定实例。”第三句话写停止条件：“发现数据写入异常或目标不符，暂停本流程并升级。”读者先知道边界，后面的命令才有含义。

### 第一课：为什么每个检查都需要预期结果

`curl` 返回一段内容只是事实，HTTP 200 也可能是统一错误页面。手册应同时写响应状态、关键业务字段和时间窗口。检查进程存在不能证明配置已加载，端口监听不能证明下游可用。让每个步骤只回答一个问题，再根据结果决定下一步。

你可以用“如果 A，则执行 B；否则收集 C 并停止”写分支。先检查最近变更和用户影响，再看依赖与资源；风险动作放在证据满足的分支里。不要把诊断和修复混成一串没有停顿的命令，因为执行到中间时可能已经改变了待分析状态。

Precondition（前置条件）是动作开始前必须成立的条件，例如目标所有者、当前版本和可用副本数。Postcondition（后置条件）是执行后应该成立的条件，例如配置值已生效且业务探测恢复。Rollback（回滚）是恢复到经过验证的先前状态；它并不保证所有数据变更都能逆转。

### 基础实验：重复执行为什么只产生一次效果

前置条件是本机安装 Node.js，在仓库根目录运行。这个例子只记录内存中的模拟动作，不访问真实服务。

```powershell
node examples/teacher-led-reliability-lab/lab.mjs runbook
node examples/teacher-led-reliability-lab/lab.mjs runbook --fault
```

正常模式给同一个 `job-42` 两次，输出 `simulatedActions: 1`，第二次为 `DUPLICATE_SKIPPED`（跳过重复请求）。这叫幂等：在规定条件下重试不增加业务效果。故障模式把实际所有者改为另一团队，出现 `PRECONDITION_FAILED`，模拟动作数为 0。先预测，再对照 `state`（条件状态）与 `journal`（执行记录）。

若结果不同，检查命令参数、目录和文件版本。程序结束后内存记录消失，无持久文件或服务要清理。这个范围非常重要：内存集合只演示机制；生产重启后仍需去重，应把请求标识和结果存进持久账本，并用原子条件更新处理并发。

### 故障实验：一份流程在执行期间过期了

纸面增加一个场景：检查时目标版本是 3，真正执行前另一任务升级到 4。若动作仍按版本 3 的假设修改，会覆盖别人的变更。你要在动作提交时再次校验版本，最好让检查和修改由服务端原子完成。这里的原子表示不会被别的并发动作插进半个操作。

把手册修改为“提交时版本不符则拒绝，重新采集状态”，再模拟两个操作同时到达。预期只有符合条件的一次通过，其余停止并留记录。不要在生产做这个竞争实验；用笔记中的状态表演练即可。清理时保留修订前后文档，作为发现陈旧假设的证据。

### 第二课：生产自动化需要哪些状态

任务通常经过待校验、待确认、运行中、成功、失败、补偿中和人工接管。每次状态转移保存输入摘要、目标、版本、时间和结果。任务超时不代表动作未发生；可能是动作成功而结果回传失败。重试前先查询业务状态或利用幂等键确认，避免再次执行不可重复动作。

权限分开设计：收集日志不需要管理员权限，读取状态不等于获准修改配置。自动化身份只获得必要能力，敏感输入不写日志。任务并发、速率和最大影响对象数都设置上限；同一时间大批服务触发告警时，不能让自动化同时重启全部实例。

手册也有版本和发布流程。配置字段变了、监控入口改了、负责人转岗了，旧手册会失效。给手册标明适用版本和最后演练日期，例行用正常及故障案例验证；发现页面链接失效或输出格式变化，先暂停受影响的自动动作再修订。

### 面试课堂：把流程讲成一条状态链

30 秒：“Runbook 把触发条件、只读证据、分支判断、动作、验证、回滚和升级写清楚，让不同值班人员能一致地处理问题。自动化时再增加前置校验、幂等、持久状态和审计。”

3 分钟用本实验说明：读取对象与版本，核对所有者，用任务标识防重，执行前再检查条件，记录结果，验证业务，失败时停止或补偿。强调课堂内存去重与生产持久账本的差别。

追问：“脚本退出 0 就能关闭事件吗？”还需业务验收。“重试安全怎么保证？”解释幂等范围、事务边界与结果查询。“为什么不能把所有步骤自动化？”有些证据不足、风险不可控或需要现场判断，应该明确人工接管条件。设计题是为 100 个服务安排有并发上限的恢复任务；事故题是超时后重试造成重复动作，沿任务账本和业务提交点还原原因。

GitHub 学习证据：一份带正常/异常输出的手册、两个模拟结果、任务状态图、权限表和演练记录。写清哪些操作只是课堂模拟，避免把模板内容当成实测履历。

## 工作坊：从一条告警写出真正可交接的手册

### 第一步，先让新同学知道自己有没有走错门

假设告警叫“订单接口错误率升高”。不要马上贴重启命令，先写服务用途、环境、租户、资源范围、维护团队和变更入口。新同学应能把告警中的对象与资源台账一一对应。如果名称相似但资源标识不同，必须先澄清，而不是“看起来像”就操作。

运行环境也要明确：命令在个人电脑、应用主机、容器里还是运维跳板上执行？需要什么只读权限？命令中的占位符从哪里取得？如果这些没说明，一个技术上正确的命令也可能在错误环境产生完全不同的结果。

把证据入口写成可维护链接或明确的查询条件，并说明时间范围。例如“查看受影响服务过去三十分钟的请求数、错误数和延迟，与告警发生前窗口比较”。不要只写“看监控”，因为读者可能挑到没有业务流量的实例，误以为系统健康。

### 第二步，每个检查只回答一个能决定下一步的问题

问题一：用户是否真的受到影响？比较业务探测、错误响应和入口流量。问题二：影响范围是什么？按区域、租户、版本和接口拆分。问题三：有无紧邻变更？查看实际发布记录与生效配置。这样形成的流程能逐步缩小范围，而不是一上来同时执行二十条命令。

“没有查到”要拆成没有数据、没有权限、查询错误、对象不对和确实未发生。手册为这些情况分别给分支。例如查询接口拒绝访问时，不应继续判断“错误数为零”；应记录权限问题并找授权人员代查，不能为了完成手册临时扩大自己的权限。

输出说明至少包含正常、异常和不确定三类。正常表示检查条件满足；异常表示某个假设需要处理；不确定表示证据不足。对不确定状态安排补采或升级，比强迫二选一更接近真实值班场景。

### 第三步，把诊断权限和修复权限分开

读配置、查看日志、查询健康状态通常属于诊断；重启、改参数、切流、删除和恢复属于改变系统状态。两类步骤可以在同一手册，但应有清晰门槛：谁批准、哪些前置证据成立、目标上限是多少、允许在哪个时间窗口执行。

例如“只回滚一个已确认异常的灰度实例”与“重启所有实例”影响范围不同。即使一个命令很短，也可能覆盖整个服务。危险程度由作用对象、可逆性和业务影响决定，不由命令字符数决定。Runbook 应让读者在执行前复述这三点。

生产中如需紧急授权，应遵循已建立的紧急流程并记录原因、范围和事后复核。不能用“事故紧急”作为永久绕过审计的借口。自动化执行器也应受同样边界约束，不能因为它叫机器人就拥有无限管理员权限。

### 第四步，解释“成功”到底指哪一层

脚本成功退出，只能证明脚本按它的规则结束。接口返回接受，可能只是任务排入队列。任务显示完成，可能只是配置已写入，应用尚未加载。实例健康，也可能只是进程存活，关键业务仍无法访问数据库。把每一层的验收条件写清楚，新同学才不会过早关单。

以配置回滚为例，先确认目标版本恢复，再确认实际运行实例加载了该版本，然后观察关键业务探测、请求错误率和延迟，最后检查没有引入新的影响。观察时间应根据业务流量与故障特征确定，不能没有样本也机械等待十分钟后宣布成功。

若业务流量很低，需要受控的合成探测补足证据；若问题只在峰值出现，离峰恢复验证应记录这个限制并安排代表性演练。把尚未验证的边界写在交接中，比让下一班猜测更可靠。

### 第五步，正确处理超时、取消与重试

超时只表示在约定时间内没有拿到期望结果，不说明远端没有执行。客户端取消也可能仅停止本地等待，远端任务仍在运行。手册遇到超时后，先查询任务标识对应的执行状态和业务结果，再决定继续等待、重试、补偿或人工接管。

幂等键要能稳定代表同一次业务意图。如果每次重试都生成新键，就失去去重效果；如果不同操作误用同一键，又可能错误跳过该做的事。生产持久账本还要规定保存多久、并发如何互斥、结果如何返回、人工修复后如何继续，不能只用内存中的一个变量代表可靠去重。

补偿也不一定是反向执行。例如重新发送通知后，无法收回已经看到的消息；恢复某个配置值，不会撤销它期间产生的所有业务数据。手册应明确哪些状态能回滚，哪些需要业务对账与人工处理。这个边界是高级面试里常见的追问点。

### 第六步，用一次交接测试暴露手册缺陷

课堂演练准备一份只含合成数据的故障包：告警摘要、当前版本、两张指标表和一段脱敏日志。让另一位同学在不询问作者的情况下按手册处理，记录他在哪个术语、路径、权限或分支处停住。作者暂时不要口头补充，停住的地方正是需要补写的内容。

故障注入可以把目标版本改成不适用版本、隐藏一项必要证据，或把接口返回改成“接受但未完成”。预期是执行者识别限制并停止危险动作，而不是想办法把每一步都执行完。恢复演练数据后重新跑一遍，验证修订确实消除了歧义。

清理只处理演练创建的本地材料或独立资源，保留脱敏证据与修订差异。学习成果包括一份可交接手册、三类结果分支、权限表、正常/故障记录和未覆盖事项。面试时说明你用交接测试发现了什么，以及为什么某些步骤仍保留人工判断。

## 进阶课堂：把一份手册变成可控的执行契约

同学，假设审批人同意“把测试服务从两个副本调到三个”，执行前有人却把目标改成了生产，或者把三个改成三十个。按钮仍然显示“已审批”，这次操作就合法的吗？显然不是。审批不是一句永久有效的“你可以操作”，而是针对某个具体计划、目标、时刻和风险条件的许可。下面我们把这个想法拆开，学会从文档走到可靠自动化。

### 计划中的每个字段，都有安全含义

目标名称方便人阅读，但名称可以被复用。同名服务删掉重建后，可能已经不是刚才检查的对象。因此执行计划应记录平台、环境、租户、资源类型、稳定资源标识和当前版本，再写预期状态与允许变化。资源版本像文件的修订号，用来检查“从读到写之间有没有别人修改”；稳定标识则回答“还是不是同一个对象”。两者不能互相替代。

参数要有明确类型和边界：副本数是整数而不是任意字符串，目标必须来自允许范围，批量操作有最大数量，缺省值不能悄悄指向生产。空筛选条件应停止，而不是理解为“所有对象”。如果检查只匹配一个对象，执行却重新按标签查询，期间新加入的对象也可能被操作。稳妥方式是审批明确的对象集合，执行前重新核对集合是否变化；需要扩大范围时重新评估。

输入校验不等于授权。副本数三十是合法整数，但某位操作者不一定有权改三十个副本；资源确实存在，也不代表当前租户拥有它。授权层检查主体与权限，策略层检查对象、额度、维护窗口和风险，执行层再校验实时状态。把这些职责拆开，是为了发现每一道防线具体挡住什么。故障时保留拒绝原因，不让用户通过反复修改参数猜出越权入口。

### 审批必须绑定计划，而不是只绑定工单标题

审批内容至少包含手册版本、精确目标、参数、当前证据、预期影响、回滚条件和有效期限。计划生成后计算内容摘要可以发现后续改动，但摘要本身不是数字签名，也不能证明审批人的身份。真正系统还需要认证、不可由执行者任意改写的审批记录和审计链。若一个人能同时改计划、改审批记录和删除日志，“有审批字段”并没有形成独立保护。

审批等待期间环境可能发生变化。CPU 已回落、服务刚完成第二次发布、原计划的健康副本已减少，都会改变原来的风险判断。执行前应刷新关键证据，并判断它们是否仍支持同一个动作。证据有效期不是随便写一个五分钟：变化很快的副本健康需要更近的观测，比较稳定的资产归属可以采用不同期限。任何未知或过期的关键前置条件都应进入重新检查或升级分支。

AWS Systems Manager 的 `aws:approve` 提供等待人工批准的步骤，可帮助理解“流程在审批点暂停”的含义；它不是所有业务风险检查的替代品。学习官方页面时注意审批主体、超时和步骤输入，在自己的平台上仍需明确批准内容和执行时再次校验的规则。[官方审批动作说明](https://docs.aws.amazon.com/systems-manager/latest/userguide/automation-action-approve.html)

## 故障模拟课堂：请求超时后，究竟有没有执行

想象你发出扩容请求，服务端已经修改副本数，网络却把成功响应弄丢了。客户端看见超时，只能确定“没按时拿到回答”，不能确定“对方没做”。再次请求若是“再加一个”，就可能多加一次；若是“设置为三个”，虽然目标看起来固定，也可能覆盖他人刚刚批准的扩容。幂等不是一句“多次运行没报错”，而是在明确的操作身份、参数和时间范围内，重复请求不会制造额外业务效果。

### 操作编号与业务对象编号要分开

业务对象编号回答“修改谁”，操作编号回答“这是哪一次意图”。同一服务今天扩一次、明天再扩一次，是不同操作；同一次操作因网络问题重试，应保持同一个编号和同一组参数。服务端需要能识别重复编号、拒绝同编号不同内容，并在约定保留期内返回可核对的结果。仅在客户端内存里放一个“已处理集合”，进程重启后就消失，不能作为生产幂等保证。

结果核对称为 reconciliation，可以理解为“对账”：把本地执行记录、远端操作回执和资源真实状态放在一起比较。优先按稳定操作编号查远端结果，然后验证资源是否符合计划；如果远端不支持查操作记录，就要结合审计和资源版本谨慎判断。对象刚好处于期望状态，不证明一定由这次操作造成。AWS 关于安全重试的工程文章也强调请求标识和重复请求语义，具体接口支持范围必须逐项核对。[官方重试与幂等设计说明](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

### 基础组：丢响应，但能查到操作回执

**前置条件**：Node.js 22 或更高版本、已经取得本仓库，在仓库根目录打开终端。本实验不需要 Kubernetes 或 AWS，不使用凭据，不访问网络，也不改变真实资源。模型中只有一个名叫 `lab/order-api` 的虚构对象，初始版本七、副本两个，批准目标三个。先预测：如果响应丢失但回执存在，恢复程序应该再写一次，还是先对账？

```bash
node examples/incident-evidence-classroom/lab.mjs runbook lost-response
node examples/incident-evidence-classroom/lab.mjs runbook lost-receipt
node examples/incident-evidence-classroom/lab.mjs runbook changed-plan
node examples/incident-evidence-classroom/lab.mjs runbook version-drift
node --test examples/incident-evidence-classroom/checks.mjs
```

第一条中的 `lost-response` 表示“写入之后丢失响应”。预期 `writes` 为一，`replicas` 为三，`resubmitted` 为 `false`，即没有再次提交；状态是 `CONTROL_STATE_VERIFIED`，表示模型中的控制状态已经核对，而不是业务恢复。`businessHealth` 明确保持 `NOT_TESTED`，因为程序既没有用户请求，也没有真实健康检查。请把这一限制写在实验结论里，不要把控制接口结果当作业务验收。

程序先记录已提交，再模拟远端原子修改和回执，随后让本地状态进入 `UNKNOWN`，即结果未知；恢复逻辑只查询和核对，不盲目补发。它通过复制 JSON 对象模拟重启前后互不共享的状态视图，**不是真实落盘、断电恢复或分布式事务实现**。真实系统必须另外验证状态存储持久性、远端原子条件写入、并发与访问权限，不能因为课堂测试通过就宣布自动化具备生产可靠性。

### 故障组：回执也丢了，或者计划已变

第二条 `lost-receipt` 表示回执缺失。即使当前副本仍为三，程序应停在 `WAIT_RECONCILIATION`，意思是等待进一步对账；写入次数仍为一且不重发。这不是系统忘了成功，而是目前无法把该状态可靠归属到本次操作。下一步应查审计记录、核对是否有并发操作者，或者升级人工判断，不是为了得到绿色结果自动再跑一次。

第三条 `changed-plan` 把已批准的三个副本悄悄改成八个；第四条 `version-drift` 模拟他人在执行前改动了资源版本。两条都应返回 `REAPPROVAL_REQUIRED`，即需要重新评估和审批，且 `writes` 为零、原副本仍为二。判断标准是没有发生越过前置条件的写入，而不只是屏幕出现“拒绝”二字。现实中版本漂移可能来自无害变更，也可能来自另一场恢复操作，仍要读取差异再决定下一步。

最后的测试同时覆盖本章和 RCA 的证据课堂，共七项。验证时逐项对照状态、写入次数和是否重发，随后让同学只看输出解释四种分支。若结果不符，先确认运行路径和场景拼写，再检查是否误改练习文件；不要连接生产环境找答案。清理只需结束进程，程序不写文件，没有集群、账号或数据需要删除。独立练习是在自己的副本里设计“回执说成功、资源又被别人改动”的案例，预期转人工核对，而不是覆盖别人的新状态。

## 持久执行课堂：控制器宕机后如何接着做

一段脚本从第一行跑到最后一行容易理解，持久执行器则需要把每个重要边界写成状态。至少分清未提交、已提交但结果未知、远端明确完成、验收通过、需人工处理。不能把所有异常都记成失败再从头运行，因为“失败”可能只发生在接收结果阶段。存储里还应有计划版本、操作编号、最后观测时间和相关回执位置，接班者才能知道从哪里继续。

### 多个执行器，不等于同一个任务可以执行多次

为防单机宕机，可以运行多个执行器，但同一任务必须有明确的当前处理者。租约是在一段时间内允许某个执行器处理任务；旧执行器卡住后租约到期，新执行器接手。危险在于旧执行器恢复后还以为自己有效。因此还需要递增的隔离令牌或等价的服务端版本条件，让远端拒绝过期处理者。只有“我拿到了分布式锁”而目标端不检查旧身份，仍可能同时产生两个写入。

队列通常可能重复投递，所以消费成功并不等于业务动作恰好发生一次。需要把任务领取、结果记录、操作编号和远端语义一起设计。若远端提供可靠的幂等键与查询回执，恢复比较容易；若是任意 shell 命令，执行效果难以查证，就应降低自动化等级。不要给所有命令套统一重试次数，有些动作可重做，有些要先核对，还有些一旦不确定就必须停住。

状态存储故障时，默认策略应保护系统。如果执行器无法可靠记录“即将提交”及其操作身份，继续写可能让之后的恢复失去依据。可以保留只读诊断与人工接管入口，但不能偷偷换到无审计的写入路径。跨机房部署还要明确状态一致性、故障切换和旧执行器隔离；这些不是把数据库改成三副本就自动获得的，需要在故障演练中验证分区与恢复行为。

### 超时、取消与补偿是三种不同动作

超时是等待结束，取消是请求停止尚可停止的工作，补偿是为已完成的效果采取另一个业务动作。三者都不保证时光倒流。例如已发出的通知不能“取消到收件人从未看到”，已处理的订单也不能简单删行当作回滚。运行手册要区分哪些步骤可中断、哪些只能等待、哪些需要受控补偿；补偿同样需要权限、前置检查和验收。

失败处理也不能无脑跳下一步。查询可选的辅助图失败，可以记录缺失继续；检查目标身份失败，就必须停止写入。AWS Automation 的步骤有超时、失败路径、取消路径等属性，可用来理解这种控制流，但不同动作能力有边界，不能假设任何步骤都可安全取消或补偿。[官方步骤属性说明](https://docs.aws.amazon.com/systems-manager/latest/userguide/automation-actions.html)

升级执行器时要考虑正在运行的旧任务。新程序如果重新解释旧计划，可能改变参数默认值和失败语义。可把执行定义版本固定在任务中，让旧任务按兼容逻辑完成，或在明确安全点暂停后迁移；不能发布新代码后从第一步自动重放。回滚程序版本也不应丢掉新版本写入的状态字段。设计评审中要问“执行到一半时升级怎么办”，这往往比正常流程更能检验成熟度。

## 生产案例：扩容为什么可能让故障更严重

服务变慢时，新人很容易想到“多加几个实例”。先沿请求路径看：用户到网关，进入应用，再借数据库连接、访问缓存和下游。应用 CPU 满且下游有余量，扩容可能有效；如果数据库已到连接上限，新应用实例反而新增连接竞争；如果慢在外部限流，加实例可能加快撞限流。手册必须把这些分支写清楚，扩容不是对所有高延迟告警都成立的答案。

### 写一个真正可判断的扩容前置检查

记录目标服务当前可用副本、请求量、单实例饱和指标、节点可调度资源、数据库连接预算与关键下游容量。举个虚构估算：每实例连接池最多二十，十个实例的理论上限就是两百，还要加后台任务和其他服务的连接。这不是实际占用值，却能暴露最坏情况预算。若数据库只剩很小余量，应先查等待与持有连接原因，而不是把实例数直接翻倍。

还要查谁拥有副本数。水平自动扩缩容器或 GitOps 控制器可能把手工设置改回去；这不是命令没执行，而是另一控制循环再次写了期望状态。应按团队约定修改真正的配置来源或协调控制器，不能为了避免回写就随意停掉全局控制服务。记录变更前后期望副本、实际就绪副本及控制器事件，才能辨别是调度不足、启动失败还是配置被覆盖。

Kubernetes 的 `--current-replicas` 和 `--resource-version` 可表达扩缩容的前置条件。前者核对当前规模，后者核对资源版本；它们不是身份认证，也不替你评估数据库容量。发生前置条件冲突时应重新读取和判断，不能删掉这些参数继续执行。具体语义以所用版本的 [kubectl scale 官方说明](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_scale/) 为准。

### 业务验收必须考虑流量、窗口与副作用

“三个 Pod Ready”只说明配置的就绪检查通过；“没有新增错误日志”可能因为没流量或采集断了。验收至少同时观察请求量、成功率、延迟、下游饱和及代表性合成请求，并确认观测覆盖没有下降。窗口长度要结合采集周期、流量和业务风险约定，不能全公司统一拿十五分钟当万能证明。低流量服务需要主动验证，不能在零请求时计算出百分之百成功。

回退也要有条件。扩到新规模后错误更高，应先冻结扩大范围、保存证据并评估恢复原规模的风险；若期间流量又增加，盲目缩回旧值可能再次过载。回退计划应包括起始状态、允许条件、停止阈值和无法回退时的升级路线，而不是仅存一条相反命令。涉及数据库结构和数据迁移的发布，更要验证新旧程序兼容，容器镜像退回不代表数据状态可逆。

## 手册生命周期：值班时能找到，半年后仍能用

### 把维护责任写成可验证的流程

手册从草稿、评审、演练、可用到退役，应有清楚状态。草稿可供学习，但告警不能把它当作唯一权威指引；退役手册要说明替代入口，不能留下失效链接等新人踩坑。每次评审记录适用版本、最近演练日期、维护人和触发复审的变化，例如告警表达式、服务拓扑、权限、发布工具或恢复方式改变。日期更新不等于内容已经验证。

文档测试不只检查链接通不通。可以检查必填字段、环境是否显式指定、命令有没有危险默认值、每个判断是否包含未知分支、每个写入是否有审批和验收；再进行一次换人演练，让没参与编写的人照着走。记录他在哪个词上停住、哪条输出看不懂、哪处找不到入口，把真实卡点回写。这样维护的是人的操作能力，而不是格式整齐的模板。

故障时文档服务也可能不可用。关键手册应有受控的离线副本或备用只读入口，带版本和更新时间，并在恢复后对账；离线可读不代表可以绕过在线审批。紧急权限采用组织批准的应急授权流程，有限时、明确责任人和事后审计。把长期高权限密码放进文档，既不能解决访问恢复，也会制造新的安全事故。

### 只读步骤也要控制成本和数据范围

一条全库扫描没有修改数据，却可能耗尽数据库；查询全租户日志可能泄露业务信息。手册应限定时间窗口、服务、最大返回量和请求超时，先查摘要再按证据缩小范围。`tail` 在本地只截断显示，不一定减少远端传输，应优先使用服务端限制。连续失败时按预算停止，不让告警风暴触发成千上万个相同查询，把诊断平台一起压垮。

对自动执行结果，记录操作者、审批、目标、手册版本、开始结束时间、关键判断和脱敏回执，但不记录令牌原文或完整敏感日志。审计可见性与业务数据可见性可以不同，需要按职责授权。观察自动化本身的排队时间、未知状态数量、误拒绝、人工接管率和重复写入拦截，才能知道它究竟在节省时间，还是把风险藏进了后台。

## 面试工作坊：设计一套一百个服务可共用的自动化

回答时先提出边界：哪些动作可自动只读，哪些低风险写入在明确策略内可执行，哪些必须人工批准，哪些暂不支持。公共平台负责认证、计划、审批、状态和审计，服务团队负责目标特有的容量、安全条件与业务验收。不要把一百份服务差异塞进一个无限长脚本；共享执行框架，保持每个动作插件的输入、输出和失败语义明确。

进一步追问“审批后换目标怎么办”，回答批准内容不可变、执行前核对资源身份与版本，差异重新评估；追问“机器宕机重启会不会执行两次”，回答持久操作编号、可查回执、远端幂等或条件写入、未知状态先对账；追问“没有回执接口怎么办”，承认不能凭空保证恰好一次，把该动作降级为人工核对或设计业务专用补偿。

如果问“大模型接进来放在哪”，让模型做手册检索、证据摘要和候选计划，不让生成文本直接变成任意命令。来自日志、网页或知识库的内容只是数据，不是执行权限；即使文本说“忽略审批”，也必须经过固定策略和操作白名单。模型版本更新用历史脱敏样本和故障分支评估，先旁路运行，再在限定对象上试用，保留关闭开关与人工路径。

本章 GitHub 交付可以是一次虚构扩容的计划、审批内容摘要、四个课堂场景的输出、未知状态的接班记录、业务验收表和演练改进记录。说明没有操作真实集群，并列出上线前还要验证的身份、持久性、并发和资源预算。能坦诚说明边界，比宣称“写了一个脚本所以实现全自动运维”更接近成熟平台工程师的表达。

## Runbook 不是什么

Runbook 不是普通知识文章。

| 文档类型 | 目标 | 特点 |
|---|---|---|
| 技术文章 | 解释原理 | 可以长、可以讲背景 |
| 架构文档 | 描述系统 | 关注组件、依赖、设计 |
| Incident 文档 | 记录一次事件 | 关注时间线、决策、结果 |
| Runbook | 指导如何处理 | 关注步骤、判断、动作、验证 |

如果一篇文档只有原理，没有“现在该做什么”，它不是合格 runbook。

## Runbook 和 Incident 的关系

```text
alert（告警）
  -> runbook tells what to do（手册说明该做什么）
  -> incident doc records what happened（事件文档记录实际发生什么）
  -> postmortem improves runbook（复盘改进手册）
```

Runbook 是事前准备。

Incident 文档是事中记录。

Postmortem 是事后学习。

三者形成闭环：

```text
runbook（运行手册）
  -> incident response（事件响应）
  -> postmortem action item（复盘行动项）
  -> runbook update（手册更新）
```

## 好 Runbook 的标准

一份好的 runbook 应该让新人也能回答：

- 这条告警是什么意思？
- 用户影响是什么？
- 先看哪个 dashboard？
- 查哪些日志？
- 执行哪些只读命令？
- 哪些结果说明问题在哪？
- 哪些动作是安全的？
- 哪些动作需要审批？
- 做完后怎么验证？
- 什么时候升级？
- 处理记录写在哪里？

判断标准：

```text
能执行。
能验证。
能升级。
能审计。
能维护。
```
## Runbook 结构

推荐结构：

```text
metadata（元数据）
  -> trigger（触发条件）
  -> impact（影响）
  -> prerequisites（前置要求）
  -> quick triage（快速分类与判断）
  -> dashboards（仪表盘）
  -> checks（检查）
  -> decision tree（判断分支树）
  -> safe actions（经评估的低风险动作）
  -> risky actions（高风险动作）
  -> verification（验证）
  -> escalation（升级处理）
  -> record（记录）
  -> automation mapping（自动化步骤映射）
```

每一节都要短、具体、可执行。

## Markdown 模板

下面是填写框架，不是可以直接操作生产的授权。阈值、窗口和副本数均为虚构示例，必须替换为本服务评审结果。涉及命令的片段使用 Bash 语法；`${变量:?说明}` 会在变量未设置或为空时拒绝继续。即使变量已经填写，真实写入前仍要核对工单批准内容、资源身份、实时版本、容量和回退条件。

````md
# Runbook: order-api HighErrorRate

## 元信息

- 服务: order-api
- 告警: OrderApiHighErrorRate
- Owner: team-order
- 严重级别: page
- 最近更新: 2026-07-02
- 适用环境: prod
- 关联 SLO: order-api-availability
- 相关 dashboard: https://grafana.example.com/d/order-api

## 触发条件

5 分钟内 order-api 5xx 错误率 > 5%。

## 用户影响

用户可能无法下单，订单提交可能失败。

## 先决条件

- 已登录监控系统。
- 有只读日志权限。
- 有 Kubernetes 只读权限。
- 有发布系统查看权限。
- 生产回滚需要 IC 审批。

## 快速判断

1. 打开 order-api dashboard，确认错误率、p95 延迟、请求量。
2. 查看最近 30 分钟发布记录。
3. 查看 order-api 错误日志。
4. 查看下游 payment-api 状态。
5. 查看 MySQL 连接池和慢查询。

## 检查命令

```bash
kubectl --context "${RUNBOOK_CONTEXT:?设置已核对上下文}" -n "${RUNBOOK_NAMESPACE:?设置已核对命名空间}" get pods -l app=order-api
kubectl --context "$RUNBOOK_CONTEXT" -n "$RUNBOOK_NAMESPACE" logs deploy/order-api --since=30m --tail=200 --request-timeout=15s
```

期望输出：

- Pod 不应大面积 CrashLoopBackOff。
- 错误日志中应定位主要错误类型。

这里的部署日志只适合初查，不代表已覆盖全部副本与容器。需要按实例、容器和时间范围核对完整性；错误为空时先检查请求量和采集覆盖。

## 决策树

- 如果错误从发布后开始，评估回滚。
- 如果日志主要是 database timeout，检查连接池和慢 SQL。
- 如果下游 payment-api 5xx 同时增加，升级 payment-api owner。
- 如果只有单个实例异常，先核对其身份、剩余容量及有无本地状态，再按审批方案评估摘除或重启；证据不足时升级。

## 安全动作

### 查看最近发布

风险：低。

审批：不需要。

结果记录：记录发布版本、时间、负责人。

### 摘除单个异常实例

风险：低到中，取决于副本数。

审批：按团队规则。

前置条件：至少还有足够健康副本。

## 高风险动作

### 回滚

风险：中。

审批：需要 IC。

```bash
kubectl --context "${RUNBOOK_CONTEXT:?设置已审批上下文}" -n "${RUNBOOK_NAMESPACE:?设置已审批命名空间}" rollout undo deployment/order-api --to-revision="${APPROVED_REVISION:?填写已核对兼容性的目标修订号}"
```

回滚后验证：

执行前还需确认没有并发发布、目标修订仍可用、配置及数据兼容。`rollout undo` 恢复部署的历史 Pod 模板，不会自动回退数据库迁移、外部配置或业务数据。

- 5xx 错误率回落。
- p95 延迟回落。
- 新版本错误日志消失。

### 扩容

风险：低到中。

审批：按团队规则。

```bash
kubectl --context "${RUNBOOK_CONTEXT:?设置已审批上下文}" -n "${RUNBOOK_NAMESPACE:?设置已审批命名空间}" scale deployment/order-api --replicas="${APPROVED_REPLICAS:?填写已审批副本数}" --current-replicas="${OBSERVED_REPLICAS:?填写刚核对的原副本数}" --resource-version="${OBSERVED_VERSION:?填写刚核对的资源版本}"
```

扩容后验证：

- Pod ready。
- 请求分布正常。
- 延迟下降。

## 验证恢复

以下数值只是示例，先确认本服务约定的统计口径、有效请求量、覆盖和观察窗口，再填写验收阈值。

- 5xx 错误率回到 1% 以下并持续 15 分钟。
- p95 延迟回到 300ms 以下。
- SLO burn rate 恢复到可接受范围。
- 新告警停止触发。
- 用户工单不再增加。

## 升级条件

- 10 分钟内没有明确缓解方向。
- 影响升级为 SEV1。
- 需要数据库、网络、安全团队参与。
- 回滚失败。
- 怀疑数据丢失。

## 处理记录

- 执行人:
- 执行动作:
- 执行时间:
- 结果:
- 后续事项:

## 自动化候选

| 步骤 | 风险 | 是否适合自动化 |
|---|---|---|
| 拉取 dashboard 链接 | 低 | 是 |
| 查询最近发布 | 低 | 是 |
| 查询错误日志摘要 | 低 | 是 |
| 摘除单实例 | 中 | 需要条件和审批 |
| 回滚生产 | 高 | 需要人工审批 |
````

## Runbook 字段解释

| 字段 | 为什么需要 |
|---|---|
| 服务 | 路由和检索 |
| 告警名 | 关联 alert rule |
| Owner | 找到责任团队 |
| 严重级别 | 响应方式 |
| 最近更新 | 判断是否过期 |
| 触发条件 | 知道为什么来这里 |
| 用户影响 | 判断优先级 |
| 先决条件 | 防止执行者卡住 |
| 检查命令 | 快速定位事实 |
| 期望输出 | 知道结果怎么解释 |
| 决策树 | 避免凭感觉 |
| 风险 | 防止危险动作 |
| 审批 | 接入事件流程 |
| 验证恢复 | 防止过早结束 |
| 升级条件 | 不让新人独自硬扛 |
| 处理记录 | 进入 incident / postmortem |

## Alertmanager 中挂 Runbook

告警必须能直接跳到 runbook。

Prometheus alerting rule：

```yaml
annotations:
  summary: "order-api high error rate"
  description: "More than 5% of order-api requests are returning 5xx."
  runbook_url: "https://runbooks.example.com/order-api-high-error-rate" # 示例地址，必须替换为已经发布并验证可访问的手册
  dashboard_url: "https://grafana.example.com/d/order-api"
```

`annotations` 是附加说明，`summary` 是一句话摘要，`description` 是详细解释，`runbook_url` 和 `dashboard_url` 分别是处理手册和仪表盘入口。示例英文描述指“超过百分之五的请求返回服务端错误”，可直接改为中文。这只是告警规则中的片段，不是完整可加载配置；还需告警名称、表达式和持续条件。通知模板必须显式呈现相应字段，添加注解不会保证所有通知渠道自动显示链接。发布后用测试告警核对最终通知中的实际入口。

## Runbook 质量检查

每份 runbook 上线前检查：

- 是否能从告警一键打开？
- 是否写了 owner？
- 是否写了适用环境？
- 是否写了用户影响？
- 是否列出只读检查？
- 是否给出期望输出？
- 是否有决策树？
- 是否区分安全动作和高风险动作？
- 是否写了审批要求？
- 是否写了验证恢复？
- 是否写了升级条件？
- 是否最近演练过？

不合格 runbook 不应该作为 page 告警的唯一处理依据。

## 从人工到自动化

AWS Systems Manager Automation runbook 的概念很适合理解自动化：runbook 由按顺序执行的 steps 组成，每个 step 围绕一个 action，前一步的输出可以作为后一步输入。

通用自动化路径：

```text
人工 Markdown runbook
  -> 只读检查脚本
  -> 参数化脚本
  -> 受控自动化
  -> 自助执行
  -> 告警触发 + 人工审批
  -> 低风险自动执行
```

不要跳过前几步直接让告警自动重启生产。

## 自动化风险分级

| 步骤 | 风险 | 自动化建议 |
|---|---:|---|
| 查询指标 | 低 | 自动 |
| 查询日志摘要 | 低 | 自动 |
| 查询最近发布 | 低 | 自动 |
| 生成状态更新草稿 | 低 | 自动，但人工发送 |
| 创建工单 | 低到中 | 可自动 |
| 扩容 | 中 | 加条件和审批 |
| 摘除实例 | 中 | 加健康检查和回滚 |
| 回滚生产 | 高 | 必须审批 |
| 删除数据 | 极高 | 不应自动 |

自动化要逐项明确这些能力及限制；不具备时降级为人工处理，不能假定所有动作都可逆：

- 幂等。
- 哪些失败可重试，哪些必须先对账。
- 哪些结果可回滚，哪些只能补偿或人工处理。
- 有超时。
- 有审计。
- 有权限边界。
- 有人工审批入口。

## Runbook 和 AIOps

Runbook 是 AIOps 的知识资产。

| AIOps 能力 | Runbook 如何参与 |
|---|---|
| 告警摘要 | 提供告警含义和用户影响 |
| Runbook 推荐 | 根据 alertname/service 检索 |
| RAG 问答 | runbook chunk 进入向量库 |
| 自动化 | 安全步骤变成执行单元 |
| 事件响应 | runbook 指导检查和缓解 |
| 复盘 | incident action item 更新 runbook |
| 新人学习 | 用真实告警学习操作路径 |

LLM 可以帮助：

- 总结 runbook。
- 根据告警推荐 runbook。
- 把长 runbook 变成步骤清单。
- 生成状态更新草稿。

但 LLM 不应该绕过审批执行高风险动作。

## 入门练习：写一个告警 Runbook

任务：为 `OrderApiHighErrorRate` 写一份 runbook。

必须包含：

1. 元信息。
2. 触发条件。
3. 用户影响。
4. 先决条件。
5. 快速判断。
6. 检查命令。
7. 决策树。
8. 安全动作。
9. 高风险动作和审批。
10. 验证恢复。
11. 升级条件。
12. 自动化候选。

再写一个只读检查脚本：

```bash
#!/usr/bin/env bash
set -euo pipefail

CHECK_CONTEXT="${1:?用法：脚本 上下文 命名空间 应用名称}"
CHECK_NAMESPACE="${2:?必须指定命名空间}"
CHECK_APP="${3:?必须指定应用名称}"

echo "== Pods =="
kubectl --context "$CHECK_CONTEXT" get pods -n "$CHECK_NAMESPACE" -l app="$CHECK_APP" --request-timeout=15s

echo "== Recent logs =="
kubectl --context "$CHECK_CONTEXT" logs -n "$CHECK_NAMESPACE" deploy/"$CHECK_APP" --since=30m --tail=100 --request-timeout=15s
```

这个 Bash 脚本只读，但仍需在获准范围内查询。先核对上下文对应集群，不提供任何生产默认值；部署日志通常不是全副本、全容器视图。`--tail` 在请求中限制日志行数，`--request-timeout` 限定接口等待时间，它们不能替代服务端访问控制或完整性核对。

## 常见错误

### 只有原理，没有步骤

Runbook 不是知识文章。必须写“下一步做什么”。

### 没有期望输出

只有命令不够，执行者还要知道结果怎么解释。

### 没有验证恢复

执行完动作不代表恢复。必须看 SLI、告警和用户反馈。

### 没有风险说明

回滚、扩容、重启、删除都要写风险和审批。

### 没有升级条件

新人可能独自卡太久。必须写什么时候拉人。

### 长期不维护

过期 runbook 比没有 runbook 更危险。

### 自动化没有权限边界

自动化必须有最小权限、审计和审批。

## 常用字段字典

### `runbook_url`

告警跳转到 runbook 的链接。

### `dashboard_url`

排障 dashboard 链接。

### `owner`

责任团队或服务负责人。

### `trigger`

Runbook 适用的触发条件。

### `preconditions`

执行前需要满足的权限、环境和工具条件。

### `safe_actions`

低风险动作，通常可以自动化或自助执行。

### `risky_actions`

需要审批或人工确认的动作。

### `verification`

执行后如何确认恢复。

### `escalation`

什么时候、找谁升级。

### `automation_id`

关联脚本、流水线、AWS SSM Automation 或内部自动化平台 ID。

## 面试怎么讲

Runbook 是故障处理的可执行手册，不是普通知识文章。好的 runbook 要从告警或任务出发，写清楚触发条件、用户影响、先决条件、检查步骤、期望输出、决策树、缓解动作、风险、审批、验证恢复和升级条件。它应该挂在告警的 `runbook_url` 上，让值班人从通知直接进入处理流程。

我会先写人工 Markdown runbook，并通过演练验证它是否真的可执行。之后把低风险、重复、只读的步骤自动化，比如查询 dashboard、最近发布、日志摘要；高风险动作如生产回滚、重启、删除数据必须保留审批、审计和回滚方案。AIOps 中，runbook 还能进入 RAG 和向量库，用于相似故障检索、告警摘要、runbook 推荐和自动化候选生成。
