# RCA 根因分析

> 目标：不是写一句“根因是人为失误”，而是能基于时间线、指标、日志、变更、决策和用户影响做无责复盘，区分触发因素、直接原因、促成因素和系统性缺口，产出有 owner、截止时间和验证方式的行动项，并把 RCA 反哺告警、Runbook、变更流程和 AIOps 知识库。

## 场景开场

故障恢复了。

大家终于能喘口气，但如果只在群里说一句：

```text
原因是某个同学配置写错了，下次注意。
```
下个月很可能还会再熬一次夜。

RCA 真正要回答的不是“谁犯错了”，而是：

- 系统为什么允许这个错误造成用户影响？
- 为什么发布前没发现？
- 为什么监控没有更早发现？
- 为什么缓解不够快？
- 为什么 runbook 没覆盖？
- 下次怎样让同类问题更难发生、更容易发现、更快恢复？

## 一句话人话版

RCA 是故障后的证据化学习：用时间线、影响、监控、日志、变更和现场决策，找到系统性改进点，而不是找人背锅。

## 官方知识地图

Google SRE 的 postmortem 文化可以按这张地图理解：

```text
Incident（事故事件）
  -> service restored（服务恢复）
  -> collect evidence（收集证据）
     -> timeline（时间线）
     -> metrics（指标）
     -> logs（日志）
     -> deploys（部署变更）
     -> decisions（决策）
     -> communications（沟通记录）
  -> postmortem（事故复盘）
     -> summary（摘要）
     -> impact（影响）
     -> detection（发现过程）
     -> response（响应）
     -> timeline（时间线）
     -> root causes（根因）
     -> contributing factors（促成因素）
     -> what went well（有效的做法）
     -> what went poorly（需要改进的做法）
     -> where we got lucky（侥幸未造成更大损失的环节）
     -> action items（改进行动项）
  -> learning（学习改进）
     -> monitoring improvement（监控改进）
     -> runbook update（手册更新）
     -> CI/CD guardrail（持续交付保护条件）
     -> automation（自动化）
     -> training（训练）
     -> architecture change（架构改进）
  -> AIOps feedback（智能运维反馈）
     -> root cause taxonomy（根因分类体系）
     -> historical incident retrieval（检索历史事故）
     -> alert enrichment（补充告警上下文）
     -> runbook recommendation（推荐操作手册）
```

初学路线：

```text
start from incident timeline（从事故时间线开始）
  -> write impact（记录影响）
  -> calculate detection and recovery times（计算发现与恢复用时）
  -> identify direct cause（识别直接原因）
  -> list contributing factors（列促成因素）
  -> ask why defenses failed（追问防线为何失效）
  -> write action items（编写行动项）
  -> assign owner and due date（指定责任人和期限）
  -> verify completion（验证完成）
  -> update runbook and alerts（更新手册与告警）
```

## 老师带你区分“怀疑”与“证明”

我们从一份课堂事故开始：10:00 发布连接池配置，10:02 接口变慢，10:08 回滚后恢复。你可能会说“发布导致故障”。先暂停一下：同期也可能有突增流量、慢查询或网络抖动。时间接近是线索，还需要一个可验证的因果机制。RCA 是 Root Cause Analysis（根因分析），我们要解释的是请求究竟怎样受损。

先把事实和解释分成两栏。事实写“最大连接数从 100 变为 10”“等待连接的请求增加”“数据库查询耗时没有同幅增加”。解释写“应用可能因为连接额度太少而排队”。缺少配置差异和等待指标时，把它标为待验证假设。这会决定下一步采集什么证据。

### 第一课：沿一次请求找等待点

请求进入应用，申请数据库连接，执行查询，释放连接，再返回用户。连接池像有限数量的通行证，但不是数据库本身。应用线程可能在等通行证，所以 CPU 不一定高。对照连接等待、在用连接、排队请求和查询耗时，才能区分“额度减少”和“查询变慢导致连接释放慢”。

两种机制可以产生相似的用户现象，却需要不同修复。直接扩连接池会增加数据库并发，若下游已饱和，可能进一步恶化。好的 RCA 不只记“调大参数有效”，还要解释为什么当时适合、数据库预算是多少、什么条件下这项修复会失效。

证据有时间、范围和可靠性。应用日志与发布平台的时钟可能不同；周期采集的指标看不见所有瞬间；用户报告可能晚于实际影响。统一时区，分别记发生、观察和报告时间，不把告警触发点当故障必然开始点。

### 基础实验与故障实验：同一条时间线能得出什么结论

前置条件是本机 Node.js 可用，在本仓库根目录打开终端。实验使用合成数据，不连接数据库，不改变服务。

```powershell
node examples/teacher-led-reliability-lab/lab.mjs rca
node examples/teacher-led-reliability-lab/lab.mjs rca --fault
```

正常案例补充“未变更组健康”和“只回退连接池配置后恢复”，应看到 `SUPPORTED_WITH_LAB_EVIDENCE`（课堂证据支持假设）。故障案例移除这两条证据，只保留时间先后和等待增加，应看到 `INSUFFICIENT_CAUSAL_EVIDENCE`（因果证据不足）。成功退出只说明课堂判定符合设计。

解释 `unchangedGroupHealthy`（对照组是否健康）和 `revertOnlyPoolConfigRecovers`（仅回退该配置是否恢复）为什么重要。真实环境还应检查分组流量是否可比、是否同时发生别的操作。输出不符时，检查参数、当前目录和脚本版本。程序不创建资源，无须清理服务；保留输出和纸笔分析。

### 第二课：原因分层，不强求唯一答案

触发因素是配置发布；直接机制是连接额度减少使等待超过请求超时；促成因素是无预算重试和共享数据库；防线缺口是缺少配置范围校验、灰度流量不代表峰值、回滚未演练。四层可以同时存在。每项结论注明证据、反例和可信程度，证据不全就安排补采。

5 Whys（连续追问为什么）可以帮助深入，但没有证据时容易变成故事。问“为什么测试没发现”，要检查覆盖范围和输入样本，不能直接归结为“不细心”。无责复盘仍有行动责任：注意力放在改善系统防线，并给每项改进明确负责人。

“加强监控”无法验收。可以改成：“流水线计算连接池上限乘服务副本数，超过数据库并发预算就拒绝继续，以两个失败样例验证。”优先级考虑影响和成本。行动上线本身也是变更，要有测试、观察和回滚；关闭工单后继续追踪同类遗漏率及恢复时长。

进入 AIOps 知识库时，保留证据引用、环境、版本与未定项。相似日志只提示相似事故，不能证明本次原因相同。摘要中的敏感数据先脱敏，原始证据按权限查询，模型的结论要能追溯到具体来源。

### 面试课堂：30 秒、3 分钟与递进追问

30 秒：“我围绕用户影响建立统一时间线，区分事实与假设，沿请求和状态路径验证原因，再把防线缺口变成可验收行动。时间相关只是线索，结论需要机制和证据。”

3 分钟按影响、证据、竞争假设、验证、修复取舍、长期行动展开。连接池案例先解释等待发生在哪，再比较配置、并发与下游耗时，说明对照和单一回退怎样提高可信度，最后提出预算校验与代表性流量演练。

追问：“回滚后恢复就完全证明了吗？”还可能伴随流量或缓存变化，要补对照。“找不到根因能关闭事件吗？”业务恢复验收与原因分析可以分别管理，原因仍保持未定。“复盘有什么价值？”看行动是否减少风险、提高防线覆盖、缩短发现和恢复，不能只数文章。

生产设计题：设计事故知识库的事件、证据、假设、动作、版本和权限关系。事故题：历史复盘建议扩连接池，而当前数据库已经饱和；先检查适用性和并发预算。GitHub 学习证据包含时间线、假设矩阵、两次实验输出和行动表，明确为个人演练。

## 推理工作坊：让结论经得住反问

### 把“看见的事”与“猜测的原因”写在不同格子

老师先给你一句话：“数据库卡了，所以请求失败。”这句话同时含一个未定义现象和一个因果结论。把它拆开：哪个数据库，哪个实例，哪个时间段，卡指查询执行慢、连接建立慢还是等待连接，哪些请求失败，失败比例是多少？问题越具体，证据采集范围越小。

一条有用的观察可以写成：“课堂数据中，10:02—10:08，订单查询接口等待连接的时间从约 5 毫秒上升到约 800 毫秒；同窗口数据库查询执行时间没有明显变化。”它仍不是最终原因，但已经指出下一步应比较连接额度、占用时长与请求并发，而不是立刻研究数据库磁盘。

证据需要来源和限制。指标是每分钟聚合值，可能漏掉短时尖峰；日志只覆盖记录成功的进程，不能代表未写出日志的崩溃请求；链路被采样，少量慢请求可能没被保留。写清这些限制不是削弱结论，而是避免把局部观察冒充完整事实。

### 三个竞争假设，比一个漂亮故事更有用

继续连接池案例。假设一是额度减少，预期配置有明确变化、等待增长但查询执行基本稳定。假设二是下游查询变慢，预期连接占用变长、慢查询或依赖跨度出现对应变化。假设三是请求激增，预期进入流量在变更前后明显上升，多个未变更实例也可能同步受影响。

接下来不是把所有命令执行一遍，而是选择能区分这些假设的检查。读取生效配置可以检验假设一；对齐数据库耗时与连接占用可以检验假设二；比较进入流量与对照组可以检验假设三。一个检查若无论结果怎样都无法改变判断，通常不应排在最前。

当多个假设同时成立，例如额度减少又遇到流量上涨，原因可以是组合。不要强求用一个产品或一个人概括整个事故。把触发、放大、失效防线分别画出来，说明哪项是证据支持，哪项仍需后续验证。

### 时间线怎样处理时钟误差和模糊时间

你有三条记录：用户说“大约十点”，发布平台记录 10:00:15，应用日志记录 09:59:58。不能简单按字符串排序就宣布应用先坏。先确认时区、节点时钟同步、日志使用事件时间还是写入时间，以及记录是否经过队列延迟。

把不确定时间写成区间，例如“首次影响在 09:59—10:02 之间，依据五分钟探测和用户报告”。保留原始时间与换算规则，避免复盘整理者无意中制造虚假的秒级精度。若无法证明先后关系，就说时间证据不足，继续寻找配置差异和请求路径证据。

对于并发系统，先后也不总能代表依赖。两个节点可能同时执行不同请求，日志相邻不表示它们属于同一交易。关联标识、父子跨度、资源标识和事务记录比单纯时间相近更有区分力，但标识缺失或复用时也要承认限制。

### 反事实：如果没做这个变更，故障还会发生吗

反事实是在问“其他条件尽量相近时，没有该因素会怎样”。生产中通常无法把所有条件完全控制，所以可以综合未变更组、隔离复现、单一配置回退、代码路径分析等证据提高可信度。它不是要求必须在生产再次制造同样的事故。

例如未变更组健康，但它们请求量远小于变更组，这个对照就不够强。回滚后恢复，但同时流量回落一半，也不能把全部改善归因于回滚。课堂练习时给每条证据标注可比性，写出至少一个可能反例，训练自己避免过早停止调查。

事故止血不能等到因果完全确定。响应阶段可以根据当前风险选择可回滚的缓解动作；复盘阶段再评估证据强度。把“当时为什么这样决策”和“后来确认了什么”分开，既避免用事后知识苛责现场人员，也不会把临时猜测永久固化为根因。

### 行动项要能证明防线变强，而不是只证明文档变多

看两种写法。第一种是“加强测试，注意连接池”。第二种是“在发布门禁中计算服务最大副本数乘单实例连接上限，超过分配预算时拒绝部署；用低于、等于和超过预算三组样本验证；负责人和交付日期明确”。第二种具备对象、机制、边界和验收。

不过这条门禁也不是万能的：连接可能分多个数据源，数据库还服务其他系统，实际最大副本数可能在紧急扩容时改变。行动审查要检查它覆盖了哪些失败方式、没覆盖哪些，以及误拒绝时怎样人工评估。为了追求零风险把所有发布都锁死，会造成另一种业务风险。

再看“增加监控”。应该说明新增什么信号、为何能提前发现、触发谁的响应、怎样避免噪声、用什么合成故障验证。告警只是发现防线，不会自动减少发生概率。预防、检测、缓解和恢复措施各有价值，别把所有改进都堆到监控团队。

### 面向 AIOps 的事故知识库该保存什么

一份知识条目应包含场景、环境与版本、症状、证据链接、适用条件、竞争假设、已验证原因、动作、风险和后置验证。对未定原因保留“未知”状态，而不是让模型补一个听起来合理的答案。知识库的可靠性来自可追溯记录，不来自摘要语气有多肯定。

检索时，相似报错可以用于推荐检查路径；执行修复前还要验证当前目标、权限、版本和风险。旧案例用扩连接解决问题，新案例却可能因为连接过多压垮数据库。系统应把“相似案例”呈现为候选证据，不把“检索相似度高”当作操作授权。

课堂交付要求：提交一份脱敏时间线、一张三假设对照表、一段说明不确定性的摘要和两个可验收行动。请同学只读你的材料再复述因果链；若他只能背出某个错误码，却解释不出请求为什么受损，就回到证据与机制部分继续修订。

## 数字取证课堂：先算对影响，再讨论原因

同学，我们现在拿到两句话：“失败率翻倍了”和“两个机房都改善了”。它们一定互相矛盾吗？先别选边站。失败率是失败次数除以符合统计条件的请求次数，整体结果还受各机房流量占比影响。如果流量从低失败率机房移向高失败率机房，即使两个机房各自变好，整体也可能变坏。这种分组与汇总趋势相反的现象常被称为辛普森悖论。它提醒我们先查看人群、路径和流量构成，而不是见到一条曲线就给发布定罪。

### 第一步：把计数单位写在数字旁边

“失败请求”“失败尝试”“受影响订单”“受影响用户”是四个不同的对象。用户提交一次订单，客户端重试两次，可能留下三次请求；最后成功了，用户仍可能经历明显卡顿。按三条错误日志统计三个受影响用户，显然不对。先问网关是否记录每次尝试，业务编号能否关联同一订单，用户标识是否经过合法脱敏，最终成功是否在观察窗口之后。没有相应数据，就分别写“已知失败尝试数”和“受影响用户数未知”。未知不是不专业，混用单位才会误导决策。

统计范围也像尺子的刻度：同一个接口、同一种成功定义、同一个时间窗口才能相比较。健康检查是否算请求，主动限流的状态码是否算坏事件，取消请求如何处理，都应服从事先定义的 SLI，即服务质量指标，而不是事故发生后为了让曲线好看再改口径。比较变更前后时，还要注明是否包含同样的租户、版本、地区和读写请求。若临时改变口径，保留旧结果并说明差异，不覆盖原证据。

### 第二步：做一次可以手算的分组实验

下面四行全部是**合成课堂数据，不是真实事故**。每行表示一个窗口内一个机房的完整计数，两个窗口各有一万次请求。`before` 是前一窗口，`after` 是后一窗口；`east`、`west` 只是分组名，不代表任何真实地域。

|---|---|---:|---:|---:|
| before | east | 9000 | 90 | 1% |
| before | west | 1000 | 90 | 9% |
| after | east | 1000 | 5 | 0.5% |
| after | west | 9000 | 450 | 5% |

先自己预测整体方向，再计算。前一窗口是 `(90 + 90) / 10000 = 1.8%`，后一窗口是 `(5 + 450) / 10000 = 4.55%`。不能把两组百分数直接平均：后一窗口的九成请求在 west，它的权重更大。整体恶化是真实的课堂统计结果，组内改善也是真实的结果；但这些数字没有告诉我们流量为什么迁移，更没有证明哪个配置导致失败。下一份证据应是路由、容量、请求类型和变更记录，而不是一份已经写死根因的报告。

**前置条件**：本地安装 Node.js 22 或更高版本，已经取得本仓库，在仓库根目录打开终端。不需要数据库、云账号和生产日志。先运行 `node --version` 确认解释器可用，再运行这个只处理内存合成数据的程序：

```bash
node examples/incident-evidence-classroom/lab.mjs rca
node examples/incident-evidence-classroom/lab.mjs rca --missing
node --test examples/incident-evidence-classroom/checks.mjs
```

第一条的 `windows` 给出两窗口总数和失败百分比，`cohorts` 给出各组比例；应看见 `1.8`、`4.55`，但 `causalConclusion` 仍是 `NOT_ESTABLISHED`，意思是尚未建立因果结论。`COMPLETE_FIXTURE` 只表示这份已知四行课堂样本完整，不代表真实监控一定完整。第二条用 `--missing` 故意移走后一窗口的 west 数据，预期返回 `INSUFFICIENT_COVERAGE`，即覆盖不足，并列出 `after/west`。它拒绝把剩下的 east 当作全站。

第三条执行七项测试，其中包括同一批数据重复导入不能重复累计、同批标识出现冲突计数必须报错、负数与失败数超过请求数必须拒绝。这里的去重单位是“窗口加机房的完整统计批次”，不是业务请求；把这个规则直接套到逐条日志会丢掉大量合法请求。验证时既要看测试通过，也要对照四行表亲手算一遍；只记住绿色输出而解释不出权重变化，还没有完成实验。

**没有得到预期结果时**，先核对当前目录、文件路径和 Node 版本，再检查是否误把 `--missing` 当作正常模式。缺失组输出是预期保护分支，不是要修掉的错误。不要连接真实监控来“补齐”课堂数据。程序不联网、不写文件、不修改系统；结束进程即完成清理。独立练习是在自己的练习副本中改变流量占比但保持组内比例，解释汇总变化；再制造一条冲突批次，记录为什么程序应拒绝出结论。

### 第三步：解释误差，而不是制造漂亮的精确数字

采样日志只保存部分事件，错误日志又可能被优先保留。因此，采样后的“错误条数除以所有保留条数”通常不能直接当作用户失败率。应说明采样策略、丢弃条件和是否能取得请求总计数。计数器重启归零、迟到事件、时间窗口交界处的重复采集也会改变分母。没有完整计数时，可以报告已确认的影响下界和缺失区间，但不能偷偷把未知事件全归为成功。

延迟的 p95 表示这组观测中约九成五不超过的延迟位置，不是平均值。两个实例的 p95 不能简单平均得到全服务 p95，因为你没有保留各实例全部延迟分布和请求权重。复盘应保存查询表达式、直方图桶边界或原始分布来源，并确认不同实例采用兼容统计方式。否则“回滚后 p95 降了一半”可能只是慢实例没有继续上报。先看流量和覆盖，再看漂亮的恢复曲线。

错误预算也必须有分母。假设一个按请求计算的三十天 SLO 目标是 99.9%，该窗口有一百万个合格请求，则预算是允许一千个坏请求；某事故贡献两百个符合相同口径的坏请求，才可以说占这份预算的百分之二十。这里所有数字仍是教学假设，且不能直接套到按分钟计算的可用性目标。若窗口还未结束，要说明分母采用当前累计量还是约定预测量，事故总失败与超出正常基线的增量也要分开报告。

## 因果推理课堂：画出能被证伪的机制链

我们再回到连接池事故。连接池是应用预先维护的一组数据库连接，排队等待连接的时间与数据库执行语句的时间不是一回事。若只有“数据库超时”日志，可能是没有借到连接，也可能是借到后查询太慢，还可能是网络等待。一个有用的假设必须说明测量位置：等待发生在哪里、谁持有资源、哪项状态先变化，以及什么证据出现时应放弃这个解释。

### 从单线故事改为带分支的因果图

因果图不是把所有同时异常的东西连起来，而是表达有机制依据的影响方向。可以先画一个小图，`pool wait` 是等待借连接，`retry` 是重试；箭头表示待验证的影响，不等于已经证明。

```text
连接上限降低 → 可借连接减少 → pool wait（借连接等待）增加 → 请求超时
慢查询增加   → 连接占用更久 ↗                          ↓
流量突增     → 同时争用增加 ↗                  retry（重试）放大负载
```

注意最后一条反馈：超时可能让调用方重试，重试又占更多连接。所以“流量增加”既可能是最初原因，也可能是故障后果。只拿一分钟聚合点无法可靠判断秒级先后。先按请求标识区分原始调用和重试，查看调用方超时与重试策略，再对齐连接池等待、活跃连接和数据库执行时间。若看不到重试来源，应把这条边标为待验证，不因图画得完整就升级为事实。

必要条件指缺少它这条机制就无法成立，充分条件指给定前提下它足以造成结果。低连接上限并不在所有流量下都会出故障；它与并发请求、持有连接时长和超时阈值共同作用。学生常问“上限二十到底对不对”，老师应带你计算业务峰值与数据库总连接预算，再做隔离压测，而不是提供全行业通用的神奇数值。多实例各自扩大连接池还可能把单机排队转移成数据库过载。

### 比较对照，但不要假装现场做了随机实验

灰度组和旧版本组看似是对照，实际上灰度可能只接收内部用户，旧版本处理大量复杂订单。两组延迟不同不能立即归因版本。应先比较请求类型、数据规模、缓存命中、机房、依赖和并发，再说明哪些条件尚未一致。把两组分层后比较可以减少混杂，却不自动消除所有隐藏因素。“对照支持该假设”比“对照证明唯一原因”更准确。

反事实是在问：如果没有这次配置变更，其他条件相近，是否仍会发生同样的问题？生产不能任意重放事故，可以用预生产隔离环境、合成流量、历史基线和容量模型逐步验证。实验中一次只改关键变量，保留基线、负载和失败条件；如果同时改版本、连接数和超时，成功了也不知道是哪项起作用。对于数据损坏、安全事件等不宜复现的情况，应采用静态证据、审计记录和保守机制分析，明确仍未验证的边界。

回滚后恢复是重要证据，但回滚常同时改变程序、配置和流量。恰好下游恢复、流量下降或缓存重新变热，也可能让曲线回落。复盘可以写“回滚后恢复与配置假设一致”，并列出同窗口其他变化；等到隔离实验单独改变连接上限复现等待，证据才更强。修复期间不要为了得到漂亮因果结论延迟止损，恢复业务与证明机制是两个优先级不同的阶段。

## 证据工程：让两周后的人仍能复核你的结论

### 建立证据账本，而不是粘贴一堆截图

证据账本可以理解为实验室样本登记簿。每条记录至少写来源、查询条件、环境、时间范围、时区、采集时间、保留位置、可见权限和关联结论。证据编号用来引用某份固定材料，避免“看那个群里的第三张图”这种会失效的描述。指标图最好同时保留查询和数值摘要；配置比较要记录两个确切版本，而不只贴颜色截图。账本让别人能够重做核对，也暴露你还缺哪一块信息。

文件摘要可以帮助发现材料后来是否被改过，但摘要相同只说明字节相同，不能证明原始系统的时钟正确、日志完整或内容真实。原始材料、脱敏副本和分析结论要分开保存，并记录版本关系。若后来发现时间偏移，追加纠正说明，不无痕重写第一次采集记录。这样调查过程可以修正，而不是为维护最初判断把新证据藏起来。

时钟也要登记。应用日志可能用本地时间，监控用统一时间，截图显示浏览器时区，机器自身还可能有误差。先统一展示时区，再写明无法校准的误差范围。例如两个事件相差一秒，但各自时钟误差可能两秒，就不能声称它们已有严格先后。顺序编号、同一请求里的跨度关系和同一进程内的持续时间，有时比跨机器墙上时间更可靠；但其来源和限制仍要写清楚。

### 从一开始就保护证据中的人和系统

订单、手机号、访问令牌、数据库连接信息可能藏在日志和截图中。采集前确定最小字段和许可范围，脱敏后才能进入学习仓库或知识库。不可逆哈希也不天然安全：可枚举的手机号经过普通哈希仍可能被猜回。需要关联同一对象时，使用组织批准的去标识化办法；不需要关联就删除该字段。公开 GitHub 学习证据应采用合成数据，保留分析结构，不上传真实业务原文。

资料保留期应与组织要求一致。知识库里留的是可复用机制、适用条件和脱敏案例，敏感原始材料留在受控系统。删除或更正原始材料后，也要处理向量库副本、检索缓存和导出文件；否则文档删掉了，问答系统仍可能复述旧数据。证据访问失败时，分析流程应标记不可核验并联系授权人，不通过复制到私人网盘绕过权限。

## 生产设计题：搭建一个不会替人武断定责的 RCA 助手

面试官问“让大模型自动根因分析怎么做”，不要先列模型名称。先说产品输出：为值班人员汇集证据、给出候选机制、建议下一项有区分力的只读检查，并保留人工确认。输入包括带时间和来源的指标、日志摘要、调用链、变更与资产关系；输出包括事实、假设、反证、未知项及证据链接。模型没有看见的数据必须保持未知，而不是依据历史套路补成一个完整故事。

可以把链路拆成采集、规范化、证据存储、候选生成、人工审核和回写知识库。采集层按服务和租户限制范围，规范化层检查时区、单位和覆盖，存储层保存不可混淆的证据版本。候选生成只在授权范围检索，审核层允许驳回并记录理由，回写层只收录审核后的结论。草稿状态与已审核状态分离，防止一次错误猜测下一轮被检索为权威事实。

高可用设计不能只说多部署两个模型实例。事件和证据任务要有稳定标识，重复消费不能复制成两起事故；采集失败要显示缺失范围；模型不可用时仍能打开静态证据和人工模板。查询大范围日志可能加重故障，故采集需要超时、并发上限、分页和费用预算，优先使用已有摘要。只读查询同样消耗资源，不能因没有写权限就允许无限并发扫描。

升级模型、提示词或检索规则前，建立有标准答案边界的脱敏评估集。评估的不只是“猜中根因”，还包括是否引用正确证据、是否把未知说成确定、是否跨租户检索、是否推荐越权操作。保留旧版本和回滚开关，先让新版本只生成旁路建议。对同时存在多个合理机制的样本，不应强行只给一个根因标签，否则训练出的系统会学会自信猜测而不是诚实取证。

### 行动项完成之后，还要观察防线是否真的有效

“校验规则已合并”只是交付，不等于风险消失。先提交一份应被拒绝的配置证明护栏能拦住，再提交合法边界配置证明不会误拦；随后核对发布路径是否都经过这条护栏，包括应急发布与旧服务。行动项要记录覆盖对象、绕过途径、验收人和后续观察窗口。一条只覆盖普通流水线的规则，不能宣称已经保护所有生产变更。

比较复发率时要考虑暴露次数。本月零事故可能因为没有发布，不一定是改进奏效。可以同时报告配置变更次数、护栏拦截次数、误报和相关事故数，按相似服务与严重程度分层。小样本时保持谨慎，不从两次事故计算出看似精确的收益。未遂事件也值得学习：某次错误被审批拦住，说明防线有效，也可能揭示上游工具仍在持续制造危险输入。

复盘会议应指定主持人，让操作者说明当时能看到什么，而不是拿事故结束后的全知视角质问“为什么没想到”。记录事实争议和待补证据，把技术分歧落实成验证任务。对安全调查或合规问责，按组织程序独立处理；无责学习不等于可以省略审计和责任边界。最后让未参与事故的人读一遍摘要，看他能否说清影响、机制、不确定性和下一道防线。

### 面试追问与独立交付

如果追问“整体失败率升高是否说明每个实例都变差”，先解释加权计数，再用前面的机房数据反例回答；接着说明要按版本、请求类型分层并检查缺失。若追问“回滚后恢复还要做什么”，回答保留止损证据、核对同时发生的变化、验证关键机制，不能为了实验再次伤害生产。若追问“如何衡量 RCA 助手”，把证据可追溯、未知识别、越权拦截和人工采纳后的结果放在根因命中率旁边。

请独立提交一份合成事件包：四行计数与手算、缺失证据时的不同结论、带反证条件的因果图、三条可复核证据登记、一个防护行动的正反测试。说明哪些属于程序验证、哪些只是纸面推演、哪些必须等待真实环境授权。这样的作品能证明你会控制推理边界；它不是实际生产履历，更不能替代 Linux、网络、编码和真实协作经验。

## RCA、Postmortem、复盘

这些词常混用，但重点不同：

| 名词 | 重点 |
|---|---|
| RCA | 分析为什么发生 |
| Postmortem | 记录事故、影响、响应、原因和行动项 |
| 复盘 | 团队学习和改进讨论 |

好的 postmortem 包含 RCA，但不止 RCA。

它还包括：

- 用户影响。
- 检测方式。
- 响应过程。
- 做得好的地方。
- 做得不好的地方。
- 行动项。

## 无责复盘

Google SRE 强调 postmortem 应该是学习文化的一部分，而不是惩罚工具。

无责不是没有责任。

无责的意思是：

```text
不把复杂系统故障简化成某个人的问题。
把注意力放在系统为什么允许错误扩大。
```
坏写法：

```text
根因：开发人员配置错误。
行动项：以后小心。
```
好写法：

```text
直接原因：新版本连接池 max connections 配置过低。
促成因素：
- CI 没有配置范围校验。
- 灰度流量不足，没有暴露连接池耗尽。
- 告警没有关联最近发布。
- Runbook 没有配置 diff 检查步骤。
```

## 什么时候必须写 Postmortem

不是每个小问题都要写长文档，但这些情况应该写：

- SEV1 / SEV2。
- 用户明显受影响。
- SLO 错误预算消耗显著。
- 数据丢失或安全风险。
- 恢复时间超出预期。
- 告警没发现，用户先发现。
- 重复发生的问题。
- 响应过程混乱。
- 需要跨团队行动项。

轻量事件可以写 mini-postmortem，但不能完全不沉淀。

## RCA 的输入

不要凭记忆写 RCA。先收集证据。

| 输入 | 用途 |
|---|---|
| 告警 | 发现时间、触发条件 |
| SLO / SLI | 用户影响和预算消耗 |
| 指标 | 错误率、延迟、流量、饱和度 |
| 日志 | 错误类型、异常堆栈 |
| traces | 请求路径和依赖 |
| 发布记录 | 最近变更 |
| 配置 diff | 变更细节 |
| incident 时间线 | 响应过程 |
| 沟通记录 | 状态更新和决策 |
| runbook 使用记录 | 文档是否有效 |
| 工单和用户反馈 | 用户影响 |

RCA 的质量上限取决于证据质量。

## Postmortem 模板

以下日期、数量、服务和过程均为虚构填写示例，不是本仓库实测事故。真实报告应替换为可核验材料，缺少的数据写“待核实”，不要沿用示例数字。错误预算计算口径见前面的数字取证课堂。

````md
# Postmortem: order-api HighErrorRate

## 摘要

2026-07-02 09:10 至 09:42，order-api 5xx 错误率升高，导致部分用户下单失败。团队在 09:12 声明 SEV2，09:35 回滚新版本，09:42 指标恢复。

## 影响

- 影响服务: order-api
- 影响请求: 示例窗口内约 12% 合格下单请求失败（实际需附失败数、总数和查询）
- 影响用户: 待按脱敏用户或订单标识核实，不能用请求比例替代
- 影响时长: 32 分钟
- SEV: SEV2
- SLO 影响: 待填写目标、统计窗口、预算分母和本事故坏事件数后计算

## 检测

- 发现方式: Alertmanager OrderApiHighErrorRate
- 告警触发时间: 09:10
- Incident 声明时间: 09:12

## 直接原因

新版本将 order-api 数据库连接池 max connections 配置从 100 降到 20，在生产流量下连接池耗尽，导致请求出现 database timeout 和 5xx。

- CI 没有校验连接池配置范围。
- 灰度阶段流量太小，没有暴露连接池耗尽。
- 告警通知没有展示最近发布。
- Runbook 没有配置 diff 检查步骤。

- 没有发布前配置校验。
- Runbook 不完整。
- 灰度验证没有覆盖真实峰值。
````

## 根因不是唯一一个

复杂系统事故通常不是单一原因，而是多个防线同时失效。

可以分层：

| 层级 | 示例 |
|---|---|
| 触发因素 | 新版本发布 |
| 直接原因 | 连接池配置过低 |
| 促成因素 | CI 未校验、灰度不足 |
| 检测缺口 | 告警缺少发布上下文 |
| 响应缺口 | Runbook 缺配置 diff 检查 |
| 系统性问题 | 配置变更缺少自动化护栏 |

不要为了文档简洁，把这些都压成“开发配置错误”。

## 5 Whys

5 Whys 是有用工具，但不要机械使用。

示例：

```text
问题：为什么 order-api 5xx 升高？
1. 因为请求出现 database timeout。
2. 为什么 timeout？连接池耗尽。
3. 为什么连接池耗尽？新版本 max connections 配置过低。
4. 为什么配置过低还能发布？CI 没有配置范围校验。
5. 为什么没有校验？配置项没有 owner 和策略基线。
```

行动项：

```text
给连接池配置建立 owner、范围基线和 CI 校验。
```

注意：

- 5 Whys 不一定正好 5 层。
- 可能有多个分支。
- 不要停在人为错误。
- 每个 why 都要有证据。

## 鱼骨图文字版

可以按维度展开促成因素：

```text
人员: 新人不熟悉连接池配置风险
流程: 发布前没有配置校验
工具: CI 未检查配置范围
监控: 告警没有关联发布信息
架构: 灰度流量不足以暴露连接池耗尽
文档: Runbook 缺少配置 diff 检查
权限: 回滚审批路径清楚，未造成延迟
```

这能帮助团队看到系统性问题，而不是只盯一个技术点。

## 行动项质量

好的行动项必须具体、可验证、有 owner、有截止时间。

坏行动项：

```text
以后发布前仔细检查。
```
好行动项：

```text
在 CI 中增加连接池 max connections 范围校验，低于 80 时阻止合并。
Owner: team-order
截止时间: 2026-07-09
验证方式: 提交错误配置 PR，CI 必须失败。
```

这里的 80 只是虚构服务已评估基线的示例，不是所有应用的推荐值。真实范围要结合实例数、连接占用时间、峰值负载和数据库总预算评审，保留例外审批与边界测试。

行动项字段：

| 字段 | 说明 |
|---|---|
| 描述 | 具体要做什么 |
| 类型 | prevention / detection / mitigation / documentation / training |
| Owner | 单一负责人 |
| 截止时间 | 明确日期 |
| 验证方式 | 如何证明完成 |
| 状态 | open / done / dropped |

## 行动项分类

| 类型 | 目标 | 示例 |
|---|---|---|
| prevention | 防止再次发生 | CI 配置校验 |
| detection | 更早发现 | 增加 SLO burn alert |
| mitigation | 更快缓解 | 一键回滚脚本 |
| documentation | 改进知识 | 更新 runbook |
| automation | 减少人工 | 自动关联发布记录 |
| training | 提升能力 | 事件响应演练 |
| architecture | 改系统设计 | 隔离连接池配置 |

行动项不要全堆在 prevention。检测和缓解同样重要。

## 度量指标

RCA 可以沉淀这些指标：

| 指标 | 含义 |
|---|---|
| MTTD | 一组事故中，从故障开始到检测的平均时长 |
| MTTA | 一组事故中，从检测到确认的平均时长 |
| MTTR | 本文约定为一组事故中从检测到恢复的平均时长，采用前必须统一定义 |
| time to declare | 从检测到声明 incident |
| time to mitigate | 从检测到缓解生效 |
| error budget consumed | 消耗的错误预算 |
| action item completion rate | 行动项完成率 |
| repeat incident rate | 重复事故比例 |

这些指标能帮助 AIOps 和 SRE 评估体系是否在进步。

前三项的 M 是 Mean，即平均，单起事故应称检测、确认或恢复时长。MTTR 在不同团队可能指修复、恢复或解决时间，必须约定起止事件后才能比较。未知的开始时间不能填零；聚合时同时公布样本数、缺失数、严重程度和分布，避免一个平均值掩盖长尾事故。

## RCA 与 AIOps

RCA 是 AIOps 的反馈层。

```text
incident（事故事件）
  -> postmortem（事故复盘）
  -> root cause taxonomy（根因分类体系）
  -> action items（改进行动项）
  -> updated alerts / runbooks / automation（更新告警、手册与自动化）
  -> fewer repeat incidents（减少重复事故）
```

可抽取的数据：

| 字段 | 用途 |
|---|---|
| incident_id | 关联事件 |
| service | 服务维度 |
| root_cause_type | 根因分类 |
| trigger | 触发因素 |
| contributing_factors | 促成因素 |
| detection_gap | 检测缺口 |
| response_gap | 响应缺口 |
| mitigation | 缓解动作 |
| action_items | 后续改进 |
| evidence_links | 证据链接 |

AIOps 应用：

- 相似事故检索。
- 根因候选推荐。
- 告警自动补上下文。
- Runbook 推荐。
- Postmortem 草稿生成。
- 重复事故识别。

但模型不能替代证据。RCA 必须回到时间线和事实。

## 入门练习：无责复盘

用这个场景写一份 postmortem：

```text
09:02 order-api 发布新版本。
09:10 5xx 错误率升高到 23%。
09:12 声明 SEV2。
09:20 日志显示 database timeout。
09:25 确认连接池配置错误。
09:35 回滚。
09:42 恢复。
```

必须包含：

1. 摘要。
2. 用户影响。
3. 检测和响应。
4. 时间线。
5. 直接原因。
6. 至少 3 个促成因素。
7. 做得好的地方。
8. 做得不好的地方。
9. Where we got lucky（哪些地方只是运气好）。
10. 至少 4 个行动项，每个有 owner、截止时间、验证方式。

## 常见错误

### 把根因写成“人为失误”

这会阻止系统学习。继续问系统为什么允许这个错误造成事故。

### 没有证据

RCA 必须基于时间线、指标、日志、变更和决策记录。

### 只有直接原因

直接原因不等于全部根因。要写促成因素和系统性缺口。

### 没有行动项

没有行动项的 RCA 只是事故故事。

### 行动项没有 owner

没有 owner 和截止时间，行动项很容易消失。

### 行动项不可验证

“提高意识”不可验证。CI 校验、告警增强、runbook 更新可验证。

### 只关注技术，不关注检测和响应

为什么没早点发现、为什么恢复慢，同样重要。

## 常用字段字典

### direct cause

直接导致故障表现的原因。

### contributing factor

让故障更容易发生、更难发现或更难恢复的因素。

### detection gap

检测缺口，例如没有告警、告警太慢、告警缺上下文。

### response gap

响应缺口，例如没有 runbook、角色混乱、回滚慢。

### action item

可执行改进项，必须有 owner、截止时间、验证方式。

### MTTD

Mean Time To Detect，平均检测时间。

### MTTR

Mean Time To Resolve / Recover，平均恢复时间。

### blameless

无责，不把复杂系统问题简化成个人问题。

## 面试怎么讲

RCA 的目标不是追责，而是从事故中学习并减少重复事故。我会先收集证据：告警、SLO 影响、指标、日志、发布记录、配置 diff、incident 时间线和沟通记录。然后在 postmortem 中写清楚摘要、影响、检测、响应、时间线、直接原因、促成因素、做得好的地方、做得不好的地方和行动项。

我不会把根因写成“人为失误”。更好的分析是继续追问系统为什么允许这个错误发生、为什么没提前发现、为什么缓解不够快。行动项必须具体、可验证、有 owner 和截止时间，比如“在 CI 中增加连接池配置范围校验”。AIOps 中，RCA 是反馈层，可以沉淀根因分类、相似事故、检测缺口、runbook 更新和自动化候选，但所有结论都必须回到证据。
