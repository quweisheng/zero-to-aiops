# 告警治理

> 目标：不是把 Prometheus 规则写得越多越好，而是能判断哪些告警值得叫醒人，哪些应该降级、合并、抑制、删除或自动化；能设计告警分级、标签、路由、分组、抑制、静默、runbook、质量指标和持续治理流程。

## 场景开场

凌晨 3 点，手机响了：

```text
DiskUsageHigh on node-17
```

你打开告警，发现：

- 昨天已经响过。
- 磁盘还有 18%。
- 服务没有用户影响。
- 没有 runbook。
- 告警发给了错误团队。
- 过 10 分钟又响一次。

这不是“监控很完善”，这是告警债务。

告警太多不会让系统更安全，只会让人更麻木。真正好的告警应该少、准、可行动，并且在该叫醒人的时候才叫醒人。

## 一句话人话版

告警治理是把“会响的规则”治理成“值得人处理的信号”：每条告警都要有用户影响、紧急性、行动路径、负责人、来源证据和持续改进机制。

## 官方知识地图

告警治理可以按这张地图理解：

```text
Monitoring（监控）
  -> metrics / logs / traces / black-box checks（指标、日志、链路与黑盒探测）
  -> alerting rules（告警规则）
     -> symptoms（用户可见症状）
     -> causes（原因线索）
     -> SLO burn rate（错误预算燃烧率）
     -> for / keep_firing_for（触发前持续时间与恢复后保持时间）
  -> alert labels（告警标签）
     -> service（服务）
     -> severity（严重级别）
     -> owner（责任人）
     -> slo（服务水平目标）
  -> alert annotations（供人阅读的附加说明）
     -> runbook_url（操作手册链接，不作为每次变化的告警身份）
  -> Alertmanager（告警处理器）
     -> grouping（分组）
     -> routing（路由）
     -> inhibition（抑制）
     -> silence（静默）
     -> receivers（接收器列表）
  -> response（响应）
     -> page（需要立即响应的通知）
     -> ticket（工单）
     -> info（信息记录）
     -> automation（自动化）
  -> review（复核）
     -> noise（噪声）
     -> duplicates（重复事件）
     -> flapping（状态反复抖动）
     -> missing runbooks（缺少操作手册）
     -> bad ownership（责任归属不正确）
  -> AIOps（智能运维）
     -> clustering（聚类）
     -> dedup（去重）
     -> enrichment（补充上下文）
     -> runbook recommendation（推荐操作手册）
```

初学路线：

```text
inventory alerts（清点告警）
  -> classify page/ticket/info（分成立即通知、工单与信息）
  -> require owner and runbook（要求责任人与手册）
  -> prefer SLO/symptom pages（优先针对服务目标和用户症状通知）
  -> move cause alerts to ticket/dashboard（把非紧急原因线索放到工单或仪表盘）
  -> configure Alertmanager grouping/routing/inhibition（配置分组、路由与抑制）
  -> track alert quality metrics（跟踪告警质量指标）
  -> review weekly（每周复核）
```

## 老师带你判断“该通知谁，要求他做什么”

一台数据库短暂中断，三十个服务各发几十条错误，你收到上千条告警。学生说“把它们全合并就安静了”。老师要再问：不同租户、不同重要性和真正独立的故障，会不会被一起隐藏？治理的目标是让通知对应可行动的问题，同时保留诊断所需的细节。

Alert（告警）是条件满足的事件，Notification（通知）是通过渠道发送的一次消息，Incident（事故或事件）是需要协调处理的用户影响。一条事故可以对应多条告警，一条告警可能多次通知。先分清这三个对象，否则“通知减少 90%”可能只是关闭了发送渠道。

### 第一课：从标签设计理解分组

标签给事件提供结构化维度，例如租户、服务、级别、环境和依赖。Grouping（分组）把相关事件放在一起；Deduplication（去重）识别重复事件；Inhibition（抑制）根据其他告警暂缓通知；Silence（静默）在明确时间和匹配范围内暂停通知。它们各有用途，不能用一个宽泛静默代替故障修复。

分组键要反映责任与影响边界。只按服务名分组，同名服务在不同租户中可能混在一起；把请求标识加入分组，又可能每条消息都变成独立组。先从用户影响、负责人和环境定义稳定维度，再验证分组后的信息是否足够行动。

### 基础实验与故障实验：少了一组，可能丢了什么

前置条件是 Node.js，在仓库根目录运行合成数据练习，不发送任何真实告警。

```powershell
node examples/teacher-led-reliability-lab/lab.mjs alert
node examples/teacher-led-reliability-lab/lab.mjs alert --fault
```

正常案例输入 4 个事件，按租户、服务、依赖和级别分成 3 组，保留不同影响边界。故障模式只按服务名分成 1 组，出现 `unsafeTenantMerge: true` 和 `REJECT_UNSAFE_GROUPING`（拒绝不安全分组）。请你先画出每条事件应去哪个组，再与程序比较。

这个实验说明“更少”不自动等于“更好”。检查输出不符时，先核对目录、参数和脚本版本。程序只在内存计算，无资源需要清理；保存两次输出以及自己挑选分组键的理由。它不验证真实 Alertmanager 的投递、重试和 HA 行为。

### 第二课：治理效果需要分母和漏报检查

先记录周期内的通知量、独立事故数、可行动通知比例、重复通知、错误路由和漏报。Actionable（可行动）意味着接收者知道是否需要立即做什么，不只是消息包含一个链接。只有通知量下降而漏报上升，治理可能损害可靠性。

影子评估是一种可用方法：新规则先只记录将如何分组和路由，保留原规则承担通知，再对照真实事件人工复核。明确观察周期、覆盖流量和退出条件后逐步启用。静默和抑制也要有到期、负责人和审计，避免忘记恢复。

告警链本身需要可观测性：规则是否在评估、事件是否发到处理器、路由是否命中、渠道是否接受、值班人员是否确认。每段的成功含义不同。合成演练要能从测试事件走到测试接收者，注明测试环境和清理，不能用生产群验证任意规则。

容量要考虑突发事件风暴、队列、外部渠道限流和恢复通知；安全要限制谁可更改规则、静默和路由。升级前保留旧规则、测试样本和匹配结果，回滚后检查通知状态，而不只检查配置加载成功。

### 面试课堂：30 秒、3 分钟与反例

30 秒：“告警治理让通知和用户影响、责任与动作对应。通过分组、去重、路由和抑制降低重复劳动，同时用漏报和可行动性验证质量。”

3 分钟讲数据库故障引发服务告警的链路，说明哪些事件可以关联、哪些边界必须保留，再讲影子评估和渐进启用。追问：“同一分钟的告警都是一个根因吗？”不一定，需要依赖和其他证据。“为什么不只看 CPU？”资源症状不直接等于用户影响。“怎么证明降噪不是漏报？”用标注样本、人工复核、真实事故回放与独立探测对照。

生产设计题：跨十个租户的告警平台如何分配规则和通知权限。事故题：一条过宽静默屏蔽了关键告警，先界定时间、匹配器和受影响事件，再恢复必要通知、检查漏掉的业务风险。GitHub 保存分组实验、规则测试样本、漏报复核与路由图。

## 治理课堂：减少噪声时怎样避免漏掉真正的事故

### 先问收到消息的人要做什么

同学，CPU 超过某个数值只是一条观察。如果服务有充足余量、用户请求正常、没有需要立即处理的风险，半夜把人叫醒可能没有行动价值。告警规则应说明用户影响或即将越过的安全边界，并指向能采取行动的人和操作手册。

反过来，资源指标也并非都应该删除。文件系统即将写满、证书即将过期，可能在影响用户前就需要行动。重点是风险机制、提前量和处理窗口，而不是只保留“已经坏了”的信号。你要能解释：为什么这项信号值得通知、现在不处理会发生什么、通知后具体做什么。

把立即中断工作处理、进入工单排期、留作观察三类分开。它们可以来自同一指标的不同风险阶段，但不应把所有波动都当最高优先级。严重程度还应结合影响范围和持续时间，不能只凭标题里写了 Critical 就自动升级。

### 分组、去重、抑制和静默各解决一类问题

分组把相关告警放在同一通知里，减少消息数量；去重避免同一告警重复通知；抑制让一个已知上层问题暂时压住相关下层症状；静默则是在指定范围与时间内暂停通知。这些手段并不等于修改原始指标，也不自动证明故障已经恢复。

例如机房网络异常引发多台主机不可达，可以按明确的机房归属关联，但仍保留每个服务的业务影响。若两套不同租户都叫 `order-api`，仅按服务名合并会把不同责任和影响混在一起。分组键必须包含能够维持故障域与权限边界的字段。

静默要有原因、负责人、开始结束时间和对象校验。一个没有到期时间的宽泛静默，可能把未来完全不同的事故也隐藏。课堂故障演练可以故意扩大匹配范围，检查能否识别额外被压住的租户；预期是拒绝这项规则或缩小范围，不是以消息越少越成功。

### 用历史回放检查规则，不只观察总消息数

准备一小组已脱敏、标注清楚的历史或合成事件：真正需要叫醒人的事故、普通波动、维护窗口和无数据故障。旧规则与候选规则对同一输入计算，比较捕获、遗漏、重复和通知延迟。这叫 Shadow evaluation（影子评估），候选规则先不替代正式通知。

评价时同时看精确率和召回率。精确率关注发出的通知里有多少确实需要行动；召回率关注应该被发现的事故里有多少被发现。删除全部规则能让通知数量归零，却让召回率极差。没有被通知的事故也要从工单、用户报告和复盘中补入评价集，否则数据天然偏向已有规则。

样本还应覆盖峰值和低流量、不同租户及版本。只在安静的一天验证规则，不能证明它能承受发布或依赖故障。对不确定标签单独处理，不要让模型把“没人反馈”自动当作误报。

### 阈值与持续时间为什么需要一起解释

阈值规定何时满足条件，持续时间规定条件需要维持多久才进入触发状态。持续时间可以过滤短时波动，但也增加发现延迟。若故障会在一分钟内耗尽容量，盲目增加等待五分钟并不是安全降噪。

同时检查采集周期、规则评估周期和通知分组等待。即使每一层都只多等几十秒，端到端通知可能晚于处理窗口。用时间线计算“故障开始到值班人员收到消息”由哪些等待组成，才能有针对性地调整。

对抖动告警，应先判断信号噪声、阈值缺少迟滞、采样缺失还是系统真的反复退化。迟滞指进入异常和退出异常使用不同条件，帮助避免边界附近反复切换。具体实现依赖规则系统，不能在不支持的配置里随意添加字段。

### 治理也是一次生产变更

告警规则、路由和静默配置都需要版本控制、审查、小范围验证与回退。发布时确认规则解析成功、实际加载版本正确、测试事件能走到预期接收者，并且无权的接收者不会收到敏感信息。配置文件格式合法只通过了其中一关。

面试事故题：规则改动后告警量下降九成，但用户投诉增加。先核对标签变化、路由覆盖、抑制范围和采集数据，再与业务事故对账；必要时回退候选规则并启用已验证的兜底通知。不要为了证明治理有效只展示下降曲线。

学习证据包括规则前后差异、回放样本、漏报与误报对照、接收链路记录、回滚条件和责任人。你要能向面试官解释一次保留“看起来很吵”的规则的决定：它也许需要改进，却覆盖了当前没有其他防线的重大风险。

## 规则推演课堂：同一个百分数，为什么需要不同动作

### 把风险时间算出来，才能决定是否叫醒人

同学，磁盘用了百分之八十二，只告诉你现在有多少空间被占用，没有告诉你多久会写满。同样剩一百 GB，一台主机每分钟增长十 GB，另一台每天增长一 GB，处理窗口完全不同。第一台需要立即确认增长来源、可用容量和业务写入风险；第二台可能适合排容量工单。增长率也不是永远不变，日志轮转、批量导入和清理会让线性预测失效，所以预测应附观察窗口、历史变化和不确定范围。

现在在纸上设一个虚构服务：还剩六十 GB，最近三十分钟净增三十 GB，假设这个速度保持不变，约六十分钟会用完。调查需十五分钟，批准和扩容需三十分钟，再留十五分钟余量，已经没有多少缓冲。若只按“剩余不足百分之十才报警”，可能来不及。这里的每个分钟数都是课堂输入，不是通用阈值；真实手册应使用团队测量过的响应和交付时间。

容量预测告警需要自己的质量检查。删除旧日志造成短时负增长，不代表可以永远不扩容；采集器没上报，也不能当作磁盘停止增长。至少并行观察可用空间、增长趋势、数据完整性和写入失败。对预测结果可采取多级动作：早期工单让团队安排容量，临近可恢复边界再中断值班。把告警等级和可执行动作对应起来，才能避免“低阈值太吵、高阈值太迟”的来回争论。

### 错误预算燃烧率是相对速度，不是失败百分数

SLO 是 Service Level Objective，即团队约定的服务质量目标。假设本课目标是百分之九十九点九的合格请求成功，允许坏请求比例就是千分之一。观察窗口失败比例为百分之一时，燃烧率为十，意思是按当前比例消耗预算的速度为允许速度的十倍，而不是“坏了百分之十”。先把分子、分母和单位写出来，再解释数字，否则所有仪表盘看起来都有百分号，结论却完全不同。

对于按请求计算的预算，某段时间实际消耗的预算比例，要用该段坏请求数除以整个 SLO 窗口允许坏请求数。只有流量足够稳定等假设成立时，才可以用“燃烧率乘观察时长除以预算窗口时长”作近似。节假日与工作日流量相差十倍时，这个近似可能误导。值班界面应优先展示真实计数和口径，容量规划中的预测要与已发生的预算消耗分开。

长窗口回答“最近累计损害是否显著”，短窗口回答“损害现在是否仍在发生”。两个窗口一起满足才紧急通知，可以避免只看历史损害导致恢复很久后仍然叫醒人；同时安排另一档较低燃烧率、较长窗口的工单或通知规则，发现慢性退化。这种多窗口、多燃烧率方法来自 [Google SRE 的 SLO 告警讨论](https://sre.google/workbook/alerting-on-slos/)，具体窗口需结合服务目标评估，不能机械抄一组比例用于所有业务。

低流量服务尤其需要判断：五分钟只有一次请求并且失败，比例是百分之百，但样本无法反映稳定的长期质量。简单加入最低请求量会减少抖动，也可能让完全无流量的故障永远不报警。可结合合成探测、较长观察窗口、业务应有流量和失败绝对次数来设计旁路信号；“没有足够样本”必须有明确去向，不能默认为健康。对于一天只跑一次的重要批处理，完成时间和数据新鲜度可能比请求错误率更合理。

## 时间状态课堂：为什么曲线超线了，手机还没有响

Prometheus 的 `for` 持续时间不是滑动窗口的别名。查询中的 `[5m]` 表示计算使用过去五分钟的样本，`for: 5m` 则要求同一告警标签集合的条件在连续评估中持续满足五分钟。两层时间可以同时存在，它们不是固定相加后就一定通知；窗口计算、评估节奏、网络传递和通知分组还会影响结果。先看规则当前处于 inactive（不活动）、pending（条件满足但尚未够时长）还是 firing（已触发），再去查通知器。

做一项不接触真实服务的纸面实验。前置材料是一张时间表，假设每分钟评估一次，条件满足时记一，不满足时记零，持续条件设为三分钟，恢复保持时间暂设为零。第一组在零、第一、第二、第三分钟均为一；预测第三分钟会进入触发，因为从首次满足到此经过三分钟，而不是数到三个样本就够。第二组为一、一、零、一、一、一、一；第二分钟被打断，第三分钟重新开始计时，到第六分钟才够三分钟。

验证方法是逐行写出评估时刻、条件值、首次连续满足时间和状态，不依赖手机通知来猜内部状态。故障注入是在第四分钟把规则标签里的 `current_value` 从九十一改成九十二；如果把不断变化的数值放进标签，就可能制造一个新的告警身份，让等待重新开始。修复是把动态值放到 `annotations` 的说明中，保持标识与路由维度稳定，然后重新推演同一时间线。这个实验结束只保留纸面记录，无外部资源需要清理。

真实环境验证时再用 [告警规则官方说明](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/) 和所用版本的规则单元测试，把相同输入送进规则计算，核对标签、状态和时刻。纸面模型没有模拟缺样本、重启后的状态恢复和查询失败，不能宣称它已经验证全部 Prometheus 行为。结果不同先检查评估间隔、表达式输出标签、持续时间及加载的实际规则版本，不立即缩短所有阈值。

`keep_firing_for` 是条件不再满足后继续保持触发的机制，可以减少短暂恢复造成的通知抖动，但也会推迟恢复消息。它不自动证明期间一直有坏请求。面试时要能同时解释检测时间和恢复时间：增大持续时间可能晚发现，增大恢复保持可能晚解除，两者是在不同阶段做取舍。网络分区和采集缺口还需要数据质量告警，不能靠无限延长触发状态掩盖监控失明。

## 路由合同课堂：把一条告警追到正确的人

### 先写归属，再写匹配器

通知对象不是一个任意字符串。接收者配置映射到值班系统、测试接收器或工单平台，值班表再决定当前真正接手的人。路由设计应明确租户、环境、服务和严重级别，缺字段时进入可见的兜底处理，而不是悄悄丢弃。`owner` 表示责任归属，不应允许不可信业务请求随意修改这个字段来把通知发给别的团队。

Alertmanager 的子路由有顺序，默认命中一个子路由后不会继续匹配其后同级路由，除非明确配置继续匹配。因此“先按 page 发值班，再按服务发团队”的平铺配置，不一定会把同一条告警发到两个地方。应先画路由树和预期接收者集合，再按真实匹配语义逐例核对。若确需多个通知，应明确重复发送的目的、权限和接班责任，避免两个团队互相以为对方会处理。

抑制规则中的 `equal` 要求源告警和目标告警在指定标签上相同；缺失标签与空值的处理尤其值得小心。若源、目标都缺 `service`，原本想限制同服务的规则可能变得过宽。安全做法是让来源和目标匹配条件都要求关键字段存在且非空，并在规则审核中加入“双方缺字段”的反例。规则合法只表示解析器接受，不表示你的责任边界被保留。

可以准备四张合成告警卡片：租户甲生产订单失败、租户乙生产订单失败、租户甲测试订单失败、租户甲生产数据库不可用。分别写预期接收团队和是否可以被数据库告警抑制。基础验收是前三张没有跨租户或跨环境合并，数据库异常只影响已证明有依赖关系的范围。故障注入是删除租户字段并重算，预期进入待人工核对而不是扩大抑制。修复后恢复字段、重跑全部卡片，保存路由前后差异。

### 数据身份变化，是一种隐蔽的告警故障

标签重命名可能同时改变告警身份、分组与路由。发布团队把 `env` 改成 `environment`，采集仍正常、规则仍有值，但旧匹配器可能不再命中。迁移时要盘点生产者、规则、通知模板、抑制、仪表盘和自动化消费者，用双字段兼容或受控切换过渡，并设定旧字段退役条件。新旧身份并存阶段可能重复通知，应明确识别迁移事件而不是自动当成两场事故。

描述字段同样需要安全边界。日志正文里可能出现手机号、令牌和用户输入，不能不加筛选就写进短信。链接应指向受控的仪表盘与手册，不直接拼接不可信内容为命令或链接。AIOps 摘要将原始日志压缩成一句话，也没有因此获得发送给外部接收人的权限；通知模板需要字段白名单、脱敏规则和租户隔离。

## 验收课堂：用漏报、延迟与人的负担一起评分

精确率与误报率必须声明统计单位。一个事故发出十条重复通知，如果按通知数当十次正确发现，会虚高收益。评价可以分两层：按独立事故看是否被及时发现，按值班接触的通知看是否需要行动。把人工确认、重复通知、预计维护和未知归因分别记录；没有人点击确认不是“必定误报”，也可能是通知到了错误的人或人已经过载。

做一个带答案的合成评分实验。假设评估集有二十个独立事故，其中十二个必须立即通知；旧策略发现这十二个并产生八次无须立即行动的通知，候选策略发现十个并产生两次无须立即行动的通知。按本课一事故最多计一次通知的约定，旧策略精确率为十二除以二十，即百分之六十，召回率百分之百；候选精确率十除以十二，约百分之八十三点三，召回率十除以十二，同样约百分之八十三点三。候选更安静，但漏掉了两个重要事故。

下一步不是自动选得分最高的策略，而是查看漏掉的两起是什么、延迟多久、是否存在独立防线。漏掉核心支付不可用，与多通知一次临时测试错误，不应被同样的一分权重抵消。把严重程度、可逆性、受影响范围和响应时间纳入评审，可以形成有条件的准入门槛。评分表里的二十起都是虚构课堂样本，不能拿它宣称真实模型提升了某个百分比。

没有事故的观测日无法测出召回率，应报告样本不足。新规则上线后还要持续收集用户报告和未触发通知的事故，防止评价集只包含系统自己发现的事件。告警聚类模型的训练集与评估集要按事故或时间分开，同一场故障的近似重复消息不要分到两边，否则模型像提前看过答案一样。可参照 [机器学习](../data-ai/machine-learning.md) 的数据泄漏与验证部分理解这个问题。

统计误报时也要看人的实际时间：一百条自动归档的信息未必比五条需要半小时调查的模糊 page 更贵。可以记录每班被中断次数、接手延迟、有效动作比例与调查时间区间，但不能把它变成员工排名，逼人快速关单。治理是降低无意义负担，同时让关键告警被认真处理；指标一旦改变人的行为，就要检查是否出现只关单不解决的反作用。

## 生产设计题：一万条规则如何安全演进

先把规则看成有版本的代码和有责任人的产品。代码层检查表达式语法、固定标签和单元样本；产品层检查用户风险、通知等级、负责人、响应动作及退役条件。对于共同模式使用经过审核的模板，服务只提供已验证的目标和标签合同。模板升级也可能一次影响数千条规则，需要固定版本、小范围试用和一键恢复旧规则集，而不是全站覆盖后等用户投诉。

容量规划要分清规则计算和通知投递两条路径。复杂长窗口查询可能压垮指标系统，标签基数增长可能产生大量活跃告警，细分组又会放大通知数量。先计算每次评估扫描成本、活跃标签集合上界、突发通知量和渠道配额；能用预计算记录规则减少重复查询，但要监控预计算是否新鲜。更多副本不能修复一条无界查询，也不能让外部短信平台无限提高吞吐。

高可用不是“通知严格一次”。重复采集与多处理器可降低漏报风险，却可能在故障或网络分区时重复发送；业务需要能识别同一事件并避免重复建单或重复执行修复。规则评估者、告警处理者、发送渠道、值班目录和手册服务分别有故障点，演练要覆盖其中一条链断开。测试接收器确认收到消息只证明渠道到达，不能当作人已经确认或业务已恢复。

生产模拟可以设四个故障场景：规则加载失败、抑制过宽、渠道限流、值班目录过期。为每个场景写可观察证据、谁接管、是否停止发布和怎样恢复，不要求真的发送生产通知。验收标准是兜底链路仍能触达受控测试接收者，失效范围可定位，恢复后没有遗忘静默或重复任务。清理演练路由、测试告警和临时权限时按明确编号操作，并保留脱敏审计。

面试三分钟可以这样展开：我先按用户风险和响应窗口定义 page，再把规则输出的稳定身份与附加说明分开。评估器负责条件状态，处理器负责路由分组与抑制，渠道接受和人员确认是不同阶段。上线前用有正反样本的回放检查召回、误报、延迟及跨租户边界，先旁路比较，再小范围启用。出现通知骤减时，我先查加载版本、标签迁移、静默和渠道，而不是先庆祝降噪成功；回退也验证实际通知和遗留状态。

继续追问“为什么不让模型直接删除低分规则”，回答模型相似度不能证明风险消失，应让它推荐复核顺序，由负责人核实替代防线；追问“规则一天没触发是否无用”，回答可能只是风险低频，要用合成故障和历史案例检查覆盖；追问“固定动作能否全自动”，回答仍要验证目标、幂等、容量和权限，重复通知绝不能直接变成重复生产变更。最终作品应包含规则版本、测试输入、预期路由、评分计算和拒绝自动化的理由。

## 告警不是监控

监控系统有很多用途：

- 趋势分析。
- 容量规划。
- dashboard。
- 事故排查。
- 业务分析。
- 告警。

告警只是其中一部分。

Google SRE 对 page 的要求很强：告警不应该因为“有点奇怪”就打扰人。page 应该代表一个紧急、可行动、正在或即将用户可见的问题。

所以：

```text
page 应由可核验的风险信号触发，也可能来自用户报告或人工升级。
但不是所有监控都应该 page。
```

## 好告警的四个条件

每条 page 级告警都要过四个问题：

| 问题 | 解释 |
|---|---|
| 是否用户可见？ | 正在影响或即将影响用户体验 |
| 是否紧急？ | 不能等到工作时间 |
| 是否可行动？ | 值班人员知道下一步做什么 |
| 是否需要人的判断？ | 如果只是固定动作，应该自动化或降级 |

如果一条告警可以被长期忽略，它就不该是 page。

如果一条告警每次都是执行同一个机械动作，可以评估自动化；只有目标、风险、权限、幂等和验收边界清楚时才启用，不能仅凭动作重复就自动执行。

如果一条告警没有明确处理人、runbook 和下一步，它应该先治理再升级。

## Page / Ticket / Info

推荐先用三类，不要一开始搞十几个等级。

| 等级 | 含义 | 通知方式 | 示例 |
|---|---|---|---|
| page | 需要立即人工介入 | 电话、短信、强提醒 | SLO 快速燃烧、核心链路不可用 |
| ticket | 需要处理但可排队 | 工单、Issue | 磁盘 7 天后可能满、错误预算慢速消耗 |
| info | 记录事实或给上下文 | 日报、日志、dashboard | 发布完成、自动扩容成功 |

不要把所有 `warning` 都发给值班人。

判断口诀：

```text
现在不处理，用户会明显受影响吗？
会 -> page
不会但应该处理 -> ticket
只是信息 -> info
```

## 症状 vs 原因

Google SRE 强调区分 what 和 why：

- 症状：用户看到什么坏了。
- 原因：系统内部为什么坏。

示例：

| 症状 | 可能原因 |
|---|---|
| HTTP 5xx 上升 | 数据库连接失败、发布 bug、下游超时 |
| 响应变慢 | CPU 饱和、锁竞争、数据库慢查询 |
| 数据延迟 | 消费者积压、Kafka broker 异常、批任务失败 |

告警策略：

```text
page 优先症状告警。
ticket 可以关注确定的原因告警。
dashboard 保存更多原因指标。
```

为什么？

因为一个原因可能不影响用户，一个症状才说明服务真的在坏。

CPU 95% 可能只是批任务高峰；但 5xx、SLO burn、用户请求超时更接近用户体验。

## 四个黄金信号

Google SRE 推荐用户侧服务优先关注四个黄金信号：

| 信号 | 含义 | 常见指标 |
|---|---|---|
| Latency | 请求耗时 | p95、p99、足够快请求比例 |
| Traffic | 流量 | RPS、QPS、消息吞吐 |
| Errors | 错误 | 5xx、失败率、错误预算燃烧 |
| Saturation | 饱和度 | CPU、内存、队列、连接池、磁盘 |

告警优先级：

```text
Errors / Latency 伤害 SLO -> page
Traffic 异常影响业务 -> page or ticket
Saturation 接近用户影响 -> ticket or page
纯资源异常但无影响 -> ticket / dashboard
```

## Alert Rule 设计

Prometheus alerting rule 的核心字段：

| 字段 | 作用 |
|---|---|
| `alert` | 告警名 |
| `expr` | PromQL 条件 |
| `for` | 持续多久才 firing |
| `keep_firing_for` | 条件恢复后继续保持 firing 多久 |
| `labels` | 路由和分组用标签 |
| `annotations` | 人看的描述、runbook、dashboard |

示例：

```yaml
groups:
  - name: order-api-alerts
    rules:
      - alert: OrderApiHighErrorRate
        expr: |
          sum(rate(http_requests_total{job="order-api",code=~"5.."}[5m]))
          /
          sum(rate(http_requests_total{job="order-api"}[5m]))
          > 0.05
        for: 5m
        keep_firing_for: 5m
        labels:
          severity: page
          service: order-api
          owner: team-order
        annotations:
          summary: "order-api 5xx error rate is above 5%"
          description: "More than 5% of order-api requests are returning 5xx for 5 minutes."
          dashboard_url: "https://grafana.example.com/d/order-api"
          runbook_url: "https://runbooks.example.com/order-api-high-error-rate" # 占位地址，替换为已发布且可访问的手册
```

注意：

- `labels` 用于机器路由和分组。
- `annotations` 用于人理解和处理。
- `for` 可以减少瞬时毛刺。
- `keep_firing_for` 可以减少抖动恢复。

本规则是教学片段，百分之五阈值不是所有服务的推荐值。英文摘要与描述意为“订单接口最近五分钟服务端错误比例超过百分之五”，可换成中文；没有请求或错误序列缺失时，比例表达式可能没有结果，应另设数据质量和流量检查。不要把无结果当作零错误。下面路由与抑制同样是配置片段，必须配套合法接收者，并加入环境、租户和字段非空约束后再评审使用。

## SLO 告警优先

如果已经有 SLO，page 应优先围绕错误预算燃烧。

```text
SLO burn-rate page（服务目标燃烧率紧急通知）
  -> 用户影响更明确
  -> 跨服务口径统一
  -> 可和发布决策关联
```

普通阈值告警：

```text
5xx > 5%
```

SLO 告警：

```text
error_rate > burn_rate * allowed_error_rate
```

两者差别：

| 方式 | 问题 |
|---|---|
| 固定阈值 | 不同 SLO 的服务难统一 |
| SLO burn rate | 直接表达预算消耗速度 |

page 规则建议：

- SLO 快速燃烧。
- 核心用户路径不可用。
- 数据丢失或强一致性破坏。
- 自动化无法恢复且影响扩大。

ticket 规则建议：

- SLO 慢速燃烧。
- 容量将在未来几天耗尽。
- 单点风险。
- runbook 缺失。
- 告警质量问题。

## Alertmanager 核心能力

Prometheus 负责判断条件是否满足。Alertmanager 负责通知治理。

Prometheus 官方文档也强调，Prometheus alerting rules 不是完整通知系统；Alertmanager 负责分组、限流、静默、抑制和通知路由。

### Grouping

把同类告警合并，避免告警风暴。

```yaml
route:
  group_by: ["alertname", "service"]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  receiver: default
```

字段含义：

| 字段 | 作用 |
|---|---|
| `group_by` | 哪些标签相同就合成一组 |
| `group_wait` | 第一条告警到来后等多久再发 |
| `group_interval` | 同组新增告警多久后再发 |
| `repeat_interval` | 同一组持续 firing 多久重复通知 |

经验：

- `group_by` 太细，会通知过多。
- `group_by` 太粗，会丢上下文。
- `repeat_interval` 太短，会制造疲劳。

### Routing

按标签把告警发给正确团队。

```yaml
route:
  receiver: default
  routes:
    - matchers:
        - severity="page"
      receiver: oncall
    - matchers:
        - severity="ticket"
      receiver: ticket-system
    - matchers:
        - service="payment-api"
      receiver: payment-team
```

路由依赖标签质量。没有 `service`、`owner`、`severity`，路由只能靠猜。

### Inhibition

当一个更高层告警已经 firing 时，抑制低层衍生告警。

```yaml
inhibit_rules:
  - source_matchers:
      - alertname="OrderApiDown"
      - tenant=~".+"
      - service=~".+"
    target_matchers:
      - alertname="OrderApiLatencyHigh"
      - severity="ticket"
      - tenant=~".+"
      - service=~".+"
    equal: ["tenant", "service"]
```

含义：

```text
如果 order-api 已经 Down，
同一非空租户、同一非空 service 的指定延迟 ticket 告警暂缓通知。
```

目标告警名必须对应已验证的衍生症状，不能仅凭级别把整个服务的独立风险一起抑制。源和目标都要求必要标签非空，避免两边都缺标签时意外相等；缺标签本身应另行治理。仍要保留被抑制事件供值班人员查看，并测试跨租户和缺标签反例。

注意：抑制不是隐藏问题，而是减少重复通知。排障时 dashboard 里仍然应该能看到底层指标。

### Silence

Silence 是临时静默。

适合：

- 计划维护。
- 已知故障处理中。
- 测试告警规则。

不适合：

- 永久掩盖坏规则。
- 代替修复。
- 没有 owner 的长期静默。

每个 silence 应该有：

- 原因。
- 创建人。
- 过期时间。
- 关联工单或变更。

## 标签规范

每条告警至少应该有：

| 标签 | 示例 | 用途 |
|---|---|---|
| `alertname` | `OrderApiHighErrorRate` | 告警名 |
| `severity` | `page` / `ticket` / `info` | 分级 |
| `service` | `order-api` | 服务路由 |
| `owner` | `team-order` | 责任团队 |
| `env` | `prod` | 环境 |
| `slo` | `order-api-availability` | 关联 SLO |

annotations 至少应该有：

| annotation | 示例 | 用途 |
|---|---|---|
| `summary` | 简短标题 | 通知标题 |
| `description` | 具体说明 | 人读 |
| `runbook_url` | runbook 链接 | 下一步 |
| `dashboard_url` | Grafana 链接 | 证据 |
| `query` | PromQL 或查询说明 | 复查 |

没有 owner 和 runbook 的 page，是债务。

## 告警命名规范

推荐：

```text
Service + Symptom
```

例如：

```text
OrderApiHighErrorRate
OrderApiLatencySLOBurn
PaymentApiDependencyFailures
KafkaConsumerLagGrowing
```

不推荐：

```text
High
Error
CPUWarning
SomethingWrong
```

告警名应该让人在通知列表中一眼知道：

- 哪个服务。
- 什么症状。
- 大概严重性。

## 告警体检表

治理告警时，对每条 page 填这张表：

| 问题 | 答案 |
|---|---|
| 过去 30 天触发几次？ | |
| 有几次是真事故？ | |
| 是否用户可见？ | |
| 是否紧急？ | |
| 是否可行动？ | |
| 是否有 owner？ | |
| 是否有 runbook？ | |
| 是否能自动化？ | |
| 是否和其他告警重复？ | |
| 是否应该降级为 ticket？ | |
| 是否应该删除？ | |

处理决策：

| 情况 | 动作 |
|---|---|
| 频繁误报 | 改规则或删除 |
| 重复告警 | grouping / inhibition |
| 不紧急 | 降级 ticket |
| 不可行动 | 补 runbook 或删除 |
| 固定机械处理 | 自动化 |
| 用户影响明确 | 保留 page，补上下文 |

## 告警质量指标

告警治理要有指标，不然会变成口号。

| 指标 | 含义 |
|---|---|
| pages per on-call shift | 每班 page 数 |
| alerts per incident | 每次事故多少告警 |
| actionable alert ratio | 可行动告警比例 |
| false positive ratio | 误报比例 |
| duplicate alert ratio | 重复告警比例 |
| flapping alert count | 抖动告警数 |
| alerts without owner | 无 owner 告警数 |
| alerts without runbook | 无 runbook 告警数 |
| MTTA | 平均确认时间 |
| MTTR | 平均恢复时间 |
| alert review backlog | 待治理告警数量 |

最小目标：

```text
所有 page 必须有 owner 和 runbook。
每周复盘 top noisy alerts。
```

## 告警风暴治理

告警风暴常见原因：

- 一个故障触发很多症状和原因告警。
- 每个实例都发一条。
- grouping 太细。
- repeat_interval 太短。
- 没有 inhibition。
- 下游故障导致上游全部报警。

处理顺序：

1. 先确认有没有用户影响。
2. 找到最高层症状告警。
3. 对实例级告警做聚合。
4. 用 inhibition 抑制衍生告警。
5. 调整 group_by。
6. 调整 repeat_interval。
7. 在复盘中删除或降级噪声规则。

不要在事故中临时乱删规则。确需静默时先核对范围、授权、到期时间及仍能发现关键影响的兜底信号，再进行有审计的临时静默；不应默认先屏蔽所有噪声。

## AIOps 如何参与告警治理

AIOps 不是一上来就“自动根因分析”。更现实的切入点：

| 能力 | 输入 | 输出 |
|---|---|---|
| 告警去重 | alert labels、fingerprint、时间窗口 | 合并重复告警 |
| 告警聚类 | 服务、拓扑、时间、文本 | 事故候选组 |
| 上下文补全 | 指标、日志、变更、runbook | enrich alert |
| 相似事故检索 | 告警摘要、embedding | 历史案例 |
| 告警摘要 | 一组告警 | 人话摘要 |
| 噪声评分 | 历史触发、确认、关闭 | 治理优先级 |
| runbook 推荐 | alertname、service、symptom | runbook 链接 |

AIOps 需要干净的输入。没有标签规范、owner、runbook、SLO 的告警，很难做出可靠的降噪和自动化。

## 入门实验：告警体检表

准备一个 CSV：

```csv
alertname,service,severity,count_30d,true_incidents,has_owner,has_runbook,action
HighCPU,order-api,page,42,0,true,false,
OrderApiHighErrorRate,order-api,page,3,3,true,true,
DiskWillFill,node,ticket,12,2,true,true,
PaymentApiLatencyHigh,payment-api,page,8,4,true,false,
```

目标：

1. 找出没有 runbook 的 page。
2. 找出 30 天触发很多但真事故很少的 page。
3. 找出应该降级为 ticket 的告警。
4. 为每条 page 补 owner 和 runbook。
5. 写一份治理建议。

示例判断：

| 告警 | 判断 |
|---|---|
| `HighCPU` | 42 次触发、0 次已记录事故，先核对事故样本与风险，再评估降级或改规则；不能仅凭这两列删除 |
| `OrderApiHighErrorRate` | 保留 page，确认 runbook 完整 |
| `DiskWillFill` | 保留 ticket，不 page |
| `PaymentApiLatencyHigh` | 保留或改 SLO burn-rate，并补 runbook |

## 常见错误

### 所有告警都是 page

这会快速制造疲劳。page 只给紧急且可行动的问题。

### 只写原因告警

CPU、磁盘、连接池都是原因或风险信号。page 应优先症状和 SLO。

### 没有 runbook

没有 runbook 的告警会让新人值班时无从下手。

### 标签随意写

`team`、`owner`、`service` 混用会让路由和聚类失效。

### repeat_interval 太短

重复通知会制造疲劳。持续故障应该在事故流程里跟踪，不靠不停响铃。

### 永久 silence

长期 silence 只是把债务藏起来。应该修规则或修系统。

### AIOps 直接自动处理所有告警

先治理标签、分级、runbook 和 SLO，再谈自动化。

## 常用配置字典

### `for`

```yaml
for: 5m
```

条件持续满足 5 分钟才触发 firing，减少瞬时毛刺。

### `keep_firing_for`

```yaml
keep_firing_for: 5m
```

条件恢复后继续保持 firing 一段时间，减少抖动。

### `labels`

```yaml
labels:
  severity: page
  service: order-api
```

机器处理字段，用于路由、分组、抑制。

### `annotations`

```yaml
annotations:
  summary: "order-api 5xx is high"
  runbook_url: "https://example.com/runbooks/order-api"
```

人读字段，用于说明和处理。

### `group_by`

```yaml
group_by: ["alertname", "service"]
```

按哪些标签合并告警。

### `repeat_interval`

```yaml
repeat_interval: 4h
```

同一组持续 firing 多久重复通知。

### `inhibit_rules`

```yaml
inhibit_rules:
  - source_matchers:
      - alertname="OrderApiDown"
      - tenant=~".+"
      - service=~".+"
    target_matchers:
      - alertname="OrderApiLatencyHigh"
      - severity="ticket"
      - tenant=~".+"
      - service=~".+"
    equal: ["tenant", "service"]
```

高层告警出现时抑制低层衍生告警。

## 面试怎么讲

告警治理的核心是把噪声变成信号。好的 page 必须紧急、可行动、用户可见，并且需要人的判断。Google SRE 强调 page 很昂贵，如果告警可以被忽略、不能行动、只是有点异常，或者只是机械处理，就不应该叫醒人。

我会优先围绕 SLO 和用户症状做 page，把原因类告警放到 ticket 或 dashboard。落地上，Prometheus 负责规则判断，Alertmanager 负责 grouping、routing、inhibition、silence 和通知。每条告警都要有规范标签，比如 severity、service、owner、slo，以及 annotations 里的 runbook_url 和 dashboard_url。治理时要追踪 pages per shift、误报率、重复率、flapping、无 owner、无 runbook 等指标，并在事故复盘后持续删除、降级、合并或自动化坏告警。AIOps 的告警聚类、降噪和摘要，应该建立在这些规范化告警数据上。
