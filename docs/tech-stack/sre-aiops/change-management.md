# 变更管理

> 目标：不是填一张审批表，而是能让代码、配置、基础设施、数据库、证书、告警规则等生产变更可评审、可追踪、可验证、可回滚，并能把变更事件自动纳入告警、事件响应、RCA 和 AIOps 根因候选。

## 场景开场

服务突然 5xx 升高。

一个成熟的值班同事第一反应通常不是立刻猜数据库，也不是立刻重启服务，而是问：

```text
最近有没有变更？
```
变更可能是：

- 代码发布。
- 配置修改。
- 数据库迁移。
- 网络策略。
- 扩容缩容。
- 证书更新。
- feature flag。
- 告警规则调整。
- 依赖服务升级。

很多事故不是系统无缘无故坏掉，而是某个变更把系统推到了新状态。变更管理的价值，就是让团队知道“谁在什么时候改了什么，风险是什么，怎么验证，怎么回滚，出了问题能不能快速关联”。

## 一句话人话版

变更管理是生产改动的安全流程：让每次修改都有记录、评审、风险分级、验证计划、回滚计划和事后观察，出事时能快速判断它是不是嫌疑人。

## 官方知识地图

变更管理可以按这张地图理解：

```text
Change（变更）
  -> request（请求）
     -> what changes（改什么）
     -> why（为什么改）
     -> owner（责任人）
     -> planned window（计划窗口）
  -> risk assessment（风险评估）
     -> user impact（用户影响）
     -> blast radius（影响范围）
     -> reversibility（可逆性）
     -> dependency（依赖）
     -> data migration（数据迁移）
  -> review / gates（评审与门禁）
     -> code review（代码评审）
     -> tests（测试）
     -> security（安全）
     -> SLO / error budget（服务目标与错误预算）
     -> approval（批准）
  -> release engineering（发布工程）
     -> reproducible build（可重复构建）
     -> artifact（交付制品）
     -> version（版本）
     -> config snapshot（配置快照）
     -> deployment plan（部署计划）
  -> rollout（逐步发布）
     -> canary（小流量灰度）
     -> rolling（滚动更新）
     -> blue-green（蓝绿两套环境切换）
     -> feature flag（功能开关）
  -> verification（验证）
     -> SLI / SLO（服务指标与目标）
     -> errors（错误）
     -> latency（延迟）
     -> traffic（流量）
     -> saturation（资源饱和度）
     -> business metrics（业务指标）
  -> rollback / roll-forward（回滚或向前修复）
  -> record（记录）
     -> timeline（时间线）
     -> result（结果）
     -> incident link（事故关联）
  -> AIOps correlation（智能运维关联）
```

初学路线：

```text
write change record（编写变更记录）
  -> classify risk（划分风险）
  -> define verification metrics（定义验证指标）
  -> define rollback plan（定义回滚计划）
  -> deploy with canary / rolling（采用灰度或滚动部署）
  -> observe SLO（观察服务目标）
  -> record result（记录结果）
  -> link to incident if failed（失败时关联事故）
```

## 老师带你走完一次发布，而不只盯着成功提示

我们要把订单接口从版本一更新到版本二。你先在黑板画五个对象：代码、制品、配置、数据、运行实例。代码是源文件；制品是经过构建、准备部署的包或镜像；配置决定运行行为；数据是已经保存的业务状态；实例是实际处理请求的程序。五者版本不一定同步变化，发布记录必须能把它们关联起来。

制品上传成功说明仓库收到文件，部署任务成功说明执行步骤满足任务条件，进程启动说明程序存活，健康探测通过说明满足该探测，用户操作成功才回答业务是否恢复。老师会不断追问“你验证的是哪一层”，因为不少事故就隐藏在这些状态之间。

### 第一课：金丝雀流量怎么比较才公平

Canary（金丝雀或灰度）让一部分请求先走新版本，观察后再扩大。对照组和新版本要有可比请求类型、地区、租户和负载。只给新版本健康检查或内部账号，可能完全看不到真实用户的失败。平均值也会掩盖少数关键交易，所以要保留按业务类型的错误和延迟。

这次课堂用新旧版本各 1,000 次请求比较错误比例。旧版本错误 1 次，新版本正常案例错误 2 次，差值为 0.1 个百分点；故障案例错误 60 次，差值为 5.9 个百分点。注意“增加多少个百分点”和“相对增加多少倍”是不同说法，报告里明确分母。

### 基础实验与故障实验：让指标决定是否停止推进

前置条件是本机 Node.js 可用，在仓库根目录运行合成演练，不创建真实发布任务。

```powershell
node examples/teacher-led-reliability-lab/lab.mjs change
node examples/teacher-led-reliability-lab/lab.mjs change --fault
```

正常输出 `CONTINUE_OBSERVATION`（继续观察），故障输出 `STOP_AND_EVALUATE_ROLLBACK`（停止并评估回滚）。`excessErrorRate` 是新旧错误比例之差，`stopThreshold` 在课堂设为 0.01，即一个百分点。阈值只是本题假设，真实策略还要考虑服务目标、流量量级、窗口和置信程度，不能照抄为统一生产门禁。

验证时用纸笔复算，并解释为什么“继续观察”不等于可以立即全量。若结果不符，检查是否追加 `--fault`、当前目录和脚本版本。脚本只读内置数据，不执行变更，无资源需要清理。保存两次输出及一次阈值选择说明就是本次证据。

### 第二课：回滚的四个兼容面

回滚代码前分别确认接口、配置、数据模式和消息格式。新版本增加可选字段，旧版忽略它，可能兼容；新版本删除旧版必需字段，回退就可能失败。数据库备份恢复也不能随意当成应用回滚，因为恢复会影响备份之后的新写入，并可能与外部支付等系统状态不一致。

常见方法是先扩展再收缩：增加兼容结构，部署能同时处理新旧格式的代码，逐步迁移，确认旧调用方退出后再清理。每阶段都有验收和停止点。无法逆转的步骤在发布前明确，准备前向修复方案，而不是事故时才发现旧包无法使用新数据。

配置也是制品的一部分。保存版本和摘要，保证实例能报告当前生效值。只看配置中心“已发布”不能证明所有节点已加载；逐节点检查，处理滚动期间新旧配置共存。对证书、权限和网络策略同样如此，控制面显示成功之后还要验证实际连接。

### 第三课：发布的容量和影响范围

滚动升级时会有副本退出、替换实例预热和缓存未命中。平时刚够的容量可能在窗口里不够。先计算最少可用实例和下游连接预算，再设置批次大小、等待条件和停止线。新实例就绪不一定代表已承接代表性流量，观察错误、延迟及队列变化。

紧急变更缩短了等待时间，但仍需要明确对象、权限、验证和恢复。把不可省的保护做成工具约束，有助于紧急时保持一致。并发变更要限制，否则同一时间多个配置、版本和网络策略一起变化，既扩大影响，也很难归因。

向 AIOps 提供变更事件时，记录时间、资源标识、版本、变更类型、实施范围和结果。模型可以关联“故障前有变更”，但只能把它作为候选原因。把应用健康和业务验收状态写回事件，避免“流水线绿了”成为唯一信号。

### 面试课堂：从 30 秒解释到 3 分钟设计

30 秒：“变更管理让生产修改可追溯、可验证、可控制影响。我要关联制品、配置、数据和实例，先小范围验证，按预先定义条件停止或恢复，并确认业务结果。”

3 分钟讲准备、实施、验收、异常退出四步：建立基线与兼容矩阵，控制发布并发和剩余容量，比较代表性流量，停止后按数据兼容条件选择回滚或前向修复，最终逐节点与业务验证。

追问：“新版本错误率是旧版两倍，必须回滚吗？”先看样本量、绝对差异和重要用户路径，极低样本可能不稳定，但高风险失败仍应立即停扩。“数据库字段删了还能回旧包吗？”分析旧代码读写依赖和恢复代价。“自动回滚后仍坏呢？”检查其他配置、数据与共享依赖，不重复盲目切换。

设计题：三个可用区同时有更新需求，怎样限制共同故障并保证足够容量？事故题：流水线成功但一个节点配置没生效，要求收集逐节点版本、生效配置和请求分布再定位。GitHub 保存变更记录、兼容矩阵、灰度对比和回滚演练，明确课堂输入不代表生产效果。

## 发布工作坊：把一次改变拆成可验证的状态迁移

### 先认识四个版本，而不是只记一个提交号

同学，一次发布通常同时涉及源代码版本、构建制品版本、运行配置版本和数据结构版本。Git 提交能说明代码来源，但不能单独证明线上运行的二进制就是它，也不能说明环境变量、数据库迁移和开关状态与预期一致。

制品是准备部署的交付物，例如容器镜像或应用包。用不可变标识和校验值记录它，可以回答“部署的究竟是哪一份”。配置也要记录可审计版本；敏感配置只保存引用与脱敏摘要，不把密码写入 Git。数据结构变化则要有独立迁移记录和兼容性判断。

前置检查把这四类信息与实际目标对应起来：目标环境正确，制品可获得，配置适用，数据迁移顺序明确。若目标不符或制品身份无法确认，应停止，而不是在执行过程中凭印象选择一个相似文件。

### 灰度流量少，不代表风险一定小

Canary（灰度）把新版本先交给一部分对象或流量，观察后再扩大范围。但流量怎么选很重要：只给内部测试账号可能覆盖不到真实支付路径；只给一个低负载区域可能看不到峰值问题；新旧版本共享数据库时，少量新代码也可能执行影响全库的操作。

所以灰度设计要包含代表性与隔离性。代表性保证测试对象包含关键接口、数据形态和负载；隔离性限制故障能传播到哪里。百分之一流量不是百分之一风险的数学保证，必须沿共享资源和写入路径评估影响范围。

比较时看比例与样本量。新版本只有十个请求且零错误，旧版本十万个请求中有少量错误，不能据此说新版本更可靠。延迟也要考虑请求类型是否相同。证据不足时继续观察或扩大受控样本，不把“还没看到坏事”当作安全结论。

### 新旧版本同时运行时，合同必须兼容

滚动发布期间，新旧实例可能同时读写同一个数据库、消息或缓存。假设新代码只认识字段 B，旧代码只写字段 A，混合运行就可能失败。把发布看成若干中间状态，而不是从旧瞬间跳到新，才能发现这类问题。

Expand and contract（先扩展兼容、再收缩旧结构）的思路是先加入兼容能力，完成迁移和验证，最后在确认旧读写者退出后移除旧结构。是否双写、如何补齐历史数据、如何核对一致性，应按业务和数据库能力设计，不能把这几个英文词当万能迁移脚本。

课堂纸面练习列四行：旧应用旧结构、新旧应用共存扩展结构、新应用扩展结构、新应用最终结构。每行分别问旧数据能否读、新数据能否读写、失败后能否退回上一行。出现空白答案的状态就是发布前需要解决的风险。

### 回滚为什么有时比继续修复更危险

代码回退不必然等于数据回退。新版本已写入旧版本不理解的数据，直接切回旧程序可能扩大失败。反过来，恢复数据库到旧时间点也可能丢失这段时间的合法业务交易。应区分程序回退、配置回退、数据补偿与灾难恢复，不把它们写成同一个“回滚按钮”。

选择回滚时先确认故障范围、当前状态、旧版本兼容性、所需时间和可能损失。若已有验证过的安全回退路径，通常能更快止血；若状态已不可兼容，需要评估前向修复或业务补偿。现场决策应有证据和负责人，不根据“发布失败都回滚”的口号机械执行。

回滚本身也要验证。确认旧制品和配置真实生效，检查业务恢复与数据一致性，观察依赖负载没有新的异常。只是流水线显示回滚任务成功，还不能关闭事故。

### 容量与连接也是发布的一部分

滚动替换时可能暂时同时保留新旧实例，增加内存、连接与下游并发。每个实例都建立固定大小连接池，副本暂时翻倍就可能超过数据库预算。启动预热、缓存加载和消息追赶也会制造与稳定运行不同的负载。

因此发布前算稳态容量，也算过渡态容量。记录允许并发启动多少实例、单批等待条件、依赖余量和失败停止点。镜像体积、启动时间和健康检查参数，都可能影响替换速度与可用实例数量，应在代表性环境观察，而非只凭开发机启动结果估计。

### 变更记录怎样帮助根因分析和 AIOps

一条有用记录包含对象、开始结束时间、实际生效版本、批次范围、操作者、观察指标和结果。AIOps 可以把异常与变更候选关联起来，但“时间上靠近发布”仍只是线索，需要核对机制、对照组和其他同期变化。

课堂事故题是配置发布后连接等待增加。先确定哪些实例加载新配置，比较新旧组的进入流量、连接占用和下游耗时，判断是额度减少还是下游变慢。修复与回退要针对被证据支持的机制，不能因看见“数据库超时”就扩容所有组件。

GitHub 交付一份状态迁移表、灰度样本设计、容量预算、停止与回滚条件，以及正常和异常观察记录。把模板中的“已验证”改成你实际完成的状态；还没做数据库恢复，就标注待演练，不能用计划冒充证据。

## 变更控制台入门：先分清提交、执行与生效

变更管理不是必须安装的某个服务器。初学者先用 Git 保存不含密钥的变更说明，用制品仓库保存明确身份的交付包，用现有部署入口执行，再把结果写入记录。Git 是版本记录工具，制品仓库是交付物的保管处，部署入口负责把批准的状态应用到目标环境。三个位置各自成功，不代表它们组合起来就是一次正确发布。

假设你提交“实例应使用版本二”的配置，平台接受了请求，但节点因为下载失败仍运行版本一。期望状态是你要求的版本二，实际状态是观测到的版本一，二者差异叫漂移。它不一定来自有人违规操作，也可能是网络、权限、控制器重试或资源不足。排查要同时保留期望与实际，不能拿审批单覆盖现场证据。

声明式控制器会不断尝试让实际状态接近期望状态。这个机制有助于自动恢复，却会与手工紧急修复冲突：你在节点临时改成版本一，控制器可能又改回版本二。事故时必须按产品能力暂停推进或更正权威配置，不能只在一台机器上修改后假定完成。暂停也要注明影响范围和恢复负责人，避免临时措施成为长期失管。

### 最小启动检查与命令字典

下面是已经具备 Kubernetes 只读权限的学习者观察现有演练环境的方法，不负责创建集群。没有集群也能完成后面的纸面实验。`kubectl` 是与集群接口沟通的客户端，context（上下文）选择连接的集群和身份，namespace（命名空间）限定一组资源。先核对上下文，再查看明确命名的演练对象，绝不把生产对象当练习材料。

```powershell
kubectl config current-context
kubectl get deployment order-api -n change-lab
kubectl rollout status deployment/order-api -n change-lab --timeout=30s
kubectl rollout history deployment/order-api -n change-lab
```

第一条回答正在连接谁；第二条显示目标部署的副本状态；第三条等待部署进度并限制本次客户端等待时间；第四条查看保留下来的部署修订。`--timeout=30s` 超时不代表服务端撤销发布，命令结束后发布可能仍在继续。出现未找到资源，先确认名称、命名空间与环境，不要为了消除报错临时创建同名生产对象。出现禁止访问，则核实所需只读权限，不申请管理员权限来省事。

部署修订主要记录 Pod 模板变化。Pod 是容器运行单元，模板里通常包含镜像和环境引用；它不是整个系统的时光机。回退部署修订不会自动把外部数据库、同名配置内容、证书或外部支付状态一起恢复。因此发布清单除了部署修订，还要记录配置来源与数据兼容阶段。命令返回成功之后，继续检查实际制品身份和用户路径。

## 容量算术课堂：稳态能跑，不代表升级期间能跑

我们设计一个教学系统：八个实例，每个在本课堂负载下可稳定处理每秒一百个请求，业务峰值每秒五百六十个请求。这里的稳定容量是通过代表性负载测得的假设，不是 CPU 核数换算出的保证。如果同时退出两个实例，剩余名义容量每秒六百，还能覆盖五百六十；但只多出四十，余量已经很薄。

再注入一个实例故障，五个实例只剩每秒五百，峰值就超过容量。老师要你学会的不是记住“每批两个”，而是把发布损耗和独立故障放进同一张预算。若需要容忍这类叠加，就缩小批次、增加预备容量或选择低峰窗口，并验证流量确实能被健康实例接住。

连接预算是另一条独立约束。假设每个实例最多建立五十个数据库连接，数据库为该服务预留四百五十个。八个实例稳态上限四百；若滚动时新旧总数暂时达到十个，理论上限五百，已经超出预留。真实连接是否建满取决于连接池配置，但不能把“通常没满”当作有保障的设计。还要给维护连接、监控和其他调用方留出空间。

观察容量不能只看当前 CPU。请求队列变长、连接等待增加、启动变慢、缓存命中降低都可能早于 CPU 饱和出现。需要记录启动峰值和稳态峰值，区分应用线程、数据库连接和依赖限额。扩容应用有时会加重数据库压力，这正是为什么变更计划应沿依赖链评估，而不只看被更新的那层。

## 可重复生产模拟：一张被修改过的批准单

### 前置条件与目标

只需要纸笔或本地文档，不连接任何服务器。目标是练习授权与执行对象绑定、超时状态判断、灰度证据缺失时的停止决策。请用明显虚构的环境和制品标识，所有“执行”均为纸面状态推进，不是真实上线。

先写批准卡：目标为演练环境的订单服务，制品为包甲，配置版本为三，每批一个实例，数据库结构保持兼容，观察错误比例和业务成功，超出停止线则暂停。另写执行卡，内容逐项相同。用两列对照核验目标、制品、配置、批次和有效时间，预期全部一致，才能把卡片状态从待执行改为允许开始。

### 故障一：审批后把批次改大

把执行卡的批次从一个改为四个，批准卡保持不变。即使包仍是包甲，也不能沿用原批准。批次改变了故障影响和容量条件，应该重新评估并批准新的计划。验证标准是“发现不一致并停在执行前”，不是“先做了再补理由”。计划摘要可以帮助识别变化，但摘要本身不替代授权身份与审批记录。

恢复方法是撤销这次未经批准的改动，重新对照两张卡；或重新评审四实例批次并更新批准。不要只修改批准卡日期，让旧授权看起来匹配新操作。清理时保留故障卡用于学习，给它标记已撤销，防止与可执行计划混淆。

### 故障二：执行入口超时

下一张卡写“请求已发出，客户端等待超时，服务端结果未知”。请分别列出三个可能：服务端未接收、已经开始但尚未结束、已经结束但响应丢失。正确下一步是查唯一任务编号和目标状态，而不是重新点发布。若平台支持幂等请求，可以用同一个请求身份查询或按协议重试；换一个新编号通常意味着另一项新任务，不能假装仍是同一次。

预期答卷把状态写成待确认，不写失败或成功，并给出查询任务、逐节点版本、事件记录的顺序。如果平台无法查询任务身份，要升级人工核对，先限制重复写入。这个模拟可以与[Runbook 设计](./runbook.md)中“丢响应不等于未执行”的课堂对照学习。

### 故障三：灰度指标没有数据

把原本的灰度观察卡替换成“监控查询为空”。有人认为零错误可以继续，有人认为立即全量回滚。先区分没有业务流量、采集失败、过滤标签错误以及指标真的为零。没有数据不支持成功结论，正确默认动作通常是暂停扩大范围，同时用允许的独立探测核验业务和采集链路。

若独立探测确认核心交易失败，再根据停止条件评估恢复；若业务健康但监控失联，先恢复观测能力，是否允许保持当前小范围由风险规则决定。不要仅为让发布通过而放宽查询过滤，导致把旧版本健康数据混进新版本。验证时必须证明每个观察样本对应的是本次批准的实例和制品。

### 验收与清理

一次完整演练应产生原批准卡、三张故障卡、停止原因、查证顺序、恢复办法和最后状态。由另一人随机抽一张故障卡，检查你能否明确区分禁止开始、已开始待确认、暂停扩大三种状态。它们需要不同处理，不能全部写成“发布失败，回滚”。实验没有创建真实资源，清理只需标记演练结束并隔离不可执行的示例材料。

## 数据演进深入一层：双写也会失败

前面讲先扩展再收缩，现在追问：两个字段同时写就一定一致吗？假设旧字段保存金额的整数分，新字段保存带币种的金额对象。新程序先写旧字段成功，写新字段失败，如果没有原子事务或其他补偿机制，两个表示就不同步。双写是迁移策略的一部分，不是独立的一致性保证。

设计时先规定权威来源和版本。迁移期由哪一侧为准，历史数据如何补齐，写入失败如何重试，重复处理如何识别，发生冲突如何裁决，都要明确。比较数量相等不够，还要比较业务主键对应的值、缺失记录以及转换规则。金额、时区和字符编码等转换尤其不能只检查“字段不为空”。

历史回填还会与在线写入竞争。例如回填程序先读取旧值，用户随后更新，新值已经写好，回填程序又把旧值覆盖回去。解决方向可能是条件更新、记录版本或单一权威写入路径，具体方式取决于数据库事务与业务模型。课堂不提供跨数据库通用修复脚本，因为正确做法必须依赖实际约束。

数据迁移验收通过之后仍要保留观察期，确认没有旧消费者读取旧字段，才考虑收缩。消费者不仅是在线应用，还可能包括定时报表、离线分析、消息重放和外部接口。删除之前查依赖清单与访问证据，不能只说“应用团队已经升级”。这也是为什么有些变更要跨几个发布周期完成。

备份是恢复准备中的一部分，恢复演练才回答备份是否可用。需要检查备份时间、完整性、可解密性、恢复耗时，以及恢复后与外部业务状态怎样核对。在正常持续写入的系统上回到旧快照可能损失合法交易，因此备份不能作为任意破坏性迁移的免责理由。不可逆步骤应有明确业务确认和前向修复方案。

## 安全与制品身份：能下载不等于可以信任

包名和版本号便于人阅读，但相同名字可能被覆盖。摘要用于识别具体字节内容，签名用于验证可信签发者对内容的声明，构建来源证明用于说明交付物从何种过程产生。三者解决不同问题。只有摘要但没有可信来源，你仍可能准确地部署了一份错误或恶意的包。

发布账号只应具有目标环境所需权限，构建任务不应因为方便就持有生产数据库管理员凭据。将构建、批准、部署责任分离，可减少一个环节被误操作或攻破后的影响。密钥使用受控引用和短期授权，公开学习材料只保存字段名、脱敏身份与权限说明，不保存实际凭据或内部地址。

审批必须绑定具体内容。若批准的是提交甲，但部署时重新从可变分支下载并构建，最终产物可能已经包含未评审修改。更稳妥的路径是先构建并验证确定的制品，再在环境间提升同一制品，只替换经过评审的环境配置。若确实需要重新构建，则应重新建立身份与验证链，不把“来源分支相同”当成字节完全一致。

对于可复现构建，还要固定依赖、工具链和影响输出的环境，并处理时间戳等非确定输入。只固定应用代码通常不足以保证同一制品。实践中先确保可追溯与来源可信，再明确项目能否达到字节级可复现；两者有联系，但不能混称已经实现。

## AIOps 关联设计题：一百次发布里找真正相关的那一次

假设半小时内有一百次变更，只有某地区的订单写入延迟增加。第一轮按时间筛选只是缩小范围，接下来应沿服务依赖、地区、租户与实际生效时间匹配。网络策略虽然不属于订单服务的代码，也可能影响订单访问数据库，因此只按服务名字相等会漏掉跨层候选。

对每个候选保存支持证据与反对证据。例如配置变更后只有加载新版本的实例异常，是支持线索；未变更组在更早时间同样异常，是反对或提示共同依赖的线索。自动评分可以帮助排序，不应把最高分直接命名为根因。若采集缺失或时钟不准，输出应降低确定性并指出需要补哪些证据。

延迟生效也是难点：证书可能在连接重建时才使用，定时任务到夜间才跑，新缓存格式可能在旧缓存过期后才暴露。固定回看三十分钟只是起点，不能把窗外变更一概排除。用配置加载、任务开始、缓存生命周期等机制确定合理观察跨度，比不断扩大时间窗堆更多候选更有效。

设计评价时使用有人工核实结果的历史事件，统计正确候选是否进入前几名、证据是否可追溯、是否漏掉跨层变更以及错误建议的风险。没有经过核实的事故标签不能当成标准答案。模型生成的“可能由于某次发布”应留在建议区，是否回退仍由具备上下文与权限的流程决定。

## 高阶面试追问：不要只背蓝绿与灰度的定义

“怎样给三可用区设计发布？”先说明区是故障隔离单元，再给出分批次、跨区剩余容量、代表性流量、共享数据库兼容和停止条件，最后说明区域故障与发布叠加时的策略。若只回答每区依次升级，面试官会追问第一个区是否占了全部数据库连接，以及恢复流量能否由剩余区域承担。

“灰度一百次请求零失败，能否全量？”回答样本和业务覆盖还不足以保证低错误目标，先看请求代表性、风险机制与预定观察标准；涉及数据破坏的风险不能靠零接口错误排除。“怎样证明回退的是正确版本？”用明确制品身份、配置版本、数据兼容阶段、实际实例观察和业务验收组成证据链，而不是仅展示一次回退命令输出。

“紧急变更是不是不用审批？”回答走预先定义的紧急授权路径，保留目标核对、审计、停止条件和事后补充，不能由紧迫程度自动扩大权限。“变更之后问题消失就证明变更是根因吗？”不一定，流量、依赖和时间都可能共同变化，需要相同口径对照与机制证据。能说清这些边界，才说明你理解发布是一组状态转换，而不是把脚本从头运行到尾。

## 变更不只是代码发布

生产变更包括：

| 类型 | 示例 | 风险 |
|---|---|---|
| 应用发布 | order-api v2026.07.02.1 | bug、兼容性 |
| 配置变更 | 连接池、超时、feature flag | 行为变化 |
| 数据库变更 | schema migration、索引 | 锁表、回滚困难 |
| 基础设施 | Kubernetes、节点、负载均衡 | 可用性影响 |
| 网络 | Ingress、DNS、安全组 | 流量中断 |
| 安全 | 证书、密钥、权限 | 认证失败 |
| 告警 | 阈值、路由、静默 | 漏报或噪声 |
| 自动化 | runbook 脚本、修复动作 | 扩大影响 |

AIOps 排障时，“最近变更”必须包含这些类型，而不是只查 Git commit。

## Release Engineering 核心原则

Google SRE Release Engineering 强调：可靠服务需要可靠发布过程。

对普通团队最重要的原则：

| 原则 | 含义 |
|---|---|
| 可复现构建 | 固定代码、依赖、工具链及相关构建输入，并验证是否得到相同制品 |
| 自动化 | 构建、测试、发布尽量自动执行 |
| 可追溯 | 制品、配置、发布记录能追到 commit |
| 策略强制 | 评审、测试、审批、权限由工具保证 |
| 渐进发布 | 按风险从小范围扩大 |
| 可回滚 | 发现问题能快速恢复 |

不要让生产发布变成：

```text
某人在某台机器手动改了一些东西。
```
那是事故材料，不是发布工程。

## 变更分类

简单分四类：

| 类型 | 风险 | 示例 | 审批 |
|---|---:|---|---|
| 标准变更 | 经评估的低风险 | 已有成熟步骤且符合预批准范围的重复操作，小版本不自动属于此类 | 按预批准条件自动或轻审批 |
| 普通变更 | 中 | 应用发布、连接池调整、扩容 | 团队评审 |
| 高风险变更 | 高 | 数据库 schema、网络 ACL、权限策略 | 多方审批 |
| 紧急变更 | 高 | 故障中回滚、临时切流 | IC 审批，事后补记录 |

风险判断维度：

- 用户影响范围。
- 是否可回滚。
- 是否涉及数据。
- 是否跨团队。
- 是否影响核心链路。
- 是否有充分测试。
- 是否在高峰期。
- 当前错误预算是否充足。

## 发布成功不等于变更成功

CI/CD 显示成功，只代表流水线执行完。

还要看：

- 用户请求是否成功。
- 延迟是否恶化。
- SLO 是否燃烧。
- 业务指标是否异常。
- 下游依赖是否被打爆。
- 告警是否新增。
- 日志是否出现新错误。

变更成功的定义：

```text
发布完成 + 目标状态核实 + 业务验收达标 + 观察窗口通过 + 残余影响已处理或明确接管
```
## 发布策略

### 滚动发布

```text
一批一批替换实例。
```
优点：

- 资源成本低。
- Kubernetes 默认容易支持。

风险：

- 新旧版本并存。
- 需要兼容数据库和接口。
- 问题可能逐步扩大。

### 蓝绿发布

```text
blue: 当前生产
green: 新版本
流量从 blue 切到 green
```

优点：

- 切换和回滚快。
- 新旧环境隔离清楚。

风险：

- 资源成本高。
- 数据状态要兼容。

### 金丝雀发布

```text
少量流量 -> 观察 -> 扩大流量 -> 全量
```
优点：

- 控制爆炸半径。
- 适合高风险变更。

风险：

- 需要流量治理。
- 需要足够的指标和样本量。
- 低流量服务可能看不出问题。

### Feature Flag

```text
代码已发布，但功能开关控制是否启用。
```
优点：

- 可以快速关闭功能。
- 支持小范围用户启用。

风险：

- flag 组合复杂。
- 旧 flag 不清理会成为债务。

## 变更门禁

常见门禁：

| 门禁 | 目的 |
|---|---|
| code review | 防止明显错误 |
| CI test | 防止构建和测试失败 |
| security scan | 防止安全风险 |
| config validation | 防止配置越界 |
| migration check | 防止数据库不可逆 |
| error budget check | 防止预算耗尽还发布 |
| approval | 高风险变更人工确认 |
| canary analysis | 自动观察关键指标 |

错误预算门禁示例：

```text
如果 order-api 30 天错误预算已消耗 > 80%，禁止普通功能发布，只允许可靠性修复。
```

这把 SLO 和发布决策连接起来。百分之八十是课堂策略示例，不是通用标准；例外类型、批准方式和预算口径应提前约定。

## 验证指标

变更后至少看：

| 类型 | 指标 |
|---|---|
| 可用性 | 5xx 错误率、成功率 |
| 延迟 | p95、p99、足够快请求比例 |
| 流量 | RPS、队列输入输出 |
| 饱和度 | CPU、内存、连接池、队列深度 |
| 业务 | 下单成功率、支付成功率 |
| 日志 | 新错误、异常堆栈 |
| 依赖 | 下游 5xx、数据库慢查询 |
| 告警 | 新增 page/ticket |

观察窗口的课堂参考如下；存在缓存、批处理或延迟生效机制时，需要覆盖相应周期，不能仅按风险标签选一个固定分钟数：

| 风险 | 建议观察 |
|---|---|
| 低风险 | 10 到 15 分钟 |
| 中风险 | 30 分钟 |
| 高风险 | 1 小时或完整业务周期 |

## 回滚计划

没有回滚计划的变更，不应该轻易进生产。

回滚计划要写：

- 回滚命令。
- 回滚负责人。
- 回滚触发条件。
- 回滚风险。
- 数据是否兼容。
- 回滚后验证。
- 如果回滚失败怎么办。

示例触发条件：

```text
发布后 15 分钟内：
- 5xx 错误率超过 2%，或
- p95 延迟超过基线 2 倍，或
- order-api SLO burn rate 超过 6，或
- 下单成功率低于 99%
则评估回滚。
```

## 数据库变更特别处理

数据库变更通常比代码发布更难回滚。

建议：

- expand / contract 模式。
- 先兼容旧代码和新代码。
- 先加字段，后读写，最后删除旧字段。
- 大表变更避开高峰。
- 迁移脚本可暂停、可重试。
- 变更前备份。
- 回滚路径写清楚。

危险信号：

- 删除字段。
- 改字段类型。
- 长事务。
- 大表加索引。
- 不可逆数据迁移。

## 配置变更特别处理

Google SRE Release Engineering 特别强调配置管理，因为配置变更也是不稳定来源。

配置变更要做到：

- 进版本控制。
- code review。
- 有 diff。
- 有 owner。
- 有范围校验。
- 有默认值。
- 能回滚。
- 能关联到发布或变更单。

不要在生产控制台里随手改配置却没有记录。

## 紧急变更

紧急变更通常发生在 incident 中，例如回滚、切流、临时禁用功能。

原则：

- 可以先做必要审批简化。
- 必须由 IC 或授权人决策。
- 必须记录原因、动作、时间、执行人。
- 事后补完整变更记录。
- 进入 postmortem。

紧急不等于无记录。

## AIOps 中的作用

变更是 RCA 和 AIOps 的高价值信号。

```text
incident starts at 09:10（事故从09:10开始）
  -> look back 30 minutes（回看此前三十分钟）
  -> change at 09:02（09:02发生变更）
  -> compare metrics before and after（比较变更前后指标）
  -> add change as root cause candidate（把变更列为根因候选）
```

AIOps 可以做：

- 变更时间线自动补全。
- 告警消息关联最近发布。
- 变更后自动观察 SLO。
- 检测发布后指标异常。
- 相似变更事故检索。
- 变更风险评分。
- 错误预算门禁建议。
- RCA 中生成变更关联证据。

但注意：

```text
变更发生在故障前，不等于它一定是根因。
```
它只是强候选，需要指标、日志、diff 和实验验证。

## 入门练习：变更记录和事故关联

准备 `changes.jsonl`：每行一个独立 JSON 对象，读取时逐行解析，不把整个文件当作单个 JSON 对象。

```jsonl
{"id":"CHG-001","service":"order-api","type":"release","time":"2026-07-02T09:02:00Z","version":"2026.07.02.1","owner":"team-order"}
{"id":"CHG-002","service":"payment-api","type":"config","time":"2026-07-02T08:20:00Z","summary":"increase timeout","owner":"payment-team"}
```

准备 incident：

```json
{"id":"INC-001","service":"order-api","start_time":"2026-07-02T09:10:00Z","symptom":"5xx error rate increased"}
```

任务：

1. 查找 incident 前 60 分钟内同 service 变更。
2. 输出候选变更。
3. 写出需要验证的指标。
4. 写出回滚触发条件。

伪代码：

```python
from datetime import datetime, timedelta, timezone

incident_time = datetime.fromisoformat("2026-07-02T09:10:00+00:00")
window_start = incident_time - timedelta(minutes=60)

for change in changes:
    change_time = datetime.fromisoformat(change["time"].replace("Z", "+00:00"))
    if change["service"] == "order-api" and window_start <= change_time <= incident_time:
        print(change)
```

## 常见错误

### 没有回滚计划

发布前必须知道怎么撤回。

### 发布成功就结束

发布成功不代表服务健康，必须观察 SLO 和业务指标。

### 只记录代码发布

配置、数据库、网络、证书、告警规则都是变更。

### 变更记录不完整

没有 owner、时间、版本、diff、回滚计划，就很难用于排障。

### 高风险变更无审批

数据库、网络、安全、权限类变更必须更严格。

### 错误预算耗尽还发功能

预算耗尽时应该优先可靠性修复。

### 紧急变更不补记录

故障中可先处理，但事后必须补完整记录。

### change_id

### service

### artifact

发布制品，例如镜像 digest、包版本。

### commit / PR

代码来源。

## 面试怎么讲

变更管理的核心不是审批表，而是让生产改动可追踪、可验证、可回滚。变更包括代码发布、配置、数据库、网络、安全、扩容、告警规则等。Google SRE 的 release engineering 强调可靠服务需要可靠发布过程：构建可复现、制品可追溯、流程自动化、策略可强制、发布渐进、回滚明确。

我会为每个变更记录 owner、服务、风险、时间、制品、commit、配置 diff、验证计划和回滚计划。发布后不只看流水线是否成功，还要看 SLO、错误率、延迟、流量、饱和度和业务指标。高风险变更要有审批、灰度或金丝雀，错误预算不足时限制普通功能发布。AIOps 中，变更是根因候选和告警补充上下文，但“变更发生在前”不等于一定是根因，还要用指标和日志验证。
