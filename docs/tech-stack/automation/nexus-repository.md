## 场景开场

构建流水线每次都从公网下载 Maven、npm 或 Python 依赖。公网抖动后所有 Job 同时失败，而且团队找不到上个月发布的内部包。Nexus 用代理缓存和内部仓库把依赖与正式制品稳定下来。

## Nexus Repository 是什么

Nexus Repository 是通用制品仓库管理器。它支持 Maven、npm、PyPI、Docker 等格式；Repository 决定访问方式，Blob Store 保存二进制内容，数据库保存组件、资产和元数据关系。

## 它解决什么问题

- 保存团队自己发布的版本化制品。
- 代理并缓存外部仓库，降低公网依赖。
- 通过 group 给客户端提供一个统一入口。
- 用权限和审计限制谁能上传、覆盖或删除。
- 用清理、备份和恢复控制容量与可用性。

## 核心原理

### hosted、proxy 与 group

- **是什么**：hosted 保存内部制品；proxy 缓存远端；group 聚合多个仓库。
- **为什么需要**：分别处理发布、外部依赖和统一访问入口。
- **怎么工作**：客户端请求 group，Nexus 按成员顺序查找；proxy 未命中时访问远端并缓存。
- **怎么看或怎么用**：本课 Maven/Raw 内部发布直接写 hosted，下载可走 group；某些格式和版本支持把 group 写入转发到指定 hosted，不能一概说所有 group 永远只读。
- **坏了怎么查**：检查成员顺序、在线状态、远端 URL、负缓存和路由规则。

### Component、Asset 与 Blob Store

- **是什么**：Component 表示一个逻辑制品版本，Asset 是实际文件，Blob Store 保存文件内容。
- **为什么需要**：一个 Maven 组件可能同时包含 JAR、POM、校验文件和元数据。
- **怎么工作**：元数据把组件和资产映射到 blob；删除记录与回收底层空间可能不是同一步。
- **怎么看或怎么用**：从 Browse 找组件，再查 blob store 用量、任务和日志。
- **坏了怎么查**：不要手工删数据目录；先查任务、数据库一致性、磁盘和官方恢复流程。

### 权限、Realm 与匿名访问

- **是什么**：Realm 接入认证机制，Privilege、Role、User 决定可执行操作。
- **为什么需要**：下载、上传、删除和管理的风险完全不同。
- **怎么工作**：请求先认证，再按仓库、格式和动作权限授权。
- **怎么看或怎么用**：流水线使用独立服务账号，只授予目标 hosted 仓库上传权限。
- **坏了怎么查**：401 查认证，403 查授权，404 还要考虑路径、格式和内容选择器。

### 清理、压缩、备份与恢复

- **是什么**：Cleanup Policy 选择过期内容，相关任务执行删除；回收空间还可能需要 blob compact。
- **为什么需要**：制品只增不减会耗尽磁盘，但误删又会破坏回滚。
- **怎么工作**：策略按最后下载、发布时间等条件匹配，任务按计划运行并记录结果。
- **怎么看或怎么用**：先预估命中范围，在非生产验证，保留发布保留期和法律要求。
- **坏了怎么查**：磁盘告警时先暂停大规模写入和清理变更，确认备份可恢复后再处置。

## 架构和数据流

```text
开发机 / CI
  -> group 仓库下载依赖
  -> hosted 命中内部包
  -> proxy 命中缓存或访问远端

发布流水线
  -> 认证与授权
  -> hosted 仓库
  -> 元数据 + Blob Store
  -> 下游部署按固定版本下载
```

## 安装与启动

本地学习使用 Sonatype 官方容器镜像并持久化 `/nexus-data`。先检查 `docker container inspect nexus-lab` 与 `docker volume inspect nexus-data`：只有两者都明确返回不存在时才创建；若已存在，停止并选择新的专用实验名称，后续命令同步使用该名称。`docker volume create` 遇到同名旧卷可能复用，不能拿它证明卷是本次新建。生产环境要评审支持矩阵、外部 TLS、存储、备份和升级。

```powershell
docker volume create nexus-data # 创建持久卷保存配置、数据库和 blob
docker run -d --name nexus-lab -p 127.0.0.1:8081:8081 -v nexus-data:/nexus-data sonatype/nexus3:latest # 仅向本机开放学习端口
docker logs -f nexus-lab # 等待日志显示服务已启动；按 Ctrl+C 退出跟踪
docker exec nexus-lab cat /nexus-data/admin.password # 读取首次登录密码
```

浏览器访问 `http://localhost:8081`。首次登录后立即修改密码，学习完成也不要把密码写入仓库。

`latest` 是可移动标签，只适合这里的首次探索；启动前后记录 `docker image inspect sonatype/nexus3:latest --format '{{index .RepoDigests 0}}'` 显示的镜像摘要以及页面版本。团队实验和生产应固定经过审核的版本或摘要，并核查对应版的数据库、内存和升级要求。容器第一次初始化可能较慢，确认启动日志后再登录，不要连续重建容器。

## 配置详解

以 Maven 为例，客户端应从 group 下载依赖，把内部发布上传到 hosted：

```xml
<mirror>
  <id>company-nexus</id>
  <mirrorOf>*</mirrorOf>
  <url>https://nexus.example.internal/repository/maven-public/</url>
</mirror>
```

`mirrorOf` 为 `*` 表示 Maven 依赖统一经过 Nexus；`maven-public` 通常是 group。发布地址应在项目 `distributionManagement` 或 CI 参数中指向 releases/snapshots hosted 仓库，而不是 group。

## 命令 / 配置 / API 字典

| 名称 | 作用 | 常用写法 | 正常结果 | 常见坑 |
|---|---|---|---|---|
| hosted | 保存内部制品 | `maven-releases` | 上传后可按坐标下载 | 允许随意覆盖正式版本 |
| proxy | 代理远端仓库 | `maven-central` | 首次回源、之后缓存 | 远端证书或代理网络失败 |
| group | 聚合成员仓库 | `maven-public` | 客户端只配置一个下载入口 | 成员顺序导致取到错误包 |
| Cleanup Policy | 选择可清理内容 | 按格式和时间条件 | 任务删除匹配内容 | 未验证规则就作用于生产 |
| REST API | 自动化管理 | `/service/rest/v1/...` | 返回 JSON 或状态码 | 版本差异和权限不足 |

## 在 AIOps 中的作用

Nexus 可提供请求量、响应延迟、错误码、远端仓库状态、任务结果、磁盘和 blob 用量。AIOps 能识别依赖下载失败是否来自远端、容量还是权限，并把部署版本与制品仓库中的不可变版本、校验值关联。

## 入门实验：上传并下载 Raw 制品

### 实验目标

在页面创建名为 `raw-lab` 的 hosted Raw 仓库，上传文本文件后通过 HTTP 下载并校验内容。

### 实验步骤

1. 登录 Nexus，进入 Repositories，新建 `raw (hosted)`，名称填写 `raw-lab`。
2. 在实验目录创建 `hello.txt`，内容写 `zero-to-aiops`。
3. 使用学习账号执行：

```powershell
$credential = Get-Credential # 弹窗输入实验账号，避免密码写入命令历史
$pair = '{0}:{1}' -f $credential.UserName, $credential.GetNetworkCredential().Password
$token = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes($pair))
Invoke-WebRequest -Method Put -Uri 'http://localhost:8081/repository/raw-lab/hello.txt' -Headers @{Authorization="Basic $token"} -InFile '.\hello.txt' # 上传文件
Invoke-WebRequest -Uri 'http://localhost:8081/repository/raw-lab/hello.txt' -Headers @{Authorization="Basic $token"} -OutFile '.\downloaded-hello.txt' # 使用同一身份下载，不依赖匿名访问开启
Get-FileHash .\hello.txt, .\downloaded-hello.txt # 两个 SHA256 应一致
Remove-Variable pair, token, credential # 清理会话中的凭据变量；不要输出其值
```

### 验证结果

上传返回成功状态，浏览仓库能看到 `hello.txt`，两个文件 SHA256 相同。

### 如果没有成功

1. 连接失败：确认容器、8081 端口和启动日志。
2. 401：检查账号密码；403：检查上传权限。
3. 404：检查仓库名、Raw 格式和 URL 路径。
4. Hash 不同：确认下载的不是代理错误页面，并查看响应状态。

## 常见故障排查

| 现象 | 先检查 | 处理思路 |
|---|---|---|
| 下载返回 401/403 | 凭据、Realm、Role、Privilege | 区分认证与授权后修正最小权限 |
| proxy 无法回源 | Remote URL、DNS、TLS、代理、负缓存 | 修复网络并按需失效缓存 |
| 磁盘持续增长 | 仓库增长、Cleanup 任务、blob 用量 | 评审保留策略后清理和 compact |
| group 返回旧版本 | 成员顺序、元数据缓存、版本策略 | 修正顺序并避免覆盖正式版本 |
| 重启后不可用 | 磁盘、权限、数据库、升级兼容 | 依据日志和官方恢复步骤处理 |

## 面试怎么讲

Nexus 用 hosted 保存内部制品、proxy 缓存远端依赖、group 统一下载入口。生产治理重点是版本不可变、最小权限、磁盘与清理策略、备份恢复和升级兼容。排障时先按 HTTP 状态区分认证、授权、路径和后端，再检查远端与 blob store。

## 老师带你把一次依赖下载拆开

今天我们接到的报错是“构建找不到 `com.example:alert-rules:1.2.0`”。你先别重启 Nexus。这个字符串叫 Maven 坐标：`com.example` 是组织标识，`alert-rules` 是包名，`1.2.0` 是版本。仓库需要把逻辑坐标翻译成实际路径，例如 `com/example/alert-rules/1.2.0/alert-rules-1.2.0.jar`。JAR 是 Java 类与资源的归档包，POM 是描述依赖及项目信息的 XML 文件。

如果上传者把文件放成了 `alert-rules.jar`，文件虽然存在，Maven 按坐标找它仍会失败。Nexus 的 Raw 格式适合练上传下载；Maven、npm 等格式还遵循各自协议和元数据结构。你不能把“HTTP 能取到一个文件”当作“包管理器一定能解析这个包”。

```text
构建工具读取坐标与凭据
  -> TLS（加密连接）与身份认证
  -> group（统一下载入口）
  -> hosted（公司发布包）或 proxy（外部依赖代理）
  -> 查元数据并定位 asset（文件）
  -> blob store（读取文件字节）
  -> 客户端核对摘要并解析依赖
```

停下来想一想：“客户端报 404，文件就一定不存在吗？”不一定。请求可能用了错误仓库、错误坐标、错误后缀，group 可能没包含正确成员，访问权限也可能限制可见范围。你应保留脱敏请求路径、HTTP 状态和仓库配置，再用有权查看的账号检查目标 hosted 是否存在该版本。

### 代理缓存为什么能降低公网依赖，也为什么会记住失败

Proxy 仓库是一个中间站。下载过的内容可由本地缓存提供；未缓存的内容仍需要远端。公网中断时，缓存命中的版本可能继续可用，第一次请求的新版本仍会失败。因此说“有了 Nexus 就完全离线可用”不准确，离线能力必须基于完整依赖清单与预取验证。

有些远端“不存在”的结果也会被暂存，这叫 negative cache（负缓存）。这样做能避免不存在的包被每台构建机反复回源查询，但远端刚发布新版本后，本地可能在一段时间内仍沿用旧的未找到结果。排查时先确认远端确实发布成功、坐标一致，再查看对应缓存设置和有针对性的失效操作。把所有仓库缓存都清掉，会让后续请求同时回源，放大网络和远端压力。

缓存命中率也要分辨指标含义。某天命中率高，不一定说明平台健康：可能只有旧包被访问，新项目的未命中请求全部失败。把命中率与错误率、回源延迟、受影响仓库和新版本发布事件一起看，才能形成可靠判断。

### 元数据与二进制：为什么备份一半不够

你可以把数据库理解成图书馆目录，blob store 理解成真正的书架。目录告诉系统“这本书在哪个位置”；书架保存内容。只复制目录，恢复后可能看得见名称却读不到文件；只复制书架，又可能缺少组件、权限、仓库配置及索引关系。

真实实现会随数据库类型和版本变化，但恢复时必须保证元数据、blob、配置以及必要密钥之间相互匹配。不要在服务持续写入时随意复制几份目录，就声称得到一致性备份。先读对应版本的[备份与恢复说明](https://help.sonatype.com/en/backup-and-restore.html)，使用支持的流程，再在隔离环境恢复并实际下载一组代表性制品。

怎样证明恢复有效？不仅看登录成功，还要检查内部 release 包能下载、代理包能读取、上传账号权限正确、旧部署依赖的版本存在、校验摘要一致。把恢复点对应的时间、版本和数据范围写清楚。RPO（恢复点目标）回答最多可以损失多久的数据；RTO（恢复时间目标）回答多久必须恢复服务，两者需要分别测量。

### 不可变版本让回滚变得可信

假设早上 `1.2.0` 的摘要为 A，下午有人用同名覆盖成 B。一台机器缓存 A，另一台下载 B，你会看到“版本相同但行为不同”。因此正式 release 通常应禁止重新部署同一版本，修复后发布 `1.2.1`。Snapshot（开发快照）可以用于开发迭代，但正式回滚应引用明确可追溯的产物。

不可变不仅是文件命名规则，还需要上传权限、仓库部署策略和发布流程协作。允许删除后同名重传，仍可能绕开你期待的不可变语义。审计时关联制品坐标、摘要、源码提交、构建流水线和发布时间；哈希只能证明字节匹配，不能证明它没有漏洞或来自可信开发者。

## 双层实验：上传、下载、注入错误并恢复

### 基础实验的完整收尾

前提是本机 Docker 可用、8081 未被占用，并已完成上面的 Nexus 初始化。Raw 是“按路径保存普通文件”的仓库格式，学习时无须先安装 Java 或 Maven。先在页面建立独立 `raw-lab`，为实验账号授予该仓库的浏览、读取和写入权限；熟悉后再收窄权限。这里账号仅用于本机学习仓库。

在一个新的本地实验目录中，用编辑器创建 `hello.txt`，内容为 `zero-to-aiops`，运行前面的上传下载命令。观察三个结果：上传返回成功响应，仓库页面出现文件，两个 SHA256 相同。如果凭据只授予写入而没有读取，上传成功但下载 403 是权限模型产生的结果，不是存储损坏。

现在把原始文件改为 `zero-to-aiops-v2`，另存为 `hello-v2.txt`，上传时也使用新路径 `hello-v2.txt`。你会同时保留两版，而不是覆盖第一版。分别下载并核对摘要，这就是最小的可追溯发布练习。

### 故障注入一：让客户端请求一个不存在的版本

在浏览器中访问 `http://localhost:8081/repository/raw-lab/does-not-exist.txt`，或使用同一实验身份发起 GET 请求。预期是 404；若匿名关闭，也可能先收到 401，此时用有读取权限的身份重试，才能观察缺少资源的结果。

收集证据：实际 URL、状态码、仓库里现有的文件名和时间。你的假设应该写成“请求路径与已上传路径不一致”，用已知正确的 `hello.txt` 路径成功下载来验证。如果所有路径都返回同一错误，则检查身份、入口和仓库在线状态，而不是坚持文件名假设。

修复是改正客户端配置中的坐标或路径，不需要重启 Nexus。保留错误与正确请求的对照，说明为什么 404 本身不足以断言磁盘丢失。

### 故障注入二：用摘要识别本地内容改变

下载成功后，用编辑器在 `downloaded-hello.txt` 末尾加一个字符，再运行 `Get-FileHash`。预期两个摘要不再一致。这里故意修改的是本地下载副本，仓库原文件不受影响。

重新从同一 URL 下载到 `recovered-hello.txt`，比较它与原始 `hello.txt`，摘要应恢复一致。这个实验教的是完整性验证：网络请求成功只说明返回了响应，真正发布时还要确认收到的内容符合预期。若恢复副本仍不匹配，核对是否下载了错误页面、源文件是否被改、换行编码是否一致、URL 是否指向了第二版。

### 清理与证据

先保存脱敏的仓库设置、三次摘要和故障结论。然后只在页面删除这次建立的 `raw-lab` 与实验账号。若整个 Nexus 实例都是本课临时创建，可先 `docker stop nexus-lab`，再 `docker rm nexus-lab`；卷 `nexus-data` 保留配置与数据，删除卷意味着实验数据不可恢复，确认仅含本次练习后才手动删除。不要对公司实例执行清理步骤。

## 生产设计题：两百条流水线共用制品仓库

老师给你一个场景：工作日上午九点，200 条构建同时启动，每条需要下载 300 MB。粗略总下载量是 60 GB，但真正回源量取决于依赖重合程度和缓存命中。你先区分入口出口带宽、磁盘读取、数据库查询和远端连接，再决定瓶颈在哪。只看 CPU 平均值，容易漏掉突发下载导致的网络饱和。

容量规划把 hosted 与 proxy 分开。Hosted 增长受发布频率、包大小、保留版本数和回滚窗口影响；proxy 受使用的依赖集合、上游变化和清理策略影响。再加数据库、日志、索引、备份以及清理过程需要的余量。容量告警不仅看 80% 这种静态阈值，也要看近期净增长速度和预计剩余天数。

清理策略先生成候选范围，和正在运行的发布清单、回滚保留版本核对。最后下载时间久，不等于版本可以删：一个稳定系统一年没重装，灾备恢复时仍可能需要它。删除元数据后磁盘未下降，还可能需要相应 blob 回收任务；具体行为遵循当前格式和版本的[清理策略](https://help.sonatype.com/en/cleanup-policies.html)及[blob store 说明](https://help.sonatype.com/en/blob-stores.html)。不要手工删除 blob 文件来追求图表立刻下降。

高可用不能简单复制两个容器挂同一数据目录。并发写入是否支持、数据库部署、共享存储、授权范围和负载均衡都要按官方架构核实。若当前部署不支持主动多节点写入，可以先做好备份恢复、冷备切换和客户端重试，再依据明确的业务目标规划受支持的 HA（高可用）方案。

升级前记录旧版本、插件、仓库格式、数据库类型和数据规模；把停止写入、备份、一致性验证、升级检查点及恢复方案写入步骤。数据库迁移后不保证旧程序能读新数据，回滚可能需要连同数据库和 blob 恢复到一致时间点。小版本升级也应先验证上传、下载、权限、代理、清理任务和代表性客户端构建。

## 事故课堂：所有 Maven 构建突然变慢

先按时间建立事实：何时开始、哪些仓库受影响、缓存命中的旧包是否也慢、是否同时发生发布或清理任务。若只有新依赖慢，优先看回源；若所有下载都慢且磁盘延迟同步升高，存储是更有力的候选；若只有一个团队 403，身份和授权比全局容量更值得先查。

修复前选择影响范围最小的一步。例如明确只有一个远端连接异常，可针对该代理仓库处理；磁盘空间紧张则先阻止非必要大上传，评估保留范围，再执行可审核清理。恢复后测量真实下载延迟、错误率和一条完整构建，而不是只看进程存活。

AIOps 可以帮助关联远端失败、磁盘趋势和构建报错，但输入需要携带仓库、时间窗、状态码及请求阶段。把密码、Authorization 请求头或内部完整地址送入模型，既无助于根因推理，也增加数据暴露；用仓库别名和脱敏路径即可保留大部分诊断价值。

## 面试课堂：从名词回答到连续追问

**30 秒回答。** Nexus 统一管理依赖与内部产物。下载通常经过 group，内部发布进入 hosted，外部依赖通过 proxy 缓存。生产重点是不可变版本、权限隔离、元数据和 blob 的一致恢复，以及不破坏回滚能力的容量治理。

**3 分钟回答。** 从 Maven 坐标到路径开始，解释认证、成员仓库选择、缓存命中或回源、元数据定位、blob 读取和客户端校验；再讲三个取舍：缓存可用性与新版本新鲜度、保留窗口与存储成本、多节点可用性与受支持的数据一致性方案。最后用构建突然变慢的事故说明如何比较命中和回源、错误码与资源曲线，针对证据修复并用真实构建验收。

1. **上传到 group 一定不允许吗？** 本课 Maven/Raw 发布明确写 hosted；不能跨格式泛化。部分 Docker、npm group 可配置可写成员，将写请求路由到指定 hosted，取决于版本和产品能力。应先核验格式与可写成员，再分别验证写入位置和读取成员。[可配置仓库字段](https://help.sonatype.com/en/configurable-repository-fields.html)
2. **只有新包 404，旧包正常，怎么办？** 核对坐标、远端发布状态、proxy 在线与负缓存，再查 group 成员和权限；不能先清空所有缓存。
3. **相同版本在两台机器行为不同？** 比较实际下载路径与摘要，检查是否覆盖 release、客户端缓存及仓库优先级。修复要恢复可信版本并建立禁止覆盖规则。
4. **备份恢复成功如何证明？** 用代表性客户端读取历史 release、验证摘要、测试权限及必要上传，记录恢复耗时和数据恢复点；目录存在或登录成功都不充分。
5. **怎样避免清理删除生产依赖？** 将部署清单与回滚清单纳入保留规则，对候选做审阅及恢复演练，明确包来源和保留期限，不能只依据最后下载时间。

## 仓库管理员课堂：从下载成功到供应链可靠

### 先认识两种身份：文件身份与发布身份

老师拿一个 `alert-service-1.0.0.jar` 给你看，问：“怎么证明这是上周批准的那个文件？”文件名不够，目录不够，上传时间也不够。你需要不可变的制品坐标或路径、内容摘要、构建提交、流水线与发布身份。摘要回答字节有没有变化，身份与审计回答谁有权把它发布到这个位置，测试报告回答它经过哪些检查。三者不能互相冒充。

在 Maven 中，同一组件通常包含 POM、JAR、校验文件，可能还有源码包与文档包。Component（组件）是逻辑组织，Asset（资产文件）是实际可下载的文件；清理一个资产与删除整个组件影响面不同。Raw 仓库允许你自己组织路径，灵活却意味着版本、生命周期和命名规则也要自己约定，平台不会自动替你判断哪个 `latest.zip` 还能回滚。

正式版本应采用明确的不可变策略：修复一个包就发布新版本，而不是让旧坐标突然对应新字节。否则某些构建节点命中旧本地缓存，另一些重新下载到新文件，相同源码和版本号却得到不同结果。此时问题不是单纯“缓存脏了”，而是仓库违反了客户端依赖的版本稳定假设。恢复时先定位被覆盖的坐标和消费者范围，再重新建立可信版本，不应让所有团队盲目清空缓存。

### 下载为什么会经过三层缓存

一次依赖请求可能先命中构建机本地仓库，再经过 Nexus 代理缓存，最后才访问公网源站。浏览器手工下载成功仅证明你这条路径成功，不能证明 Runner 使用了相同 DNS、代理、认证和仓库地址。排障时请同时保存客户端实际访问 URL、仓库名、响应码、发生时间与请求关联标识，别只转发“依赖不存在”四个字。

Negative cache（负缓存）是把上游曾经返回“没有这个文件”的结果暂存起来，减少反复回源。它的必要性很直观：错误坐标若每秒被请求上千次，不应把上游打满。但它也带来可见性延迟：上游刚补发文件，代理可能暂时仍按旧的未找到结果回答。遇到这种情况，要确认上游真实存在、当前代理配置和缓存策略，再按当前版本支持的管理方式处理对应仓库；不要把整台实例重启当成唯一办法。

另一个常见误区是“代理缓存中有一个包，断网就能完整构建”。构建还需要插件、父 POM、传递依赖、元数据和可能的其他仓库内容。只有目标项目所有必要坐标都准备好，且客户端不会额外依赖新元数据，离线构建才可能成功。企业离线交付应通过指定版本的依赖清单、预取过程和隔离网络验收证明，不凭一个成功下载截图宣布完成。

### Group 的顺序为什么属于安全设计

Group（聚合仓库）给客户端一个统一入口，但它不是把所有仓库内容变成没有来源差别的一份文件。成员顺序和格式解析行为会影响查找路径；某个内部包如果错误地从公网同名坐标获取，可能形成依赖混淆风险。内部命名空间、仓库路由、权限和允许上游范围应共同设计，不能只把内部仓库摆在前面就认为安全问题全解决。

建立一份组件来源规则：内部组织坐标只能由受信发布身份写入内部 hosted 仓库；公共依赖只能经审查过的代理入口获取；发布账户不能删除历史正式版本；普通构建账户只读。具体权限项和路由能力因版本与授权而异，要在当前实例确认。验证权限时使用专用测试用户分别尝试读取允许路径与禁止写入，不要用管理员账号测出“都能访问”就结束。

上传账号权限过大，还会放大流水线被篡改的后果。恶意脚本若取得全仓库删除权限，可以破坏多个团队的回滚材料。把权限限定到仓库、动作和必要命名范围，并将生产正式发布与普通合并请求的身份分离。日志掩码只隐藏显示，不阻止脚本使用密钥；需要持续评估谁能改流水线、谁能批准发布以及凭据在何处注入。

### 上传成功、搜索可见、下载可用是三个检查

学生问：“页面搜索不到，可上传接口是成功的，为什么？”先分清接口响应代表的那一步，再检查直接下载路径与搜索索引。搜索依赖的元数据和索引，与文件内容的存储路径不是同一层；暂时搜索不可见不必然表示字节没保存，直接下载成功也不代表所有元数据完整。相反，列表中存在一个组件，也不能排除某个资产文件缺失。

发布验收最好从一个独立只读客户端进行：按发布记录中的精确坐标下载必要资产，计算摘要，验证内容格式，再用最小消费者构建或启动。独立客户端减少“上传机本地文件被误当作远端下载结果”的假通过。验证记录要写清从哪个仓库取回，而不是只写 `BUILD SUCCESS`。

如果上传连接中断，结果可能未知。先查精确路径和摘要；目标已经存在且字节一致时，应转入验证，不要立即覆盖；目标不存在时才能按批准流程重新上传；目标存在但摘要不同则应停止并调查。对于一组资产部分成功的发布，还要判断消费者是否已看到不完整版本，避免继续向正式仓库零散补文件却没有版本一致性约束。

### 清理课堂：空间、可恢复性与保留策略分开记账

磁盘告警出现后，先问哪个存储层增长：二进制内容、数据库、索引、日志、临时文件还是备份。只看一个挂载点总占用无法决定能删什么。再按仓库类型拆分：公共代理缓存通常可以重新下载，内部唯一制品未必能重建，正式发布与临时快照也不该使用同一保留策略。

Cleanup policy（清理策略）负责筛选候选内容，执行清理与后续物理空间回收可能是不同步骤。具体格式、任务和版本行为必须查阅当前实例的[清理策略文档](https://help.sonatype.com/en/cleanup-policies.html)。不要把界面上组件消失、磁盘立即释放、备份也同步可回收当成必然同时发生的事。更不能绕过应用直接删除 blob store 中的随机文件，那会让内容与元数据不一致。

“最近没有下载”也不等于“业务不再需要”。低频灾备包、上一正式版本、审计保留材料可能很久没被访问，却仍是恢复依赖。先列候选清单和总量，让所有者确认保留边界，再在专用测试仓库验证规则，最后小范围执行并观察。容量治理是业务生命周期决策，不是找一个能够释放最大空间的删除命令。

清理前还要确认备份是否真实可恢复。只备份数据库，可能有资产描述却没有内容；只备份 blob store，可能有字节却缺少定位和权限信息。数据库、二进制内容、必要配置和密钥应按官方方法形成一致恢复点。恢复演练至少验证登录、只读下载、摘要一致、代理回源以及受控上传；仅看到进程启动并不够。

### 一个不删除历史内容的仓库恢复推理练习

本节是生产模拟，不故意破坏现有数据。前置条件是已完成本机 Raw 实验，拥有专用学习仓库和两份自己创建的文件。先把正文内容不同的 `rule-v1.txt` 与 `rule-v2.txt` 上传到不同路径，分别独立下载并记录 SHA-256。发布记录中把 v1 设为上一个批准版本，把 v2 设为待验证版本，路径都必须是本次创建的学习对象。

然后在本地把“待发布摘要”故意写成 v1 的摘要，却仍下载 v2，执行已有的 `Get-FileHash` 比较。预期比较不一致，发布应停止；仓库和文件都保持不变。这个故障说明内容验证能挡住“版本指向错了”，不是在模拟 Nexus 内部损坏。修复时改正发布记录，重新下载 v2 并匹配；再按 v1 的精确路径和摘要验证回滚材料仍可取得。

如果比较居然一致，先检查两份文件是否真的不同、下载是否覆盖到了同一路径，以及你比较的是源文件还是远端取回的文件。如果下载返回登录页面而 HTTP 是 200，摘要同样不会匹配，但根因在认证或反向代理，不是文件损坏。保存完整状态码、响应类型和脱敏路径，避免把所有摘要不符都归因于磁盘故障。

清理只删除这次创建的学习路径和本地下载文件，操作前核对仓库名与路径；若你选择保留远端证据，在记录中注明保留策略。不要修改正式仓库的清理策略来完成本实验。与前面的权限故障实验合起来，你应掌握“禁止写入”和“允许写入但内容错误”两类完全不同的故障。

### 容量与高可用怎么回答才不是口号

容量先拆字节吞吐与元数据请求。一百个作业同时下载同一个大文件主要考验出口、磁盘读和缓存；一百个冷启动构建各自下载成千上万小依赖，还会给认证、数据库、索引与请求处理带来压力。仅增加 Java 堆可能无法改善网络带宽饱和；只扩大磁盘容量也不会自动增加随机读写能力。

建议分开观察读写请求率、大小分布、命中与回源耗时、错误码、活跃连接、数据库等待和存储延迟。AIOps 关联时把流水线启动潮、代理上游异常、清理任务开始和平台升级标在同一时间轴上。一次全体构建变慢，可能源于冷缓存洪峰，也可能是对象存储延迟；先看时间线和失败层，不能只凭名称相同就判断“仓库坏了”。

高可用不是复制一个容器然后让两个进程同时写同一数据目录。必须采用当前产品版本支持的架构和授权能力，按官方要求组织数据库、共享内容存储、入口与节点。即使支持多个节点，数据库、对象存储、身份服务和外部网络仍可能形成共同故障域。回答设计题时，应明确可接受中断时间、数据恢复点、读写降级方式和恢复演练，而不只画两个盒子。

## 协议与权限进阶：不是所有仓库都按普通文件夹工作

### Maven 快照为何需要元数据而不只是一个文件名

正式发布坐标应稳定，开发快照则描述持续变化的开发结果。客户端声明一个 `SNAPSHOT` 依赖后，还要利用仓库元数据解析具体时间戳和构建号对应的资产。因此更新了 JAR 却没有匹配的 POM 或快照元数据，可能出现“浏览器能下载，Maven 仍失败”。不要手工改文件名猜协议，使用支持该格式的发布工具生成相互匹配的资产。[Maven 仓库语义](https://help.sonatype.com/en/maven-repositories.html)

诊断时先区分解析元数据失败、下载具体资产失败、摘要失败与依赖冲突。记录客户端实际请求的路径，而不是只记录开发者写在项目里的逻辑版本。代理端的新鲜度策略和客户端更新策略都可能影响何时看到新快照；强制客户端更新不等于自动清除所有代理状态。正式发布需要可审计的固定版本，不能用“当时最新快照”当作长期恢复依据。

Maven 的镜像设置也只是客户端仓库解析规则。`mirrorOf` 为星号不意味着任意脚本中的所有 HTTP 下载都会经过 Nexus；构建插件若自己调用别的地址，仍需单独治理。服务凭据的 `server` 标识要与实际使用的仓库或镜像标识匹配，名字相近不代表认证配置生效。遇到本机成功、执行器失败，应比较有效设置和请求入口，不复制个人完整凭据文件到流水线。

### 内容选择器是授权筛选，不是最高优先级拒绝墙

Content selector（内容选择器）可以按格式、路径等条件描述内容范围，再与相应权限结合。它适合缩小某类访问授权，但不会撤销用户通过其他角色已经获得的更大权限。若用户同时拥有全仓库读权限，新增一个狭窄选择器不能把他的访问自动缩回小目录。这是权限并集与显式拒绝模型的区别。[内容选择器及格式限制](https://help.sonatype.com/en/content-selectors.html)

测试权限要从角色链开始：用户有哪些直接和间接角色、各角色授权哪些仓库与动作、group 是否带来额外读取入口。以管理员试读成功没有意义，应使用专用受限测试身份，既验证允许路径成功，也验证相邻但禁止的路径不可访问。两个入口指向同一组件时，还要分别测试直接 hosted 与 group 路径，不把一个入口的拒绝当成全局保护。

不同格式的上传协议会限制按路径筛选的效果。有些发布先向仓库根路径发送请求，真正的包坐标在请求内容里，不能用普通 Raw 文件路径的经验推断所有格式。选择器适用范围应按当前格式确认；跨租户的强隔离优先考虑独立仓库和清晰角色边界，再评估更细粒度授权。自动化建议“加一个选择器”前必须说明它实际控制哪类请求。

### 下载入口统一不等于写入位置可以模糊

某些 group 支持配置可写成员，这是把入口请求转发给指定仓库，不是任意成员自动接收上传。使用前明确写目标、部署策略、命名范围和权限；验证时查询具体 hosted 是否收到内容，同时检查 group 是否能按预期读回。若更换可写成员，后续新包和旧包可能位于不同仓库，清理及恢复清单必须包含这次配置变更。

对初学者，直接发布到明确的 hosted 更容易理解来源；组织希望简化客户端配置时，再使用当前产品明确支持的统一读写入口。二者没有绝对优劣，但都不能放弃产物身份。把入口地址当成唯一发布证据，会在成员顺序、路由或代理调整后失去可追溯性。AIOps 发布事件应同时记录入口别名、实际存储仓库和摘要。

### 纸面授权故障：为什么新增限制反而没有限制住

前置条件是完成本课只读下载与摘要实验。本节不修改真实角色，只在笔记创建用户甲，角色一允许读取整个学习仓库，角色二仅允许读取 `team-a/`。预测甲读取 `team-b/` 是否会因角色二被拒绝：不能这样推断，因为角色一仍授予读取。故障就是把狭窄授权误认为否定授权，而非产品随机放行。

修复推演先移除过宽授权，再保留实际需要的范围，并列出允许与拒绝两组验收路径。第二轮加入 group 读取权限，重新审核是否又扩大可见性。预期每次授权变化都重新计算有效范围；若仅凭角色名称判断，回到具体权限和入口检查。清理删除合成笔记即可；真实生产权限调整要由管理员审核并准备恢复原角色映射，不能用课堂身份替换服务账户。

最后核对基础实验的凭据边界：示例手动生成的 Basic 认证值只是可逆编码，且使用 ASCII，实验账号与密码应选该字符范围；它只在本机回环 HTTP 教学，跨主机必须使用受信 TLS。移除 PowerShell 变量减少误打印机会，并不证明内存被安全擦除。不要把响应头、会话记录或自动转录中的认证值上传 GitHub；学习证据保留状态与摘要即可。

验收表还应记录仓库格式与版本，避免把某个格式的成功经验错误推广到全部包协议。
