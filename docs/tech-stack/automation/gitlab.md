## 官方知识地图

```text
GitLab（源码协作与交付平台）
  -> Group（组织分组）/ Project（项目）/ Repository（代码仓库）
  -> Merge Request（合并请求）与代码评审
  -> .gitlab-ci.yml（项目流水线定义文件）
  -> Pipeline（一次流水线）/ Stage（阶段）/ Job（作业）
  -> Runner（任务执行代理）/ Executor（执行环境实现）
  -> Cache（加速缓存）/ Artifact（作业产物）/ Package（版本包）/ Registry（镜像等制品登记仓库）
  -> Environment（目标环境）/ Deployment（一次部署）/ Approval（审批）
  -> 权限、变量、审计与运维
```

## 场景开场

开发把代码推到仓库后，测试、构建镜像和部署仍靠人在终端逐条执行。结果是步骤不一致、凭据散落、失败无法复现。GitLab CI/CD 的目标，是让每次变更经过同一条可审计流水线。

## 一句话人话版

GitLab 保存代码和协作记录，GitLab CI/CD 再把仓库中的步骤交给 Runner 自动执行并保存结果。

## 为什么要学

岗位明确要求 GitLab、CI/CD 和 DevOps。平台运维不仅要会点“运行”，还要理解 Runner 容量、构建隔离、凭据、制品追溯、审批、回滚以及流水线指标。

## GitLab 是什么

GitLab 是覆盖代码托管、协作和软件交付的平台。仓库中的 `.gitlab-ci.yml` 定义流水线；Runner 是领取并执行 Job 的程序；Executor 决定 Job 在 Shell、Docker 或 Kubernetes 等环境中怎样运行。

## 它解决什么问题

- 把代码、评审、构建、测试和部署记录关联起来。
- 让交付步骤版本化并可重复执行。
- 通过受保护变量和环境限制生产权限。
- 保存测试报告和构建产物。
- 用流水线状态阻止未经验证的变更进入主分支。

## 核心原理

### Pipeline、Stage 与 Job

- **是什么**：Pipeline 是一次流水线；Stage 是阶段；Job 是最小执行单元。
- **为什么需要**：把复杂交付过程拆成有依赖、有并行度的步骤。
- **怎么工作**：GitLab 根据 YAML 创建 Job，前一 Stage 成功后进入下一 Stage，同 Stage 通常并行。
- **怎么看或怎么用**：从 Pipeline 图进入失败 Job，查看脚本、Runner、变量和日志。
- **坏了怎么查**：先区分 YAML 未创建、Job 等待、脚本失败还是部署失败。

### Runner 与 Executor

- **是什么**：Runner 从 GitLab 领取 Job；Executor 决定执行环境。
- **为什么需要**：GitLab 服务本身不直接在服务器上执行用户脚本。
- **怎么工作**：Runner 注册并轮询任务，按标签和保护规则匹配 Job，执行后回传日志和状态。
- **怎么看或怎么用**：查看 Runner online 状态、标签、版本、并发和最近任务。
- **坏了怎么查**：Pending 先查是否有匹配标签和权限的 Runner，再查网络、令牌和容量。

### Cache、Artifact 与 Package

- **是什么**：Cache 加速重复下载；Artifact 保存 Job 输出；Package/Registry 保存可发布制品。
- **为什么需要**：加速数据和交付证据的生命周期不同。
- **怎么工作**：Cache 可跨 Job 复用但不保证永久；Artifact 按流水线保存；Package 有版本和仓库语义。
- **怎么看或怎么用**：为测试报告设 Artifact，为依赖目录设 Cache，为正式包使用制品仓库。
- **坏了怎么查**：检查 key、路径、过期时间、对象存储、权限和上传大小限制。

### 变量、环境与发布控制

- **是什么**：CI/CD Variable 提供参数或秘密；Environment 记录部署目标；保护规则限制生产操作。
- **为什么需要**：代码可以公开流程，但不应包含密码，也不能让任意分支发布生产。
- **怎么工作**：GitLab 在 Job 运行时注入变量，并按分支、环境和审批规则决定是否允许执行。
- **怎么看或怎么用**：秘密使用 masked/protected 变量，生产 Job 使用受保护环境和手动审批。
- **坏了怎么查**：不要输出秘密；检查变量 scope、分支保护、环境授权和 OIDC/凭据有效期。

## 架构和数据流

```text
Git push / Merge Request（推送或合并请求）
  -> GitLab 读取 .gitlab-ci.yml
  -> 创建 Pipeline 与 Jobs
  -> 匹配 Runner
  -> Executor 准备隔离环境
  -> 执行测试 / 构建 / 发布
  -> 回传日志、报告、制品与部署状态
```

## 安装与启动

企业环境通常由平台团队部署 GitLab，项目使用者先验证仓库与 Runner。Runner 的安装方式应按官方文档和操作系统选择。

```powershell
git remote -v # 确认代码指向预期 GitLab 项目
git ls-remote origin # 验证 Git 协议、DNS 和权限，正常会返回远端引用
gitlab-runner --version # 在 Runner 主机上确认程序版本
gitlab-runner verify # 在 Runner 主机上验证已注册实例的连通性
```

## 配置详解

```yaml
stages:
  - test # 先验证代码
  - package # 测试通过后再生成交付物

shell-test:
  stage: test
  image: alpine:3.20 # Docker/Kubernetes executor 使用的隔离镜像
  script:
    - test -f README.md # 文件不存在时命令返回非零，Job 失败

package-evidence:
  stage: package
  image: alpine:3.20
  script:
    - mkdir -p dist
    - cp README.md dist/README.md
  artifacts:
    paths:
      - dist/ # 保存给下载或后续 Job 使用的输出目录
    expire_in: 7 days # 学习制品七天后自动过期
```

`image` 只对支持容器镜像的 Executor 生效；Shell executor 会直接在 Runner 主机执行，必须特别关注隔离和权限。

## 命令 / 配置 / API 字典

| 名称 | 作用 | 常用写法 | 正常结果 | 常见坑 |
|---|---|---|---|---|
| `rules` | 决定 Job 是否创建 | `if: '$CI_COMMIT_BRANCH == "main"'` | 只在符合条件时出现 | 同时混用 `only/except` 造成误判 |
| `needs` | 声明 Job 依赖 | `needs: [build]` | 可跨 Stage 提前执行 | 忘记传递所需 Artifact |
| `tags` | 匹配 Runner | `tags: [linux]` | 被带对应标签的 Runner 领取 | 没有 Runner 匹配导致 Pending |
| `artifacts` | 保存 Job 输出 | `paths: [dist/]` | 页面可下载制品 | 路径相对工作目录，写错会为空 |
| CI Lint | 校验 YAML | 项目 Build > Pipeline editor | 配置显示 Valid | 语法有效不等于脚本一定成功 |

## 在 AIOps 中的作用

GitLab 提供流水线成功率、排队时长、Job 时长、部署频率、失败日志和变更关联。AIOps 可以识别 Runner 容量异常、归类常见失败原因，并把生产告警关联到最近一次 Deployment 和 Commit。

## 入门实验：运行第一条流水线

### 实验目标

让一次提交依次完成文件测试和学习制品打包，并能从页面下载 Artifact。

### 实验步骤

1. 在测试项目根目录创建上面的 `.gitlab-ci.yml`。
2. 在 Pipeline editor 中打开 CI Lint，确认配置 Valid。
3. 提交到非生产分支并推送。
4. 打开流水线，观察 `shell-test` 成功后 `package-evidence` 开始。
5. 从第二个 Job 下载 Artifact，确认包含 `dist/README.md`。

### 验证结果

流水线为 passed，两个 Job 都成功，Artifact 可下载且文件内容与提交一致。

### 如果没有成功

1. 流水线未创建：查 YAML 路径、语法、workflow/rules。
2. Job 一直 Pending：查 Runner online、标签、保护规则和容量。
3. 脚本失败：从第一条非零退出命令开始读日志。
4. Artifact 不存在：查相对路径、生成步骤、大小限制和过期时间。

## 常见故障排查

| 现象 | 先检查 | 处理思路 |
|---|---|---|
| Pipeline 不出现 | YAML、workflow、rules | 用 CI Lint 和模拟规则检查 |
| Job 一直 Pending | Runner、标签、保护、并发 | 恢复匹配 Runner 或调整容量 |
| 构建偶发失败 | 依赖锁定、网络、Cache、资源 | 消除不确定依赖并保留失败证据 |
| 发布成功但应用异常 | 部署对象、健康检查、版本、回滚 | 关联环境与 Commit，执行回滚 Runbook |
| Runner 风险过高 | Executor、权限、网络、秘密 | 使用隔离 Runner 和最小权限 |

## 面试怎么讲

GitLab CI/CD 由仓库里的 YAML 定义，GitLab 负责调度，Runner 负责执行。我的设计会把测试、构建和部署分开，正式制品写入 Harbor 或 Nexus，生产环境使用受保护变量、环境审批和可验证回滚；故障则按规则、队列、Runner、脚本、制品、环境逐层排查。

## 老师带你串起来：一条告警规则怎样安全到达生产

先把屏幕上的按钮放一放。假设你的任务是把“订单接口错误率大于 5%”改成“连续五分钟大于 5%”。这只是几行配置，但写错可能让值班人员整夜收到告警，或者让真正的故障没有人知道。我们需要回答：是谁提出修改，谁看过，测试用的哪份文件，真正部署的是不是那份文件，出了问题如何回到上一版。

这六个问题，分别对应 GitLab 的提交、合并请求、流水线、制品、环境记录和回滚。你以后看一个平台，可以先问它是否把这条证据链连起来，再问功能多不多。

```text
规则源文件与提交 SHA（提交唯一标识）
  -> Merge Request（讨论并评审变更）
  -> Pipeline（对这个提交执行检查）
  -> Artifact（保存检查后的文件与校验值）
  -> 人工批准与部署互斥
  -> 测试环境接收文件并返回版本
  -> 观察告警行为
  -> 发布记录关联提交、产物、操作者和结果
```

学生问：“有了 Git 提交，为什么还要存制品？”老师带你想一个反例：今天从同一提交下载依赖成功，明天某个远端依赖变了，你重新构建得到不同文件。源码一样，不代表产物一样。正式发布应尽量构建一次，把这份产物逐级晋升到测试和生产；晋升是改变它获准进入的环境，不是每到一站重新烹饪一遍。

学生再问：“流水线绿色就能发布了吗？”绿色只证明被执行的检查通过。若 YAML 根本没安排规则语法检查，绿色对语法正确没有证明力；若检查用的是旧产物，绿色也不能证明当前提交可靠。观察时要同时核对提交 SHA、实际命令、产物校验值和部署目标。

### 从网页请求到脚本执行，平台内部怎么分工

GitLab 网页/API 服务处理登录、项目、权限和流水线请求；数据库保存大量业务记录；后台任务处理异步工作；Git 仓库存取由对应存储服务承担；日志、制品、上传附件等可以进入对象存储。Gitaly 是 Git 仓库访问服务，Redis 常参与缓存和队列相关工作，Sidekiq 是后台任务处理组件。具体拆分和高可用方式要对照所用版本的[参考架构](https://docs.gitlab.com/administration/reference_architectures/)。

你先不用安装所有组件，但要理解一次“页面卡住”未必是 Runner 故障。网页能打开、Job 一直排队，问题可能在执行资源；网页本身 500、项目列表加载不了，则要查应用和数据库一侧。代码拉取慢可能在仓库存储、网络或仓库体积；制品下载慢又可能是对象存储。它们共用一个网站入口，不等于共用一个故障根因。

Runner 是主动领取任务的执行代理。Docker executor 为作业准备容器，Kubernetes executor 为作业创建 Pod，Shell executor 直接在宿主执行命令。Pod 可以理解成 Kubernetes 调度的一组紧密协作的容器。执行器改变隔离方式和资源生命周期，不会自动保证脚本安全；给容器宿主 Docker socket 等高权限访问后，隔离边界会明显变弱。[Runner 安全说明](https://docs.gitlab.com/runner/security/)

观察一个 Job 时，按“等多久、准备多久、脚本跑多久、上传多久”拆总耗时。队列时间长，优先查匹配和并发；准备时间长，查镜像和仓库拉取；脚本时间长，查测试、编译、资源；上传时间长，查产物体积、对象存储和网络。不要把总耗时全部归成“服务器慢”。

### 状态模型：失败、重试与取消都需要说明后果

Job 有等待、运行、成功、失败、取消等状态。GitLab 保存的是它观察到的执行结果，外部系统也有自己的状态。例如部署脚本已经发出升级请求，Runner 随后断网，Job 可能失败，但外部应用已升级。此时点击 Retry（重试）可能重复执行升级，不能假定失败等于什么都没发生。

让部署脚本具备幂等性：对同一个目标版本反复执行，应收敛到同一个结果。例如先读目标当前 SHA，如果已经是目标版本，转入健康验证；如果是旧版本，执行受控升级；如果检测到另一个发布正在进行，等待或退出。幂等不是“把所有错误忽略”，而是重复操作的副作用有定义。

两条流水线部署同一个环境还会出现竞争。提交 A 先开始，但 B 构建更快先部署，A 最后完成又把环境覆盖成旧版。`resource_group` 可以给相关 Job 设置共享互斥资源，让同组部署串行，但排队顺序、旧任务取消和过期部署检查还需单独设计。它不会锁住平台外的手工发布。[部署互斥官方说明](https://docs.gitlab.com/ci/resource_groups/)

## 双层带练：从可运行检查到可回收失败

### 先准备什么

使用一个只有你练习用的 GitLab 测试项目，具备创建分支、运行流水线和查看制品的权限。项目需有可用的 Linux Docker 或 Kubernetes executor Runner；是否允许使用实例 Runner、是否有计算配额，以你的实例为准。这个实验只生成文本证据，不连接生产环境。镜像标签用于演示，实际团队应按兼容性和安全流程固定审阅后的镜像摘要。

在新分支 `lab/gitlab-evidence` 中用编辑器创建 `rule.txt`，内容只有一行 `threshold=5`，再创建以下 `.gitlab-ci.yml`。`script` 里的命令在 Runner 的 Linux Shell 中运行，不是在你的 Windows PowerShell 中运行。

```yaml
stages: [validate, package, verify]

default:
  image: alpine:3.20

validate-rule:
  stage: validate
  script:
    - grep -qx 'threshold=5' rule.txt # 必须整行精确匹配，错误配置返回非零

package-rule:
  stage: package
  script:
    - mkdir -p dist
    - cp rule.txt dist/rule.txt
    - printf '%s\n' "$CI_COMMIT_SHA" > dist/commit.txt
    - cd dist && sha256sum rule.txt > SHA256SUMS
  artifacts:
    paths: [dist/]
    expire_in: 7 days

verify-artifact:
  stage: verify
  needs:
    - job: package-rule
      artifacts: true
  script:
    - cd dist
    - sha256sum -c SHA256SUMS # 检查收到的文件内容是否与打包时一致
    - test "$(cat commit.txt)" = "$CI_COMMIT_SHA"
```

`grep -q` 只返回匹配状态，`-x` 要求整行匹配，避免 `threshold=50` 被误认成 5。`CI_COMMIT_SHA` 是 GitLab 注入的当前提交标识；`needs.artifacts: true` 要求取回上游制品；`sha256sum -c` 按清单重新计算文件摘要，正常输出 `rule.txt: OK`。摘要验证内容一致，不能独自证明发布者可信，身份验证和签名属于另一层。

提交前用 Pipeline editor 的校验能力检查 YAML，再推送测试分支。点击这次提交对应的流水线，观察三个 Job。基础实验成功的标准是：三个 Job 成功，最后的日志有 `rule.txt: OK`，下载的 `commit.txt` 与这次流水线的提交 SHA 一致。

如果第一步失败，打开仓库确认 `rule.txt` 大小写、换行和内容；如果 Pending，先看 Runner 是否在线及标签匹配；如果拉镜像失败，查看 Registry（镜像仓库）访问；如果打包成功但验证找不到目录，查 `artifacts.paths` 和 `needs`，不要直接加重试掩盖文件传递错误。

### 注入一次失败，然后证明门禁确实挡住了它

现在只把 `rule.txt` 改成 `threshold=50` 并提交。你的预期是 `validate-rule` 失败，后面的打包和验证不执行。如果依然全部绿色，说明检查没有在你以为的文件、分支或流水线上运行，先核对页面的提交 SHA。

把值改回 5，再提交一次。预期验证恢复成功。保留两次不同提交的流水线链接、失败命令、修复差异和恢复后的摘要输出。不要把失败流水线删掉，教学证据恰好说明门禁不是装饰。

再做一个状态推理练习：如果最后一个 Job 下载不到制品而失败，是否能得出规则本身错误？不能。前置语法检查已经通过，故障发生在制品传递层。记录证据要注明失败阶段，AIOps 才能把“业务规则错误”和“执行平台错误”分成不同处理路径。

实验结束后取消仍在运行的实验 Job，在 GitLab 页面删除这个专用测试分支；保留需要的脱敏记录。临时制品可等待 7 天过期，或在确认下载证据后按页面能力删除。不要删除共用 Runner 或组织级变量，因为本实验未创建它们。

## 生产课堂：为什么加一台 Runner 不能解决全部问题

假设高峰每分钟到达 6 个 Job，单个平均执行 3 分钟，粗略平均并发需求是 `6 × 3 = 18`。这是用来理解容量的简化估算，不是购买 18 台机器的结论。一个 Runner 可承载多少并发取决于每个 Job 的 CPU、内存、磁盘、网络和隔离策略；尖峰和长尾任务还需要余量。观察排队时长分位数、实际运行数和资源使用，再决定扩容。

缓存可缩短依赖安装时间，却会引入污染和兼容性问题。用锁文件、语言版本、系统架构等组成缓存键；把缓存失效视为应能退化到重新下载的情况；正式产物不要只存在缓存里。某次构建只有“命中缓存”才成功，通常说明依赖声明不完整或网络路径仍未解决。

高可用要按层设计：Runner 多实例减少执行单点；GitLab 服务端还需要数据库、Git 存储、对象存储、后台任务和入口的可用性方案。把全部 Runner 放在同一个宿主或一个机房，即使页面显示多个实例，也可能共享电源、磁盘、网络故障域。灾备还要演练恢复密钥和配置；只有数据库备份，没有相应对象存储和仓库数据，不足以证明能恢复整个平台。

安全从代码来源开始。不受信任的合并请求里可以包含任意脚本；若它拿到生产凭据，即使日志显示星号，脚本仍可能通过网络把值发走。Masked（掩码）主要减少日志直出，Protected（受保护）限制注入场景，二者均不能替代评审、隔离和最小权限。公共贡献任务与生产部署任务应分离信任域，发布凭据尽量短期化并限制目标环境。

升级时分别记录 GitLab、Runner、执行器和基础镜像版本。先验证受支持组合和升级路径，在测试环境覆盖仓库拉取、缓存、制品、变量、流水线规则及恢复流程。数据库发生不可逆迁移时，回滚不只是换旧镜像，还可能需要匹配版本的数据备份。将维护窗口、停止条件、备份时间点和恢复验证写入变更单。

对 AIOps 而言，最有价值的字段是项目、提交 SHA、流水线 ID、Job ID、Runner 类别、失败阶段、耗时和环境，不是把所有日志一次性送给模型。先按“排队、拉取、测试、制品、部署、验证”分类，再提取脱敏错误摘要；模型建议修复后，由受控 Runbook 执行并验证目标版本和业务指标。

## 面试课堂：把流程讲成机制和判断

**30 秒回答。** GitLab 把源码协作和交付记录关联起来，CI 配置描述要做什么，Runner 在选定执行环境中执行。生产设计必须同时管好代码来源、执行隔离、产物不可变、环境权限和部署互斥。排障时先定位失败阶段，再关联同一提交、Job、制品和目标版本。

**3 分钟回答。** 先讲一条规则发布的路径：提交进入合并请求，经语法和测试验证后生成带 SHA 与摘要的产物，受控部署读取这份产物，健康检查回报目标版本。再讲三个取舍：缓存提高速度但不能作为事实来源；并发提高吞吐但同环境发布需串行和过期检查；短期凭据减少长期泄漏风险但依赖身份基础设施。最后讲失败语义：Job 失败可能发生在外部变更已经生效之后，恢复应先读取目标状态，按幂等方式重试或回滚，而非无条件再跑一遍。

1. **Runner 在线却不接 Job，先看什么？** 看 Job 的全部标签、Runner 作用域、是否只接受受保护分支、是否接受无标签任务，再看并发和网络。在线只是最近有联系，不能证明匹配规则满足。
2. **`needs` 为什么有用？** 它显式声明作业依赖，可以在无须等待整个阶段时提前运行；追问制品时要回答依赖与数据传递同时检查，不能只画执行顺序。
3. **失败任务能自动重试吗？** 网络读取或安全的幂等操作可以有限重试，测试断言失败不应靠重试刷绿；对已产生外部副作用的发布，要先确认状态与幂等键。
4. **如何设计一百个团队共用的交付平台？** 按信任和负载拆 Runner 池，限制并发及配额，共享模板固定版本，制品集中存储，生产授权单独管理，统一收集排队与失败阶段指标；服务端容量依据实际参考架构和测量规划。
5. **事故复盘：新发布完成后又变成旧版，怎样推理？** 按环境时间线列出所有部署，核对提交顺序、Job 开始结束时间和目标版本，验证是否发生并发覆盖；先停止过期发布并恢复已验证版本，再补互斥和旧部署拒绝机制。没有时间线之前，不先断言是缓存。

## 平台工程精讲：把“配置正确”拆成四次判断

### 第一次：平台为什么创建了这条流水线

老师让你同时打开一条 push 流水线和一条合并请求流水线：它们可能指向相近的提交，却有不同的触发上下文。`workflow: rules` 决定是否创建整条流水线，Job 的 `rules` 决定某个作业是否进入流水线及其相关属性。一个控制全局，一个控制成员，不能用“我写了 rules”概括它们全部正确。

规则按照规定的顺序匹配，第一条命中的规则决定相应行为。宽泛的兜底规则可能使一个推送同时产生你不希望的分支和合并请求流水线；反过来，过窄条件可能让正式发布缺少必需检查。调试时先记录触发来源、分支或标签、是否有关联合并请求，再用 Pipeline editor 或 CI Lint 检查实际配置，不先怀疑 Runner。

`rules:changes` 判断文件变化，适合减少不相关任务，但不能简单理解成“某文件没变，依赖它的服务就一定不用测”。共享库、构建镜像、远端模板和运行环境变化也可能影响结果。平台设计应说明比较基准和事件类型；对关键发布保留可靠的全量验证路径，避免优化条件变成隐形漏检。

共享 `include` 模板减少复制粘贴，却会把一处模板改动传播到很多项目。固定审阅过的版本或提交，记录最终合并的配置，并给升级模板设计试点项目。GitLab 对重新运行 Job 与重新创建流水线的配置取用行为不同；排障时需要知道你是“重跑已有配置的作业”，还是“重新解析了一份可能已经变化的配置”。具体取用规则可查[官方 YAML 参考](https://docs.gitlab.com/ci/yaml/#include)。

### 第二次：依赖图中是否存在真正的数据通道

Stage（阶段）让初学者容易表达“先检查后部署”，`needs` 则能表达更精细的依赖图。你可以让只依赖前端构建的验证提前开始，不等待同阶段漫长的后端测试。但这项加速的前提是依赖真的独立，而不是因为名字不同就认为没有关系。

学生问：“我已经写 needs，为什么读不到上游文件？”依赖关系回答何时可运行，制品声明回答保存哪些文件，下载配置回答从哪些上游取回。三个条件要全部对齐。先检查上游产物相对路径是否正确、上传日志是否成功，再看下游是否拿到正确 Job 的产物，最后才查脚本文件名。缓存目录中碰巧有同名文件不能算通过，因为下一台干净 Runner 可能完全没有它。

某个上游 Job 被规则排除了，下游却硬性依赖它，可能导致流水线在创建时就失败。这不是执行器宕机。只有在业务上确实允许上游不存在时，才考虑可选依赖；若发布必须经过安全扫描，就不能为了消除配置错误把扫描改成可选。依赖图的边代表业务承诺，删除一条边要像修改代码一样评审。

矩阵构建同样要维护身份。Linux 与 Windows 产物、不同架构或 JDK 产物不能都叫一个不带区分的文件，然后让下游随便取。使用明确的产物命名、构建环境元数据和校验清单，使消费者知道拿到的是哪个组合。比起把所有构建都塞进一个很长的脚本，分拆为边界清晰的 Job 更容易定位失败，也需要更明确的数据传递契约。

### 第三次：Runner 接到任务后能否准备正确环境

Runner 在线只说明它近期能与平台联系。领取 Job 还受标签、作用域、保护规则、并发和执行能力影响。Job 要求多个标签时，Runner 需要满足相应匹配条件；把标签随意加到不具备能力的 Runner 上，可能让排队变少却在执行时失败。标签应代表稳定能力或信任域，不要当作随意绕过调度的按钮。

Docker executor 中，Job 容器与服务容器拥有各自的进程和文件系统。脚本连接 `localhost` 时，通常指当前 Job 容器，而不是数据库服务容器；应使用配置的服务别名及端口，并区分容器已启动与服务已就绪。数据库初始化可能仍在进行，正确做法是有超时的就绪检查，而不是看到容器状态 running 就马上执行全部测试。

Shell executor 则直接使用宿主环境，安装的软件、工作目录残留和权限可能成为隐形依赖。一次任务留下的文件使下次任务成功，不是可重复构建。需要固定运行时、清晰工作目录边界和按任务隔离的数据；不受信任任务不应与生产部署共享宿主。对容器执行器也不能掉以轻心，特权模式和宿主 socket 会改变隔离风险。

环境准备故障常表现为仓库拉取、镜像拉取、服务启动、缓存恢复四种不同日志段。网络读取失败可以做有次数上限、带退避的重试；缺少文件、断言失败、权限设计错误不能靠无限重试解决。为失败类别建立统一标签，AIOps 才能统计“公共仓库抖动”而不误算成“产品代码缺陷”。

### 第四次：成功状态到底承诺到了哪一步

`allow_failure` 意味着允许某个作业失败而不阻断相应流水线结果，不意味着该检查通过。若质量门禁被设置为允许失败，页面仍可能给出看起来可发布的总结果。发布规则应明确哪些检查是强制、哪些只是咨询性信息，不能让同一个绿色图标替代整套质量解释。

`after_script` 适合收集额外诊断，但它有自己的运行环境与时限，不能依赖前面 shell 里临时 export 的所有变量，也不应作为关键业务验证的唯一位置。必须阻断发布的检查应在正式脚本步骤中明确返回非零。证据上传还要考虑失败时保留策略，否则最需要日志的时候恰好没有文件可下载。

人工 Job 是执行动作的入口，不天然等于完整审批系统。受保护环境、审批规则、允许执行身份和许可证支持要分别核实；某人能够点击按钮，不代表他看过准确的制品摘要或目标版本。重要发布应把待部署产物、计划、目标、风险与回滚材料关联到批准记录，执行时再检查计划是否过期。

Environment（环境记录）和 Deployment（部署记录）帮助建立变更时间线，但添加一个环境名称不会自动把应用真正部署过去。演示脚本只打印一句 `deploy` 时，平台可以记录作业成功，真实服务器却没有变化。因此完成标准应由目标自己返回版本，并结合健康与业务指标验证，而不是仅查看 CI 状态。

## 追加故障模拟：让上游成功但下游发现产物不对

前置条件仍是前面的独立学习项目，使用其已通过的三阶段流水线，文件只包含 `rule.txt` 和提交标识。创建新分支 `lab/gitlab-tamper`，保留正常版本的 YAML 作为对照。不要在团队生产发布流水线上制造故障。

在 `verify-artifact` 的 `cd dist` 后、摘要检查前增加一行 `printf '%s\n' 'threshold=999' > rule.txt`。这个命令只改当前 Job 下载到工作目录的学习文件，不改远端上游制品。推送后预期上游验证与打包成功，下游摘要检查失败。它证明文件即使“存在且能打开”，内容也可能不符合被批准的那一份。

观察失败位置应为 `sha256sum -c SHA256SUMS`，而不是前面的规则校验；下载上游原始制品再计算摘要，确认它仍然正确。这样你就能区分“生产者生成了坏文件”与“传递后被改动”。若所有阶段都通过，先查看实际流水线 SHA 和这行命令是否进入运行配置；若文件未找到，说明故障发生在更早的数据传递层，需要先恢复基础实验。

删除人为改写行，再推送修复提交，预期全部恢复。保存坏版本差异、失败 Job、上游原始摘要及修复后的结果。清理时只删除本次分支和自己的临时下载文件，保留必要证据与正常流水线；制品按既定期限过期。这个实验不证明网络中真实发生过篡改，也不测试代码签名，它只验证你的内容完整性门禁会拒绝不一致的字节。

## 大厂设计追问：把项目流水线升级成组织交付平台

一百个团队共用模板时，先划分稳定公共能力和项目差异。公共能力包括身份、制品证据、错误分类、日志保留与部署审计；项目差异包括语言版本、测试命令和健康入口。若模板开放任意脚本和任意生产凭据，所谓标准平台仍会变成一百种不受约束的执行方式。用有类型或明确约束的输入、受审阅模板版本和升级记录，使平台接口可维护。

容量隔离要考虑“吵闹邻居”：某团队的大型编译不能长期占满所有资源，让紧急回滚排队半小时。按工作负载和信任域拆池，设置项目配额、并发与超时；为关键恢复保留可用路径，但不绕过授权。平均执行时长会掩盖少数卡死任务，应同时看等待时间分位数、最老队列年龄、准备耗时和失败率。

高可用演练也应分层：停止一个学习 Runner，验证待执行任务能由其他符合条件的执行器领取；服务端恢复验证则另用支持的备份与参考架构完成。不能从“Runner 换了一台还能执行”推导数据库和 Git 存储也具备灾备能力。恢复证据要覆盖仓库拉取、变量解密、制品下载、审批权限以及历史部署记录。

最后一道事故题：有人重新运行两周前的部署 Job，环境回到旧版怎么办？先暂停继续写环境的任务，核对该 Job 对应 SHA、实际产物、部署身份和目标返回版本，恢复当前批准版本并验证。长期措施是部署互斥、过期版本拒绝、批准绑定制品与明确的回滚入口，而不是禁掉所有重试。重试是有用途的工具，关键是结果和副作用要受约束。

## 课堂验收：先保护恢复入口，再追求流水线速度

交付平台失效时，最需要的是找到最后批准的制品和恢复说明。把恢复材料只存在七天过期的普通 Job 制品里，可能在真正事故时已经找不到；把所有日志永久保留，又会带来成本与秘密暴露风险。按用途制定不同保留周期：临时调试、质量证据、正式发布和法规要求各自管理。

备份恢复后，不只验证管理员能登录。用受限测试身份拉取仓库、下载指定制品、运行一条无副作用流水线，确认权限与变量恢复正确；再检查未获授权的操作仍被拒绝。安全边界没有恢复的系统，不能因为首页能打开就认为灾备演练完成。

面试展示一条失败到恢复的证据链比十张绿色截图更有说服力。说明你知道错误发生在哪一层、做过什么只读检查、为什么选择该修复、影响了哪些目标、如何证明恢复，以及哪些生产能力只是设计而未实测。学习项目可以充分展示推理，但不要把教程中的模拟写成自己经历过的真实线上事故。

## 控制面补课：领取能力、人工门禁与子流水线

### 空闲机器为什么仍可能领不到任务

先分清三个数。Runner 配置的全局 `concurrent` 限制这个 Runner 进程下所有已注册配置的同时运行作业总数；某个注册项的 `limit` 限制该项可运行多少作业；`request_concurrency` 控制同时向平台请求新作业的数量。最后一个是领取请求并发，不是容器里测试线程数，也不等于能够运行多少构建。[Runner 高级配置](https://docs.gitlab.com/runner/configuration/advanced-configuration/)

老师给出一个合成例子：同一进程全局并发为四，甲注册项上限三，乙上限三。不能相加后宣称能跑六个，进程总上限仍然限制四个。如果甲作业平均要占八吉字节内存，机器只剩十吉字节可用，也不能因为配置允许三就认为实际容量足够。调度上限、真实资源和工作负载开销必须同时满足。

长轮询是领取请求可以等待一段时间，减少无事可做时的反复查询。如果领取请求槽位不足，某些请求长期等待，可能让有空闲资源的执行端仍迟迟接不到合适任务。故障证据是排队时间与请求行为相关，而不是编译期间持续占满处理器。先看 Runner 的配置告警、注册项分布、实际运行数和领取请求指标，再调整对应限制；不要把所有并发值一起翻倍。

增加领取并发会增加对平台的请求负担；增加作业并发会增加镜像下载、磁盘、内存和对象存储压力。两者的收益与代价不同。用相同任务样本比较调整前后的等待分位数、执行耗时和失败率，才知道改善的是哪一层。回退保留原配置并停止继续扩大变更，不通过删除已注册 Runner 来“重新来一遍”。

### 人工按钮的默认失败规则不能靠记忆猜

`when: manual` 表示人工启动，但可选还是阻断还取决于 `allow_failure`。在普通作业级声明和在 `rules` 内设置人工执行时，默认行为并不相同。生产门禁最好明确写出希望的 `allow_failure`，并检查最终合并配置，而不是把一个示例复制到规则内部后假设状态完全不变。[人工与阻断作业](https://docs.gitlab.com/ci/jobs/job_control/)

可选人工任务未运行，可以不阻塞后续结果；阻断人工任务则会使流程等待适用操作。两种都有用途：可选诊断按钮适合需要时采集额外证据，生产发布批准通常需要明确的阻断边界。把“人工”当成天然安全，会漏掉谁能点击、输入能否修改、变量是否敏感、目标是否受保护等问题。记录批准人和批准对象，不只是按钮被按过的时间。

事故中若看到“部署没点但流水线通过”，先查它是不是可选人工任务；若看到“文档测试通过但整体 blocked”，先查是否有阻断人工任务还在等待。不要为了消除黄色状态就取消所有门禁。状态颜色是规则的结果，正确性要由业务期待决定；AIOps 汇总必须分别呈现检查完成与发布未批准。

### 子流水线创建成功不等于子任务全部成功

下游流水线可以分解单体仓库工作，也可以触发另一个项目的交付。触发作业与下游流水线是不同对象：默认触发步骤成功，可能只表示下游成功创建；若主流程要等待并反映下游结果，需要使用当前实例支持的相应触发策略，并查明状态传播规则。不能凭父流水线有一个绿色触发节点，就宣称后续部署成功。[下游流水线模型](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/)

父子之间的数据也要显式传递。输入、变量、制品和权限是不同通道，传一个版本字符串不会自动传文件；跨项目下载制品还涉及访问授权。建议记录父流水线、下游项目、下游编号、源码摘要、制品摘要和目标环境，使排障时能沿这条链找到实际失败处。禁止把任意外部输入直接拼成受信模板路径或高权限项目标识。

跨项目凭据还要区分调用者身份与目标项目允许范围。某个作业令牌能够读取本项目，并不代表可以任意读取其他项目的制品；允许列表和目标资源权限应按实例能力配置。验证时分别测试允许的下载与应被拒绝的访问，不在日志打印令牌正文。令牌生命周期结束后，后台脚本也不能假定它仍有效；长任务应在受控身份模型内安排，而不是偷偷复制一份长期令牌。认证错误先查身份和有效期，授权错误再查目标边界，避免扩大组织权限来解决单项目问题。

### 一次无服务的三层状态实验

前置条件是已经完成前面的文件制品实验。现在只用笔记造三条记录：父触发成功、子构建失败、部署未开始。先给出结论“下游已创建但交付失败”，不能写成已发布。故障注入把子构建状态删掉，预期变为下游结果未知；需要查询下游编号，而不是重复触发另一次发布。

再加入人工诊断可选、生产批准阻断两条记录，分别推断它们未运行时影响哪些结论。验证依据是每个状态的职责和显式失败规则；若得出所有按钮都必须点，说明没有区分可选诊断与必需门禁。清理删除本次合成笔记即可，不修改实例设置或领取容量。本练习只验证判断能力，实际调度与权限仍需在授权测试项目验证。

三分钟面试追问可以这样收束：先说明创建流水线、领取作业、执行脚本、传播下游状态和批准部署是五个关口，再用各自证据排除假设。面对“空闲机器很多但发布很慢”，不会马上扩容，而是定位领取、依赖或审批瓶颈；面对“父任务绿色而生产没更新”，会追到下游实际版本和业务验证，而不是重跑整个项目。

记录还应注明实例版本和授权能力，避免他人在不同版本照搬门禁配置。
