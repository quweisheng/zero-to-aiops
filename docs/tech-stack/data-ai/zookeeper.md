# Apache ZooKeeper 深讲

> 学习目标：理解 ZooKeeper 的 znode、Session、Watch、临时节点、顺序节点、Quorum 和 ACL，能启动学习环境、完成配置/成员/选主实验，并按会话、网络、磁盘和多数派链路排查常见故障。

## 老师先带你认路

今天要解决的不是“多保存一份数据”，而是让三个自动化调度器知道谁现在有资格发指令。进程是正在运行的程序，客户端是来请求协调结果的程序，服务端是保管协调状态的程序。一台机器可以运行多个进程，因此“三个客户端”不一定是“三台机器”；后面讨论故障域时，这个区别非常重要。

先记住两个“节点”不是同一回事：服务器节点是运行 ZooKeeper 的成员；znode 是服务里一条有路径的数据记录。路径像 `/aiops/config`，斜杠分层只是命名方式，不是你电脑上真的有这个文件。ZooKeeper 的树更像“很小的共享公告栏”，但它不替应用执行任务，也不证明公告里写着在线的实例此刻一定健康。

基础实验只需要已经可用的 Docker 和两个终端，Windows 可用 PowerShell，Linux 可用常见命令行；Java 运行环境由教学镜像提供，不要求先编译 Java 项目。不会容器时只补 [Docker](../cloud-native/docker.md) 的镜像、容器和端口概念；连接失败时查 [网络基础](../foundation/networking.md) 的地址、端口与域名；看到 JVM 和 GC 时再读 [Java](../foundation/java.md) 中运行时与内存回收部分。

第一遍先创建节点，观察数据版本、监听和会话关闭；第二遍再理解多数派怎样提交写入、旧主为什么仍可能发出错误指令，以及生产如何隔离它。今天的验收是能用两个客户端复现一次版本冲突，并说明拒绝更新为什么是正确结果。本次文档修订没有启动 ZooKeeper，真实服务实验和跨节点故障切换仍需在读者的隔离环境执行，不能把预期输出当成已发生的记录。

## 场景开场

三个调度器实例同时启动，但同一时刻只能有一个实例执行全局任务。你还希望主实例宕机后，其他实例能及时发现并重新选主。

把“谁是主实例”写进普通数据库并不断轮询，会遇到锁超时、故障检测、并发覆盖和脏状态清理问题。ZooKeeper 用 Session、临时顺序节点和 Watch 提供了一套更适合分布式协调的基础能力。

## 一句话人话版

ZooKeeper 保存少量关键协调状态，让多个进程对成员、配置、顺序和主节点达成一致。

## 为什么要学

ZooKeeper 广泛用于分布式系统的配置协调、服务成员管理、Leader Election（主节点选举）、锁和元数据管理。HBase、SolrCloud 和部分存量 Kafka 集群等系统会直接依赖它。

在 AIOps 中，ZooKeeper 故障经常表现为上层系统大面积不可用。只看上层报错容易误判，必须能把连接失败、Session Expired（会话过期）、没有多数派、事务日志磁盘变慢等信号串起来。

## ZooKeeper 是什么

ZooKeeper 是 Apache 的分布式协调服务。它向客户端提供一个类似文件目录的树形命名空间，每个数据节点叫 `znode`。应用通过创建、读取、更新、删除 znode，以及监听变化来实现更高层协调逻辑。

ZooKeeper 不是用来保存业务大表、日志流或大文件的通用数据库。znode 适合保存体积较小、读多写少、需要一致顺序和通知的协调元数据。

## 它解决什么问题

- **配置协调**：保存当前配置版本，并通知订阅者重新读取。
- **成员发现**：用临时节点表示当前在线实例。
- **主节点选举**：用临时顺序节点选出序号最小的候选者。
- **分布式锁**：让竞争者按顺序等待前一个节点删除。
- **命名与元数据**：保存分布式系统中的位置、状态和归属信息。
- **故障感知**：Session 过期后自动删除该会话拥有的临时节点。

锁、队列和选主并不是一个“执行按钮”，而是客户端基于 ZooKeeper 原语实现的 recipe（协调配方）。真实项目应优先使用经过验证的客户端库，不要自行拼接一个看似能跑的锁算法。

## 核心原理

### znode 与树形数据模型

- **是什么**：znode 是 ZooKeeper 命名空间中的数据节点，例如 `/aiops/config`。
- **为什么需要**：路径天然表达层级、归属和子节点关系，便于组织协调元数据。
- **怎么工作**：每个 znode 可保存一段字节数据和 `Stat` 元数据，持久节点可以有子节点，普通临时节点不能有子节点；单节点数据读写是原子的。
- **怎么看或怎么用**：用 `ls` 看子节点，`get -s` 看数据和版本，`stat` 只看元数据。
- **坏了怎么查**：先核对路径、大小、子节点数量、`dataVersion` 和 ACL；不要把大量业务数据塞进 znode。

`Stat` 中常见字段：`dataVersion` 是数据修改次数，`cversion` 是子节点列表变化次数，`ephemeralOwner` 非零时表示它属于某个 Session。

### Persistent、Ephemeral 与 Sequential

- **是什么**：Persistent 是持久节点；Ephemeral 是随 Session 消失的临时节点；Sequential 会在名称后追加单调递增序号。
- **为什么需要**：持久节点保存配置根路径，临时节点表示在线成员，顺序节点提供公平排队和选主顺序。
- **怎么工作**：服务端把临时节点与 Session ID 关联；会话真正过期后自动删除。顺序号由父路径下的计数生成。
- **怎么看或怎么用**：使用 `create`、`create -e`、`create -s`；用 `getEphemerals` 查看当前会话的临时节点。
- **坏了怎么查**：节点没有消失时先判断会话只是断开还是已经过期；节点重复时检查连接结果不确定后的重试逻辑。

临时节点不能拥有子节点。网络短暂中断也不会立刻删除临时节点，因为客户端可能在 Session Timeout（会话超时）内重连到其他服务器。

### Session 与连接状态

- **是什么**：Session 是客户端与 ZooKeeper 服务之间有超时时间的逻辑会话，不等同于某一条固定 TCP 连接。
- **为什么需要**：客户端可以在服务器切换时保留身份、Watch 和临时节点，同时让集群识别真正失联的成员。
- **怎么工作**：客户端在服务器列表中连接一个节点并发送心跳；断线后尝试恢复原会话，是否过期由集群根据会话活动与协商超时判定，不是客户端一次 TCP 超时就自行确定。
- **怎么看或怎么用**：客户端必须处理 `SyncConnected`、`Disconnected`、`Expired` 和认证失败等状态。
- **坏了怎么查**：检查 GC 停顿、网络抖动、CPU 饱和、Session Timeout、服务器延迟和客户端事件处理线程是否阻塞。

收到 `Disconnected` 时应进入保守模式，因为此时收不到 Watch；收到 `Expired` 后旧会话不可恢复，客户端必须新建会话并重新创建临时节点、注册监听。

### Watch 通知

- **是什么**：Watch 是服务端在 znode 数据或子节点变化时发给客户端的异步通知。
- **为什么需要**：避免客户端高频轮询配置和成员列表。
- **怎么工作**：普通 Watch 默认是 one-time trigger，即触发一次后需要重新读取并重新注册；3.6 起还支持 Persistent Watch 和递归 Watch。
- **怎么看或怎么用**：`get -w` 监听数据变化，`ls -w` 监听子节点变化；收到通知后重新读取当前状态。
- **坏了怎么查**：检查 Session 状态、是否重新注册、事件处理线程、Watch 数量和是否把通知误当成完整数据。

Watch 不是消息队列，也不保证把每次中间变化都当成独立事件交给业务。正确模式是“通知告诉你可能变了，然后读取最新状态”。

### Leader、Follower、Observer 与 Quorum

- **是什么**：Leader 负责协调写事务；Follower 参与投票并服务请求；Observer 同步数据但不参与投票；Quorum 是协议认可的法定投票集合，本课使用默认的过半多数派规则。
- **为什么需要**：多副本必须对写入顺序达成一致，才能在节点故障后保持协调状态可靠。
- **怎么工作**：写请求被转交 Leader，Leader 提议事务，超过半数投票成员确认后提交；读取通常由客户端连接的服务器本地处理。
- **怎么看或怎么用**：逐台检查角色、当前 zxid、延迟和同步状态；验证存活的投票成员是否仍超过一半。
- **坏了怎么查**：反复选主先查 2888/3888 网络、DNS、时钟、磁盘延迟、GC 和 `myid`/`server.X` 一致性。

三台投票成员能容忍一台故障，五台能容忍两台。四台仍只能容忍一台，因此通常选择奇数投票成员。Observer 可以分担读请求，但不能增加可容忍的投票成员故障数。

### 一致性、zxid 与版本写入

- **是什么**：`zxid` 是 ZooKeeper 事务顺序标识；版本字段支持带版本更新，即 CAS（Compare-And-Set，比较版本符合预期后再更新）。
- **为什么需要**：并发客户端必须知道谁先修改，并防止旧数据覆盖新数据。
- **怎么工作**：所有更新按统一顺序提交；客户端可用 `set -v VERSION` 只在版本匹配时更新。
- **怎么看或怎么用**：用 `get -s` 查看 `mZxid` 和 `dataVersion`，更新时携带已读取版本。
- **坏了怎么查**：出现 BadVersion 不要直接去掉版本检查，应重新读取、重新计算并决定是否重试。

ZooKeeper 的写入有全局顺序，但普通读取可能来自某个尚未追上最新事务的 Follower。`sync` 后读取是常见同步手段，但也不能承诺在所有异常情况下获得绝对最新状态；3.9.5 官方内部机制文档指出它本身不是多数派操作。严格一致性需求应按后文的协议边界设计，而不是把所有读取想象成数据库强制主库读。

### ACL、认证与传输安全

- **是什么**：ACL 是 Access Control List（访问控制列表），对 znode 定义 Create、Delete、Read、Write、Admin 五类权限，常缩写为 `cdrwa`。
- **为什么需要**：协调数据能影响整个集群，匿名写入或删除会造成大面积故障。
- **怎么工作**：客户端先按 digest、SASL 等方案认证，服务端再依据每个 znode 的 ACL 授权；TLS 用于保护网络传输。
- **怎么看或怎么用**：用 `getAcl` 检查权限，用受限服务身份访问业务根路径。
- **坏了怎么查**：`AuthFailed` 先查认证，`NoAuth` 先查 ACL 和身份映射；不要用 `skipACL` 当长期修复。

## 架构和数据流

```text
客户端
  -> ZooKeeper Server（当前连接的服务器）
      -> Read（读取）：返回该服务器的本地视图
      -> Write（更新）：转交 Leader（主成员）排序
          -> Voting members（投票成员）记录提案并确认
          -> Commit（提交）：达到多数派后确认统一顺序
          -> Apply（应用）：各副本更新内存状态
          -> Watch（监听通知）：通知相关客户端重新读取
```

磁盘侧的数据路径：

```text
写事务
  -> Transaction Log 事务日志
  -> 内存数据树
  -> 周期性 Snapshot 快照
  -> 重启时由快照 + 后续事务日志恢复
```

第一张图的分支区分本地读与多数派写，第二张图表示磁盘恢复关系，不能据此把异步快照当成每次写入的必要步骤。`dataLogDir` 可把事务日志放到独立低延迟设备，`dataDir` 保存快照和 `myid`。JVM 是运行 Java 程序的虚拟机，GC 是回收不再使用对象的过程；交换分区和长时间回收停顿可能拖慢心跳与请求。

## 安装与启动

### Docker 单节点学习环境

单节点只适合学习和开发，不具备复制或多数派容错。先执行 `docker ps -a` 确认 `zk-lab` 不存在，存在则核对归属，不覆盖旧容器。以下没有挂载宿主业务目录，先预留约 1 GiB 可用内存作为小实验起点，实际消耗以本机观察为准。

```powershell
docker pull zookeeper:3.9.5 # 拉取固定教学版本，非“始终最新”标签
docker run -d --name zk-lab -p 127.0.0.1:2181:2181 zookeeper:3.9.5 # 单节点教学，只允许本机连接
docker logs zk-lab # 查看启动日志，确认没有持续报错或退出
docker exec zk-lab zkServer.sh status # 正常应看到 standalone 模式和客户端端口
docker image inspect zookeeper:3.9.5 --format '{{json .RepoDigests}}' # 记录镜像摘要
```

### 三节点生产结构

三节点必须分布在不同故障域。把三个容器放在同一台电脑只能学习协议，不能提供真实冗余。

```properties
tickTime=2000
dataDir=/var/lib/zookeeper
dataLogDir=/var/log/zookeeper-txn
clientPort=2181
initLimit=5
syncLimit=2
server.1=zk1.example.internal:2888:3888
server.2=zk2.example.internal:2888:3888
server.3=zk3.example.internal:2888:3888
```

每台服务器的 `dataDir/myid` 只写自己的数字，例如第一台写 `1`。`2888` 用于 Leader 与 Follower 同步，`3888` 用于选主通信，`2181` 用于客户端连接。

## 配置详解

```properties
tickTime=2000
# 基础时间单位为 2000 毫秒；心跳和多个超时参数都以它为单位

initLimit=5
# Follower 初次连接并同步 Leader 最多等待 5 个 tick，即本例 10 秒

syncLimit=2
# 正常运行时 Follower 与 Leader 通信最多落后 2 个 tick

dataDir=/var/lib/zookeeper
# 保存快照、myid；目录必须持久化并监控容量

dataLogDir=/var/log/zookeeper-txn
# 单独保存事务日志，生产环境宜使用独立低延迟磁盘

clientPort=2181
# 明文客户端连接端口；生产环境应评审 secureClientPort 和 TLS

autopurge.snapRetainCount=5
# 保留最近 5 份快照及对应事务日志，最低允许值是 3

autopurge.purgeInterval=24
# 每 24 小时执行一次自动清理；默认 0 表示关闭

metricsProvider.className=org.apache.zookeeper.metrics.prometheus.PrometheusMetricsProvider
# 启用官方 Prometheus MetricsProvider

metricsProvider.httpPort=7000
# 在 7000 端口暴露 Prometheus 指标

4lw.commands.whitelist=srvr,stat,mntr,ruok
# 只允许列出的四字命令，不要为了省事长期配置为星号
```

配置修改必须在同版本文档中确认。`reconfigEnabled` 默认关闭；动态增删成员涉及 Quorum 和授权，必须先在测试环境演练并准备回退。

| 名称 | 作用 | 常用写法 | 关键参数或结果 | AIOps 场景 | 常见坑 |
|---|---|---|---|---|---|
| `zkCli.sh` | 连接命令行客户端 | `zkCli.sh -server zk1:2181,zk2:2181` | 连接成功后显示 `SyncConnected` | 验证客户端路径 | 只写一个地址降低故障切换能力 |

## 在 AIOps 中的作用

ZooKeeper 位于“平台依赖与协调状态”层：

- **指标**：请求延迟、未完成请求、连接数、Watch 数、znode 数、包收发、Leader 选举、快照和同步。
- **日志**：Session 过期、连接拒绝、选主、磁盘、认证和快照异常。
- **拓扑**：把 ZooKeeper Ensemble 与 HBase、SolrCloud、存量 Kafka 等上层依赖关联起来。
- **告警**：多数派风险、Follower 落后、延迟升高、磁盘不足、连接接近限制、选主频繁。
- **根因分析**：当多个上层系统同时异常时，优先判断是否共享同一个 ZooKeeper 故障域。
- **自动化**：只读诊断可以自动执行；成员变更、快照恢复和数据清理应保留审批、备份与回滚。

不要只告警“进程存活”。更有效的健康判断是：多数派存在、读写探针成功、延迟可接受、事务日志磁盘健康、上层 Session 稳定。

## 入门实验：节点、Watch 与会话

### 实验目标

在单节点环境中完成持久节点、临时节点、顺序节点和一次性 Watch 实验，亲眼看到 Session 与节点生命周期的关系。

### 实验步骤

1. 按前文命令启动 `zk-lab`。
2. 打开终端 A，进入交互客户端：

```powershell
docker exec -it zk-lab zkCli.sh -server 127.0.0.1:2181 # 打开终端 A 的 ZooKeeper 会话
```

3. 在终端 A 创建实验路径：

```text
create /aiops zero-to-aiops
create /aiops/config version-1
create /aiops/agents online-members
create -s /aiops/task- pending
create -e /aiops/agents/agent-01 online
ls -s /aiops
```

正常会看到类似 `Created /aiops/task-0000000002`，末尾以实际返回为准：序号来自父节点相关计数，不保证从零开始，也不是仅对相同前缀单独计数。你应能在 `/aiops` 下看到 `agents`、`config` 和顺序任务节点。

4. 在终端 A 注册普通 Watch：

```text
get -w /aiops/config
```

5. 打开终端 B，修改配置：

```powershell
docker exec zk-lab zkCli.sh -server 127.0.0.1:2181 set /aiops/config version-2 # 触发终端 A 的数据 Watch
```

终端 A 应出现 `NodeDataChanged`。终端 B 上一条是一次性调用，此时仍在宿主终端，因此第二次更新也使用完整命令：

```powershell
docker exec zk-lab zkCli.sh -server 127.0.0.1:2181 set /aiops/config version-3 # 再次更新，但没有重新注册终端 A 的普通 Watch
```

普通 Watch 不会再次通知，因为它已经触发并移除；终端 A 的会话仍应保持打开。

6. 在终端 A 输入 `quit` 结束 Session，再从终端 B 查询：

```powershell
docker exec zk-lab zkCli.sh -server 127.0.0.1:2181 ls /aiops/agents # agent-01 应在会话关闭后消失
docker exec zk-lab zkCli.sh -server 127.0.0.1:2181 get -s /aiops/config # config 持久节点仍存在，内容为 version-3
```

### 验证结果

- 顺序节点名称带自动生成的递增数字。
- 第一次修改触发 Watch，第二次修改不会触发同一个普通 Watch。
- 终端 A 的会话结束后，临时节点 `agent-01` 消失。
- 持久节点 `/aiops/config` 继续存在。

### 如果没有成功

1. 容器退出：执行 `docker logs zk-lab`，先处理端口、磁盘或配置错误。
2. 客户端连接失败：检查容器是否运行、2181 端口和命令中的地址。
3. Watch 没显示：确认是在终端 A 执行了 `get -w`，并保持该会话在线。
4. 临时节点没消失：确认关闭的是拥有该节点的终端 A，会话可能需要短时间完成关闭处理。
5. 提示 NodeExists：先 `get /aiops`、`ls /aiops` 核对是不是本课上次数据。若不是自己的路径，停止并换一套独立实验路径；不能因为重名就执行递归删除。

### 清理与实验记录

记录两次修改的时刻、通知次数、实际顺序节点名及关闭会话前后的成员列表。确认 `/aiops` 完全由本次隔离实验创建后，先删除实际生成的顺序叶节点，再依次 `delete /aiops/config`、`delete /aiops/agents`、`delete /aiops`。如果 agents 仍有子节点，先确认拥有者会话是否关闭，不能擅自删除未知成员。这里使用从叶到根的精确删除，让你看清各对象归属。

接下来的版本竞争实验不依赖 `/aiops` 数据，可以先保留容器。所有课堂结束后，在宿主终端执行 `docker stop zk-lab`，再执行 `docker rm -v zk-lab` 删除已确认的教学容器及匿名数据卷；这会丢弃本课数据，不清理本机其他容器和镜像。

## 常见故障排查

### 集群没有 Leader

- **现象**：上层持续连接失败，节点反复进入 LOOKING，选主日志频繁出现。
- **检查**：存活投票成员数、2888/3888 双向网络、DNS、`myid`、`server.X`、磁盘和时钟。
- **处理**：先恢复能组成多数派的成员和网络，不要为了“凑数”临时复制数据目录或修改 ID。

### Session Expired 激增

- **现象**：临时节点消失，上层服务频繁重新注册或选主。
- **检查**：客户端/服务端 GC、网络抖动、请求延迟、Session Timeout 和事件线程阻塞。
- **处理**：消除长停顿和网络问题，确认客户端正确重建 Session；不能简单无限增大超时。

### 写请求延迟升高

- **现象**：配置更新和选主变慢，但部分读取仍然成功。
- **检查**：Leader 磁盘 fsync、事务日志设备、Follower 确认延迟、未完成请求、GC 和快照。
- **处理**：为事务日志使用稳定低延迟存储，减少资源争用，并通过压测验证改动。

### 磁盘持续增长

- **现象**：`dataDir` 或 `dataLogDir` 接近满，服务可能因无法写入退出。
- **检查**：快照、事务日志、autopurge、日志滚动、备份状态和实际磁盘占用。
- **处理**：先备份并确认恢复流程，再启用合理的自动清理；不要手工随意删除最新快照和日志。

### Watch 或连接过多

- **现象**：内存、连接数或通知压力升高，配置变化时出现尖峰。
- **检查**：客户端连接复用、Watch 注册路径、是否重复注册、znode 和连接指标。
- **处理**：复用客户端、收窄监听范围、修复重连重复注册，并评估 Persistent Recursive Watch 的放大范围。

### NoAuth / AuthFailed

- **现象**：能连上但无法读写，或认证后 Session 立即失败。
- **检查**：认证方案、账号、SASL/TLS、目标 znode ACL、父子节点权限和时钟。
- **处理**：修正身份与最小权限；修改 ACL 前先验证仍保留可管理路径，避免把所有管理员锁在外面。

## 与 etcd、Consul、Kafka 的边界

| 技术 | 主要定位 | 不应混淆的点 |
|---|---|---|
| ZooKeeper | 分布式协调和元数据 | 不是业务消息流或大数据存储 |
| etcd | 强一致键值存储，Kubernetes 控制面核心存储 | API 和 Watch 模型不同，不能直接替换现有 ZooKeeper 依赖 |
| Consul | 服务发现、健康检查、配置和服务网格能力 | 产品边界比纯协调服务更宽 |
| Kafka | 持久化事件流平台 | Kafka 2.8 引入 KRaft，现代 Kafka 可不依赖 ZooKeeper；存量集群仍需按版本处理迁移 |

选型先看上层产品官方支持，不要为了统一技术栈擅自替换其协调组件。

## 面试怎么讲

ZooKeeper 是分布式协调服务，核心抽象是树形 znode、Session 和 Watch。持久节点保存配置，临时节点表达在线成员，临时顺序节点可实现选主和锁。写入由 Leader 排序并经多数派提交，Follower 可服务读取；生产一般部署 3 或 5 个投票成员。排障时我先判断客户端会话和多数派，再看选主网络、事务日志磁盘、GC、连接/Watch 和最近变更。

## 状态课堂：连上了，不代表资格已经恢复

### 会话是逻辑身份，连接是承载它的线路

三个调度器只能一个发指令，就像三位值班员只能一位持有当前值班资格。网络连接类似当前通话线路，会话类似在协调服务登记的身份；电话换了一条线路，不等于换了人。但这个比喻也有边界：服务端只能根据收到的活动和超时做判断，不会真正知道客户端是停机、卡顿，还是被网络隔开。

客户端创建会话时请求超时，服务端返回实际协商值；请求值不一定被原样采用，要记录返回的会话超时。一次请求超时、TCP 连接断开、会话过期是三个不同事件。应用收到 Disconnected 时，库通常会尝试在服务器列表里重连原会话；此时频繁新建客户端反而制造更多会话和短暂重复成员。会话过期由服务端集群判断，失联客户端可能在重新连接后才收到 Expired，见 [会话生命周期](https://zookeeper.apache.org/doc/r3.9.5/zookeeperProgrammers.html#ch_zkSessions)。

```text
Connecting（尚未建立可用会话连接）
  -> SyncConnected（已经连接并可按协议操作）
      -> Disconnected（连接丢失，资格需要保守对待）
          -> SyncConnected（原会话仍有效，重读并核对状态）
          -> Expired（服务端已判定原会话失效）
              -> New session（新建会话，重新注册与竞争）
```

箭头表示应用接收到连接事件后的处理方向，不是一个精确倒计时表。Disconnected 期间停止新的高风险领导者动作；重连后先读取当前候选节点、配置与所有权，再决定恢复；Expired 后旧临时节点和旧锁资格不能复用。认证失败也不应该无限当作普通断线重试，否则会用错误凭据压垮日志。

为什么“连上就恢复执行”不够？你可能已经错过一次领导者变化，旧工作队列还在内存里，外部任务也可能已被新主处理。恢复时需要区分可重放查询与有副作用动作：前者可以重读，后者先查业务结果和幂等标识。幂等的意思是同一个业务请求重复到达，不会重复产生实质效果；它是下游接口或数据约束的能力，不是会话重连自带的效果。

### 临时节点证明的是会话活动，不是应用健康

临时成员存在，说明拥有者的会话还没有结束，并不能证明其线程池、磁盘、数据库连接或任务执行功能正常。一个客户端主业务线程堵住，但底层心跳线程仍活跃，临时节点可能一直在；相反，机器运行着但 JVM 暂停太久，服务端仍可能判定会话过期。因此服务发现要把成员存在与业务就绪、负载和健康检查区分开。

普通持久节点用于保存不会随客户端离线消失的配置，临时节点用于表达与会话绑定的资格。Sequential（顺序）是创建时追加序号的属性，可和持久或临时组合；它不是独立的健康机制。序号只在相关父路径范围内有意义，不是跨集群的全球时间，也不保证永远不溢出或删除重建父路径后继续原历史。借它实现令牌时必须处理命名空间生命周期。

这里的 version、zxid 和真实时间也不要混用。dataVersion 反映一个节点数据被修改的次数，cversion 反映子节点列表变化，aclVersion 反映权限变化；zxid 则把整个协调服务的写事务放在统一顺序中。修改时间适合辅助审计，但不能用两台电脑的时钟大小替代并发版本检查。

## 写入课堂：ZAB 为什么需要排序、落盘和重新同步

ZAB 是 ZooKeeper Atomic Broadcast（ZooKeeper 原子广播协议），原子广播的目标是让成员以一致顺序交付状态变化，而不是同时在每台机器同一纳秒改完内存。调度器竞争资格时，多个更新必须有共同顺序；若一台认为甲先获得、另一台认为乙先获得，协调就没有意义。

一个客户端连在 Follower 上发出更新，接入成员把写请求转给 Leader。主成员检查操作并安排事务编号，将提案送给投票成员；成员记录事务日志并确认，主成员取得法定数量确认后提交，副本按顺序应用到内存树，接入成员最终返回结果。日志是崩溃后恢复顺序的依据，快照是缩短恢复所需回放范围的工具；两者不是两份可随意互删的同类文件。

```text
Request（客户端写请求）
  -> Proposal（主成员提出带顺序编号的更新）
  -> Durable ACK（投票成员记录事务并确认）
  -> Quorum（收到过半投票成员的确认）
  -> Commit（提交已确定的更新顺序）
  -> Apply / Reply（应用到内存并返回结果）
```

这张图解释正常写路径，不把观察成员计入投票，不把“任意一台已收到”写成“多数派已提交”。zxid 通常可看作任期与任期内计数两部分：任期区分领导权历史，计数安排该历史内的更新次序。关键不是背位数，而是理解新主不能把旧主已经提交的历史当作没发生。协议与一致性边界见 [ZooKeeper Internals](https://zookeeper.apache.org/doc/r3.9.5/zookeeperInternals.html)。

老师问：“三台只剩两台，为什么还能继续？”默认多数派要求超过一半，两台能够组成法定集合；任意两个多数派至少相交一个成员，使新领导权能与已确认历史相衔接。只剩一台时，虽然磁盘里可能还有数据，却无法证明另一边没有形成新的多数派，所以不能让它继续正常提交协调写入。这是选择安全边界，不是多重试几次就能修好的连接问题。

Leader 失效后也不是随便选一个进程名当主就立刻服务。新领导权需要完成状态对齐，补齐缺失历史或处理未提交尾部，再进入正常广播。故障切换期间客户端可看到暂时不可用，恢复时间由选举、同步、网络、磁盘和客户端重连共同决定。不要用“有三副本”推导“切换一定零中断”，也不要直接复制一个可能落后的数据目录来快速凑人数。

### 读得快和读到绝对最新不是同一个目标

普通读取通常由当前连接成员的内存树返回，因此读性能好，但可能落后于另一个客户端刚完成的写入。同一个客户端操作有顺序保证，不等于两个客户端在任何时刻同时看到同一值。配置观察端读到旧值时，先核对连接成员、数据版本与写入是否已完成，不要看到差异就认定数据损坏。

`sync` 后读是常见做法，但 3.9.5 的官方内部说明特别指出，sync 不是多数派操作，因此在特定异常领导权场景也不提供无条件最新保证。若严格要求线性一致，即操作看起来在请求与响应之间某一时点生效并尊重实际先后，应采用经过论证的多数派操作与后续读取协议，或由带版本的更新直接检验业务条件，不能偷偷加一条 sync 就宣称问题解决。额外写入也有负载和权限代价，不应给只读监控随意引入写操作。

## 监听课堂：通知之后，谁负责把配置真正用起来

先看两个观察对象：`get -w /aiops/config` 关心配置节点数据，`ls -w /aiops/agents` 关心成员子列表。修改某个成员节点的内容，不等于增加或减少成员列表，因此不能期望父节点的普通子列表 Watch 感知所有子节点数据修改。监听对象与读取对象必须一致，故障排查第一步往往是确认到底注册了哪种监听。

普通 Watch 触发一次即需重新注册。可靠的业务模式是“读取并注册监听、应用读取的版本、收到通知再重新读取”，不是先读数据、隔很久再随意发起另一次独立订阅。后者会把变化窗口留在两步之间；前者也不保证看见每一个中间版本，因为通知到重新读取之间，数据仍可能继续更新。若 A 快速变成 B 再变成 C，配置消费者应能直接收敛到 C，而不是一定依次播放三种配置。

持久监听省去触发后重新订阅的部分管理，递归监听扩大观察范围，但仍不提供消息队列式逐条历史消费。断线期间不能接收变化，恢复后要重新核对当前状态。官方还指出：对尚不存在节点的存在监听，如果它在断线期间被创建又删除，可能错过整个过程。因此财务事件或任务执行历史不能只存于一次存在通知里，需有独立可靠记录。参见 [Watch 语义](https://zookeeper.apache.org/doc/r3.9.5/zookeeperProgrammers.html#ch_zkWatches)。

回调线程的工作应该短：接收事件、更新本地标记、把读取或应用工作交给合适执行路径。若回调里同步调用一个慢外部接口，其他通知和连接状态处理可能排队，表现得像“服务端迟迟不通知”。为此保留四个时间：配置提交、事件收到、重新读取、应用生效。只记录 Watch 到达，并不能证明服务真的用了新配置。

配置应用最好有版本、校验和可回退状态。新配置语法错时，不要因为读取成功就替换正在工作的配置；先验证，再原子切换本地视图，失败时保留旧版本并告警。读取权限和配置生效权限也应分开，模型生成的参数不能直接以监听回调形式自动下发高风险命令。

## 选主课堂：排队资格和下游执行资格分两层

### 临时顺序节点怎样避免所有人一起惊醒

三个候选者在同一个选举父路径下创建临时顺序节点，读取子列表后按序号比较，最小者获得候选资格，其他人监听比自己稍小的前驱。这里的前驱是队伍里自己前一位，而不是所有人都盯第一位；当前驱消失时才重新读取队伍，减少一次变化唤醒所有客户端的惊群效应。官方 [协调配方](https://zookeeper.apache.org/doc/r3.9.5/recipes.html)给出了这种思路。

比较与注册之间还有竞态：你刚找到前驱，它就在你开始监听前删除了。因此要使用能检查存在并注册监听的操作；如果返回前驱已经不存在，就立即重新读列表，而不是等一个永远不会到来的删除通知。收到通知也不能直接断言自己赢了，其他更小节点或自己的会话状态可能已变，必须重新核对。

创建顺序节点后连接断开，结果是“未知”，不是“肯定失败”。服务端可能已成功创建，只是返回的路径没到客户端；盲目重试会得到两个候选节点。可以用本次申请的唯一标识作为名称前缀，重连有效会话后查找是否已经创建，并核对节点所属会话。成熟客户端库会封装很多细节，教程里的简单排序不能替代经过验证的生产锁实现。

### 旧主恢复后为什么仍可能越权

设甲原来持有资格，随后长暂停；集群判定会话过期并删除甲的临时节点，乙成为新主。甲此刻并没有收到“你的资格失效”的消息，因为它正处于暂停或网络隔离中。甲恢复后，内存里的布尔变量可能仍写着自己是主，因而向外部数据库提交旧任务。ZooKeeper 内部没有两个合法多数派主写入，也不代表业务世界绝不会有两个自认为主的进程。

Fencing token（隔离令牌）让下游拒绝过时持有者。一个新任期取得比旧任期更大的令牌，下游在写入同一资源时原子比较已见最高令牌，小于最高值的请求被拒绝。检查必须发生在资源修改时，若先检查后暂停再写入，时间窗口仍存在。每个业务请求还需要自己的幂等标识，因为同一任期内重复请求依然可能重复执行。

顺序号或事务顺序可帮助构造令牌，但要保证同一受保护资源的编号来源、作用域、持久化与生命周期正确；删除重建选举父路径、恢复旧备份或换集群后，不能让旧令牌重新变成新资格。下游不支持原子校验时，必须明确能力缺口，采用能执行校验的提交层或其他业务协议。对真实服务器重启、权限修改和数据清理，仍保留审批与影响面限制。

## 故障实验：用版本竞争证明旧写入被拒绝

### 前提、步骤与预测

使用前文的独立 `zk-lab`，在两个终端分别执行 `docker exec -it zk-lab zkCli.sh -server 127.0.0.1:2181`，等待各自显示 SyncConnected。下面的 create、get、set 都输入 ZooKeeper 客户端，不是 PowerShell。本实验只用没有子节点的 `/lesson-version`，先用 `stat /lesson-version` 检查不存在；若存在先核对归属，不能直接覆盖。

终端甲执行：

```text
create /lesson-version A
get -s /lesson-version
```

终端乙也执行 `get -s /lesson-version`。二者都记下同一个 dataVersion，新建时通常为零。现在先预测：甲和乙都带这个版本写入，是否有可能都把自己看到的旧配置覆盖成功？

```text
set -v 0 /lesson-version B
```

这条由甲先执行；确认成功后，乙执行：

```text
set -v 0 /lesson-version C
get -s /lesson-version
```

预期乙得到版本不匹配，客户端可能显示 BadVersion 或 `version No is not valid`；再次读取应是 B，dataVersion 为一。这里“冲突”是正常防护，证明服务端拒绝使用旧前提的更新，不是服务不可用。实际版本与错误文本以输出为准，不能只匹配一个英文字符串判定实验失败。命令语法见 [CLI 官方指南](https://zookeeper.apache.org/doc/r3.9.5/zookeeperCLI.html)。

### 恢复、清理与证据

乙重新读取 B 后，按业务评估是否仍应改为 C。仅在本课堂明确同意覆盖时，执行 `set -v 1 /lesson-version C`，再读取验证版本为二；如果真实业务是累加配额或修改部分配置，就应基于 B 重新计算，不能仅把版本号加一后照写旧内容。CAS 防止旧前提提交，不替你决定业务冲突该怎样合并。

如果甲第一次写就失败，检查路径是否已经被修改、读写是否连到同一教学集群；如果乙也成功，检查是否漏了 `-v`、第一次没有真正提交，或路径被删除重建。用提交前版本、甲写入结果、乙拒绝结果和最终状态四项证据验收。最后执行 `delete -v 2 /lesson-version`，若版本不是二则先重读核对，不强删；用 stat 确认不存在，再按前文清理容器。

本实验没有杀进程或断网络，验证的是实际服务的版本并发控制；它不能证明真实会话超时、重新选主或下游隔离已经通过。后面用一个不连接任何服务的模型，把另一类风险单独演算。

## 生产模拟：离线看见过期主指令被隔离

只需 Python 3 标准解释器，不需要 Docker、ZooKeeper 或网络。在本地教学目录新建 `fencing_model.py`，复制以下代码并执行 `python fencing_model.py`。它是受保护资源的教学模型，不实现 ZAB、会话或分布式锁；甲过期、乙获得新资格的情节由我们明确给定。

```python
# 离线模型：同一资源记录最高资格编号和已执行的业务请求。
highest_token = 0
applied = set()
result = []


def submit(token, request_id, action):
    global highest_token
    if token < highest_token:
        return "stale-owner"
    highest_token = token
    if request_id in applied:
        return "duplicate"
    applied.add(request_id)
    result.append(action)
    return "applied"


assert submit(41, "job-1", "first") == "applied"
# 模拟乙已接替暂停的甲；甲并不知道自己的资格已经失效。
assert submit(42, "job-2", "new-owner") == "applied"
assert submit(41, "job-3", "late-old-owner") == "stale-owner"
assert submit(42, "job-2", "new-owner") == "duplicate"
assert result == ["first", "new-owner"]
print("PASS: stale owner rejected; duplicate suppressed")
```

预期输出为最后的 PASS 行，断言不满足会报错。现在故意在你自己的副本里暂时移除过时令牌检查，旧主动作就能进入结果，断言应失败；恢复原判断再执行应通过。这里没有真实数据需要回滚，恢复代码即撤销注入，练习完可以保留脚本和两次输出作为证据。

本次修订在 Windows、Python 3.14.5 中实际执行了这段离线模型：原版退出码零，移除令牌检查后触发 AssertionError，恢复原版后再次通过。该记录只证明教学模型和反例断言可执行，没有连接 ZooKeeper，也没有测试真实服务器的锁安全。

老师要你解释模型省略了什么：这些比较、最高令牌更新、去重记录与业务修改在模型里顺序执行，生产必须是可靠的原子提交，并能在进程重启后保留状态。模型不能证明任意外部接口具有这些能力，也不能保证新令牌来源本身可靠。它只让你看到“协调服务选出新主”之外，下游校验为什么必要。

## 生产设计：协调数据小，故障影响不一定小

### 容量先算扇出，不只看节点字节数

ZooKeeper 的协调数据通常完整复制到各成员，而不是每增加一台就分走一部分键。因此投票成员从三台加到五台不等于数据容量增加三分之二；每台仍要容纳数据树、会话、监听和请求缓冲。Observer 可增加非投票读接入，但它仍要同步更新，不能当作任意扩展写吞吐的分片节点，见 [Observer 官方指南](https://zookeeper.apache.org/doc/r3.9.5/zookeeperObservers.html)。

估算时至少问：有多少客户端会话，每个会话注册多少监听，一个热点节点变更会唤醒多少消费者，每个消费者又会发多少重读。一个只有几百字节的配置，被数万客户端监听时，一次发布就可能造成大量通知与读请求。递归监听放得越靠近根，越需要评估这种扩散；把业务明细流、模型文件或大批量日志放入 znode 会同时增加网络、内存、落盘和恢复成本。

容量计划应采集节点数量、数据字节、子列表大小、连接与监听数量、写频率、峰值未完成请求和磁盘同步时延。大子列表一次读取可能形成大响应，不要只根据单个节点值很小就判断安全。给新业务定每个命名空间的数量、单项大小和变更频率预算，再用代表性负载测试，而不是故障后统一提高各种上限。

### 多数派放在什么地方

题目要求容忍任意一台服务器故障，三台投票成员是常见起点；但如果三台都在同一宿主机或电源域，它只增加进程数量，没有满足故障目标。若两台在机房甲、一台在机房乙，机房甲整体故障仍会失去多数派。架构评审要把机器、机架、网络、电源与维护窗口分别标在图上。

也不要盲目把多数派分散到高延迟远距离网络。每次协调写入需要投票链路参与，链路变慢会增加提交时间并影响上层故障检测。需要跨地域容灾时，先明确延迟目标、故障域和恢复策略，再按上层产品支持方案设计；本课不提供把地址换成远端机房就算完成的配方。

三个条件取舍可以这样回答：读接入压力高、写负载稳定时评估 Observer；数据树或写入已经过大时先改数据模型而不是只加成员；故障容忍要求提高时考虑五投票成员，但同时增加资源和运维成本。任何取舍都应检查上层依赖支持、实际负载与可恢复证据。

### ACL 不是文件夹继承权限

ZooKeeper 对每个 znode 保存 ACL，父节点权限不会自动递归传给子节点。根路径限制很严而子节点 world 可读时，后者仍可能暴露信息；创建子节点要看父节点 CREATE，删除子节点要看父节点 DELETE，读写节点数据则看该节点相应权限。这与“我拥有一个目录，所以其下全部天然安全”的直觉不同，见 [访问控制说明](https://zookeeper.apache.org/doc/r3.9.5/zookeeperProgrammers.html#sc_ZooKeeperAccessControl)。

连接串的 chroot 后缀可以把客户端看到的根映射到某个业务前缀，便于避免路径碰撞，但不是授权隔离替代品。认证解决你是谁，ACL 解决你可以做什么，TLS 解决传输是否被窃听或篡改；SASL 是可插拔认证框架，具体身份要以部署方案为准。客户端流量、成员间流量、管理端口和指标端口都需要各自检查，开启其中一类加密不自动保护所有入口。

审计可以记录谁对哪个路径做了什么以及是否成功，但不应该把凭据、会话密码或敏感配置正文写进学习记录。按 [审计日志文档](https://zookeeper.apache.org/doc/r3.9.5/zookeeperAuditLogs.html)启用后，还要验证日志持久保存、访问权限和容量。修改 ACL 前保留有效管理身份，并用受限账号分别测试允许与拒绝操作，避免一边修权限一边把所有管理员锁在门外。

### 备份、升级与回滚是完整工作流

事务日志设备的稳定时延对写路径很重要；把日志目录改到同一块繁忙磁盘的另一个文件夹，不等于获得独立存储性能。快照与相应日志构成恢复所需集合，自动清理只是控制保留数量，不是异地备份。磁盘告警时先核对快照、日志、清理设置和可恢复副本，不能按文件修改时间随意删除。

恢复演练要在隔离环境验证数据版本、关键路径、ACL、上层注册和业务探针。恢复“很久以前的协调状态”可能与外部系统当前事实不一致，因此还要核对上层是否需要重新登记或重建派生状态。允许丢失多少协调变化以及多快恢复，不只看服务能否启动；外部执行资格与令牌历史也必须避免回退后误放行。

升级前列出服务端、Java、客户端库、上层产品、认证方式和磁盘格式兼容性，保存配置与恢复材料。滚动升级应一次只处理一个计划成员，确认其重新加入、追上、业务会话稳定后再动下一个；不要把程序版本升级和新协议功能启用混成一次变更。官方管理指南对某些新功能明确要求分阶段开启，不能把“支持滚动升级”理解为任意版本与参数都可混跑。

回滚点要提前定义：如果新程序还没改动不兼容格式，可按已验证流程退回；若已引入旧版本不理解的格式或功能，则可能需要从兼容备份恢复并重新核对外部状态。出现持续选举、同步失败、延迟越过预算或上层会话不稳就停止后续批次。依据是 [版本化管理指南](https://zookeeper.apache.org/doc/r3.9.5/zookeeperAdmin.html)，不在生产临时摸索降级可不可行。

## 事故推理：磁盘慢，为什么最后变成多套系统掉线

给你一条合成时间线：十四点事务日志设备延迟上升，随后未完成请求增加；十四点零二分多个客户端出现会话异常，上层调度器开始重选主；十四点零三分重连数量激增，数据库却没有先出现异常。初步假设是共享协调依赖变慢，但也可能是共同网络或宿主资源抖动，不能只凭第一条磁盘告警就直接结案。

收集证据按因果链展开：确认哪些上层系统使用同一 Ensemble，哪台当时是 Leader；核对成员的磁盘同步、CPU、GC、网络和请求积压；再看客户端在哪个时刻失去连接、收到过期、重新注册。Session 异常若只集中于某一台应用宿主，客户端暂停比全体服务端磁盘问题更可疑。日志时间要考虑时钟偏差，关键顺序还应参考服务端事务与事件信息。

先保住多数派和高风险动作边界，停止未经批准的自动化变更，限制无退避重连并减轻非关键发布压力。不要同时重启多台“清空积压”，也不要删除数据目录求快。修复可以是消除存储争用、恢复链路或处理明确的长暂停；每一种都需对应证据及回退方法，操作前明确影响哪些依赖和会话。

恢复验证应分层：成员角色稳定、真实读写探针成功、写延迟回落、客户端会话重新稳定、上层成员与领导权正确、任务没有漏执行或重复执行。仅 `ruok` 返回 imok 不覆盖这些条件。AIOps 可将这些信号组合成依赖故障事件，减少几百条上层连接告警，但自动化修复仍应限制权限、对象数量和审批边界。

## 递进面试参考答案

**30 秒用途回答**：ZooKeeper 保存少量协调状态，用树形节点、会话、监听和有序更新支持成员发现、配置与选主。它不执行应用任务；临时节点代表会话存续，普通读取不必然最新，业务旧主隔离还需要下游协议。

**3 分钟机制回答**：从三个调度器创建临时顺序节点说起，解释按顺序竞争与只监听前驱，再沿客户端、接入成员、Leader、事务日志、多数派确认和提交画写路径。随后说明断线可恢复原会话、过期需重新注册，最后用旧主暂停恢复的反例引出隔离令牌与业务幂等。以自己实际验证的 CAS 或监听实验收尾，不把离线模型说成经历过跨机房事故。

**追问一：断线就删除临时节点会怎样？** 会把短暂网络抖动都放大为成员退出和重新选主。会话超时是在故障发现速度与误判间取舍，增大能容忍更长暂停，也使真正故障后的资格释放变慢。继续追问“怎么选超时”，应从暂停分布、网络时延、业务切换目标和协商值出发，不背固定秒数。

**追问二：Watch 丢了怎么办？** 先确认监听类型、会话状态、重注册和回调积压；业务应重读当前状态并按版本收敛，不把通知当事件账本。继续问持久监听是否解决所有遗漏，应说明它改善订阅生命周期，不改变断线期间缺少完整历史这一事实。

**追问三：只有读成功，集群健康吗？** 不足以证明。普通读可由本地数据服务，写入需要多数派和稳定磁盘链路；要结合角色、投票成员可达性和受控读写探针。继续问四台比三台更安全吗，应计算两者都需在失去两台前保持多数派，并进一步讨论故障域而不是只比较数字。

**追问四：CAS 冲突以后重试几次？** 先重读数据并重新判断业务条件，不把删除版本检查当修复。操作可能已经成功但响应丢失时，需查业务请求标识或当前版本确认；无上限重试会增加竞争。继续问选主是否绝对互斥，应分别回答协调服务内部顺序与外部旧主执行的边界。

**设计题自测**：要求一个全局维护任务不能重复启动，能容忍一台投票成员和一台调度器分别故障。你应画出故障域、资格节点、重连状态、下游令牌检查和任务唯一约束，给出停止动作、恢复与回滚路径。若只能写出三台服务器地址，还没有回答任务安全性；若下游无法校验，必须诚实写出尚未解决的风险。
