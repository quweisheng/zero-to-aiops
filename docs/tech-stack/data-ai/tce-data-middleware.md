## 官方知识地图

```text
权威事务：TDSQL/MySQL 类 -> 用户、事件、配置、工单状态
加速读取：Redis 类 -> 热点缓存、会话、限流状态（须核对产品）
异步解耦：CKafka/Pulsar 类 -> 告警、日志、任务和事件流
检索分析：Elasticsearch 类 -> 日志全文检索、事件搜索
大对象/共享：COS/CFS/CBS -> 模型、附件、归档、卷和共享目录
计算分析：按 BOM 的流/批处理/数据开发能力

共同治理：身份 -> 网络 -> Schema（数据结构契约） -> HA（高可用） -> 备份 -> 监控 -> 升级
```

权威数据源是能回答“最终真相是什么”的系统；缓存是可重新构建的加速副本；消息连接状态变化；搜索索引为了查询优化，通常不应反过来当唯一业务真相。

## 场景开场

用户在数据库中把告警状态改为 ACKED，页面仍显示 OPEN；消息系统重复投递导致生成两个工单；搜索索引十分钟后才出现最新事件。

三个现象来自缓存一致性、消息幂等和索引延迟。逐个重启 Redis、消息和搜索不能解释数据应该以谁为准。

## 一句话人话版

数据库记正式账，缓存放常用复印件，消息负责通知，搜索建立快速目录，对象/文件保存大材料；设计者要规定它们不同步时听谁的、怎样补齐。

## 小白常问

### Redis 能不能当数据库？

Redis 有数据结构和持久化能力，但是否适合作为权威数据取决于产品形态、持久语义、备份和业务要求。AIOps 常用它做缓存、限流和短状态，不应因“快”就替换所有事务库。

### Kafka 和 Pulsar 都是消息，选哪个？

比较现场已交付能力、协议生态、Topic/分区/订阅语义、保留、运维、跨地域和团队经验。不要只比跑分，也不要假定 TCE 必然同时安装。

### Elasticsearch 为什么不能保存唯一工单？

搜索索引为查询和聚合优化，写入可能异步，映射和重建会变化。正式事务状态应有权威数据源，索引丢失可重建。

### 数据最终一致是不是“以后总会一致”？

必须定义触发、重试、幂等、最大延迟、失败队列和对账。没有机制与指标，“最终”可能永远不来。

## 为什么要学与解决的问题

平台级系统几乎不会只用一个存储。跨组件链路带来双写、重复、乱序、缓存陈旧和恢复顺序问题。学习目标不是记产品名，而是为每份数据定义所有者、复制方式、失败状态和恢复证据。

## 组件选择表

| 需求 | 首要候选语义 | 为什么 | 不能忽略 |
|---|---|---|---|
| 事件状态与用户权限 | 关系事务库 | 约束、事务、查询 | 热点、锁、备份和 Schema |
| 高频读取的规则摘要 | 缓存 | 低延迟、减数据库压力 | 过期、穿透、雪崩、一致性 |
| 告警异步处理 | 消息/流 | 解耦、缓峰、重放 | 重复、顺序、积压、保留 |
| 日志全文检索 | 搜索引擎 | 倒排索引和聚合 | 映射、分片、堆、磁盘水位 |
| 模型/附件/归档 | 对象存储 | 大对象、API、生命周期 | 哈希、权限、版本和恢复 |
| 数据库数据文件 | 块存储/产品后端 | 随机块 I/O | IOPS、延迟、一致性 |
| 多客户端共享目录 | 文件存储 | 文件/目录/锁语义 | 小文件、元数据、权限 |

“首要候选”不是固定答案，要结合数据大小、读写模式、延迟、RPO/RTO、安全和现场产品。

## 核心数据流：事务之后怎样通知其他系统

```text
API 请求
  -> 数据库事务：更新 incident + 写 outbox event
  -> 提交成功
  -> 发布器读取 outbox -> Message Topic
  -> 缓存失效/更新消费者
  -> 搜索索引消费者
  -> 自动化任务消费者
  -> 对账器检查数据库与派生系统
```

Outbox 是与业务数据同事务写入的待发布事件表，避免“数据库成功却没有留下待发事实”这类双写裂缝。它仍需要健康发布器才能真正送达。发布后可标记处理状态；即使消息重复，消费者仍按 event ID（事件编号）幂等。

另一种 CDC（变更数据捕获）从数据库日志识别变化，减少应用侵入，但要管理位点、Schema、权限和延迟。现场是否提供相关产品能力需核对 BOM。

## 权威库：一致状态和约束

关系库用于用户、配置、事件状态、审批等需要事务和约束的数据。表主键、唯一约束、外键/业务检查、索引和事务共同保护状态。

对外写 API 使用业务幂等键；提交超时后查询该键判断结果。数据库副本和备份不同，Schema 升级要兼容滚动发布。详见 [TDSQL-C MySQL](./tdsql-mysql.md)。

## 缓存：命中只是加速，不是真相

典型 Cache Aside：读缓存，未命中读数据库再写缓存；更新时先更新数据库，再让缓存失效。删除/失效也可能失败，需要重试和合理 TTL（生存时间）。

### 三类典型事故

- 穿透：大量查询不存在 key，每次都打数据库。可做输入校验、短期空值或过滤，但防止误判。
- 击穿：一个热点 key 到期，大量请求同时回源。可用请求合并/互斥更新和提前刷新。
- 雪崩：大量 key 同时到期或缓存整体失效。过期时间加入随机抖动、限流并保护数据库。

Redis Cluster 之类的分片/复制/持久化语义按实际产品。禁止把 `FLUSHALL`、全量 key 扫描作为常规排障；生产 `KEYS *` 可能阻塞。

观察命中率、请求/带宽、延迟、连接、内存、淘汰、热 key、大 key、复制和持久化。命中率高也可能返回旧数据，仍需业务正确性探针。

## 消息：至少一次世界里的幂等

消息负责解耦和缓冲，不能代替业务事务。Producer 确认、broker 持久化、Consumer 处理和 ACK 是不同阶段。

稳定 business/event ID、数据库唯一约束和处理记录帮助防重复；顺序通常只能在 key/partition 等有限范围保证。失败使用退避、重试 Topic 或 DLQ，并设置可观察的人工处理。

Kafka/Pulsar 机制见 [Kafka](./kafka.md) 与 [Apache Pulsar](./apache-pulsar.md)。选择前比较客户端协议、分区/订阅、保留、顺序、跨地域、运维能力和版本支持。

## 搜索：分片、副本和索引生命周期

Elasticsearch 类产品把文档建立倒排索引以支持全文检索和聚合。Index（索引）由 shard（分片）组成，replica（副本）用于可用性和读扩展。

分片太大恢复慢，太多则消耗堆和管理资源；映射字段爆炸会增加内存和元数据。日志按时间滚动并设置生命周期，比一个永不结束的大索引更可治理。

近实时搜索意味着写成功后可能有短暂不可检索窗口。索引来自权威数据或消息，可重建；更新映射、reindex（重建索引）和别名切换要有空间、版本兼容与回退。

观察索引速率、查询 P99、拒绝、JVM 堆、GC、磁盘水位、分片状态和重建。集群绿色不代表查询结果业务正确。

## 数据与对象存储

日志原文、模型、报告和附件适合按访问模式落对象/文件；数据库卷适合块语义。消息长期保留不一定是最经济归档，应按重放要求和对象存储设计分层。

模型发布使用内容哈希和版本化 key；上传完整并验证后，再原子切换元数据指针，避免消费者读到半成品。详见 [TCE 存储](../storage-data-protection/tce-storage.md)。

## 跨组件一致性状态

一次事件更新可能处于：数据库未提交、已提交待发消息、消息已发待消费、缓存已失效、搜索未更新、全部完成。每个中间状态都要有重试/对账和指标。

不要使用一个跨所有产品的“大事务”幻想消除所有失败。可用本地事务 + Outbox/CDC + 幂等消费者 + 对账修复，并向业务明确延迟窗口和失败展示。

补偿不是机械反操作，例如已发送通知无法真正撤回。应生成修正事件并保留审计。

## 高可用与容灾

每个组件的 HA 语义不同：数据库有主备/复制，缓存有分片副本，消息有分区/副本/游标，搜索有主分片/副本，对象有数据保护策略。多个“三副本”不等于跨组件业务可恢复。

DR 恢复顺序通常先网络/身份/时间，再权威数据库和对象，再消息/缓存/索引，最后应用和流量；实际依赖图决定顺序。缓存和搜索可重建，但重建会给数据库/消息带来巨大压力，要限速。

定义每层 RPO/RTO，消息恢复点与数据库恢复点必须协调，否则可能消费数据库不存在的事件或重复副作用。

## 容量与性能联动

一个流量峰值会同时增加数据库写、缓存回源、消息速率、搜索索引和日志量。容量模型以业务事件率为输入：

```text
数据库增长 = 事件率 × 行/索引字节 × 保留
消息空间 = 字节率 × 保留/积压窗口 × 副本开销
搜索空间 = 文档原始量 × 索引放大 × 副本 × 安全余量
缓存内存 = 热 key 数 × 平均对象大小 × 数据结构开销
恢复时间 = 积压量 ÷ (可持续处理率 - 新增速率)
```

每个公式都需实测修正，包含故障预留、扩容周期和重建开销。局部扩容可能把瓶颈推向下游。

## 安全与治理

按应用/环境分账号和网络，权限细化到数据库/Topic/index/bucket；凭据进入 Secret 管理，不写代码和镜像。传输加密、静态加密、密钥恢复、审计、保留和脱敏同等重要。

消息和日志可能包含账号、IP、SQL、告警内容；发送前分类，消费侧继续权限控制。测试环境不复制未经脱敏的生产数据。

## 配置与查询字典

| 项目 | 用途 | 验证 | 常见坑 |
|---|---|---|---|
| TTL | 缓存/消息/对象生存期 | 业务最大延迟与合规 | 过短丢恢复机会，过长占容量 |
| partition/shard | 并行与容量分片 | key 分布、热点、恢复 | 过多元数据开销，过少热点 |
| replica | 故障冗余 | 真正故障域和可恢复性 | 同域副本、误删同步 |
| eventId | 幂等和追踪 | 稳定唯一、可查询 | 用随机重试 ID 失去去重 |
| Schema version | 契约演进 | 新旧生产/消费兼容 | 忽略存量积压旧格式 |
| timeout/retry | 限制等待与短暂恢复 | 有界、退避、总预算 | 各层重试放大流量 |
| watermark | 此处指磁盘或队列容量阈值，不是流处理事件时间水位 | 趋势、重建和预留 | 只到 100% 才告警，或跨产品误解同名术语 |

## 基础实验：数据库、缓存、消息和索引的职责

### 前提与步骤

Python 3.10+；脚本只用内存，不联网、不写文件、不安装 TCE 产品。

```powershell
python examples/tce-data-middleware-lab/lab.py
```

脚本把事件写入数据库字典作为权威账，把副本放入缓存，通过队列通知搜索索引。预期 `result=PASS handled=1 duplicates=0 backlog=0`。

阅读代码后回答：若删除缓存能否重建？能；若删除数据库而缓存还在能否认为数据安全？不能；搜索应从哪里重建？从权威数据/可靠事件链。

若 Python 不存在，使用 `py -3`；不要为了脚本修改系统全局 PATH。它没有真实并发/持久化，只验证职责划分。

## 故障注入实验：重复消息

```powershell
python examples/tce-data-middleware-lab/lab.py --fault
```

故障模式把相同 `eventId` 入队两次。预期 `handled=1 duplicates=1`，搜索副作用只执行一次。消费者先检查稳定事件 ID，第二条被识别为重复。

这不是完整 exactly-once（精确一次）实现：去重集合只在内存，进程重启会丢。生产应把去重状态与副作用放在可恢复的一致边界，例如数据库唯一约束/事务，并定义保留窗口。

清理：脚本没有生成文件或服务。若输出不符，确认运行仓库当前版本，并检查是否自行改了 `eventId`。

## 生产模拟实验设计

在隔离测试租户中，用现场已交付组件实现一条小链路：数据库 Outbox -> 消息 -> 幂等消费者 -> 搜索；关闭消费者形成可控积压，再恢复并测数据库/搜索承载。

前提是审批、测试数据、容量上限和清理方案。记录业务/event ID、Topic/订阅、数据库事务、索引版本和各阶段时间。禁止用生产消息做故障注入，禁止清空 Topic/缓存作为实验清理。

## AIOps 观测与自动化边界

建立 service -> database/cache/topic/index/storage 的拓扑，使用业务/event/request/change ID 关联。统一看事务成功率、缓存陈旧/命中、生产/消费、backlog、搜索延迟、存储和最终业务一致性。

规则可检测“数据库提交正常但 Outbox 年龄增长”“消息消费正常但搜索未更新”。AI 提供候选链路和证据，不自动执行删订阅、清缓存、切数据库、跳消息、改生命周期等高风险动作。

## 升级与回滚

跨组件升级先明确兼容矩阵：TCE/产品服务端、客户端、协议、驱动、Schema 和操作系统。契约先向后兼容，再滚动消费者/生产者；数据库/索引迁移采用扩展-迁移-收缩。

保留旧索引别名、旧客户端兼容和可回放事件，备份权威库并真实恢复。回滚应用时要能读升级期间的新消息/数据；否则不是可回滚发布。

## 排障字典

| 现象 | 权威证据 | 可能问题 | 安全处置 |
|---|---|---|---|
| 页面旧数据 | DB、缓存版本/TTL、请求 ID | 缓存失效失败 | 定点失效/修链，不全量清缓存 |
| 重复工单 | event/business ID、消费记录 | ACK 不确定或重投 | 唯一约束、幂等、补偿 |
| 搜索缺记录 | DB/Outbox/Topic/消费/索引 | 任一阶段积压/失败 | 从断点重放并限速 |
| 全链路变慢 | 流量、连接、重试、下游 | 重试风暴或公共存储 | 限流、关局部重试、找共同依赖 |
| 磁盘同时上涨 | 消息积压、索引、日志、备份 | 消费停或保留错误 | 先止增长，保留业务证据 |
| DR 后状态冲突 | 恢复点、位点、event ID | 各组件恢复时点不一致 | 停止写入，按权威账对账 |

## 生产设计题

为 AIOps 事件中心选择数据库、缓存、消息、搜索和对象存储。要求接口 200 ms、事件可审计、附件保留 3 年、搜索可接受 30 秒延迟、消息至少一次。

答案应定义每类数据所有者、Outbox/CDC、幂等、TTL/保留、分片 key、Schema、索引重建、容量、跨 AZ、备份/DR、权限和观测。追问搜索故障能否继续受理事件：权威库/消息健康且降级设计允许时可以，页面明确搜索延迟。

## 事故题

## 老师带你做一张工单的“五本账”

先暂停背产品名称。我们一起画一张工单：数据库保存 `INC-001` 已被小王领取，这是正式账；缓存保存页面常读的工单摘要，这是快取账；消息记录“INC-001 状态变为 ACKED”，这是通知账；搜索保存便于按关键词查询的文档，这是检索账；对象存储保存排障截图，这是附件账。

学生：“五个地方都有数据，那究竟谁说了算？”老师：“先按字段说了算。领取状态由事务库负责，截图内容由对应对象及校验值负责，消息记录传递了什么，搜索负责快速找出候选。你要找领取结果，不能只问搜索；你要确认截图完整，不能只看数据库里有个文件名。”

给每份数据标上 `incident_id`、业务版本、事件 ID 和产生时间，就能把它们连起来。它们未必每秒完全相同，但你必须能回答：差的是哪一版，卡在哪一段，允许晚多久，谁负责补齐。这才是最终一致的工程含义。

### 双写裂缝为什么会出现

假设程序先更新数据库，再发布消息。第一步成功后程序退出，其他组件收不到通知。反过来先发消息再更新数据库，消费者可能读到根本不存在的新状态。调换顺序改变裂缝出现位置，不能消除两个独立系统之间的原子性问题。

Outbox 把业务数据和“必须发出的事件”放进同一个数据库事务。事务没提交，两者都不算数；事务提交，发布器最终能看到事件。发布器发送后还要标记已发送，网络异常可能使它不知道是否已经发送，所以事件仍可能重复。下游依赖稳定事件 ID 和幂等处理，将不确定结果收敛。

CDC（Change Data Capture，变更数据捕获）通过日志识别已提交变化，减少应用逐处埋点，但你依然要管理快照起点、日志位点、表结构演进、权限和断线追赶。只说“用了 CDC 就实时一致”不够：采集延迟、消息积压和下游更新都会形成时间差。

### 缓存课堂：读到旧值不总是因为忘了删除

我们按时间推理一次竞争。读请求 A 缓存未命中，从数据库拿到旧版本；写请求 B 更新数据库并删除缓存；A 随后把之前读到的旧版本写回缓存。即使 B 的失效动作成功，旧数据仍可能重新出现。

解决思路需要结合业务：短 TTL（存活时间）限制陈旧窗口；版本比较阻止旧版本覆盖新版本；对热点回源做请求合并；重要的写后读直接访问权威库。延迟双删也是有假设的策略，不是对任意网络延迟与执行时间的数学保证。老师希望你先画出竞争顺序，再讨论方案适用条件。

缓存重建速度也要受控。数据库每秒只能额外接受 2,000 次查询，缓存故障后每秒 50,000 次读取全部回源，会把本来健康的数据库压垮。应按业务优先级限流，合并相同键请求，必要时返回明确的短暂不可用或陈旧标记。错误地返回看似新鲜的旧审批状态，比提示延迟更难处理。

### 搜索课堂：能搜到与已经保存是两种证据

数据库提交后，事件经历发布、消费、转换、索引和可见性刷新，搜索才可能看到新文档。搜索接口查不到，先按同一业务 ID 查数据库，再查待发布事件年龄、消息位置、消费错误、目标索引和文档版本。这样能够把“丢数据”缩小成具体阶段的延迟或失败。

Mapping（字段映射）告诉搜索引擎把字段当文本、关键词、数值还是时间。把状态码当全文分词文本，精确筛选可能不符合预期；把日期当普通文本，范围排序可能错误。字段爆炸常来自把任意用户标签都动态展开成新字段，治理要规定字段合同、动态映射范围和索引生命周期。

重建索引时通常建立新版本、导入数据、追平增量、核对数量与抽样结果，再切换别名。Alias（别名）像对外固定门牌，后台可以指向不同索引版本；别名切换也必须验证写入路由和旧版本保留。只比较文档数不够，还要核对删除、更新版本、权限过滤和时间区间。

### 增强带练：用 SQLite 看到事务内幂等边界

前提是 Python 3 可用。下面代码仅使用标准库和内存 SQLite 数据库，不联网；它模拟消费端 Inbox（收件去重记录）与工单在同一个本地事务里，用于解释数据库约束的作用，不替代 TCE 产品压测。保存为自己学习目录的 `inbox_lesson.py`，运行 `python inbox_lesson.py`。它不是发送端 Outbox，两个模式的方向要分清。

```python
import sqlite3

db = sqlite3.connect(':memory:')
db.executescript('''
CREATE TABLE processed(event_id TEXT PRIMARY KEY);
CREATE TABLE tickets(id TEXT PRIMARY KEY, status TEXT NOT NULL);
''')

def consume(event_id, ticket_id, fail=False):
    try:
        with db:  # 两张表在同一事务提交或回滚
            db.execute('INSERT INTO processed VALUES (?)', (event_id,))
            if fail:
                raise RuntimeError('模拟写工单前进程异常')
            db.execute('INSERT INTO tickets VALUES (?, ?)', (ticket_id, 'OPEN'))
        return 'handled'
    except sqlite3.IntegrityError:
        return 'duplicate'
    except RuntimeError:
        return 'retry'

print(consume('event-001', 'INC-001', fail=True))
print(db.execute('SELECT COUNT(*) FROM processed').fetchone()[0])
print(consume('event-001', 'INC-001'))
print(consume('event-001', 'INC-001'))
print(db.execute('SELECT COUNT(*) FROM tickets').fetchone()[0])
db.close()
```

预期依次是 `retry`、`0`、`handled`、`duplicate`、`1`。第一次故意在两张表写入中间失败，事务回滚后去重记录也不存在，所以重试可以补建工单；第三次同事件被唯一约束识别为重复。正常实验去掉第一次故障调用，仍应得到一份有效工单。

这个示例简化了错误分类：真实系统不能把任何唯一约束错误都当成同一事件重复，还要查询是事件键冲突、工单键冲突还是数据契约错误。SQLite 内存数据库在退出后消失，生产必须使用可靠持久化和备份；实验没有消息 ACK，也没有外部工单接口。若输出不符，先确认事务块未被拆开、主键约束保留、两次使用相同事件 ID。清理只需删除自己新建的教学脚本，无服务或持久数据遗留。

### 全链路恢复课堂：每层单独恢复成功为什么还会错

数据库恢复到 10:00，消息恢复到 10:05，搜索恢复到 09:50，这三个局部结果都可能符合各自恢复操作，却没有共同业务时间点。消费者可能拿到数据库不存在的事件，搜索也可能缺少此前已提交修改。容灾方案需要规定权威恢复点与重放范围，并用事件 ID、版本和对账修补差异。

恢复时先保证网络、身份和时间服务，然后恢复权威数据及必要附件，再逐层恢复事件传播和派生索引。缓存和搜索重建都可能大量读取数据库，因此共享一份恢复流量预算。每提高一档消费者或重建并发，观察数据库 P99、连接排队、错误和净积压下降速度，超过停止条件就退回上一档。

一个可评审方案至少写出：哪一层可以降级、允许延迟多久、哪些操作必须停止、恢复依据是什么、如何防重放副作用、最后如何验证。AIOps 可以自动比较各层业务版本和积压年龄，生成候选断点；它不能靠组件全绿推断全链路账目正确。

## 现场架构课堂：先把资源、产品和业务身份对上

### 你看到的一个实例，可能只是服务的一层

控制台的一条数据库实例记录，可能包含代理、计算节点、存储和备份；一个消息集群也可能依赖独立元数据和对象存储。资源台账不能只记“名称、IP、CPU”。老师建议按服务实例编号、所属租户与项目、资源关联编号、可用区、版本、负责人、数据职责和恢复依赖分层记录，再与现场导出范围核对。

为什么特别强调关联编号？同名资源可能跨项目存在，地址可能因切换变化，展示名称也可能被重命名。用稳定 ID 才能把业务服务、数据库实例、备份策略与监控对象连起来。学习项目使用合成 ID；真实现场关联数据按权限保存在内部，不要把完整台账、授权文件和内网拓扑上传公开仓库。

TCE 是交付平台背景，不代表所有腾讯公有云产品在现场都已安装。产品目录说明可能有什么，BOM 和授权说明本次交付包含什么，控制台与实例清单说明当前可见什么，运行指标和业务连接再说明正在使用什么。四者有差异时要记录待核对项，不能用品牌名填空，也不能因为一个模块没有入口就推断该能力必定不存在。

### 权威不应被当成整张表唯一的答案

工单状态在数据库，附件二进制在对象存储，检索结果在搜索引擎，看似分工明确，但还需要规定对象删除和版本更新。数据库把附件标记删除后，旧事件若晚到又重建搜索文档，可能出现“已删除内容重新可见”。解决办法是传播删除标记和版本，消费者拒绝落后的事件，重建任务也遵守同一生效规则。

Tombstone（删除标记）是告诉下游“这个对象已被删除”的事实，不等于随时可以从所有地方清除其痕迹。保留多久取决于消息最长延迟、重放窗口、离线消费者和审计要求。若先删标记再回放更旧的创建事件，系统可能错误复活对象。删除链路与新增链路一样需要对账和验收，不能只验证新工单能搜到。

### 身份和权限也有同步一致性

假设员工已从某服务团队移出，但搜索索引或应用缓存仍保存旧权限，他可能短时间内读到不该读的内容。这说明最终一致不只影响页面新鲜度，还影响访问控制。权限判断尽量在可信服务端执行，缓存键包含必要租户与权限版本；权限撤销的容许延迟应单独定义，不简单沿用普通数据十分钟刷新策略。

把所有组件都使用同一个管理员账号接通，虽然入门容易，却破坏故障隔离。数据库读写、消息生产、消费、搜索读写、对象读取和备份管理应按职责分离。链路中某个账号被泄露时，明确它能影响哪些资源、怎样轮换、是否需要重建会话，以及哪些审计能证明被使用范围。密钥不能跟应用镜像或教学截图一起提交。

## 联动容量课堂：扩一个组件，可能压垮另一个

假设数据库每秒可额外承受三千次查询，缓存正常时每秒只回源五百次。搜索重建用了两千次，消息积压恢复又新增一千次，再叠加缓存节点故障，系统便超过预算。每个组件负责人看自己的资源都可能“还能扩”，但共同下游没有余量。恢复与扩容计划必须按整条依赖链分配预算。

预算不只是 QPS。平均查询两毫秒和两秒占用连接的时间差上千倍；小消息和大附件消耗的网络不同；索引重建还可能占用写入、磁盘与合并资源。先收集代表操作的耗时和大小分布，再估算同时恢复多少工作。用平均值做初算，用高分位、峰值与故障少一节点状态验证保守余量。

反压是让下游承载不足的信息回到上游，限流是主动限制接受或执行的速率。没有反压的链路会把等待转成越来越多的线程、连接和内存；没有有界队列的系统则可能从“请求慢”变成进程退出。按业务优先级保护关键工单事务，暂缓历史索引重建和非紧急分析，但必须让被延后的工作可追踪、可恢复，不能静默丢弃。

## 一次协调恢复的桌面演练

不用动任何生产系统，也能先训练恢复推理。准备一张合成记录表：工单 A 在 10:00 更新到版本 7，工单 B 在 10:02 更新到版本 3，数据库恢复点为 10:01，消息中还有 B 的版本 3，搜索只有 A 的版本 6。先问每条记录是否在权威恢复点内，再决定哪些事件可重放、哪些需要等待业务补偿。

A 的版本 7 已存在于恢复库，搜索缺一版，可以从权威记录重建；B 的版本 3 不在恢复点里，不能只因消息存在就直接把它认作已提交的当前业务状态。需要根据保存的提交证据、恢复策略和数据损失决策处理，而不是让消费者随意创造数据库没有确认的业务事实。演练的输出不是一个统一命令，而是逐对象的决策依据。

再加入重复事件和乱序事件：让 A 的版本 6 晚于版本 7 到达，预期索引版本不倒退；让同一事件出现两次，预期有效工单只有一份；让删除标记先到、旧创建后到，预期不复活对象。把这些情形写成消费端测试，有条件时再在隔离组件中执行。桌面推演并不证明真实产品的复制或恢复成功，它用于提前发现规则不完整。

恢复结束检查两个维度：数据是否符合选定的权威点与补偿规则，服务是否达到当前流量下的延迟和错误目标。某层完成重建但仍超过时延目标，属于恢复尚未完成；业务能查询但后台冗余未恢复，也需保留风险状态。对外报告分别说明已恢复服务、剩余积压、未完成冗余和数据差异，不用一个“全绿”混过去。

## 面试架构题的回答升级

“为什么不用强事务把五个系统锁在一起？”先解释跨系统强协调的延迟、可用性和运维成本，再按操作决定边界。工单领取和本地操作记录可同库事务，搜索可接受延迟更新，权限撤销与高风险动作需要更严格校验。最终一致不是放弃正确性，而是明确中间状态、收敛规则和超时处理。

“怎样证明十秒同步目标？”在同一事件上记录权威提交、发布、消息接收、消费提交、索引可见等时间，验证时钟与采样口径，分阶段观察延迟。超出目标时生成待对账记录，定位是哪一段，不只看消息中间件延迟。业务 ID 放日志与追踪，监控标签使用受控服务维度，避免每条工单制造一组无限增长的时间序列。

“升级先升哪个？”答案不是固定从左到右，而是根据契约兼容：先让消费者能读新旧格式，再变更生产者；索引新版本导入与追平后切别名；数据库结构采用可兼容过渡；旧客户端退出前不急着删旧字段。每一步都有业务验证和停止条件，最终回滚还要交代升级期间新增数据如何保留，而非只有旧镜像备份。

## 再做一次可复算实验：重复与乱序是两道题

稳定事件编号能识别同一个事件重投，但不能独自阻止旧状态覆盖新状态。假设工单版本七已经进入搜索，版本六因重试晚到；两个事件编号不同，所以去重表会认为它们都合法。如果消费者无条件覆盖，工单就倒退了。处理完整快照事件时，可以在同一个原子边界内比较业务版本，拒绝不比当前新的状态。处理“余额增加十元”这类增量事件则不能直接跳过中间版本，需要另一种顺序或补齐协议。

下面仅使用 Python 内存字典，保存为自己的 `version_order_lesson.py` 后执行 `python version_order_lesson.py`。它不连接 TCE，不模拟分布式锁，只验证单线程规则。先预测旧创建事件在删除之后到达时，是否会重新显示工单。

```python
states = {}
seen = set()

def consume(event):
    if event['id'] in seen:
        return 'duplicate'
    current = states.get(event['ticket'])
    seen.add(event['id'])
    if current is not None and event['version'] <= current['version']:
        return 'stale'
    states[event['ticket']] = dict(event)
    return 'applied'

new = {'id': 'a7', 'ticket': 'A', 'version': 7, 'deleted': False}
old = {'id': 'a6', 'ticket': 'A', 'version': 6, 'deleted': False}
deleted = {'id': 'a8', 'ticket': 'A', 'version': 8, 'deleted': True}
assert consume(new) == 'applied'
assert consume(new) == 'duplicate'
assert consume(old) == 'stale'
assert consume(deleted) == 'applied'
assert consume(dict(old, id='old-replay')) == 'stale'
assert states['A']['version'] == 8 and states['A']['deleted']
print('duplicate blocked; old version blocked; deletion retained')
```

预期最后保留版本八的删除标记，重复和旧版本分别被识别。故障注入可以临时去掉版本比较的两行，末尾断言应失败；恢复比较后再次运行，应通过。若删除后又出现旧工单，先检查是否只保留了去重集合、没有保存版本与删除标记。清理结束进程即可，没有文件数据和服务遗留。

不要把这个内存函数直接搬进多个生产消费者。真实并发中“读版本、比较、写结果”需要目标数据库的条件更新、事务或相应原子接口保护；去重状态与结果提交也需要一致边界。否则两个消费者各自读到旧版本，仍可能由最后到达的旧写覆盖新写。进程重启后的去重、版本和删除事实必须可恢复，事件保留期之外的重放策略也要明确。

## 把厂商能力核验变成具体交付问题

现场评审时，不问笼统的“支持高可用吗”，而问“哪种故障会触发谁决策的切换，旧角色如何隔离，客户端入口是否变化，已确认写入的损失边界是什么”。不同版本、产品形态和采购规格可能有不同答案。公开 [TCE 方案](https://intl.cloud.tencent.com/zh/solutions/tce?lang=zh) 只能说明平台定位，不能替代现场版本手册、授权清单和真实演练记录。

同样，不问“有没有备份”，而问最近一份备份覆盖哪些对象、保存在哪里、能否获得密钥、恢复到独立目标用了多久、恢复后应用校验是什么。对消息问保留与消费位置是否共同恢复，对搜索问能否从权威数据重建，对缓存问恢复期间怎样保护数据库。这些问题把五种产品拉回一条业务路径，避免各供应商都说正常而业务仍然不一致。

容量验收也需要共同场景。单组件空载测试达到吞吐，不代表带数据库、网络、搜索和鉴权的端到端链路达到目标。明确消息大小、热点比例、批量方式、并发、持久化和副本条件，再记录正常与少一个节点时的延迟和净追赶能力。没有现场测试权限时提交模型和待验证清单，不把课堂算术包装为厂商性能结论。

## 三分钟完整回答示范

“我先按字段确定权威源：工单状态归事务库，附件内容归对象存储，缓存和搜索是派生视图，消息负责传播变化。一次状态更新在本地事务里同时保存业务记录与 Outbox，发布器允许重发，消费者用事件编号和业务版本分别处理重复与乱序。删除也作为带版本的事实传播，不能只删除原文后就认为所有副本消失。”

“我监控从提交到派生可见的每段延迟，用积压年龄与业务对账判断链路是否收敛。恢复时先明确权威恢复点，再协调消息重放、索引重建和缓存回源，共享下游容量预算；恢复服务与恢复冗余分别报告。升级依据客户端和数据契约兼容矩阵，不固定照某个产品顺序操作。现场产品是否存在、支持什么能力，必须用 BOM、版本和交付证据核对，不能拿公有云目录代替。”
