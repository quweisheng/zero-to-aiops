# Apache Hive 深讲

> 学习目标：从零理解 Hive 如何把 SQL 转成分布式计算任务，能区分 HiveServer2、Metastore、执行引擎和底层存储的职责，能完成建表与聚合实验，能分析慢查询、元数据故障、小文件、分区、倾斜、事务和高可用问题，并能在面试中说明 Hive、Spark SQL、Trino 与传统数据库的边界。

## 老师先带你认路

今天我们不先背产品名，而是回答一个具体问题：昨天告警文件明明还在，为什么日报却是零？你只需先认识三件东西：文件保存实际记录；表结构规定每列的名字和类型；查询语句描述想从哪些记录中得到什么结果。SQL 是 Structured Query Language，即结构化查询语言，本文只用建表、筛选和计数；不熟悉时读 [SQL 入门](./mysql-sql.md) 的查询部分即可，不用先学完数据库运维。

接下来要用到的进程是正在运行的程序，端口是程序接收连接的入口，容器是带有独立运行环境的进程集合。[Docker 文章](../cloud-native/docker.md) 中的镜像、容器和端口映射足够支撑第一节实验。HDFS 是 Hadoop Distributed File System，即把文件块分布到多台机器保存的文件系统，详细机制见 [Hadoop](./hadoop.md)，本实验不要求你先建集群。

课堂选择 Windows PowerShell 加 Docker Desktop 的 Linux 容器，建议为实验预留至少四个逻辑核心、八 GB 可用内存以及十 GB 可用磁盘作为起步预算；这不是生产容量结论。镜像包含服务端运行环境，不要求宿主机另外安装 Java。你将先完成三行告警聚合，再观察分区清单和执行计划，最后区分“入口不可用”与“数据不存在”。没有 Docker 时可以先完成后文元数据纸面推演，但应把真实 SQL 验证保持为待办。

第一次读到入门实验和故障恢复即可停下来整理证据；第二次再研究事务、数据质量、容量和恢复设计。本文提供可复现步骤与预期结果，本轮文档修订没有启动 Hive，也没有验证多节点、事务恢复或生产性能，不把课堂说明写成实测经历。

## 场景开场

你有半年告警明细，数据已经按天落到 HDFS。直接用脚本遍历文件既慢又难维护，于是团队建了一张 Hive 表，让分析人员用 SQL 统计“每天哪个服务的严重告警最多”。

第二天查询突然从 3 分钟变成 40 分钟。CPU 没打满，HDFS 也没有坏。真正的问题可能是：查询没有分区裁剪、上游产生了几十万个小文件、Join 一侧数据严重倾斜、表统计信息过期，或 Metastore 响应变慢。

## 一句话人话版

`Hive = 给分布式文件和数据湖加上表、元数据和 SQL 能力，再把 SQL 编译成底层计算引擎能够执行的任务。`

## 小白可能会问

### Hive 是数据库吗

它有 Database、Table 和 SQL，但通常不负责像 MySQL 那样自行保存每一页用户数据。表数据主要在 HDFS、对象存储或表格式中，Hive 保存和使用元数据，并协调计算引擎完成查询。

### Hive 查询为什么不是毫秒级

传统 Hive 面向大规模分析吞吐，查询可能需要生成任务、申请资源、扫描大量文件和执行 Shuffle。它不是为高并发单行点查设计的。低延迟交互分析要结合数据规模、缓存、文件格式和其他引擎选型。

### 分区是不是自动把数据分到不同机器

Hive Partition（分区）通常对应目录层级，例如 `dt=2026-07-23`。它首先解决查询裁剪和数据管理问题，不等于 HDFS 副本放置，也不等于 Spark/Flink 的运行时分区。

### Hive 和 Spark SQL 是什么关系

Hive 提供 SQL 语义、Metastore 和表管理生态；Spark SQL 是 Spark 的结构化计算模块。Spark 可以读取 Hive Metastore 中的表，但二者的执行引擎、会话、缓存和调优方法不能混为一谈。

## 为什么要学

- 运维日志、告警、审计和历史指标常以文件或数据湖表长期保存。
- Hive Metastore 已成为许多计算引擎共享的表目录服务。
- 分区、列式格式、统计信息和小文件治理直接决定数据平台成本。
- AIOps 离线特征、告警趋势、容量预测和复盘报表常需要大规模 SQL。
- 面试会连续追问查询路径、分区裁剪、Join、倾斜、Metastore、ACID 和高可用。

## Hive 是什么

Apache Hive 是面向分布式数据的 SQL 数据仓库系统。用户提交 HiveQL 后，Hive 解析 SQL、查询元数据、生成逻辑和物理计划，再交给执行引擎读取底层数据并返回结果。

Hive 主要解决：

1. 用表和列描述原本只是目录与文件的数据。
2. 用 SQL 代替大量手写 MapReduce 程序。
3. 通过分区、统计信息和列式格式减少扫描成本。
4. 用 Metastore 让多个引擎共享表结构和数据位置。
5. 为批处理、ETL、数据湖和离线分析提供统一入口。

Hive 不适合替代高并发 OLTP 数据库，也不能自动保证上游数据质量、HDFS 高可用或对象存储的一致性。

## 核心组件

这里的 JDBC 是 Java Database Connectivity，即 Java 程序连接查询服务的接口；ODBC 是 Open Database Connectivity，即另一类通用数据库访问接口。Thrift 是组件之间交换请求与响应的远程调用协议。不要因为名称带 Database 就认为连接一定直达保存业务行的数据库。

| 组件 | 人话解释 | 重点证据 |
|---|---|---|
| Beeline | 用户执行 Hive SQL 的命令行客户端 | JDBC URL、退出码、查询日志 |
| HiveServer2 | 接受 JDBC/ODBC 会话和 SQL 的服务端 | Session、Operation、编译与执行日志 |
| Hive Metastore | 保存库、表、列、分区、位置和统计信息 | 元数据库、Thrift 延迟、Schema 版本 |
| Driver | 管理查询生命周期 | Query ID、状态、错误阶段 |
| Compiler | 解析 SQL 并生成计划 | 语法、语义、EXPLAIN |
| Calcite CBO | 基于代价和统计信息优化计划 | 行数、NDV、Join 顺序 |
| Execution Engine | 真正运行分布式任务 | Tez/YARN DAG、Container、Counters |
| SerDe | 在文件字节与表中行列之间转换 | 格式、分隔符、Schema |

## 查询数据路径

```text
Beeline / BI / JDBC Client（命令行、报表或应用客户端）
  -> HiveServer2（查询服务）建立认证会话
  -> Driver（查询生命周期协调者）接收 SQL 并分配 Query ID（查询标识）
  -> Parser / Semantic Analyzer（语法解析与语义检查）验证语句和对象
  -> Metastore（元数据服务）返回表、分区、位置和统计信息
  -> Optimizer（优化器）生成物理计划并选择关联和扫描策略
  -> Tez（执行引擎）经 YARN（集群资源管理器）申请资源并运行 Task（计算任务）
  -> Task（计算任务）从 HDFS/对象存储读取 ORC/Parquet 等文件
  -> Shuffle（按键重分布中间数据）、Join（表关联）、Aggregate（聚合）、Sort（排序）
  -> 结果返回 HiveServer2，再返回客户端
```

排障时先确定慢在哪一段：连接、编译、Metastore、排队、扫描、Shuffle、写结果还是返回客户端。只看 HiveServer2 进程存在没有意义。

图中箭头表示查询推进与数据读取的先后关系，不表示所有业务文件都经 Metastore 转发。元数据服务给的是“去哪儿读、怎样读”，工作任务才去存储取数；YARN 负责分配资源，不负责解释 SQL。官方资料中的历史 Hive-on-Spark 设计也不能推导出任意 Hive 4.x 与 Spark 版本能直接搭配，本篇不让读者用一个配置开关替代兼容性核验。

## 元数据与状态

Hive 至少有四类状态：

| 状态 | 保存位置 | 常见风险 |
|---|---|---|
| 表定义与分区 | Hive Metastore 后端数据库 | Schema 不兼容、分区未注册、连接池耗尽 |
| 数据文件 | HDFS/对象存储 | 路径误删、权限错误、小文件、延迟可见性 |
| 查询运行状态 | HiveServer2 与执行引擎 | 服务重启、队列等待、任务失败 |
| ACID 事务状态 | Metastore 事务表和 delta/base 文件 | Compaction 积压、锁等待、Write ID 异常 |

Metastore 备份不等于数据备份，HDFS 快照也不自动包含外部元数据库。恢复设计必须同时覆盖元数据、数据和权限。

## 表、分区与文件格式

### Managed Table 与 External Table

- Managed Table：Hive 管理表生命周期，删除表可能同时删除数据，具体行为受版本和表格式影响。
- External Table：Hive 主要管理元数据，数据生命周期通常由外部系统负责。

生产执行 `DROP TABLE` 前必须确认表类型、Location、对象存储版本控制和回收策略，不能凭“External 一定不删数据”做高风险判断。

### Partition

分区把数据按业务维度组织到不同路径。告警明细常按 `dt` 或 `hour` 分区：

```text
/warehouse/alerts/dt=2026-07-22/
/warehouse/alerts/dt=2026-07-23/
```

查询带 `WHERE dt='2026-07-23'` 时，优化器可以只扫描一天。若在分区列上套无法下推的函数，可能失去裁剪。

### Bucket

Bucket（分桶）按哈希把行分到固定数量文件。它可辅助采样、Join 或文件组织，但只有写入过程真正遵循分桶规则才有意义。声明了 `CLUSTERED BY` 不代表历史文件自动重排。

哈希可以理解为根据字段值算一个分配编号，但不是每个不同值各分一桶；很多值会落在同一个桶。因此分桶不能保证一个热门服务被均匀拆开，也不能和日期分区互相替代。使用分桶前先确认目标查询或采样能获得收益、写入方遵守同一哈希与桶数约定，再检查建表定义、实际文件布局和执行计划。若关联没有减少交换，先核验两侧桶布局与当前引擎优化条件，不通过反复修改表声明来伪装已有文件满足规则。

### ORC 与 Parquet

二者都是列式格式，适合只读取部分列、压缩和谓词下推。选择要考虑引擎兼容、Schema 演进、统计信息、压缩、生态和实际压测，不能只背“谁更快”。

### 第一课：表是说明书，文件才是原料

先在纸上画三个格子：表定义、分区条目、数据文件。表定义中有列类型、文件解释方式和默认位置；某个分区条目可以指定自己的位置，不必机械地等于表根目录拼接分区名。实际文件里有记录，但通常不会保存虚拟分区列的同一份内容。读者因此要沿着元数据记录的实际路径检查，不能根据一个看起来合理的目录名猜测结果。

为什么要拆开？因为同一批历史数据可能由不同引擎读取，数据搬到另一套存储时也不一定需要改变分析人员眼中的表名。代价是两套状态需要协调：只复制文件没有完成分区登记，目录存在却可能查不到；只建分区没有放好文件，则会出现空结果或者存储错误，表现取决于读取路径和引擎行为。这里不是“一定报错”或“一定为零”的单选题。

现在预测：把表的列名改了，原文件里的文字会自动改变吗？不会。改列名主要改变解释方式；改列类型还可能让某些旧字节无法按新规则读取。Schema 即数据结构约定，Schema evolution 即结构随版本演进。给一列从整数扩展为更宽类型、修改列顺序、删除列，各自是否兼容，要结合文件格式、按名称或按位置映射方式和读取引擎验证，不能把元数据修改误当成数据转换。

现场看法很具体：先保存表的完整建表语句，再看分区级详细描述，最后只读检查目标路径的文件数量、大小和权限。异常时对照同一天的正常表，而不是先删表重建。若存在表格式协议，由该协议决定文件可见性，目录里能看到一个文件也不等于它已经提交为有效数据。外部表的意义是生命周期责任分离，不是备份或防删除保险；Hive 4 的外部清理属性可以改变删除行为，必须检查属性和存储保留策略。[DDL 生命周期说明](https://hive.apache.org/docs/latest/language/languagemanual-ddl/#external-tables)

### 第二课：三种裁剪发生在不同位置

我们把“只统计昨天严重告警的服务名”拆开。分区裁剪先减少需要访问的目录；列裁剪只读取需要的列，避免把长日志正文也搬进计算；谓词下推把过滤条件交给文件读取层，可能利用文件内部统计跳过不符合条件的数据段。这三件事分别减少目录、列和行组层面的工作，不是给表加一个传统数据库索引。

ORC 中的 stripe 是一组按列组织的数据条带，Parquet 中的 row group 是行组。它们都有用于定位和跳读的内部信息，但不能把各自名词相互替换。若一个数据段的级别最小值和最大值已经排除了目标条件，就可能跳过；如果各种级别混杂在每个数据段里，虽然条件可以下推，实际能跳过的数据仍可能很少。是否生效要看扫描字节和读取器指标，不是只看文件扩展名。

为什么日期字段要直接写条件？优化器容易根据分区值确定要访问哪些目录。若只过滤事件时间列，而日期分区列没有条件，引擎未必能推导两者关系；若用了自定义函数，优化器可能看不懂它。先把业务日期范围明确写到分区字段，再检查执行计划中的目标分区，最后用扫描字节验证。注意“补日期条件”必须保留原来的业务语义：跨午夜、时区变化、迟到记录都会让事件时间与入仓日期不同。

课堂检查可以只做计划，不急着扫描大表。把同一查询分别写为有日期、无日期和日期列套函数三个版本，记录计划差异；函数版本是否仍裁剪由版本和表达式决定，不预设它一定失败。生产需要先用可控分区做运行对照，避免为了证明无裁剪很慢而真的读一整年数据。

### 第三课：文件小，为什么反而更费资源

把一 GB 数据做成两个文件与做成十万个文件，总字节相同，系统工作量却不同。每个文件需要发现、打开、读取元信息和关闭，规划器还要把文件组织成任务。HDFS 的 NameNode 保存文件系统元信息，小文件会增加它的对象负担；对象存储则还有列表、读取请求与限流成本。许多短任务消耗在准备而不是读取正文，平均 CPU 因而不一定很高。

首先统计一个专用分区的文件数和文件尺寸分布，比较增长发生在何时；再看上游批次频率、并行写入数及失败重试。假如每分钟向一万个低流量服务分区写一小份数据，单纯把读取任务合并只能暂时缓解，持续制造小文件的写入设计没有改变。可以降低分区维度、在时效允许范围内积攒批次，或给热点和冷门数据采用不同落盘粒度。

文件合并也有成本：重读、重写、额外临时空间和下游可见性切换。普通非事务表重写分区、Hive ACID 整理、Iceberg 表维护不是同一种命令。先识别表协议，再让对应引擎按协议完成；不要用操作系统直接把 ORC 或 Parquet 二进制文件拼接，它们有各自的头尾和内部索引。合并验收需要总行数、业务键与核心汇总不变，以及文件数和查询资源确实下降。

### 第四课：统计信息不是事实本身

优化器选择方案前需要估计处理多少行、每行多宽、一个字段有多少不同值。统计信息相当于规划时可用的样本说明，CBO 即 Cost-Based Optimizer，意为根据估算成本选择执行计划。它需要这些信息来决定先关联哪两张表、是否适合把小表复制到工作节点，但写入增加十倍后旧统计可能仍描绘昨天的规模。

例如服务目录原本几百行，某次上游改成保留所有历史版本，关联行数就可能成倍膨胀。即使优化器选择正确，业务上多对多连接也会制造巨量结果。因此排查先做连接键唯一性与过滤条件检查，再谈更新统计。统计正确不代表 SQL 正确，广播失败也不必然意味着广播阈值太小。

在专用实验库中，可用下面语句学习统计入口。它会实际读取目标分区来计算信息，只有确认范围和资源预算后才执行；大表不要随手改成全表。收集之后保存新旧计划，查看估算是否更符合已知的三行样本，运行性能仍需另外证明。

```sql
ANALYZE TABLE aiops.alerts PARTITION(dt='2026-07-23')
COMPUTE STATISTICS; -- 只收集本课日期分区的基本统计
SHOW CREATE TABLE aiops.alerts; -- 保存列、分区和表属性的完整定义
DESCRIBE FORMATTED aiops.alerts PARTITION(dt='2026-07-23');
```

最后一条查询的目的不是输出越多越好，而是明确这一分区到底指向哪里、使用什么存储描述。若用户看不到位置，先检查权限，不借管理员身份绕过治理。统计信息还能进入 AIOps：同一表扫描字节突然激增、估算与实际偏离扩大，都可触发调查，但不应自动修改表定义。

## SQL 与 DDL 入门

```sql
CREATE DATABASE IF NOT EXISTS aiops;                         -- 创建 aiops 数据库；已存在时不报错

CREATE TABLE IF NOT EXISTS aiops.alerts (                    -- 创建告警明细表
  service_name STRING,                                       -- 服务名称，例如 order-api
  severity STRING,                                           -- 告警级别，例如 critical
  created_at TIMESTAMP                                       -- 告警产生时间
)
PARTITIONED BY (dt STRING)                                    -- 按日期分区，查询时用 dt 裁剪目录
STORED AS ORC;                                                -- 使用 ORC 列式格式保存数据

INSERT INTO aiops.alerts PARTITION (dt='2026-07-23')          -- 把数据写入指定日期分区
VALUES
  ('order-api', 'critical', TIMESTAMP '2026-07-23 09:00:00'),
  ('pay-api', 'warning', TIMESTAMP '2026-07-23 09:05:00'),
  ('order-api', 'critical', TIMESTAMP '2026-07-23 09:10:00');

SELECT service_name, COUNT(*) AS alert_count                 -- 按服务统计告警数量
FROM aiops.alerts                                             -- 从告警表读取数据
WHERE dt = '2026-07-23'                                      -- 只扫描目标日期分区
GROUP BY service_name                                        -- 每个服务独立聚合
ORDER BY alert_count DESC;                                   -- 最吵的服务排在前面
```

预期 `order-api` 为 2，`pay-api` 为 1。若结果为空，先检查当前数据库、分区是否存在、数据 Location 和文件权限。

## EXPLAIN 怎么看

```sql
EXPLAIN FORMATTED
SELECT service_name, COUNT(*)
FROM aiops.alerts
WHERE dt = '2026-07-23'
GROUP BY service_name;
```

重点看：

- 是否只访问目标分区。
- TableScan 读取哪些列和文件。
- 聚合是否分成局部与全局阶段。
- 是否产生 Shuffle/Exchange。
- Join 顺序和 Join 类型是否合理。
- 估算行数是否明显偏离真实数据。

EXPLAIN 是计划，不是运行证据；还要结合执行 DAG、Counters、扫描字节和阶段耗时。

## 入门实验：HiveServer2 与分区聚合

### 实验边界

只使用本机 Docker 和临时容器，不连接生产 Metastore，不挂载生产数据。官方镜像标签会变化；执行前到 Hive 下载页核对当前版本。

### 启动

```powershell
docker run --detach `
  --name hive-lab `
  --publish 127.0.0.1:10000:10000 `
  --publish 127.0.0.1:10002:10002 `
  --env SERVICE_NAME=hiveserver2 `
  apache/hive:4.2.0

docker logs --follow hive-lab # 看到 HiveServer2 启动完成后按 Ctrl+C 退出日志跟随
```

### 进入 Beeline

```powershell
docker exec -it hive-lab `
  /opt/hive/bin/beeline -u 'jdbc:hive2://localhost:10000/default'
```

`-it` 会为 Beeline 分配交互终端。Hive 4.2.0 镜像中的 JLine 在无终端批处理环境里可能报 `Unable to create a terminal`；自动化脚本可使用 `docker exec -t` 配合 Beeline 的 `-f` 文件参数，并始终检查退出码。

启动前先用 `docker ps -a --filter name=hive-lab` 检查是否已有同名对象；如果有，先确认归属，不覆盖或删除他人的容器。参数中的名称只标识本课容器，两个端口分别供 SQL 和服务页面使用，回环绑定使它们仅从本机访问。该快捷环境使用嵌入式元数据配置，不代表生产已实现 Metastore 高可用。出现首次初始化错误时保存日志，不要把生产元数据库地址填进实验命令试图解决。

在 Beeline 中执行前面的建库、建表、写入与聚合 SQL，再执行：

```sql
SHOW PARTITIONS aiops.alerts;                                -- 应看到 dt=2026-07-23
DESCRIBE FORMATTED aiops.alerts;                             -- 记录表类型、格式和 Location
```

### 验证

保存三类证据：聚合结果、`SHOW PARTITIONS` 输出和 `DESCRIBE FORMATTED` 中的 Location。三者分别证明 SQL、元数据和数据位置正常。

### 如果没成功

1. `docker version` 是否同时显示 Client 和 Server。
2. `docker logs hive-lab` 是否有 Metastore Schema 或端口错误。
3. `Get-NetTCPConnection -LocalPort 10000` 是否存在冲突。
4. Beeline JDBC URL 是否写成容器内的 `localhost:10000`。
5. 镜像标签是否仍存在，代理是否允许访问 Docker Hub。

## 故障注入实验：停止 HiveServer2

### 建立基线

先确认 `SELECT COUNT(*) FROM aiops.alerts;` 能返回 3，并保存时间和 Query ID。

### 注入故障

```powershell
docker stop hive-lab # 仅停止本地实验容器
Test-NetConnection localhost -Port 10000 -InformationLevel Quiet
```

端口探针预期返回 `False`，同时 `docker ps -a --filter name=hive-lab` 应显示 `Exited`。如果宿主机或另一个客户端容器已安装 Beeline，也可再次连接并保存连接拒绝或超时；不要在已停止的 `hive-lab` 内执行 `docker exec`，那只能证明容器已停止，不能产生 JDBC 客户端证据。

### 假设、修复与验证

假设是 HiveServer2 不可用，而不是表被删除。执行：

```powershell
docker start hive-lab
docker logs hive-lab | Select-Object -Last 80
Test-NetConnection localhost -Port 10000 -InformationLevel Quiet
```

等待端口探针恢复为 `True`，再连接并查询 `COUNT(*)`。如果数据仍为 3，说明本次故障影响服务可用性，没有破坏实验数据。生产环境还要验证负载均衡摘除、会话重连、执行中查询和 Metastore 是否独立可用。

### 清理

```powershell
docker rm --force hive-lab # 删除本地实验容器；不要对生产容器照搬
```

## 性能与容量

### 小文件

每个文件都带来 NameNode 元数据、对象存储请求、任务调度和打开文件成本。治理顺序：先定位上游为什么产生小文件，再通过合理分区、批量写入、Compaction 或重写合并，最后验证扫描文件数和查询耗时。

### 分区数量

分区太粗会扫描过多，太细会放大 Metastore 对象数和文件数。按查询条件、写入频率、保留策略和单分区数据量设计，不要机械地“按小时分区”。

### 数据倾斜

某个 key 占据大部分行时，一个 Reducer/Task 会成为长尾。证据包括单 Task 输入远高于平均值、Shuffle Read 集中、阶段迟迟不结束。修复可能是过滤异常值、预聚合、Map Join、拆分热点或加盐，必须验证结果语义。

### 统计信息

过期统计信息会让 CBO 误判表大小、NDV（Number of Distinct Values，不同值数量）和 Join 顺序。收集统计前评估扫描成本，收集后对比 EXPLAIN，不要把 `ANALYZE` 当万能调优。

## ACID 与 Compaction

Hive ACID 使用事务元数据、Write ID、base/delta/delete_delta 文件和 Compaction 协作。它能支持行级变更，但会引入更多文件、锁、事务清理和兼容性要求。

排查 ACID 表：

1. 确认表属性和客户端是否支持事务。
2. 查看 open/aborted transaction 与 lock。
3. 查看 Compaction 队列、失败记录和 Worker。
4. 检查 delta 文件数量、Metastore 和存储权限。
5. 修复服务和配置后再决定是否重跑 Compaction，不能直接删除 delta。

### 事务课堂：文件写完为什么还不能随便读

事务是把一组修改当作受规则约束的一次提交；ACID 分别要求原子性、一致性、隔离性、持久性。这里的一致性不是承诺源日志真实，也不是说所有引擎在任何时候看到完全相同的目录，而是事务操作必须遵守表协议。Hive 的事务管理器跟踪事务状态，表内写入标识帮助读取者判断哪些修改在自己的读取视图里有效。

先想一个更新严重级别的例子。旧文件中有原始记录，写入者可能生成插入或删除相关增量，读取者依据有效写入集合合并这些内容，而不是看到哪个文件修改时间最新就相信哪个。正在运行、已中止和已提交的写入需要区分，否则报表可能读到半次修改。文件存在只说明有字节，事务提交才赋予相应可见性；给目录手工塞一个文件绕过了这个协议。

整理的目的，是减少读一次表需要合并的增量数量。Minor compaction 即小整理，侧重合并增量；Major compaction 即大整理，把基础与增量整理成新的基础布局。整理写新文件与清理旧文件不是同一时刻：旧读取者可能仍需要旧版本，清理器需要确认它们不再被引用。还有重平衡整理等版本相关能力，其锁和并发影响不能套用普通大小整理的结论。[官方事务与整理机制](https://hive.apache.org/docs/latest/user/hive-transactions/)

课堂先看状态，不安排直接删除文件的“实验”。在有权限的隔离事务集群里，`SHOW TRANSACTIONS` 查看事务是否长期未结束，`SHOW LOCKS` 看谁在等待资源锁，`SHOW COMPACTIONS` 区分等待执行、执行失败和等待清理。若整理任务完成而空间未释放，调查老查询、事务心跳、清理器权限和存储删除失败；不能根据“整理成功”就手删旧增量。若任务尚未启动，先查整理工作进程和执行队列，盲目增加整理频率反而会放大争用。

并非每张 ORC 表天然支持完整行级修改，也不是加上事务属性就能保证所有外部引擎都按同一协议读写。托管方式、事务属性、存储格式、引擎连接器及具体版本共同决定能力。上线前用专用样本验证写入、更新、中止后的读取和并发可见性，把读取兼容与写入兼容分别列项。只追加的日志原始层通常没有必要为了一个展示修正频繁更新所有历史记录，可以保留原始层并在加工层管理修订。

## 数据质量课堂：日报正确比查询成功更重要

现在给报表设一个数据合同：每条告警需要稳定事件标识、服务名称、级别、事件发生时间和采集入仓时间。事件标识用于识别重复，两个时间分别说明“什么时候发生”和“什么时候到达”。如果源头没有可靠标识，不应随意把同一秒同一服务当作同一事件去重；那可能把真实的两次故障合并掉。字段合法性、唯一性和来源覆盖率需要单独核验。

假设昨天二十三点五十九分产生的告警，今天凌晨一点才送达。按事件日期分区时需要补写昨天；按入仓日期分区时查询昨天业务事件就不能只读昨天入仓分区。老师会先让你画时间线，再决定查询范围。技术选型不能代替业务确定口径：日报究竟是截止八点已知的事实，还是允许后续修订的最终事实？两者应有不同的版本与水位记录。

稳妥的离线流程是先落不可变原始批次，再校验、隔离坏行、加工目标日期、检查覆盖率，最后发布报告版本。迟到修订必须记录影响日期和输入批次，避免今天重跑昨天时把旧报告静默覆盖。若选择覆盖加工分区，需要有批准的发布窗口与旧版本恢复点；若选择追加修订记录，查询端必须理解如何选有效版本。Hive 本身不会替你判断哪个业务修订是真相。

数据质量也进入 AIOps 告警链。空服务比例突然上升可能是解析器变更，行数下降可能是源头缺报，重复率上升可能是重试失控，事件到达延迟变大可能是队列积压。把这些信号与查询耗时分开看：系统很快地算出一个错误报表，不是成功。报告发布门禁可以要求关键源齐全、坏行低于明确阈值、总量守恒，并保留人工放行原因。

## 生产高可用与容量设计：从二十 TB 推回时间预算

前面的系统设计题不能只回答“部署双节点”。先明确二十 TB 是未压缩原始量还是实际读取量，计算链有几次扫描和重写，凌晨什么时候数据齐全，八点截止前还有多久可计算。若只剩四小时，单次扫描二十 TB 的平均有效吞吐就约需每秒一点四 GB；这只是理想下界，不包含关联、重分布、失败重算或多份报表。用真实格式的样本压测补齐放大系数，再设计队列配额和余量。

存储预算同样分层：原始数据保留、压缩后的加工层、冗余副本或纠删码、重写临时空间、备份和失败批次不能只算一遍。重算会同时消耗读带宽和写空间，容量接近极限才启动全量整理可能扩大事故。按数据增长率提前安排保留策略，但删除前必须确认下游模型训练、审计和恢复窗口，没有“超过某天就都能删”的通用规则。

高可用要按故障域逐层解释。两台查询入口能帮助新会话找到可用服务，却不意味着旧会话和执行中查询自动迁移；多个元数据服务若共用一个没有恢复能力的数据库，仍有数据层单点。后端数据库切换后需要验证连接池重连、读写一致性和事务表状态。把入口、元数据、计算资源、存储、身份服务部署在同一个会停电的区域，也不能因为进程数很多就宣称容灾。

升级回滚需要给出两个时间点：停止旧版本写入的时间，以及新版本开始改变元数据库或文件协议的时间。若只替换可兼容的服务程序，回退旧制品较简单；若已经升级元数据库结构或生成旧版本不能读取的数据，回滚就涉及恢复点、停写窗口和增量对账。先在数据库备份副本上演练升级及恢复，再固定输入做影子查询，比较结果、权限、计划和耗时。影子查询输出独立目录，不能与正式任务竞争发布同一份日报。

权限设计也要沿数据路径检查。只读分析人员通过查询服务访问允许的表，不应同时拥有仓库文件的任意写权限；服务身份需要的存储权限也不等于允许用户自由指定所有外部位置。UDF 是用户自定义函数，可以加载执行代码，因此上传依赖包是代码执行授权，不只是上传数据。审核授权时要同时测试“允许的查询成功”与“禁止的直读和导出被拒绝”，并保存脱敏审计证据。

### 将设计落实为独立检查项

- HiveServer2 多实例放在负载均衡后，健康检查要验证可登录和执行轻量 SQL。
- Metastore 多实例共享受支持的高可用后端数据库；服务无状态不代表数据库无状态。
- 元数据库做备份、PITR 和恢复演练，并与数据快照保持恢复点关系。
- YARN/Tez、HDFS、ZooKeeper、Kerberos/KDC 也要有各自的 HA 设计。
- 查询历史、审计和日志进入独立可观测平台，避免服务故障时证据一起丢失。

## 安全

- Kerberos 解决“你是谁”，Ranger/Sentry 类策略解决“你能访问什么”；具体能力取决于发行版。
- HiveServer2 禁止匿名公网暴露，启用 TLS、强认证和最小权限。
- 表权限之外还要检查 HDFS/对象存储权限，避免绕过 SQL 直接读文件。
- UDF、`ADD JAR`、外部表 Location 和导出路径需要管控。
- SQL、审计日志和查询结果可能含账号、路径和业务数据，进入 GitHub 前必须脱敏。

## 可观测性与 AIOps

### 关键指标

- HiveServer2 活跃/排队 Session 与 Operation。
- SQL 编译时间、执行时间、成功率和取消率。
- Metastore 请求延迟、错误率、连接池使用率。
- YARN 队列等待、Container 失败和 Tez DAG 阶段耗时。
- 扫描字节、扫描文件数、Shuffle、输出行数和长尾 Task。
- ACID open transaction、aborted transaction、Compaction backlog。

### 关联模型

```text
query_id + user + queue + database + table + partition
  + hs2_instance + metastore_instance
  + yarn_application_id + tez_dag_id
  + deployment_id + config_version
```

这组加号表示关联字段组合，不是数值相加。`query_id` 是查询标识，`user` 与 `queue` 是提交用户和资源队列，`database/table/partition` 指库、表及分区；两个实例字段定位查询入口和元数据服务。`yarn_application_id` 与 `tez_dag_id` 连接资源申请和执行任务图，部署标识与配置版本则帮助比较变更前后。同一告警不必收集所有字段，只留最小必要、可脱敏关联的证据。

AIOps 可以基于这些字段识别慢查询模式、元数据热点、文件数异常、数据倾斜和变更回归，但自动 Kill 查询、改队列或重写表都需要审批、影响评估和回滚。

## 常见故障排查

### 无法连接 HiveServer2

按 DNS/TCP/TLS/Kerberos/JDBC URL/HiveServer2 进程/负载均衡顺序检查。连接失败与 SQL 执行失败不是同一层。

### 查询长期排队

看 YARN Queue 容量、用户配额、AM 资源、并发限制和上游大作业。不要仅重启 HiveServer2，因为任务可能根本没获得资源。

### 查询突然变慢

对比数据量、分区裁剪、文件数、计划、统计信息、Task 分布和最近变更。先找变化，再调参数。

### `Table not found` 或分区缺失

确认环境、Database、Catalog、Metastore URI、账号权限和分区注册。文件存在不等于 Metastore 已登记。

### Metastore 超时

关联 Thrift 延迟、后端数据库连接/锁/慢 SQL、GC、线程池和网络。扩大连接池前先确认数据库承载能力。

### 写入产生大量小文件

查上游并发、动态分区、每批数据量和重试；合并只是补救，根因通常在写入粒度。

## 升级与回滚

1. 盘点 Hive、Java、Hadoop、Tez、Metastore DB、JDBC Driver、UDF 和客户端。
2. 备份 Metastore 并验证恢复，保存配置、权限和关键表清单。
3. 在测试环境运行 Schema Upgrade 与兼容性查询。
4. 对核心 SQL 做结果、计划、性能和权限回归。
5. 先灰度客户端或服务实例，观察错误率和延迟。
6. 明确 Metastore Schema 升级是否可逆；不可逆时回滚依赖数据库恢复和停写窗口。

## 生产事故题：日报查询全部超时

现象：HiveServer2 可连接，所有日报 SQL 都卡在编译后等待，Metastore 正常。

处理主线：

1. 控制影响：暂停低优先级批任务，保留失败 Query ID。
2. 收集证据：YARN 队列、AM 申请、Tez DAG、资源使用和最近调度配置变更。
3. 形成假设：队列资源耗尽、AM 上限、节点故障或单个大作业挤占。
4. 验证：对比故障前后队列指标与应用状态，不把“SQL 已编译”误判为 Hive 正在扫描。
5. 修复：恢复正确队列配置、释放异常任务或扩容，并逐步恢复流量。
6. 回滚：若变更无效，回退调度配置；验证新旧作业都能分配资源。

## 系统设计题

为每天 20 TB 日志设计 Hive 离线分析平台，要求 T+1 报表 8 点前完成，元数据和查询入口无单点。

答题至少覆盖：数据进入、分区、ORC/Parquet、压缩、小文件治理、HDFS/对象存储、双 HiveServer2、双 Metastore、元数据库 HA、Tez/YARN 队列、Kerberos/权限、统计信息、SLA 指标、备份恢复、升级回滚和成本模型。

## 选型取舍

- Hive：适合数据湖表管理、批量 SQL、Metastore 生态和成熟 Hadoop 集成。
- Spark SQL：适合通用 DAG、复杂 ETL、机器学习前处理和批流一体应用。
- Trino/Presto：更强调多数据源交互式 SQL，运维模型和事务能力不同。
- HBase：适合按 RowKey 的低延迟随机读写，不适合大范围扫描聚合替代 Hive。
- 传统数据库：适合事务、索引点查和高并发业务请求，不应把全部 OLTP 搬到 Hive。

## 面试怎么讲

### 30 秒版本

Hive 给 HDFS 或对象存储上的数据提供表、元数据和 SQL。查询从 HiveServer2 进入，经过解析、Metastore 查询和 CBO 优化，再由 Tez/YARN 等执行引擎读取 ORC/Parquet。生产排障要区分连接、编译、元数据、排队、扫描和 Shuffle，并重点治理分区、小文件、倾斜、统计信息和 Metastore 高可用。

### 3 分钟版本

可以用本课告警报表展开：用户通过查询入口提交 SQL，入口先检查身份与语句，元数据服务返回表结构、分区位置和统计信息，优化器生成扫描与关联策略，执行引擎申请资源后读取实际文件。元数据不负责把全部告警内容转发给计算任务，因此入口可连接、表可见和数据可读是三种不同证据。

接着解释成本来自哪里：按业务日期筛选可减少分区，列式格式减少无关列读取，聚合需要交换同服务相关数据，热点键和小文件会让成本放大。我的实验只能证明三行样本聚合结果和分区登记，不能据此报告生产加速倍数。真实慢查询应先按查询标识区分编译、排队、扫描和写出，再比较任务长尾及近期变化。

最后讲状态与恢复：事务表依赖有效写入信息和文件整理，不能手工删除增量；高可用需要覆盖查询入口、元数据后端数据库、计算与存储依赖，旧会话不保证随入口切换自动恢复。日报还要检查迟到数据和质量门禁，升级则固定输入比较结果与权限，并预留元数据库及数据恢复点。这样回答既说明了机制，也交代了实验和生产能力的边界。

## 递进面试题

### 1. Hive 的数据到底存在哪里

**定义：** 通常在 HDFS、对象存储或表格式管理的数据文件中，Metastore 保存描述这些数据的元信息。

**追问：** 只恢复 Metastore 会怎样？表定义可能回来，但数据文件若丢失仍无法查询；只恢复数据则可能缺表、分区和权限元数据。

### 2. 分区和分桶有什么区别

**定义：** 分区通常映射目录并用于裁剪，分桶按哈希把行分到固定文件集合。

**追问：** 为什么分区越多不一定越好？因为会放大 Metastore 对象、小文件、规划时间和维护成本。

### 3. 小文件为什么慢

**机制：** 文件打开、元数据、对象请求和 Task 调度成本相对数据读取变大。

**追问：** 怎么证明？比较文件数量、平均文件大小、Task 数、扫描字节与耗时，不能只看 HDFS 总容量。

### 4. Hive SQL 慢怎么定位

**答案主线：** Query ID -> 编译/Metastore -> YARN 排队 -> 扫描和裁剪 -> Shuffle/Join -> 长尾 Task -> 写出结果 -> 变更对比。

### 5. Metastore 怎样高可用

多个 Metastore 服务实例共享高可用后端数据库，客户端配置多个 URI，并对数据库、Schema 升级、连接池、认证和备份恢复做完整设计。

## 老师带你理解：目录中的文件怎样变成一张表

假设告警日志只是对象存储里的许多文件，文件自己不会告诉查询者第几列是服务、哪一段目录是日期。Hive Metastore（元数据服务）记住表结构、位置、分区与统计信息，SerDe（序列化与反序列化组件）解释文件字节如何变成行列，执行引擎负责真正读取和计算。知道这三件事，就不会把“表存在”误认为“文件一定可读”。

学生：“我已经把文件拷进目录，为什么查询看不见？”老师：“先检查表位置、分区是否注册、格式和权限，再看使用的目录服务是不是同一套。”元数据与文件状态可能不同步。修复目录后仍要用小范围查询验证，不能因为 `SHOW TABLES` 有名字就认为数据完整。

### 分区、分桶与列式存储分别省什么

Partition（分区）通过日期等字段减少要访问的路径；Bucket（分桶）按规则把行分到若干桶，帮助组织并行与某些连接；ORC/Parquet（列式格式）让读取所需列并利用编码压缩成为可能。三者作用层次不同，配置分桶不会自动把历史任意文件重写成正确桶布局。

按天分区能让昨天报表只读昨天，按请求 ID 分区却可能产生数百万目录和小文件。把所有数据写成一个超大文件又降低并行度与恢复灵活性。应根据每日体量、常见过滤、写入批量、文件尺寸和查询并发设计，观察元数据请求与实际扫描字节，而不是只比较 SQL 长短。

COUNT 查询很快不必然代表完整扫描很快，它可能利用元数据或统计信息；同样，`LIMIT 10` 不保证所有上游连接与排序都只处理十行。看 EXPLAIN（执行计划）中的扫描范围、连接策略、数据交换和统计估计，再用实际任务指标验证。

### 为什么一条 SQL 会变成很多机器交换数据

按服务聚合需要把同服务行放到一起，形成 Shuffle（重分布）；大表连接如果两边都分散，网络和磁盘成本可能很高。小维表可以在适用条件下广播到执行节点，但小是相对于每节点内存和并发而言。统计信息过期时，优化器估错表大小，可能选错连接方式。

大量记录的服务名为空，聚合会把这些行聚到同一个空键，形成倾斜。先查空值率、TopN 键和任务长尾，再决定清洗、单独处理热点或拆分聚合；不能随意删除空服务记录让报表“变快”，它们可能代表采集质量事故。

### 带练检查点与故障复盘

完成前文基础表实验后，记录表类型、Location（数据位置）、分区清单、输入行数、结果行数和查询 ID。沿前文故障步骤观察错误发生在编译、元数据、权限还是执行阶段；恢复后使用相同输入与条件重跑。清理前确认教学表是否托管及是否会删除文件，只清理专用实验范围。

另做一个只读比较：给已有日期分区查询加上明确日期条件，再对无该条件的查询看计划，预期扫描分区范围存在差异；小样本耗时未必明显，不能伪造性能倍数。记录计划中的分区裁剪证据比写“感觉更快”有价值。

### 生产状态与恢复课堂

ACID（事务原子性、一致性、隔离性、持久性）表可能涉及基础文件、增量文件、删除增量和写入标识。压缩整理积压会影响读取与空间，事务元数据也需要维护。不能绕过表协议随意增删文件，再期待事务层自动理解。不同表格式与引擎对并发和事务的支持需查对应版本。

恢复要同时覆盖 Metastore 后端数据库、数据文件、权限、执行配置和必要密钥。只恢复元数据会得到指向不存在文件的表，只恢复文件可能失去表与分区语义。升级前比较 SQL、SerDe、函数、连接器、权限和结果一致性；影子查询固定输入快照，避免把数据变化当成版本差异。

30 秒面试回答用“元数据定义表、引擎计算文件、分区和格式减少扫描”解释价值。3 分钟展开查询路径、分区裁剪、连接倾斜、事务表维护和恢复。事故题设置日报耗时突然十倍，先用查询 ID 定位等待阶段，再关联分区遗漏、小文件激增、统计变化和队列拥堵，修复后验证结果准确与时效共同恢复。
