## 官方知识地图

```text
SQL（结构化查询语言）基础：表/行/索引 -> 查询计划 -> 事务/锁/MVCC（多版本并发控制） -> 日志与恢复
产品路径：应用 -> DNS（域名解析）/VIP（稳定虚拟入口） -> 数据库代理/入口 -> 计算节点 -> 存储
高可用：复制 -> 主备/仲裁 -> 故障切换 -> 连接恢复 -> 数据验证
运维：账号权限 -> 参数/Schema（库表结构） -> 容量性能 -> 备份恢复 -> 升级回滚
AIOps（智能运维）：业务 SLO（服务目标） -> 慢查询/锁 -> 资源/拓扑 -> 变更 -> 根因候选
```

SQL 是数据库查询语言；Schema 是表、列、索引等结构；MVCC 是多版本并发控制，让不同事务按规则看到不同版本；VIP 是稳定入口地址。

## 场景开场

告警平台“确认事件”突然超时，数据库 CPU 只有 30%。重启应用后短暂恢复，随后再次积压。真正原因可能是一条未提交事务持有热点行锁，连接池持续等待；重启只是释放了部分连接，没有解决事务设计。

## 一句话人话版

TDSQL-C MySQL 是面向企业数据的数据库服务；你不仅要会写 SQL，还要理解每次提交怎样被并发控制、记录、复制、恢复和观察。

## 小白常问

### 数据库和表是什么？

数据库管理数据和事务，表用行列组织一类记录。索引像目录，能加速特定查询，但会占空间并增加写入维护。

### `COMMIT` 后一定不会丢吗？

提交语义取决于日志持久化、复制和产品配置。客户端超时还可能不知道服务端是否已提交，应用需要业务幂等与结果查询，不能盲目再扣款或再建工单。

### 主备等于备份吗？

不是。误删或错误 SQL 可能复制到备库；备份保留历史恢复点，且必须验证能恢复。

### 慢 SQL 就是没索引吗？

也可能是锁等待、数据量/分布变化、错误索引、内存/存储延迟、网络、连接池或执行计划改变。先看证据。

## 为什么要学与解决的问题

AIOps 的事件、用户、规则、任务状态需要一致保存。数据库故障会表现为页面慢、消息积压和调用超时。理解事务、索引、连接、复制和恢复，才能避免把所有问题都归为“数据库 CPU 高”。

## 从一条 SQL 到磁盘/存储的路径

```text
应用连接池
  -> DNS/VIP/代理
  -> 认证与会话
  -> SQL 解析/优化/执行
  -> InnoDB 缓冲池/索引/锁/MVCC
  -> redo/undo/binlog 等日志（按实际产品）
  -> 数据页与底层存储
  -> 复制/备份链
```

代理是否存在、日志类型和存储架构取决于 TDSQL 产品形态。不要从通用 MySQL 文章猜测闭源服务内部拓扑。

## 核心概念一：事务与 ACID

**是什么：** 事务把多个读写作为一个业务单元。ACID 常概括原子性、一致性、隔离性、持久性。

**为什么需要：** “创建事件 + 写操作记录”不能只成功一半。

**怎样工作：** `BEGIN` 开始，执行读写，`COMMIT` 提交或 `ROLLBACK` 回滚。数据库使用日志、锁和多版本维持语义。

**怎样使用/观察：** 事务尽量短；记录开始/结束、错误与业务请求 ID；观察活跃事务、历史列表、锁等待和提交延迟。

**坏了怎样查：** 长事务会持锁、阻塞清理并扩大恢复时间。先找谁等待谁、事务做了什么、是否仍有业务价值，再按审批处理；不要见阻塞就杀所有连接。

“一致性”不是数据库替应用自动保证所有业务规则。余额不能为负、状态只能合法迁移等规则需要 Schema、约束和应用共同实现。

## 核心概念二：隔离、MVCC 与锁

隔离级别定义并发事务能看到什么。MVCC 保存可见版本，让普通一致性读减少互相阻塞；修改和锁定读仍需锁。

`SELECT ... FOR UPDATE` 是锁定读，适合先读取再更新同一业务记录。它必须在事务中有明确范围，查询条件和索引不当可能锁住比预期更多数据。

死锁是事务形成循环等待。数据库通常选择一个事务回滚来打破循环；应用需要把事务写成可重试、幂等并缩短持锁时间。锁等待超时只是等太久，不一定形成循环，二者证据不同。

排障查看等待者、阻塞者、SQL 摘要、事务年龄、锁对象和业务请求。敏感 SQL 参数要脱敏。

## 核心概念三：索引与执行计划

InnoDB 的主键索引通常组织行数据，二级索引保存索引列和定位主键所需信息。索引顺序决定哪些条件能有效缩小范围。

执行计划是优化器对访问路径的估计，例如扫描哪个索引、预计多少行、怎样连接。`EXPLAIN` 用于查看计划，但估计行数不等于实际；生产执行带分析功能的命令可能真的运行查询，需评估风险。

排障比较数据量、选择性、统计信息、SQL 变化和计划变化。加索引会增加写放大、磁盘和 DDL（结构变更）时间，应在接近真实数据分布的环境验证。

## 核心概念四：缓冲、日志与持久化

缓冲池缓存数据/索引页，命中时减少存储读取。redo 类日志帮助崩溃恢复已提交更改，undo 支持回滚和多版本；binlog 常用于复制/审计生态。具体格式与路径按产品版本。

数据库写入不是简单把每行立刻写回数据文件。提交延迟可能受日志刷盘、复制确认、存储延迟和组提交影响。不能仅凭数据文件时间戳判断事务是否持久。

观察缓冲命中、脏页、日志写入/等待、检查点、存储延迟和恢复时间。修改持久化参数可能改变数据安全语义，必须走架构评审。

## 核心概念五：连接与代理

连接建立包含网络、TLS、认证和会话。连接池复用连接，但池过大会把应用并发直接放大到数据库；超时过长会堆积线程，超时过短会在正常峰值误失败。

代理/VIP 能提供入口、路由或切换，但既有长连接是否自动恢复取决于客户端。应用要有连接有效性检测、有界重试、指数退避和熔断，并区分只读/读写语义。

## 高可用、复制与一致性

主备/多副本的核心问题：写由谁接受，提交需等哪些副本，故障由谁判断，如何防止双主，切换后客户端怎样重连。

同步确认通常降低 RPO 但增加延迟和跨故障域依赖；异步复制延迟时切换可能丢最近数据。拓扑必须与业务 RPO/RTO、网络质量和容量匹配。

切换成功包含五层：新角色正确、入口更新、连接恢复、数据位点/一致性正确、关键业务事务成功。控制台“主节点已切换”只完成其中一部分。

## 备份与恢复

全量备份提供基线，增量/日志将恢复点向前推进。PITR 是按时间点恢复，仍要确定时区、目标时间和可能丢失的事务。

恢复到新实例/隔离环境，验证 Schema、行数/校验、权限、关键查询和应用事务，再决定切流。不要用生产原实例做首次恢复试验。

备份成功率、备份年龄、日志连续性、恢复耗时和业务校验都要监控。没有定期恢复证据，不能宣称 RTO 已达标。

## 分库分表与分布式事务边界

某些 TDSQL 产品形态可能提供分片。分片键决定数据落点；跨分片查询、聚合、唯一约束和事务可能成本更高。是否支持、语法和限制以本版本为准。

选择分片键看访问模式、数据分布、扩容迁移和热点，不能只选自增 ID。分布式事务提高一致性但增加协调、时延和故障状态，业务也可用事件/补偿模式，但必须明确重复、乱序和最终一致窗口。

## 安装、开通与配置验收

TCE 中的 TDSQL 由产品交付体系部署，不使用本文 Docker 命令安装生产。开通前确认产品形态、版本、字符集/排序规则、时区、规格、网络、账号、备份、监控、维护窗、RPO/RTO 和兼容矩阵。

字符集决定字符编码，排序规则影响比较排序和索引行为；上线后修改可能代价很大。参数模板应版本化、评审、灰度，区分动态/重启生效和只读参数。

## SQL 与字段字典

| 命令/概念 | 用途 | 关键点与预期 | AIOps 场景/坑 |
|---|---|---|---|
| `START TRANSACTION` | 开始显式事务 | 最终提交或回滚 | 忘记结束形成长事务 |
| `COMMIT` | 提交事务 | 应记录结果和业务 ID | 客户端超时会结果未知 |
| `ROLLBACK` | 放弃未提交修改 | 不一定撤销外部副作用 | 已发消息要另做补偿 |
| `SELECT ... FOR UPDATE` | 锁定将修改的行 | 条件和索引必须准确 | 扩大锁范围引发阻塞 |
| `EXPLAIN` | 查看执行计划 | 估计而非业务成功 | 计划好不代表无锁等待 |
| `SHOW ENGINE INNODB STATUS` | 看 InnoDB 摘要 | 包含锁/死锁/内部状态 | 输出可能敏感且是瞬时快照 |
| Performance Schema | 观测等待、语句、事务 | 控制采集开销 | 高维原始 SQL 要脱敏 |
| `version_no` | 业务乐观并发版本 | 更新时比较旧版本 | 失败应重读，不无限覆盖 |

生产只读诊断也需授权；`KILL`、DDL、参数修改、切换和恢复属于写操作。

## 基础实验：事务提交与锁定读

### 前提

Docker 可用，至少 1 GiB 可用内存和 1 GiB 磁盘；端口 `127.0.0.1:13306` 未占用。实验容器名固定为 `tdsql-learning-mysql`，只绑定本机回环地址。

### 步骤

```powershell
docker run --name tdsql-learning-mysql -e MYSQL_ROOT_PASSWORD=lab-only-password -p 127.0.0.1:13306:3306 -d mysql:8.4
docker exec tdsql-learning-mysql mysqladmin ping -uroot -plab-only-password --wait=60
Get-Content examples/tdsql-mysql-lab/init.sql -Raw | docker exec -i tdsql-learning-mysql mysql -uroot -plab-only-password
docker exec tdsql-learning-mysql mysql -uroot -plab-only-password -e "SELECT VERSION(); SELECT * FROM aiops_lab.incident_ticket;"
docker inspect tdsql-learning-mysql --format "{{json .Image}}"
```

第一个命令只用于一次性本地教学，生产不要把密码放命令行；第二个等待数据库可响应；第三个创建 InnoDB 表、用 `FOR UPDATE` 锁定并更新后提交；最后记录版本/镜像标识作为实验证据。

预期 `status=ACKED`、`version_no=2`。如果容器未启动，查 `docker logs tdsql-learning-mysql`；镜像失败检查网络；端口冲突只改主机侧 `13306`，容器仍是 3306。

## 故障注入：两个会话争抢同一行

只对上述实验容器操作。打开终端 A：

```powershell
docker exec -it tdsql-learning-mysql mysql -uroot -plab-only-password aiops_lab
```

在 A 中执行且暂不提交：

```sql
START TRANSACTION;
UPDATE incident_ticket SET status='PROCESSING' WHERE id=1;
```

打开终端 B，连接同一容器后执行：

```sql
SET SESSION innodb_lock_wait_timeout=3;
START TRANSACTION;
UPDATE incident_ticket SET status='CLOSED' WHERE id=1;
```

预期 B 等待约 3 秒后收到锁等待超时错误。此时 Pod/进程和 CPU 都可能正常，业务仍超时。在终端 A 执行 `ROLLBACK;` 释放锁；终端 B 也执行 `ROLLBACK;` 清理失败事务，再以新事务重试并 `COMMIT`。

验证：

```powershell
docker exec tdsql-learning-mysql mysql -uroot -plab-only-password -e "SELECT * FROM aiops_lab.incident_ticket; SHOW ENGINE INNODB STATUS\G"
```

若 B 未超时，确认 A 的事务未结束、两端操作同一行且使用 InnoDB。先保留教学容器，继续后文版本冲突和死锁练习，文末再统一清理。这个实验是锁等待，不是 TDSQL 故障切换或真实死锁。

## AIOps 观测与容量性能

业务侧看成功率、P95/P99、连接池等待与事务重试；入口看连接/认证/代理错误；引擎看 QPS/TPS、慢查询、锁、事务、缓冲和日志；资源侧看 CPU、内存、存储 IOPS/延迟/容量；拓扑侧看角色、复制延迟和备份。

QPS 是每秒查询数，TPS 是每秒事务数。容量模型还需要行大小、索引倍数、增长、保留、备份空间、日志、故障预留和扩容交付周期。压测必须模拟真实 SQL 分布、并发和数据量，不能只跑简单主键查询。

高基数 SQL 指纹、业务 ID 适合受控日志，不能无限做监控标签。异常检测要关联发布、DDL、参数和流量变化。

## 安全、升级与回滚

应用使用独立最小权限账号，读写/管理/备份职责分离；限制来源网络，启用传输和静态加密（按产品支持），轮换凭据并审计。备份和密钥权限不能被同一普通账号删除。

升级前核对 TCE/TDSQL/客户端/字符集/SQL/参数/备份兼容，回放关键查询并恢复备份。先只读/影子/小业务灰度。数据库格式和 Schema 变更可能不可降级，回滚应包括新实例恢复或反向兼容路径，不是简单安装旧包。

## 排障字典

| 现象 | 证据 | 假设 | 处置 |
|---|---|---|---|
| 连接超时 | DNS/VIP/网络/代理/连接数 | 网络、入口或连接耗尽 | 有界重试，先限流保护 |
| 查询慢但 CPU 低 | 锁等待、存储 P99、计划 | 锁或 I/O | 定位阻塞/热点，不重启代替分析 |
| CPU 高 | SQL 指纹、计划、流量、变更 | 扫描/并发/计划回退 | 限流、优化并灰度 |
| 复制延迟 | 写入量、网络、I/O、长事务 | 下游追赶不过来 | 评估 RPO，勿贸然切换 |
| 磁盘增长 | 表/索引/日志/备份 | 数据增长或清理滞后 | 先确认保留和回收语义 |
| 切换后仍失败 | 角色/VIP/连接/数据/业务 | 客户端未重连或数据问题 | 逐层验证，保留回退 |
| 恢复失败 | 备份链、日志、密钥、版本 | 不完整/损坏/不兼容 | 隔离恢复，升级原厂 |

## 生产设计题

设计一个事件处理数据库：每个事件只能从 OPEN 合法迁移到 ACKED/CLOSED，写入高峰 5000 次/秒，要求跨 AZ、可时间点恢复。

答案要包括主键/索引、事务边界、并发版本、幂等键、连接池、容量和热点、复制取舍、备份/PITR、跨 AZ 失效容量、发布 Schema 兼容和观测。追问客户端提交超时如何防重复：用业务唯一键并查询最终状态，而不是无条件再插入。

## 事故题

一次索引变更后数据库延迟升高。先冻结继续 DDL，关联变更时间，收集受影响 SQL、执行计划、锁、临时空间、I/O 与复制延迟。验证是 DDL 锁、资源竞争还是新计划。

处置可能是停止/回退变更、限流或使用兼容索引方案，前提是确认数据库支持和影响面。涉及内部节点、复制位点、数据修复和补丁由原厂操作。恢复后验证事务、复制、备份和业务 SLO。

## 面试回答

### 30 秒

我先分清 TDSQL 产品形态，再沿应用连接、代理、SQL 引擎、InnoDB、存储和复制取证。事务问题看锁和可见性，性能问题结合计划、资源和业务；主备不能代替备份，恢复必须用业务验证。

### 3 分钟

以事件状态更新讲事务、锁定读和幂等；用锁等待实验说明 CPU 正常也会超时；再讲索引/计划、日志持久化、连接池与复制切换。生产补充跨 AZ、RPO/RTO、备份恢复、最小权限和兼容升级。

### 递进追问

1. **MVCC 是否不需要锁？** 普通一致性读可少阻塞，写/锁定读仍需锁。
2. **为何索引越多不越好？** 写放大、空间、优化器和 DDL 成本。
3. **锁等待与死锁区别？** 超时是等待过久；死锁是循环，需回滚一方。
4. **主备切换怎样算成功？** 角色、入口、连接、位点/一致性、业务共同验证。
5. **备份成功为何仍失败？** 日志链、密钥、版本、配置或从未做恢复。
6. **何时找原厂？** 闭源拓扑/仲裁/复制、数据页修复、补丁、升级和高风险恢复。

## 老师带你读懂一次“确认工单”的数据库动作

先把数据库从一堆缩写还原成生活中的台账。工单 `INC-001` 当前是 OPEN（待领取），小王和小李几乎同时点击“我来处理”。如果应用先查询状态，再无条件更新负责人，两个人都可能看到 OPEN，后提交的人覆盖先提交的人。页面显示成功，业务规则却被破坏了。

第一种做法是条件更新：`UPDATE ... WHERE id=1 AND status='OPEN'`，由数据库在修改时检查条件；影响行数为 1 表示领取成功，为 0 表示条件已变化。第二种做法是事务内锁定读：先 `SELECT ... FOR UPDATE` 获取修改权，再完成相关更新并提交。第二种适合需要在锁保护下做多步判断的情况，但持锁期间不能让用户慢慢填写备注，也不要调用耗时外部接口。

学生：“有事务了，发通知也一起成功吗？”老师：“普通数据库事务只覆盖它管理的读写，已经发出的短信不能用 `ROLLBACK` 收回来。”可以在同一事务中写工单和待发送事件，事务提交后由发布器处理事件；通知端使用业务唯一键，容忍发布器在确认不确定时重发。这样解释，面试官才知道你分得清数据库内部原子性与跨系统一致性。

### 从页、索引到热点：慢查询究竟慢在哪

InnoDB 管理的是数据页，页里有多行数据。主键索引把行组织在树的叶子层，二级索引通常通过主键继续找到完整行。你只问“这个服务的最近十条工单”，合理索引可以缩小范围并减少排序；如果查询选择了很多不需要的大字段，就算匹配到了索引，也可能产生大量额外读取和网络传输。

联合索引 `(service_name, created_at)` 像先按服务分档案柜，再按时间排序。它不是两个独立目录的简单相加；查询只按时间筛选时，访问方式和效果要重新评估。字段上做函数、隐式类型转换、前导通配符、返回比例过大、统计信息偏差都可能让既有索引收益变差。每个候选原因都要由计划、数据类型、扫描行数与实际耗时验证。

锁也落在具体索引访问和事务语义上。Record lock（记录锁）保护索引记录，Gap lock（间隙锁）和 Next-key lock（临键锁）涉及记录之间的范围，用于适用隔离级别下的并发控制。不要背成“所有范围查询都锁全表”或“有索引一定只锁一行”；应结合唯一条件、扫描范围、隔离级别和语句类型分析。进一步依据 [InnoDB 锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html) 对照本地实验版本。

热点行是许多事务争抢同一条记录，比如所有服务都更新一行“全站告警总数”。增加应用副本可能让争抢更严重。你可以考虑按服务拆分计数、异步汇总或减少事务内更新，但这些方案改变实时性和一致性，必须说明允许的延迟。分片也不能自动解决所有请求都落在同一个业务键上的问题。

### 用乐观版本亲眼看到并发冲突

前提是上文实验容器仍存在，`incident_ticket` 的 `version_no` 已确认。先查询它；假设目前为 2，分别在两个客户端运行下面的更新，不要把示例版本盲目当成当前值：

```sql
UPDATE incident_ticket
SET status='PROCESSING', version_no=version_no+1
WHERE id=1 AND version_no=2;
SELECT ROW_COUNT() AS changed_rows;
```

第一位预期修改 1 行，第二位预期修改 0 行，因为版本已经变成 3。`ROW_COUNT()` 必须紧跟目标更新执行；中间插入其他语句会影响你正在观察哪一步。这个方法叫乐观并发控制，含义是先尝试、提交时发现别人改过，再由业务决定重读或拒绝覆盖。它不等于没有锁，数据库执行更新仍需要内部并发控制。

这是可回收的业务冲突模拟，不是引擎异常。恢复方法是查询最新记录，按当前合法状态重新发起请求；不要为了“成功”去掉版本条件。记录两次影响行数、状态与版本号，然后随前文实验容器一起清理。如果两次都成功，首先检查你是否每次都把条件改成了最新版本，或 `WHERE` 漏掉版本条件。

### 生产接入：老师带你把连接预算算清楚

应用到数据库之间至少有三个等待池：入口请求排队、应用连接池等待、数据库内部锁或资源等待。一个请求超时，错误可能显示在最外层，但真正排队处在最里面。诊断时把这三段耗时分开记录，才能知道应该优化 SQL、减少并发，还是处理网络和认证。

例如 20 个应用副本、每个池上限 40，就是潜在 800 条数据库连接，另有报表和定时任务。数据库实例扩容后连接预算可能变化，但代理、引擎与下游存储也各有上限。先用接近真实 SQL 分布的测试找可持续吞吐，再定连接池；把超时设为很大只会让用户等待更久。

切换实验也要带客户端验证。你要记录故障前连接、切换过程中错误、重连耗时、结果未知事务和切换后业务状态。入口恢复可连接仅证明入口层正常；正在执行的事务是否重试、重试是否重复、只读连接是否仍指向旧节点，都属于验收项目。故障演练必须由现场支持流程执行，本文本机 MySQL 实验不能替代 TDSQL 产品级演练。

### 备份课堂：把“昨天备份成功”变成可恢复证据

先问业务允许回退到多早，这叫 RPO（可接受的数据损失窗口）；再问多快恢复服务，这叫 RTO（恢复时间目标）。二者决定全量频率、日志连续性、备份带宽、恢复空间和演练方式。目标说十分钟恢复，但备份光下载就要一小时，方案在纸面上已经不成立。

恢复演练按“目标时间—选备份链—恢复到隔离实例—校验数据—接入测试应用—记录耗时”进行。校验不仅是行数，还包含主键、关键状态、字符集、时区、账号权限和业务事务；行数相同也可能记录内容不对。恢复环境访问真实短信或自动修复接口前，应使用模拟下游，避免重放副作用。

向面试官解释回滚时，可以分三层：应用回滚依赖新旧 Schema 兼容；参数回滚要知道是否需重启；数据回滚需要隔离恢复与差异补偿。数据库已经接收新写入后，直接切回旧实例会丢掉哪部分数据，必须说清楚，不能只说“有备份所以可以回滚”。

### 连续追问练习：从名词走到证据

“TDSQL 和 MySQL 一样吗？”先答协议与 SQL 兼容不等于内部拓扑一致，产品家族、版本与现场交付决定架构。继续问“那你怎样排障”，给出能实际读取的会话、计划、等待、慢 SQL、复制和资源证据，并标明哪些由租户账号查看、哪些交原厂处理。

“CPU 只有 20%，为什么不加应用实例？”答先看连接排队、锁等待与 I/O；如果瓶颈是一条热点行，加实例只会增加竞争。继续问“怎样证明”，拿前文双会话超时实验说明等待者、阻塞事务和释放后恢复的因果关系。

“一次事务重试会不会重复创建工单？”答使用稳定业务幂等键和唯一约束，提交结果未知时先查询；跨消息和外部工单再用 Outbox 与消费端幂等。最后补上验证：统计同一业务键的有效工单数，记录重试与最终状态，而不是只看异常日志是否消失。

完成这些练习后，把“表为什么这样设计、等待如何定位、备份怎样恢复”各写一页自己的说明，再使用下面的检查清单。真实项目经验、SQL 编写和网络基础仍需另外练习，文章长度不能替代这些能力。

## 老师带你把“数据库慢”拆成三个问题

### 查询慢、等待慢、返回慢

一次查询耗时高，可能大部分时间在执行扫描，也可能根本没得到执行机会，还可能数据库已完成但网络传输或应用消费结果很慢。查询计划主要解释访问路径，锁等待解释争用，连接池指标解释进入数据库前的排队。把三个阶段混在一起，就会出现“给被锁的 SQL 加了五个索引，页面还是卡”的情况。

收集计划时先固定 SQL 结构与参数类型，记录预期返回行数、实际业务范围和表统计。优化器的估计成本不是毫秒，不应把两个不同实例的 cost 直接当性能成绩比较。估计行数偏差提示统计信息或分布问题；估计合理但实际慢，继续查看等待、缓存与存储。索引命中率好也不能证明读取字节少，宽字段和回表可能仍很昂贵。

服务名加时间的联合索引通常适合“固定服务查最近时间段”，但不是所有条件顺序都有相同收益。范围条件、排序、覆盖列与返回比例共同决定访问路径。把所有条件列都加进索引会增加大小与每次写入维护；频繁更新的列放进多个索引，还会放大页修改和日志压力。评审索引时同时拿出代表查询和代表写入，而不是只展示一条查询变快。

### 结构变更为何也会堵住业务

DDL（数据定义语言）修改表结构，可能需要元数据锁，且不同产品、版本和具体操作支持的在线算法不同。所谓在线不等于完全无锁、无额外空间、无复制影响。大表重建可能在后期取得某种锁之前等待长事务，其他业务又排在它后面，形成锁队列。

因此上线前要问：这次加列或索引使用什么算法、需要多少临时空间、预计多久、哪些阶段会等待、失败如何清理、能否中止、从哪里继续或回退。不能凭公有云某版本宣传就认定现场私有云也支持同样路径。受托管限制看不到底层细节时，应要求原厂提供变更方案与观测点，而不是用猜测补齐架构。

## 第二个故障实验：亲眼区分死锁和超时

前提是本课 MySQL 容器仍运行，前面所有事务已提交或回滚。教学库中另外建立一张两行小表，不复用真实业务表。任选一个客户端执行：

```sql
CREATE TABLE lesson_lock_pair (
  id INT PRIMARY KEY,
  visits INT NOT NULL DEFAULT 0
) ENGINE=InnoDB;
INSERT INTO lesson_lock_pair(id) VALUES (1),(2);
```

现在在会话 A 开始事务并修改第 1 行；在 B 开始事务并修改第 2 行。每一步都等待提示返回后，再去下一个会话：

```sql
-- 会话 A：先锁第 1 行，暂不提交
SET SESSION innodb_lock_wait_timeout=30;
START TRANSACTION;
UPDATE lesson_lock_pair SET visits=visits+1 WHERE id=1;
```

```sql
-- 会话 B：先锁第 2 行，暂不提交
SET SESSION innodb_lock_wait_timeout=30;
START TRANSACTION;
UPDATE lesson_lock_pair SET visits=visits+1 WHERE id=2;
```

接着 A 执行 `UPDATE lesson_lock_pair SET visits=visits+1 WHERE id=2;`，它会等待 B。趁 A 仍等待，B 执行 `UPDATE lesson_lock_pair SET visits=visits+1 WHERE id=1;`，这样 A 等 B、B 又等 A，形成循环。默认启用死锁检测的本地 MySQL 预期让其中一个事务收到死锁错误并回滚，另一个继续；被选中的事务不是固定 A 或固定 B。

检查 `SHOW ENGINE INNODB STATUS\G` 中最近死锁部分，找两个事务的持有和等待关系。为了不改变教学数据，最后在 A、B 都执行 `ROLLBACK;`，然后查 `SELECT * FROM lesson_lock_pair;`，预期两个计数都回到零。确认两个会话均结束事务后，执行 `DROP TABLE lesson_lock_pair;`，只删除这张本课新建的表。

若只看到锁等待超时，可能 A 已经超时后才执行 B 的第二步，循环没有同时存在；也可能死锁检测被关闭。先确认步骤顺序与 `SHOW VARIABLES LIKE 'innodb_deadlock_detect';`，不要去改生产参数。这个实验只演示本地 InnoDB，不能证明现场 TDSQL 的诊断权限和控制台展示与它相同。

### 从实验推导修复，而不是背“加重试”

假设两个业务事务都需要修改编号 1 和 2，统一按主键从小到大加锁，会减少这个例子中的循环。事务尽量短、更新范围准确、合适索引、外部调用移出持锁区间也能降低冲突。但复杂业务仍可能发生死锁，所以应用必须知道如何安全重试整个事务，而不是只重跑最后一条 SQL。

死锁受害者的事务被回滚，与普通语句错误或锁等待超时的事务边界可能不同。为避免驱动配置差异和错误事务状态，应用捕获异常后显式结束失败事务，再在有界次数和退避下重新执行业务单元。若事务已经调用外部收费或发短信，重跑就可能重复，因此再回到前面的 Outbox 与外部幂等设计。

## 托管数据库验收：向产品问对问题

第一组问接口：读写地址与只读地址分别是什么，DNS 与代理切换需要多久，已建立连接是否会断开，驱动如何检测失效连接，刚写完是否可能读到旧值。把控制台字段和应用配置逐一对应，不能用“兼容 MySQL”代替全部接入合同。

第二组问持久化：提交确认覆盖哪些故障范围，计算故障与存储故障怎样处理，同步与异步路径是什么，跨可用区失败后还有多少承载余量。对于不能公开的实现，要求厂商明确可验证的语义与责任边界；既不捏造内核细节，也不只接受“高可用”三个字。

第三组问恢复：全量与日志保留多少时间，密钥谁管理，是否允许恢复到新实例，恢复时间从何时计到何时，备份失效与日志断链如何告警。若恢复依赖同一故障域中的账号服务、网络或对象存储，方案需要补齐这些依赖，否则数据库备份本身正常也可能无法使用。

第四组问升级：当前内核与客户端兼容矩阵、参数变化、SQL 行为差异、字符集排序差异、备份兼容、维护窗口、回滚截止点与新写入去向。尤其在新版本接受了旧版本不支持的结构或格式后，直接切回旧实例不一定安全；应该准备兼容迁移、隔离恢复和差异补偿路径。

最终验收用同一个合成业务：创建工单、并发领取、提交超时查询最终结果、切换后重连、备份恢复后校验。记录每层“预期—实际—差异—处理人”，才能把云产品能力转换成业务可用性。本文提供的是问题与实验方法，真正现场演练必须由有权限的团队按批准方案执行。
